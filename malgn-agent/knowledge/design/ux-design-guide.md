# UX 설계 가이드

## 사용자 흐름(User Flow) 작성법

### 흐름도 표기
```
[시작] → (판단) → [화면A] → [화면B] → [완료]
              ↓
          [에러 화면]
```

### 핵심 시나리오 유형
1. **온보딩**: 회원가입 → 프로필 설정 → 대시보드
2. **CRUD**: 목록 → 상세 → 생성/수정 → 확인
3. **검색**: 검색 입력 → 결과 목록 → 상세
4. **인증**: 로그인 → 토큰 → 보호된 페이지
5. **결제**: 장바구니 → 주소/결제 → 확인 → 완료

## 정보 구조(IA) 설계

### 네비게이션 패턴
- **탑 네비게이션**: 5~7개 이하 메뉴
- **사이드바**: 계층적 메뉴, 관리자 대시보드
- **탭**: 같은 수준의 콘텐츠 전환
- **브레드크럼**: 깊은 계층 탐색

### URL 구조 설계
```
/                    → 대시보드
/items               → 목록
/items/:id           → 상세
/items/new           → 생성
/items/:id/edit      → 수정
/settings            → 설정
/settings/profile    → 프로필 설정
```

### IA는 기능이 아니라 사용자 목표로 묶는다 (산출물 진단 2026-06-20)

> 실제 진단에서 IA가 "코치 관리 / 고객사 관리 / 세션 관리"처럼 **DB 테이블·기능 단위**로 나뉘어, 운영자의 진짜 일(성과 가시화·계약 관리)과 안 맞는 사례가 반복됐다. 화면 목록만 나열하고 그룹핑 근거가 없으면 평범한 IA다.

- **목표 단위 그룹핑**: 화면을 "학습 시작 / 진단·평가 / 커뮤니케이션 / 관리"처럼 **사용자가 이루려는 일(JTBD)** 카테고리로 묶는다. 기능명("○○ 관리")으로 묶지 않는다.
- **대안 1개 비교 후 선택**: IA를 확정하기 전 다른 구조 하나를 적고 비교한다. 예: `대안 A(KPI 중심 대시보드) vs 대안 B(기능 태스크 중심) → 선택: A, 근거: 운영자의 핵심 JTBD가 성과 의사결정이므로`. 비교 없이 "표준 사이드바"로 자동 수렴하지 않는다.
- **Dead End 점검**: 각 화면에서 나가는 경로(CTA)가 실제 화면으로 연결되는지, 막다른 길은 없는지 화면↔시나리오를 쌍방향으로 추적한다. "과제 목록 → 과제 상세"인데 상세 화면이 IA에 없으면 Dead End.
- **제품원칙 교차 확인**: `docs/product-principles.md`가 정한 것(예: "AI는 별도 탭이 아니라 모든 화면에 녹아든다")을 IA가 어기지 않는지 본다. 원칙은 "AI 탭 없음"인데 화면 인덱스에 `AI 튜터` 별도 화면이 있으면 위배.

## 상태 매트릭스(State Matrix) 설계법 (산출물 진단 2026-06-20)

> UX 산출물이 화면의 정상 모습만 그리고 빈/로딩/에러/권한 상태를 형식적으로만 적는 일이 잦다. 상태는 happy path와 **동급**으로 설계한다.

- **화면(또는 컴포넌트)마다 6상태를 채운다**: 기본 / 로딩 / 빈(Empty) / 에러 / 권한 없음 / 비즈니스 경계(예: 목표 5개 상한, 0건/1건). 빠진 상태가 있으면 미완성.
- **전이 조건은 "주체 + 이벤트"로**: "채점중" = *"교수가 채점 시작 버튼을 누른 시점"* 처럼 누가 무엇을 해서 그 상태가 되는지 쓴다. "채점 전" 같은 모호한 조건 금지.
- **역할별로 분리**: 같은 데이터라도 학생/교수/관리자가 보는 상태·가능 행동이 다르다. 한 관점만 적지 않는다.
- **빈 상태는 정상 vs 비정상을 구분**: "강좌가 없습니다"가 *아직 신청 안 함(정상)*인지 *동기화 오류(비정상)*인지 메시지로 구분되고, 다음 행동(CTA)으로 이어져야 한다.
- **에러는 원인별 차등**: "시간 초과 / 서버 오류 / 네트워크 없음"을 같은 메시지로 뭉뚱그리지 않는다 — 사용자가 취할 행동(재시도 vs 대기 vs 문의)이 다르다.

## 실제 화면을 근거로 한 UI/UX 작업 (Screen-Grounded UI Work)

> 신설 사유 (2026-06-19): malgnai 웹앱 UI/UX 리뷰가 **실제 렌더링된 화면을 한 번도 보지 않고** 코드만으로 수행됐다. UI/UX는 "화면에 실제로 어떻게 보이는가"가 본질이므로, 코드 추론만으로 평가·개선하면 빗나간다.

**원칙: 이미 배포/실행 중인 UI를 리뷰·개선·검증할 때는, 코드뿐 아니라 반드시 실제 렌더링된 화면을 눈으로 확인한다.** 화면 이미지가 곧 작업의 근거 산출물이다.

### 언제 화면 확인이 필수인가
- 기존 웹/앱 화면의 UI/UX **리뷰**
- 디자인/스타일 **수정의 before/after 확인**
- 반응형(모바일/데스크탑) 동작 점검
- "잘 보인다 / 가독성이 좋다 / 위계가 산다" 같은 **시각적 판단을 보고할 때**

### 언제 생략 가능한가 (비용 대비 효과)
- 아직 렌더링할 화면이 없는 **신규 와이어프레임/IA 설계 단계** (이때는 텍스트 와이어프레임이 산출물)
- 화면과 무관한 순수 로직/데이터 작업
- 로컬 서버를 띄울 수 없는 환경 — 단, 이때는 **"화면 미확인, 코드 기반 추정"임을 보고서에 명시**한다 (정직 보고).

### 가장 가벼운 표준 절차 (vue-zero 제로빌드 / 로컬 dev 서버)
이 프로젝트 스택에서 화면을 재현 가능하게 캡처하는 최소 방법. 새 도구 도입 비용은 거의 없다 — Playwright는 이미 `package.json`의 test 스크립트로 선언되어 있다.

1. **로컬 서버 기동 확인**: `pnpm run dev` (예: http://127.0.0.1:9000). 떠 있지 않으면 먼저 띄운다.
2. **캡처 실행**: 이 플러그인의 `bin/capture.mjs`(`node <malgn-agent 경로>/bin/capture.mjs <url> [output.png] [플래그]`)로 라우트별 캡처. 플래그(`--full/--vp/--wait/--click/--sel/--dark/--responsive`)와 위험도별 캡처 깊이는 `skills/common-screen-verification-and-capture/SKILL.md` 참조.
   - 최소판: 헤드리스 chromium으로 각 라우트를 `goto` → `screenshot({ fullPage: true })`로 `docs/screenshots/`에 저장.
   - 데스크톱(1440×900) + 모바일(390×844) 두 뷰포트는 반응형 판단에 거의 필수.
3. **이미지를 Read로 직접 본다**: 저장된 png를 Read 도구로 열어 눈으로 확인하고, 그 이미지를 근거로 지적/개선을 적는다.
4. **수정 후 재캡처**: 스타일을 고쳤으면 다시 캡처해 before/after를 남긴다 (또는 `curl <정확한 자산 경로> | grep <변경 문자열>`로 라이브 반영 확인).

> vue-zero 제로빌드 주의: SPA는 미지 경로에 index.html(fallback)을 200으로 반환한다. `curl <경로>` 200 응답만으로 "반영됨"을 판단하지 말고, index.html의 link/script src 기준 **정확한 자산 경로**(/assets/, /pages/, /layouts/)에 grep으로 변경 문자열 존재를 확인한다.

### 안티패턴
- ❌ 코드만 grep해서 "UI/UX 리뷰 완료" — 화면을 안 봤다. 시각적 판단의 근거가 없다.
- ❌ 화면 캡처 0개인데 "잘 보인다/가독성 좋다"고 단정 — 추정을 사실로 보고.
- ❌ 첫 화면만 한 장 — 탭/모달/빈 상태/에러/모바일을 빠뜨림 (`screenshot-capture-guide.md`의 상태 체크리스트 활용).

## 역할 분리형 SaaS의 UI/UX 명세 패턴 (산출물 역추출, 2026-06-20)

> 출처: coaching 프로젝트 `docs/specs/50~54-ui-ux-*.md` (역할 3종 코칭 SaaS). trainer가 모드 7(산출물 기반 진단)으로 우수 기법을 역추출해 박제. 이 명세 세트는 IA·역할 분리·상태·폼 검증·흐름·정합성 점검을 일관되게 처리한 모범 사례다. 신규 SaaS UI/UX 명세 시 이 골격을 출발점으로 삼는다.

### 1. 명세 분할 전략 (분량이 큰 UI/UX는 인덱스 + 분할 문서로)
한 화면군이 20개를 넘으면 단일 파일은 읽기·유지가 어렵다. **인덱스 문서 1개 + 주제별 분할 문서 N개**로 나누고, 인덱스에 분할 표(파일↔내용)를 둔다.
- 50=인덱스(범위+IA+공통), 51/52=역할별 화면 인벤토리, 53=컴포넌트/상태/폼/반응형/접근성, 54=흐름/추적성/Gap.
- 효과: 화면 추가 시 해당 분할 파일만 수정, 컴포넌트 변경은 53만 본다.

### 2. 단일 SPA · 역할별 뷰 분리 (RBAC를 IA에 반영)
역할(operator/coach/coachee)별로 **라우트 접두사 + 레이아웃을 분리**하고 표로 명시한다.

| 뷰 영역 | 대상 | 라우트 접두사 | 레이아웃 |
|---|---|---|---|
| 인증 | 비인증 | `#/auth/*` | layout: null |
| 운영자 포털 | operator | `#/operator/*` | 운영자 레이아웃 |
| 공유 리포트 | 토큰 기반 비인증 | `#/reports/shared` | layout: null |

핵심: **같은 기능(세션 이력)이라도 역할마다 화면·권한·동작이 다르면 별도 화면으로 정의**한다. 코치 세션 이력은 "요약 수정/확정"이 되지만 코치이 세션 이력은 "피드백 작성/취소"만 된다 — 같은 데이터, 다른 행동유도.

### 3. IA 매핑 표 (메뉴 → 라우트 → 아이콘, 깊이 ≤2)
메뉴를 1단계/2단계/라우트/아이콘 4열 표로 만든다. 메뉴 깊이는 최대 2단계로 제한(인지 부하). 2-depth는 "하위가 여러 개일 때만", 억지로 만들지 않는다. 아이콘까지 명세에서 못박으면 구현 일관성이 보장된다.

### 4. 화면 인벤토리 표준 항목 (각 화면을 동일 골격으로)
화면마다: **파일 경로 · 라우트 · 접근 역할 · 목적(FR-ID) · 레이아웃 스케치(ASCII) · 주요 동작(번호 매긴 절차) · API 의존(엔드포인트 나열)**. ASCII 스케치에 그리드 컬럼(col-lg-8/4)까지 표기하면 visual/frontend가 바로 구현 가능. "주요 동작"을 번호 절차로 적으면 인터랙션이 빠짐없이 드러난다.

### 5. 상태를 매트릭스로 (모든 데이터 화면의 5상태 + 화면별 빈 상태 문구)
- **공통 상태표**: Loading / Empty / Error / Success / Permission Denied — 각각 "조건 + 표시 방법". Error는 "다시 시도" 버튼까지.
- **화면별 Empty State 문구표**: 화면마다 빈 상태 메시지 + 액션 버튼을 개별 지정("등록된 코치가 없습니다" + "코치 등록하기"). 빈 상태를 다음 행동으로 연결하는 것이 핵심.
- **인증 상태표**: 토큰 만료(401→refresh→실패 시 logout), 비인증 접근, 역할 불일치(타역할 라우트→본인 대시보드 리다이렉트).

### 6. 폼 검증 명세 (필드 단위 6열 표)
폼마다: **필드 · 필수 · 형식 · 최대 길이 · 에러 메시지(빈값/형식 차등)**. 빈값과 형식 오류 메시지를 구분("이메일을 입력해주세요" vs "올바른 이메일 형식"). 추가로:
- **교차 검증**: "계약 종료일은 시작일 이후" 같은 필드 간 규칙 명시.
- **비즈니스 규칙**: "활성 목표 5개 상한 → 추가 버튼 비활성 + 안내" 같은 UI 제약을 폼 명세에 포함.

### 7. 사용자 흐름 + 엣지 케이스 의무 (happy path 금지)
흐름마다 **번호 절차(정상) + "에러/엣지 케이스" 블록**을 둔다. coaching 사례의 엣지 분기 예:
- 중복 이메일(409), CSV 일부 행 오류(오류 행 + 성공 건수 표시), 동시 예약 충돌, 초대 토큰 만료/사용됨, AI 요약 생성 실패(draft로 저장 후 수동 작성), SSE 스트리밍 중 네트워크 끊김(부분 응답 + 안내), 분당 요청 제한 초과.
> 외부 의존(AI/이메일/결제)이 있는 흐름은 **"그 외부가 실패하면?"을 반드시 분기**로 적는다.

### 8. FR-ID 추적성 매트릭스 (요구사항 ↔ 화면 양방향)
모듈별로 **FR-ID · FR 제목 · 관련 화면(라우트)** 표를 만든다. 효과: ① 요구사항이 어느 화면에서 충족되는지 추적, ② 화면 없는 FR(예: 이메일 알림=백엔드 내부, 화면 없음)을 명시적으로 N/A 처리, ③ 누락 화면 발견. 한 FR이 여러 역할 화면에 걸치면 모두 나열(세션 이력=operator/coach/coachee 3개).

### 9. API Gap Report (UX ↔ Backend 정합성 자가 점검) ★UX의 차별 기법
화면이 요구하는 API를 **api-spec과 대조**해 누락 엔드포인트/응답 필드를 보고한다. 구조화 출력으로:
```json
{ "has_gaps": false, "gaps": [] }
```
gap이 있으면 `gaps`에 "어느 화면이 어떤 엔드포인트/필드를 필요로 하는데 명세에 없음"을 적어 backend에 넘긴다. **UX 명세가 그냥 그림이 아니라 백엔드와 맞물리는 계약임을 증명하는 기법** — 구현 단계 재작업을 크게 줄인다.

### 약점·보완 지점 (이 사례에서도 부족했던 것 — 다음엔 보강)
- **접근성이 체크리스트 수준**: WCAG AA, 포커스 트랩, aria-label, aria-live까지 언급은 좋으나, **화면별로 어디에 어떤 aria가 붙는지**(예: 감정 그래프 데이터 포인트의 스크린리더 대체 텍스트, 캘린더 셀 키보드 이동)까지는 안 내려감. 차트·캘린더 같은 복합 위젯의 접근성은 별도로 깊게 명세할 것.
- **모션/전환 명세 부재**: 모달 등장, 스트리밍 커서, 페이지 전환의 모션을 UX에서 정의하지 않음(visual에 떠넘김). 핵심 인터랙션의 모션 의도는 UX에서 짚어주는 게 좋다.
- **IA 대안 비교 누락**: 채택한 메뉴 구조는 좋으나 "왜 이 구조인가 + 검토한 대안"(IA 대안 의무)이 문서에 안 남음. 추적성·상태는 훌륭하나 IA 자체의 발산적 검토 흔적이 약함.
