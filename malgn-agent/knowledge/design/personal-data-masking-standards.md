# 개인정보 화면 마스킹 기준

> owner: trainer

## 범위 — 이 문서가 다루지 않는 것

이 문서는 **화면(UI) 표시 단계**에서 개인정보를 얼마나 가려서 보여줄지의 기준이다. 저장 시 암호화, 전송 구간 암호화(TLS), DB 접근 제어 같은 **저장/전송 계층 보안**은 다루지 않는다 — 그쪽은 `skills/domain-backend-api-security`(인증·인가·DB 접근 제어)와 `skills/domain-security-audit-checklist`(암호화·로깅)가 정본이다. 이 문서는 그 위에서, 정당한 권한으로 화면에 값을 뿌릴 때조차 **꼭 필요한 만큼만 보여준다**는 화면 설계 규칙을 다룬다.

## 왜 화면 단위 규정이 따로 필요한가

"암호화해서 저장했으니 안전하다"와 "화면에 전체 값을 그대로 노출해도 된다"는 별개 문제다. 관리자·상담원·일반 사용자 누구나 화면을 캡처하거나 어깨너머로 볼 수 있고, 권한이 있는 화면이라도 업무상 전체 값이 필요 없는 경우가 대부분이다. 아래 수치는 국내 서비스에서 통용되는 일반적 관행을 기준으로 삼는다 — 프로젝트별 법무·컴플라이언스 요구가 이보다 엄격하면 그쪽을 따른다(이 문서는 하한선이지 상한선이 아니다).

## 필드별 마스킹 기준

| 필드 | 표시 규칙 | 예시 |
|---|---|---|
| 이름(2자) | 뒤 1자 마스킹 | 김* |
| 이름(3자) | 가운데 1자 마스킹 | 김*수 |
| 이름(4자 이상) | 첫 글자·마지막 글자만 노출, 나머지 전부 마스킹 | 김**수 |
| 휴대폰번호 | 앞 3자리 노출 + 가운데 4자리 마스킹 + 뒤 4자리 노출 | 010-****-1234 |
| 유선전화 | 지역/국번 노출 + 뒤 4자리 중 뒤 4자리는 노출, 국번 일부 마스킹 | 02-***-5678 |
| 이메일 | 로컬파트(@ 앞부분) **앞 2글자만 노출**, 나머지 마스킹, 도메인은 그대로 | ab***@example.com |
| 주민등록번호 | 생년월일 6자리 노출 + 성별 구분자 1자리 노출 + 나머지 6자리 전부 마스킹 | 901231-1****** |
| 계좌번호 | 앞 4자리 + 뒤 4자리 노출, 중간 마스킹 | 110-***-**5678 |
| 카드번호 | 앞 6자리(발급사 BIN) + 뒤 4자리 노출, 중간 마스킹(PCI DSS 관행과 정합) | 123456-**-****-5678 |
| 주소 | 시/구/동까지만 노출, 상세주소(번지·동/호수)는 마스킹 | 서울시 강남구 ***-** |

**공통 원칙**: 마스킹 문자는 `*`로 통일한다(임의로 `#`·`X` 등 혼용하지 않는다). 마스킹된 자릿수는 원래 자릿수와 동일하게 유지한다(예: 010-****-1234에서 `****`는 항상 4자 — 자릿수를 다르게 표시하면 역으로 자릿수 추정 정보가 샌다).

## 마스킹 해제(unmask) 정책

- 전체 값이 실제로 필요한 업무(본인 확인, 결제 처리 등)에서만 권한 등급별로 마스킹 해제를 허용한다 — 목록 화면은 항상 마스킹, 상세 화면에서도 기본은 마스킹 후 "전체 보기" 액션으로만 해제.
- **마스킹 해제는 감사 로그 대상이다**: 누가·언제·어떤 레코드의 전체 값을 조회했는지 기록한다(백엔드 접근 로그 요구사항은 `skills/domain-security-audit-checklist` §로깅/모니터링 참조).
- 마스킹 해제 버튼/토글은 목록 화면 전체 일괄이 아니라 **레코드 단위**로 제공한다(일괄 해제는 대량 유출 리스크를 키운다).

## 화면 설계 체크리스트

- [ ] 목록(리스트) 화면의 개인정보 컬럼이 기본 마스킹 상태인가?
- [ ] 위 표의 필드별 자릿수·노출 범위를 따랐는가(자릿수 임의 변경 없음)?
- [ ] 마스킹 해제 액션이 레코드 단위이고, 해제 시 감사 로그가 남는가?
- [ ] 인쇄/PDF 내보내기·엑셀 다운로드 등 화면 밖으로 나가는 산출물도 동일한 마스킹 기준을 적용했는가(화면만 마스킹하고 다운로드는 평문으로 새는 경우가 흔한 함정)?
- [ ] 에러 메시지·로그 화면(관리자 콘솔 등)에 개인정보가 마스킹 없이 그대로 노출되지 않는가?
