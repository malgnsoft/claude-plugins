# 화면 재사용·재렌더 시 일관성 검증 (설계→구현→리뷰 파이프라인 공통)

## 배경 사례

설계 문서가 신규 페이지를 기존 페이지와 별도 라우트로 분리하면서, 프로즈 서술에는 "기존 헤더를
자체적으로 다시 렌더한다"고 적어놓고, 바로 아래 ASCII 와이어프레임에는 이와 **모순**되게 다른
내용(예: 제목에 원본엔 없는 접미사 추가, 부제 내용이 원본과 다른 성격으로 변경, 탭바를 헤더보다
위에 배치)을 구체적으로 그려놓는 경우가 있다. 구현 에이전트는 프로즈보다 더 구체적인 아티팩트
(와이어프레임)를 우선 따라 **문자 그대로 정확히 구현**한다 — "설계를 안 보고 대충 만든" 게
아니라 "프로즈보다 더 구체적인 아티팩트를 우선 따른" 것이며, 이는 그 자체로는 합리적인 행동
패턴이다. 결과: 같은 대상을 다루는 기존 페이지와 헤더 내용·순서가 완전히 달라지고, 백엔드가
관련 필드를 안 내려주는 등의 결함까지 함께 발생할 수 있다. 리뷰 파이프라인이 백엔드/롤업 로직이나
기능/회귀 테스트만 검토하고, "기존 페이지와 헤더·탭 마크업을 재사용/재렌더하는 신규 화면"에
대해 시각적 일관성을 명시적으로 체크하는 단계가 파이프라인 어디에도 없으면, 이 불일치는 아무도
잡지 못한 채 완료 처리된다.

## 핵심 실패 패턴

구현 에이전트가 프로즈보다 더 구체적인 아티팩트(와이어프레임/코드 스니펫)를 우선 따르는 것 자체는
정상적 행동이다. 진짜 문제는 **설계 문서 내부에서 프로즈와 와이어프레임이 같은 대상을 서로 다르게
서술**했는데, 그 불일치를 아무도 잡지 않았다는 것이다 — 작성한 architect도, 구현한 frontend-dev도,
리뷰한 reviewer도.

## 역할별 반영 원칙

### architect — 설계 산출물 자체 정합성 검증
새 화면이 기존 화면의 마크업·헤더·탭 등을 "재사용" 또는 "동일하게 재렌더"한다고 프로즈에 쓸 때는,
**같은 문서의 ASCII 와이어프레임·코드 스니펫이 그 재사용 대상 화면의 실제 문구·요소 순서와 1:1
일치하는지 자체 대조**한 뒤 제출한다. 와이어프레임을 그릴 때 "대충 비슷하게"가 아니라 대상 화면의
실제 `.vue` 파일을 열어 문구·클래스명·순서를 그대로 옮겨 적는다. 프로즈와 와이어프레임이 어긋나면
아무도 못 잡을 수 있다는 전제로, 제출 전 self-diff를 습관화한다.

### frontend-dev — 와이어프레임 신뢰 전에 실물 대조
설계 문서가 "기존 화면 X와 동일하게" 재사용/재렌더를 명시한 요소는, 와이어프레임만 보고 구현하지
말고 **실제 X 화면의 소스(`.vue` 파일 마크업)를 직접 열어 문구·클래스·순서를 대조**한 뒤 구현한다.
프로즈와 와이어프레임이 서로 다르면 (a) 실제 기존 화면 쪽 마크업을 우선하거나 (b) 설계자에게
불일치를 확인 질문한다 — 와이어프레임을 무비판적으로 그대로 옮기지 않는다. 여러 페이지가 공유해야
할 마크업(헤더·탭바 등)은 손으로 복붙하지 말고 공용 컴포넌트로 추출해 두 화면이 같은 소스를
쓰게 만드는 편이, 나중에 원본이 바뀔 때 드리프트를 원천 차단한다.

### reviewer — 재사용/재렌더 신규화면의 시각적 일관성 리뷰 항목
"기존 페이지의 헤더·탭·네비게이션 마크업을 복붙/재렌더하는 신규 페이지"가 생기면, 백엔드 계약
검증·기능 테스트와 별개로 **원본 페이지와 나란히 놓고 클래스명·문구·렌더순서를 diff**하는 시각적
일관성 체크를 리뷰 체크리스트에 반드시 포함한다. 이 리뷰 항목이 스코프에서 "다음 Step"으로 미뤄질
경우, 그 Step이 실제 착수될 때 반드시 별도로 호출돼야 함을 보고서에 명시한다(스코프 생략이 "안 해도
됨"으로 유실되지 않도록).
