# 토큰 효율 협업 원칙

> 신설 사유 (2026-06-20): 사용자 지시 — "에이전트들이 서로 연계하며 동작하면 토큰을 많이 쓴다. 토큰을 아끼다 문제 해결을 못 하는 것보다는 적절히 쓰는 게 낫지만, 방만하게 쓰는 것은 절대 안 된다. 토큰은 절대 수치가 제한되어 있으니 에이전트들은 효율적이고 줄이는 방향으로 소통해야 한다."

이 문서는 **모든 에이전트**에 적용된다. 특히 PM이 하위 에이전트를 호출하고 결과를 통합하는 **다중 에이전트 협업**에서 토큰 낭비를 막는 공통 규범이다.

---

## 대원칙 — 효율 우선, 단 문제 해결이 최우선

**토큰은 절대량이 제한된 자원이다.** 그러나 우선순위는 분명하다:

1. **문제 해결 실패 > 토큰 낭비.** 아끼려다 일을 못 끝내는 것은 최악이다. 필요한 조사·검증·재작업은 한다.
2. **방만한 사용은 절대 금지.** "혹시 몰라서" 전체를 다 읽고, 다 반환하고, 다 복붙하는 것은 금지.
3. **목표: 같은 결과를 더 적은 토큰으로.** 품질을 떨어뜨리지 않으면서 줄일 수 있는 모든 곳에서 줄인다.

판단 기준: **"이 토큰을 쓰지 않으면 결과 품질이 실제로 나빠지는가?"** 아니라면 쓰지 않는다.

---

## 원칙 1 — 산출물은 파일로, 대화로는 경로만 (Pass Paths, Not Payloads)

에이전트 간 중간 산출물(기획서, 설계서, 코드, 분석 결과)을 **대화 본문으로 통째로 주고받지 않는다.**

- 하위 에이전트는 결과를 **파일로 저장**하고, PM에게는 **저장 경로 + 3~5줄 요약 + 핵심 결정사항**만 반환한다.
- PM은 다음 에이전트에게 전체 내용을 복붙하지 않고 **"입력: `docs/architecture.md` 읽어라"**라고 경로만 전달한다.
- 다음 에이전트가 필요한 부분만 Read하면 된다. 전체를 대화에 실어 나르면 같은 내용이 N번 토큰으로 계산된다.

```
❌ PM → architect 결과 전문(2000줄)을 대화에 받음 → backend-dev에게 그대로 복붙
✅ architect가 docs/architecture.md 저장 → PM에 "저장 완료, 핵심 결정 3가지: …" 반환
   → PM이 backend-dev에 "docs/architecture.md 기반으로 구현, API 섹션 우선" 위임
```

## 원칙 2 — 하위 에이전트의 반환은 압축한다 (Return Compressed)

하위 에이전트가 PM에게 돌려주는 메시지는 **보고이지 산출물 자체가 아니다.** 다음만 반환한다:

- ✅ 한 일 1~2문장 + 산출물 경로 + 핵심 결정/수치 3~5개 + 다음 단계에 필요한 주의사항
- ❌ 작성한 문서 전문, 코드 전체, 사고 과정 나열, 장황한 인사·자기소개

PM도 사용자에게 통합 보고할 때 **2분 규칙**(2분 내 읽힘)을 지킨다. 전체 산출물은 파일에 있으니 경로로 가리킨다.

## 원칙 3 — 위임 프롬프트는 짧고 정확하게 (Lean Delegation)

PM의 위임 프롬프트는 **필요한 것만** 담는다:

- 입력 산출물 **경로**, 기대 산출물 + **저장 경로**, 반드시 지킬 제약 2~3개, 참조할 product-principles 경로.
- 전체 프로젝트 맥락을 매번 장황하게 재설명하지 않는다 — 경로로 가리킨다.
- 단, **과도한 압축으로 지시가 모호해져 재작업이 발생하면 오히려 토큰 손해다.** 명확성은 유지한다.

## 원칙 4 — 필요한 만큼만 읽는다 (Read What You Need)

- 파일 전체를 습관적으로 Read하지 말고, Grep/Glob으로 위치를 먼저 찾고 **필요한 구간만** Read한다.
- 넓은 탐색이 필요하면 Explore/general-purpose 에이전트에 위임해 **결론만** 돌려받는다(파일 덤프 회수 방지).
- 같은 파일을 방금 수정했으면 재확인용으로 다시 Read하지 않는다.

## 원칙 5 — 팀 구성은 일에 맞게 (Right-Size the Team)

- 단순 작업에 풀 파이프라인을 가동하지 않는다. 1회성 질의·조사는 에이전트 체인 없이 직접 처리.
- 불필요한 단계는 생략한다(예: 작은 수정에 reviewer 패널 전체 가동 불필요).
- 반대로, **품질에 꼭 필요한 검증·리뷰 단계는 토큰을 이유로 생략하지 않는다.** (원칙 0의 1번)

## 원칙 6 — 재작업이 가장 큰 낭비다 (Rework Is the Biggest Waste)

토큰을 가장 많이 잡아먹는 것은 **잘못 만들어 다시 만드는 것**이다. 따라서:

- 위임 시 기대 산출물과 제약을 명확히 해 **한 번에 맞게** 만든다(원칙 3).
- 유령 보고(`verifiable-output-and-honesty.md`)는 재작업을 부르므로 토큰 효율 관점에서도 금지.
- 모호하면 추측으로 진행하지 말고 **시작 전 사용자/PM에 한 번 확인**한다 — 잘못된 방향으로 길게 가는 것보다 싸다.

## 원칙 7 — 과다 턴을 통제한다 (Turn Budget)

토큰은 산출물 크기뿐 아니라 **대화 턴 수 × 누적 컨텍스트**로 늘어난다. 서브에이전트가 목표 없이 탐색·자문자답을 반복하면 매 턴 전체 컨텍스트가 재과금돼 조용히 폭증한다. 이것이 가장 놓치기 쉬운 낭비다.

- **턴 예산을 먼저 정한다.** 위임 전 "이 일은 몇 턴이면 끝나는가"를 어림하고, 단순 조회·수정은 1~3턴, 설계·구현도 대체로 한 자리 턴 안에서 끝나야 정상이다. 예산을 크게 넘기면 그건 진척이 아니라 **길잃음 신호**다.
- **목표를 완수하면 즉시 멈추고 반환한다.** "혹시 더"라며 추가 탐색·재확인·과잉 검증을 반복하지 않는다. 요구된 산출물이 나왔으면 끝이다.
- **탐색은 한 번에 폭으로.** Grep/Glob/Explore로 필요한 곳을 **병렬 1턴**에 훑는다. 파일을 하나씩 순차로 열어보며 턴을 소모하지 않는다(원칙 4와 결합).
- **막히면 배회하지 말고 보고한다.** 2~3턴 시도해도 안 풀리면, 같은 접근을 반복(=턴·토큰만 소모)하지 말고 막힌 지점을 요약해 PM/사용자에게 되묻는다. 배회는 재작업보다 은밀한 낭비다.
- **자기 검증 루프를 무한정 돌지 않는다.** 방금 만든 것을 다시 읽어 확인하는 루프는 1회로 족하다(원칙 4).

## 원칙 8 — 서브에이전트를 감독한다 (Supervise Delegates)

호출자(PM·리더 에이전트)는 위임으로 끝이 아니라 **서브에이전트의 소비를 감독할 책임**이 있다:

- 위임 프롬프트에 **범위·산출물·턴 예산**을 명시해, 서브가 스스로 멈출 기준을 준다("X를 만들면 끝. 못 찾으면 3턴 내 보고").
- 서브가 예산을 초과하거나 배회하는 조짐이면 계속 두지 말고 **중단·재지시**한다.
- 서브의 반환은 압축을 강제한다(원칙 2) — 서브가 전문을 게워내면 그 자체가 턴·토큰 낭비다.

## 빠른 체크리스트 (협업 시작 전·반환 직전)

- [ ] 중간 산출물을 파일로 저장하고 **경로만** 넘기는가? (전문 복붙 ❌)
- [ ] 반환 메시지가 보고 수준(요약+경로+핵심)인가? 산출물 전체를 싣고 있지 않은가?
- [ ] 위임 프롬프트가 경로 중심으로 간결한가? 그러면서도 모호하지 않은가?
- [ ] 파일 전체 대신 필요한 구간만 읽는가?
- [ ] 이 단계/에이전트가 결과 품질에 실제로 필요한가? (불필요하면 생략, 필요하면 유지)
- [ ] 한 번에 맞게 만들어 재작업을 피하는가?
- [ ] 턴 예산 안에서 끝나는가? 목표 완수 후 즉시 멈추는가? (배회·과잉 검증 ❌)
- [ ] (호출자) 서브에이전트에 범위·산출물·턴 예산을 주고, 초과·배회를 감독하는가?
