# i18n 용어 감사·번역 가이드

> localizer.md 본문의 원칙을 압축·구조화한 참조 자료. 새 내용을 지어내지 않고 기존 원칙을 정리한 문서.

## 1. 직역 금지, 관용구 우선

원문 형태소를 그대로 대응시키지 않는다. 판단 기준은 "이 단어가 자연스러운가"가 아니라 **"실제 제품에서 이렇게 쓰는가"**다.

- 나쁜 예: "사용자 관리" → "User Management" (형태소 직역)
- 좋은 예: "사용자 관리" → "Users" (실제 SaaS/LMS 관리자 화면에서 흔히 쓰는 표현 채택)

## 2. 외부 UI 관용구는 추정 금지, 실사례로 확인

기억에 의존해 "아마 이렇게 쓰겠지"로 용어를 창작하지 않는다. 의심되는 용어는 WebSearch/WebFetch로 실제 제품의 공식 UI 문구·문서를 찾아 대조한 뒤 채택한다.

**도메인별 레퍼런스 제품**:
- 관리자/대시보드류: GitHub, Slack, Notion 관리자 설정 화면
- LMS/교육 도메인: Google Classroom, Canvas LMS, Moodle, PowerSchool

확인하지 못한 용어는 "확인 필요"로 표시하고 추측으로 채우지 않는다.

## 3. 로케일별 관용 차이 인지

같은 언어 코드(예: `en`)라도 로케일마다 관용구가 다를 수 있다(미국식 vs 영국식 등).

- 참고 자료가 적은 로케일(예: `uz`)은 인접 언어권(러시아어·튀르키예어) UI 관용구나 현지 도메인(교육행정 등) 용어를 보조로 참고한다.
- 그래도 어색하면 사용자에게 확인을 구한다 — 억지로 채우지 않는다.

## 4. 용어 감사(Audit) 절차

1. 프로젝트의 i18n 소스 파일(예: `useI18n.js`, `locales/*.json` 등 — 프로젝트마다 파일명·구조가 다르므로 착수 전 실제 파일을 먼저 확인) 전수 확인 — 값이 한글 표현을 형태소 단위로 옮긴 직역인지 판정.
2. 의심 용어는 도메인·화면 유형별 실제 레퍼런스 제품에서 대응 문구를 검색(WebSearch/WebFetch)해 확인.
3. 교정안을 "기존 표현 → 교정 표현 (근거: 참고 제품/화면)" 형태로 정리.
4. 사용자/PM 승인 후 실제 파일에 반영. 사소한 오역(명백한 직역 오류)은 감사 중 바로 교정 가능하나, 의미가 갈리는 애매한 건은 목록화해 확인을 구한다.

## 5. 용어 일관성·기존 컨벤션 계승

- 같은 개념은 프로젝트 전체에서 같은 용어로 통일한다. 신규 작업 전 기존 번역 파일에서 유사 개념이 이미 어떻게 번역돼 있는지 먼저 확인한다.
- 시드 데이터(고유명사·인명·과목명 등)·코드 주석·route title은 번역 대상에서 제외하는 등, 프로젝트에 이미 확립된 컨벤션이 있으면 임의로 바꾸지 않고 따른다. 프로젝트별 컨벤션은 STATUS.md/decision 이력을 먼저 확인한다.

## 6. 용어집(Glossary) 관리

프로젝트에 `docs/i18n-glossary.md`(또는 유사 파일)가 있으면 재사용·갱신하고, 없으면 감사/번역 중 확정한 용어를 정리해 신규 생성을 제안한다.

형식: `한글 표현 | 채택 영어(관용구) | 근거(참고 제품) | 비고`

## 7. 검증 없는 완료 보고 금지

번역/감사 작업 완료 시 다음을 스스로 확인 후 보고한다:
1. 언어별 키셋 1:1 일치
2. 문법 검사(`node --check` 등)
3. `git diff` 앞/끝 대조로 스트레이 아티팩트 없음
4. 잔여 원문 텍스트 0건(시드·주석·route title 제외)
