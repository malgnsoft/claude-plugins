# 검색 전략: 벡터 검색 vs Full-text 검색 선택 기준

## 상황
- DB에 문서·레코드 검색 기능을 설계/구현할 때 (예: KB(지식베이스) 검색, FAQ 검색, 컨텐츠 추천, 시맨틱 검색 도입 검토).
- 특히 한글 등 비영어 쿼리를 지원해야 하는 경우 판단이 갈리기 쉽다 — 임베딩 모델의 언어 지원 범위를 먼저 확인해야 한다.

## 원칙
1. **기본 검색은 Full-text(키워드) 검색을 우선한다.** PostgreSQL tsvector+GIN 인덱스 등. 정확한 키워드가 존재하는 질의에서는 Full-text가 벡터보다 항상 우위다.
2. **벡터(의미론적) 검색은 보조 역할로 배치한다.** "동의어·관련 개념 확장"(예: "payment gateway integration" → payment method, QR 등 연관 문서 추천) 목적에는 강하지만, 전반적 정확도는 Full-text보다 낮을 수 있다.
3. **다국어(특히 한글) 쿼리 지원이 필요하면 다국어 임베딩 모델(예: multilingual-e5)이 전제 조건이다.** 영어 전용 모델(BGE-small-en 등)은 한글 쿼리에서 사실상 무력화된다(실측 0% 매칭) — "벡터 검색 도입"을 결정하기 전에 지원 언어 범위부터 확인한다.
4. **프로덕션 지향점은 하이브리드(벡터+키워드 랭킹 결합) 검색이다.** 어느 한쪽만으로는 커버리지가 부족하므로, 규모가 커지면 두 방식을 결합하는 설계를 권장한다.
5. **인덱스 전략은 데이터 규모에 따라 재평가한다.** 데이터가 수백~수천 건 미만일 때는 IVFFlat 등 벡터 인덱스의 이점이 크지 않다 — 데이터가 수천 건 이상으로 커질 때 벡터 인덱스 도입을 재검토한다.

## 근거
- kb-draft 375개 문서 대상 POC(`embed_kbdrafts.py`, `search_kbdrafts.py`, `test_search_comprehensive.py`).
- 벡터 검색 강점: 의미상 유사한 문서를 동의어·관련 개념 매칭 없이도 자동 추천.
- 벡터 검색 약점: 영어 쿼리 기준 정확도 60% (Full-text 95% 대비 낮음), 정확한 키워드 매칭이 필요 없는 상황에서도 정밀도가 떨어질 수 있음.
- 한글 쿼리 실측: Full-text 100% vs 벡터 0% (임베딩 모델이 영어 전용이라 완전 무력화).
- 성능(로컬 환경, 375건 기준): BGE-small-en-v1.5 임베딩 약 7초 소요, Full-text 응답 속도가 벡터보다 빠름 — 단 이는 소규모 데이터셋 기준이며 IVFFlat류 벡터 인덱스는 수천 건대부터 진가를 발휘한다.

## 예외
- 데이터 규모가 수만 건 이상으로 커지고 벡터 인덱스(IVFFlat 등)가 진가를 발휘하는 구간이면, 위 "Full-text가 더 빠르다"는 성능 비교는 재검증이 필요하다.
- 검색 대상이 애초에 영어 단일 언어 컨텐츠이고 의역·동의어 매칭이 핵심 요구사항이면 벡터 검색 비중을 상대적으로 높이는 설계가 타당할 수 있다.
- 이 결론은 로컬 POC(375건, BGE-small-en-v1.5, 1회 실측) 기준이다 — 다른 임베딩 모델·데이터 규모·언어 조합에서는 결론이 달라질 수 있으므로, 프로덕션 도입 전 동일한 방법(hybrid 비교 테스트)으로 재검증할 것을 권장한다.
