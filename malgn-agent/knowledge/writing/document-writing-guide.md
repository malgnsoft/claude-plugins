# 비즈니스 문서 작성 가이드

## 문서 유형별 구조

### 사업 제안서
```markdown
# [프로젝트명] 제안서

## 1. Executive Summary (1페이지)
- 핵심 제안 내용 3줄 요약
- 기대 효과
- 소요 예산/기간

## 2. 배경 및 필요성
- 현재 상황 (As-Is)
- 문제점/기회
- 해결 방향 (To-Be)

## 3. 제안 내용
### 3.1 목표
### 3.2 범위
### 3.3 방법론/접근 방식
### 3.4 주요 기능/서비스

## 4. 기대 효과
- 정량적 효과 (비용 절감, 생산성 향상 등)
- 정성적 효과 (만족도, 브랜드 가치 등)

## 5. 추진 일정
| 단계 | 기간 | 주요 활동 |
|------|------|----------|

## 6. 예산
| 항목 | 금액 | 비고 |
|------|------|------|

## 7. 팀 구성
| 역할 | 담당 | 책임 |
|------|------|------|
```

### 기술 문서 (Divio 4유형)
1. **튜토리얼**: 단계별 따라하기 (학습 지향)
2. **How-to 가이드**: 특정 문제 해결 (목표 지향)
3. **설명/개념**: 왜/어떻게 동작하는지 (이해 지향)
4. **레퍼런스**: API/설정 명세 (정보 지향)

# [주제] 보고서

## 작성 원칙

### 독자 맞춤 톤
| 독자 | 톤 | 예시 |
|------|-----|------|
| 경영진 | 간결, 결론 먼저 | "비용 30% 절감이 가능합니다" |
| 개발자 | 구체적, 코드 예시 | "Hono의 미들웨어로 구현합니다" |
| 일반 사용자 | 쉬운 용어 | "버튼을 누르면 자동으로 저장됩니다" |

### 시각적 구조화
- 표: 비교/목록 데이터
- 리스트: 순서 있는 절차, 체크리스트
- 다이어그램: 흐름, 구조, 관계
- 강조: **핵심 용어**, `코드/명령어`

### 한국어 작성 팁
- 문장은 짧게 (한 문장에 한 메시지)
- 능동태 사용 ("~합니다" > "~됩니다")
- 불필요한 조사/접속사 제거
- 전문 용어는 첫 등장 시 설명

## 평범한 문서를 넘는 4가지 기법 (모드 7 자가진단으로 도출, 2026-06-20)

> 출처: malgnai 소개 문서를 실제 작성하고 "평범한 5가지 냄새"로 자가평가한 결과 정착된 방법론. 어느 회사에나 붙일 수 있는 소개서를 쓰지 않기 위한 실전 기법.

### 1. 일반 기능을 "의도된 선택"으로 서술하라
나쁜 예: "엣지 서버를 사용해 확장성이 좋습니다." (← 누구나 쓰는 일반론)
좋은 예: "별도 서버 없이 `wrangler deploy` 한 줄로 엣지에 올라간다 — 개인/소규모 팀이 인프라 부담 없이 모바일 확인을 얻기 위한 의도된 선택." (← *왜 이 선택인지*를 붙임)
- 기능을 나열하지 말고, **각 기능 옆에 "이 프로젝트가 이걸 택한 이유"**를 한 줄 붙인다. 그러면 복붙이 불가능해진다.

### 2. 코드/스키마의 실제 식별자를 인용하라 (근거의 구체화)
- 추상어("활동을 기록합니다") 대신 실제 시그니처(`activity_log(agent_name, action, detail, project_id, task_id)`), 실제 테이블명(6개), 실제 도구 수(11개)를 박는다.
- 작업 전 `server/`·스키마·`bin/`을 Read해 **고유 식별자를 최소 5개 확보**하고 본문에 심는다. 이것이 "복붙 가능" 냄새를 가장 확실히 없앤다.

### 3. "솔직한 경계" 섹션을 의무화하라 (happy path 탈출)
- 제안/소개 문서일수록 한계를 숨기고 싶어지지만, **"지금 못 하는 것" 섹션이 오히려 신뢰를 만든다.**
- 형식: 한계 2~3개를 명시하고, 각 한계를 다음 로드맵 항목과 연결("이 격차를 줄이는 것이 다음 과제"). 한계가 회피가 아니라 방향성의 근거가 된다.

### 4. 차별점 표는 "한 줄 수렴"으로 닫아라
- 비교표(흔한 접근 vs 우리)는 근거이고, 그 아래 **"한 줄: 핵심 차별 = ___"**로 수렴시킨다. 표만 두면 독자가 결론을 직접 만들어야 한다.
- 차별점 칸을 형용사("더 빠름")가 아니라 **메커니즘**("D1 적재로 검증")으로 채운다 — 근거 없는 단정 냄새 제거.

### 작성 후 1분 자가검증 (writing 전용)
- [ ] 프로젝트명만 바꿔 다른 회사에 붙여도 말이 되는가? → 그렇다면 고유 식별자/의도된 선택을 더 박는다.
- [ ] 한계를 명시한 섹션이 있는가? happy path만 그렸는가?
- [ ] 모든 차별점 주장에 메커니즘 근거가 붙었는가, 형용사뿐인가?
- [ ] Executive Summary가 "한 줄 인용 블록(> )"으로 핵심을 박는가?
