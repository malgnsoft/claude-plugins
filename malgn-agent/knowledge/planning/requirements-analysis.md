# 요구사항 분석 가이드

> 상용 수준 PRD 작성의 고급 기법(분할 전략, FR-ID 추적성, 인수조건, 범위 경계 3중, 도메인 용어 사전)은 `prd-craft-patterns.md` 참조 — coaching 우수 사례에서 역추출.

## 요구사항 도출 프로세스

### 1단계: 원문 정리
- 고객 요구사항을 해석 없이 원문 보존
- 모호한 표현도 그대로 기록 (이후 해석)

### 2단계: 기능 요구사항 도출
- 각 기능의 상세 동작 정의
- 입력/출력 명시
- 예외 상황 정의
- 비즈니스 규칙 도출

### 3단계: 비기능 요구사항 정의
- 성능: 응답 시간, 동시 접속자
- 보안: 인증/인가, 데이터 보호
- 확장성: 예상 성장률 대응
- 호환성: 브라우저, 디바이스

### 4단계: 우선순위 분류
- **Must Have**: 없으면 서비스 불가
- **Should Have**: 있으면 좋지만 없어도 런칭 가능
- **Nice to Have**: 여유가 있을 때

## PRD 구조 템플릿

```markdown
# [제품명] PRD

## 1. 제품 개요
- 목적
- 타겟 사용자
- 핵심 가치 제안

## 2. 기능 요구사항
### F-001: [기능명]
- 설명
- 사용자 스토리: "[역할]로서 [행동]을 하여 [가치]를 얻고 싶다"
- 입력/출력
- 예외 처리
- 우선순위: Must/Should/Nice

## 3. 비기능 요구사항
- NFR-001: 성능 — 페이지 로딩 3초 이내
- NFR-002: 보안 — HTTPS 필수, 비밀번호 해싱

## 4. 제약사항 및 가정
- 기술 제약
- 비즈니스 제약
- 전제 조건

## 5. 용어 정의
```

## 모호한 요구사항 처리

| 상황 | 기본 결정 |
|------|----------|
| "게시판" | CRUD + 페이징 + 검색 |
| "로그인" | 이메일/비밀번호 기본, JWT 토큰 |
| "관리자" | 별도 관리자 페이지, RBAC |
| "대시보드" | 주요 지표 카드 + 차트 |
| "알림" | 인앱 알림 (이메일/SMS는 Nice to Have) |

## 사용자 스토리 작성법

```
As a [역할], I want to [행동] so that [가치].
```

### 좋은 예시
- "관리자로서, 사용자 목록을 검색할 수 있어서 특정 사용자를 빠르게 찾을 수 있다"
- "일반 사용자로서, 비밀번호를 재설정할 수 있어서 계정 접근을 복구할 수 있다"
