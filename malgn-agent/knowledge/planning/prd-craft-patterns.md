# PRD 작성 고급 기법 (우수 산출물 역추출)

> 출처: `coaching` 프로젝트 Coach Connect PRD (`docs/specs/10~13`, 2026-06) — 실전 우수 사례에서 역추출한 재사용 가능 기법. trainer 모드 7(산출물 기반 진단)로 추출.

이 문서는 "PRD 구조 템플릿"(requirements-analysis.md)을 넘어, **무엇이 평범한 PRD와 상용 수준 PRD를 가르는가**를 다룬다.

---

## 1. PRD 분할 전략 (분량이 커지면 쪼갠다)

PRD가 길어지면 단일 파일에 욱여넣지 말고 **역할이 다른 문서로 분할하고, 인덱스 문서에 분할표를 둔다.**

Coach Connect 실제 분할:

| 파일 | 역할 |
|------|------|
| `10-product-requirements.md` | 인덱스 + 제품 요약 + 대상 사용자 |
| `11-prd-scenarios.md` | 핵심 사용자 시나리오 |
| `12-prd-requirements.md` | 기능 요구사항 (모듈별) |
| `13-prd-nonfunctional.md` | 비기능 + 가정 + 범위제외 + 용어 + 미결사항 |

- **인덱스 문서 최상단에 분할표**를 두어 어디에 무엇이 있는지 한눈에 보이게 한다.
- 각 분할 문서 최상단에 `> 본 문서는 [인덱스](./10-...md)의 분할 문서입니다.` 역참조를 단다.
- 번호 접두사(`10-`, `11-`)로 읽는 순서를 강제한다.
- 효과: 한 문서가 너무 길어 리뷰·수정이 어려워지는 것을 막고, 아키텍트/개발자가 필요한 부분만 열어볼 수 있다.

## 2. FR-ID 추적성 매트릭스 (기능 요구사항을 표로 고정한다)

기능 요구사항은 산문이 아니라 **고유 ID를 가진 표**로 작성한다. 한 행 = 하나의 검증 가능한 요구사항.

```
| ID | 제목 | 설명 | 우선순위 | 인수 조건 |
|----|------|------|----------|-----------|
| FR-001 | 역할 기반 로그인 | ... | Must | 1. ... 2. ... 3. ... |
```

핵심 규칙:
- **모듈별로 묶고 ID를 연속 부여**한다 (모듈 A: 인증 FR-001~004, 모듈 B: 코치관리 FR-005~008 ...). ID는 PRD→아키텍처→개발→QA→리뷰 전 단계의 **추적 키**가 된다.
- **인수 조건(Acceptance Criteria)을 번호 매겨 구체적으로** 쓴다. "로그인 가능"이 아니라 "1. 이메일+비밀번호 로그인 성공 시 JWT 발급 2. 역할별 대시보드로 리다이렉트 3. 실패 시 정확한 오류 문구". QA가 그대로 테스트 케이스로 쓸 수 있어야 한다.
- 인수 조건에 **실제 UI 문구·구체 수치**를 박는다: "이메일 또는 비밀번호가 올바르지 않습니다", "최대 2MB", "1-5점", "최근 20건". 모호함을 제거하면 개발자 추측이 줄어든다.
- **우선순위는 MoSCoW(Must/Should/Could)**를 각 행에 명시. 2단계 이관 항목은 표에서 `~~취소선~~ + **2단계로 이관**`으로 시각적으로 구분.

## 3. 사용자 시나리오 작성법 (구조화된 6요소 + 번호 흐름)

시나리오를 "사용자 스토리 한 줄"로 끝내지 않는다. 각 시나리오를 다음 구조로 작성한다:

- **시나리오명**: 한 문장 행위 ("코치이가 배정된 코치와 첫 세션을 예약한다")
- **행위자**: 역할 명시 (Operator/Coach/Coachee)
- **목표**: 이 시나리오로 사용자가 얻는 가치
- **기본 흐름**: 1→2→3... **번호 매긴 단계별 행동**. 각 단계는 한 행동만. (예약 시나리오를 9단계로 분해)

추가 기법:
- 시나리오는 **핵심 가치 흐름(happy path) 위주로 N개**를 선정하되, 제품의 차별점을 보여주는 시나리오를 반드시 포함한다 (Coach Connect는 "AI 코치 시스템 메시지 설정"을 별도 시나리오로 — 이게 제품의 핵심 차별점이라서).
- 시나리오와 FR을 연결: 시나리오의 단계들이 어떤 FR로 구현되는지 추적 가능하게 (예: 예약 시나리오 → FR-016, FR-017).
- **MVP 범위 밖 단계는 시나리오 안에서 명시**: "*(2단계 예정 — 1단계 MVP 범위 외)*"를 해당 단계에 인라인 표기. 시나리오는 완전한 비전을 보여주되 범위 경계를 흐리지 않는다.

## 4. 비기능 요구사항 구조화 (카테고리별 표 + 측정 가능한 수치)

NFR도 FR처럼 **ID를 가진 표**로, **카테고리별로 분류**한다. Coach Connect의 카테고리:

보안 / 가용성 / 성능 / 다국어·지역화 / 접근성 / 규정준수 / 내보내기·상호운용성

핵심 규칙:
- **모든 NFR은 측정 가능한 수치를 포함**한다. "빠르게"가 아니라:
  - "Access Token 만료 1시간, Refresh Token 7일"
  - "CRUD API 응답 500ms 이내, 목록 조회 1초 이내"
  - "월간 가용성 99.5%", "WCAG 2.1 AA 4.5:1 이상", "동시 접속 100명"
- **기술 스택 제약을 NFR에 반영**: "Cloudflare Workers 서버리스 특성 활용", "ViewLogic i18n 시스템 활용" — 추상적 NFR이 아니라 이 프로젝트의 실제 환경에 맞춘 NFR.
- **규정 준수를 빠뜨리지 않는다**: 도메인에 맞는 법규(PIPA, 데이터 보관기간)를 NFR로 명시.

## 5. 범위 경계를 3중으로 명시한다 (가정 + 범위제외 + 미결사항)

평범한 PRD는 "할 것"만 적는다. 우수한 PRD는 **"안 할 것"과 "아직 모르는 것"을 적는다.** Coach Connect는 세 섹션으로 경계를 친다:

### 가정 (Assumptions)
구현 전제를 번호로 명시. "AI 코치는 GPT API 기반(자체 모델 학습 안 함)", "화상은 외부 서비스 iframe 임베드", "1단계 동시 접속 코치 10-30명/코치이 100-500명". → 아키텍트가 이 가정 위에서 설계한다.

### 범위 제외 (Out of Scope)
표로 `제외 항목 | 사유 | 예정 단계`. "왜 빼는가"와 "언제 할 건가"를 함께 적어, 빠진 게 누락이 아니라 **의도된 결정**임을 증명한다. (멀티테넌트→2단계, 결제→2단계, 자체 AI 모델→4단계)

### 미결 사항 (Open Questions)
표로 `# | 질문 | 영향 범위 | 임시 결정`. **아직 안 정해진 것을 숨기지 않고 드러내되, "임시 결정"을 달아 개발이 멈추지 않게** 한다.
- 예: "OQ-2 AI 코치 LLM은? → OpenAI GPT 기본, LLM 추상화 레이어로 교체 가능하게 설계"
- "임시 결정"에 **설계 방향까지 제시**(추상화 레이어, iframe 교체 용이 구조)하는 것이 핵심. 미결을 던지기만 하는 게 아니라 아키텍트에게 방향을 준다.

## 6. 도메인 용어 사전 (한국어 ↔ 코드 식별자 매핑)

비즈니스 용어와 코드/DB 식별자를 **1:1로 매핑한 표**를 PRD에 포함한다.

```
| 한국어 | 영어(코드/DB 식별자) | 정의 |
|--------|---------------------|------|
| 코치이 | Coachee | 코칭을 받는 고객사 소속 직원... |
| 세션 요약 | SessionSummary | 세션 종료 후 AI가 자동 생성하는... |
```

효과: 기획-설계-개발-DB가 **같은 용어**를 쓰게 강제한다. "코치이"가 코드에서 `Coachee`인지 `Trainee`인지 흔들리지 않는다. 멀티 역할 도메인(운영자/코치/코치이/고객사/HR)에서 특히 중요 — 헷갈리기 쉬운 유사 개념을 명확히 구분(코치 Coach vs 코치이 Coachee, 고객사 Client vs 코칭회사 Company).

## 7. 메뉴/IA 구조를 PRD에 미리 박는다

기능 요구사항만 나열하지 않고, **역할별 메뉴 구조(정보 구조 IA)를 표로** PRD에 포함한다 (운영자/코치/코치이 각각 1단계·2단계 메뉴). UX 제약("최대 2단계 depth")도 명시. → ux-designer가 IA를 0부터 만들지 않고 PRD 기반으로 다듬을 수 있다.

## 8. 제품 기획서·피치 장르도 "스펙처럼" 단단하게

PRD/requirements 본문은 위 기법으로 보통 단단하지만, **제품 개요·product_plan·가치제안 같은 "피치 장르" 문서에서 일반론으로 무너지는 경향**이 산출물 진단(malgnhrd `02_product_plan.md`)에서 관찰됐다. 같은 기획자가 쓴 dev_plan은 단계·시간예산·리스크 레지스터로 우수했는데, 피치 문서만 "어느 LMS에나 붙는" 톤으로 약했다. 장르가 피치라도 다음을 강제한다:

- **복붙 테스트 통과**: 제품명만 바꿔 다른 제품에 붙여도 말이 되는 비전·가치 문장은 평범 → 이 제품 고유 판단으로 교체. (나쁜 예: "AI로 더 스마트하게 인재를 키운다" = 어느 AI LMS에나 해당.)
- **수치·우위 주장엔 근거 첨부**: "기존 대비 1/3 비용" 류는 원가 근거(COGS·단가 비교·경쟁사 가격 출처) 없이 쓰지 않는다. 없으면 finance/researcher에 위임하거나 "가정(검증 필요)"으로 표기.
- **트레이드오프 최소 1개**: 핵심 가치가 전부 win이고 포기한 것이 없으면 의심. "X 위해 Y 포기"를 1곳 명시.
- **경계/실패 모드 한 줄**: 피치라도 규모 한계·실패 모드·데이터 격리(B2B2B 확장 시) 같은 경계를 명시.

> 판별 질문: "경쟁사 PM이 이 기획서를 봐도 '우리 얘기'라 할 문장인가? 비용/우위 숫자에 근거가 붙었나? 포기한 것이 적혀 있나?"

## 9. 차별점 서술은 경쟁사 비교표 인용 필수

"차별점"을 자유 서술로 적지 않는다. 경쟁사 3~5곳의 핵심기능 유무를 비교한 표(반나절 경량 스캔, 전면 리서치 아님)를 먼저 만들고, PRD의 차별점 문장마다 이 표의 구체 셀을 인용하는 형태로 쓴다. **표 없이 "경쟁사 대비 우수" 같은 서술만 쓰지 않는다** — 인용 없는 차별점 서술은 evaluator 반려 사유다.

- 표 구조: `기능 | 경쟁사A | 경쟁사B | 경쟁사C | 우리 제품` — "범위 경계" 섹션의 표준 산출물로 포함.
- 인용 예시: "경쟁사 A·B 모두 X 기능이 없음 → 우리는 X를 핵심 경험으로 설계".
- **경쟁사 선정 기준**: 임의로 유리한 경쟁사만 고르지 않는다 — ①대상 시장에서 검색 노출 상위(트래픽/인지도 기준) 2곳 이상 ②우리 제품과 타깃/가격대가 가장 가까운 직접 경쟁사 1곳 이상 ③차별화하려는 기능을 이미 갖춘 곳(있다면) 1곳을 우선 포함.
- **실제 스캔 필수**: 기억에 의존해 표를 채우지 않는다. WebSearch/WebFetch로 각 경쟁사의 실제 공식 페이지·요금제·기능 목록을 열람해 확인한 뒤 표를 작성한다.
- **설계로 이어지는 인용(architect 연동)**: architect는 이 표의 셀을 인용해 "무엇을 기술적으로 다르게 설계했는가"를 명시한다(예: "경쟁사 A·B가 못하는 X 기능 → 실시간 동기화가 필요해 WebSocket 채널을 별도 설계"). 표가 없거나 인용할 기술적 차별점이 없으면 architect가 planner/PM에 반려 에스컬레이션한다.

## 체크리스트 (PRD 완성도 자가 점검)

- [ ] 분량이 크면 인덱스+분할 구조인가? 분할표가 있는가?
- [ ] 모든 FR이 고유 ID + 모듈 분류 + MoSCoW 우선순위를 가지는가?
- [ ] 모든 FR에 **번호 매긴 구체적 인수 조건**(실제 문구·수치 포함)이 있는가?
- [ ] 시나리오가 6요소(명/행위자/목표/흐름) + 번호 단계로 구조화됐는가? 차별점 시나리오를 포함하는가?
- [ ] 모든 NFR이 **측정 가능한 수치**를 가지는가? 도메인 법규(개인정보 등)를 포함하는가?
- [ ] 가정 / 범위제외(사유+예정단계) / 미결사항(임시결정 포함)을 모두 적었는가?
- [ ] 도메인 용어 사전(한국어↔코드 식별자)이 있는가?
- [ ] 역할별 메뉴/IA 구조를 포함했는가?
- [ ] (피치 장르) 비전·가치가 복붙 테스트를 통과하는가? 비용/우위 주장에 근거가 붙었는가? 트레이드오프 1개 이상·경계/실패 모드를 명시했는가?
- [ ] 경쟁사 3~5곳 비교표가 존재하고, 모든 차별점 서술이 그 표의 구체 셀을 인용하는가(자유 서술 금지)?
