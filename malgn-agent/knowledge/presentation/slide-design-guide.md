## 슬라이드 구성 원칙

### 1슬라이드 1메시지
- 한 슬라이드에 전달할 메시지는 1개
- 텍스트는 5줄 이하, 각 줄 10단어 이하
- 키워드 중심, 문장 최소화

### 발표 자료 구성
| 순서 | 슬라이드 | 목적 |
|------|---------|------|
| 1 | 표지 | 제목, 발표자, 날짜 |
| 2 | 목차 | 전체 흐름 안내 |
| 3~N | 본문 | 핵심 내용 전달 |
| N+1 | 요약 | 핵심 메시지 정리 |
| N+2 | Q&A | 마무리 |

### 시각적 전달 기법
- 숫자 강조: **"30%"** 를 크게 표시하고 맥락 부가
- 비교: Before/After, 표, 대비 색상
- 프로세스: 화살표, 단계 번호
- 데이터: 차트(복잡) 대신 핵심 숫자(간결)

## 스토리텔링 구조

### 문제-해결 구조
1. **Hook**: 청중의 관심을 끄는 질문/사실
2. **Problem**: 현재 문제 상황
3. **Solution**: 제안하는 해결책
4. **Evidence**: 근거/데이터

## 평범한 덱을 넘는 5가지 기법 (모드 7 자가진단으로 도출, 2026-06-20)

> 출처: malgnai 소개 문서를 슬라이드(reveal.js)로 변환하고 "평범한 5가지 냄새"로 자가평가한 결과 정착된 방법론. 원문을 글머리표로 옮기기만 한 덱(=평범)을 피하기 위한 실전 기법.

### 1. "피벗 슬라이드"를 박아 서사를 꺾어라
- 문제→해법으로 넘어가는 **전환점에 통찰 한 문장만 담은 슬라이드**를 둔다 (예: "가시성 없는 자율성은 통제 불능과 구별되지 않는다").
- 이 슬라이드는 **배경색을 반전**(accent 풀배경)시켜 시각적으로도 "여기서 톤이 바뀐다"를 신호한다. 발표자는 여기서 잠깐 멈춘다(pause).
- 효과: 슬라이드 나열이 아니라 *이야기*가 된다. 덱에 피벗이 없으면 그냥 목차 낭독이다.

### 2. 표는 반드시 "한 줄 메시지"로 닫아라
- 비교표/로드맵표를 슬라이드에 두면 청중·발표자 모두 읽어내려간다(=평범). 표 아래에 **굵은 한 줄 takeaway**를 붙여 "이 표가 말하려는 것"을 못박는다.
- 발표자 노트에 "표를 읽어주지 말 것 — 한 줄로 묶어 전달"을 명시한다.

### 3. 숫자/식별자 1개를 슬라이드 주인공으로
- 텍스트 5줄 대신, 핵심 숫자(예: `1 call`, `11 tools`)나 실제 시그니처를 **크게 단독 배치**하고 맥락 한 줄만 붙인다.
- 추상적 기능 설명("효율적으로 집계")을 구체 식별자(`dashboard_summary` 단일 호출)로 치환 — 슬라이드에서도 근거 없는 단정을 없앤다.

### 4. "정직하게 — 못 하는 것" 슬라이드를 넣어라 (happy path 탈출)
- 제품 소개 덱일수록 한계를 빼고 싶지만, **한계 슬라이드가 신뢰를 만들고 로드맵으로 자연 연결**된다.
- 한계 2~3개 → "이 격차를 줄이는 게 다음 단계"로 이어 클로징/로드맵과 연결.

### 5. CTA는 "거대한 결정"이 아니라 "작은 첫 행동"으로
- "도입을 검토하세요"(추상·부담)가 아니라 **그 시스템에서 실제로 가능한 가장 작은 한 행동**을 제시 (예: "워크스페이스에 폴더 하나 올려보세요 → 그 순간 모니터링 시작").
- CTA가 제품의 실제 동작(sync-projects 자동 등록)과 연결되어야 공허하지 않다.

### 발표 후 1분 자가검증 (presentation 전용)
- [ ] 문제→해법 사이에 피벗 슬라이드(통찰 1문장)가 있는가?
- [ ] 모든 표 아래에 한 줄 takeaway가 붙었는가? (발표자가 표를 낭독하게 두지 않았는가)
- [ ] 슬라이드마다 기억할 메시지가 정확히 1개인가? (글머리표 나열로 흐려지지 않았는가)
- [ ] "못 하는 것" 슬라이드가 있는가? (happy path만 그렸는가)
- [ ] CTA가 청중이 *당장 할 수 있는 작은 1행동*인가?

## 브랜드 로고: 실제 PNG를 삽입하라 — CSS 합성 로고 금지 (2026-07 사고 재발방지)

> 출처: 사내 배포 슬라이드 PDF 제작 시 실제 맑은소프트 로고(`맑은_로고.png`)를 산출 폴더에 **복사만** 해두고, 표지·전 푸터에는 **CSS 합성 가짜 로고**(파란 사각형 안 "M" + "맑은소프트" 텍스트)를 넣어 대표가 "절대 안 됨"으로 강하게 지적한 브랜드 아이덴티티 훼손 사고.

- **전제조건**: 맑은소프트처럼 **확정된 실제 로고 파일이 존재하는** 브랜드 문서/슬라이드/PDF를 만들 때.
- **권장 행동**: 로고 자리(표지·목차·푸터 등)마다 실제 로고 PNG를 `<img>`로 삽입한다.
  - 파일: 사내 디자인 자산 저장소의 확정 로고 PNG(예: "(기본) 맑은소프트_가로문서" 스타일가이드 폴더 내 `맑은_로고.png`, 180×50, 투명 배경, 파란 소문자 'm' + "맑은소프트" 워드마크)를 찾아 쓴다. 산출 폴더로 복사 후 상대경로 `<img>` 참조. **복사 ≠ 삽입**(이번 사고의 핵심 실수).
  - CSS 합성 마크(`<span class="mark">M</span>`, 파란 박스+글자), div/CSS로 그린 워드마크, 임의로 지어낸 로고는 금지.
  - **다크 배경**(표지/마무리)에선 로고 워드마크가 안 보이므로 **둥근 흰 칩(padding 있는 흰 배경) 위에** 로고 img를 얹어 가시성 확보. 로고 색을 바꾸거나 흰색 버전을 지어내지 않는다.
  - 로고 PNG 자체에 아이콘+"맑은소프트" 워드마크가 이미 포함돼 있으므로, 로고 옆에 "Malgnsoft"/"맑은소프트" 회사명 텍스트를 별도로 또 병기하지 않는다(중복). 문서/제품 제목("STYLE GUIDE" 등)을 옆에 두는 것은 회사명 반복이 아니라 무방.
- **함정**: 스타일가이드 원본 `(기본) 맑은소프트_가로문서/style-guide.html`이 편의상 `<span class="mark">M</span>맑은소프트` 합성 마크를 쓴다 → **이건 따라 하면 안 되는 나쁜 예.** CSS 토큰(색·타이포·박스 어휘)만 계승하고 로고는 실제 PNG로.
- **반례/예외**: 브랜드 로고가 아직 없는 **신규 브랜딩 프로젝트**에서 로고를 새로 정의·제작하는 경우는 다르다(그건 visual-designer의 정당한 창작). 이 규칙은 "확정된 기존 로고가 있는데 멋대로 합성/재창작하는 것"을 금한다.
- **판별 질문**: ① 이 브랜드에 확정된 실제 로고 파일이 있는가? → 있으면 반드시 그 PNG를 `<img>`로. ② 배경이 어두운가? → 흰 칩 위에 얹기.
- **제작 후 자기검수(필수)**: `grep -n 'class="mark"\|>M</span>' out.html`로 합성 마크 잔존 확인 + `grep -n '맑은_로고.png\|<img' out.html`로 실제 로고 img 참조 확인. 합성물이 남아 있으면 실패로 간주하고 교체 후 재검수.

## HTML 슬라이드 덱 → 발표 PDF: 표시 충실도(브라우저=출력물) 보장 (모드 7, 2026-06-26)

> 출처: malgnai `바이브코딩_대표발표_v4.html`(16개 .slide, 1280×720 16:9, Pretendard/JetBrains Mono 웹폰트)을 발표 PDF로 변환하며 정착. 1차 산출물이 브라우저엔 없는 '유령 레이어'를 PDF에 남겨 2회 재작업한 사례. **표면이 '단순 변환'이어도 발표 충실도가 걸리면 1차부터 올바른 방식·올바른 검증도구를 쓴다(재작업이 최대 낭비).**

### 근본 함정: 컬러 box-shadow / 그라데이션의 벡터 PDF 래스터화 차이
- **전제조건**: HTML 덱에 **크고 진한 컬러 box-shadow**(예 `.stat.hi{box-shadow:0 12px 30px rgba(30,94,255,.28)}`, `.barhead`·`.callout`·`.cmp-card.hi`의 파란/네이비 그림자)나 큰 그라데이션이 있고, 이를 headless Chrome `page.pdf()`(벡터 PDF 엔진)로 변환하는 경우.
- **현상**: 브라우저 화면 컴포지터에선 은은한 blur지만, 벡터 PDF 엔진은 같은 그림자를 **박스보다 큰 진한 둥근 덩어리('유령 레이어')로 래스터화**한다. → 화면엔 없던 연파랑 둥근 배경이 PDF에만 생긴다.
- **`emulateMedia({media:'screen'})`만으로는 못 막는다**: 이건 미디어쿼리 문제가 아니라 **벡터 PDF 엔진의 그림자 래스터화 차이**다. `@media print`가 없어도 발생한다. `element.screenshot()`는 screen/print가 동일해 "미디어 무관"으로 **오판**하기 쉽다 — 차이는 `page.pdf()` 단계에서만 드러난다.
- **반례/예외**: 그림자가 작고 옅거나(예 `0 1px 2px rgba(0,0,0,.1)`) 그라데이션이 없는 평이한 덱은 벡터 `page.pdf()`로도 충실하다. 컬러·대형 그림자가 없으면 아래 스크린샷 조립의 트레이드오프(파일 크기·비선택 텍스트)를 감수할 이유가 없다.

### 확정 해법 — 스크린샷 조립 (화면 100% 일치가 최우선일 때 1순위)
- 각 `.slide`를 **screen 미디어에서 `element.screenshot()`** 로 캡처(`deviceScaleFactor`/뷰포트 DPR=2). 화면 컴포지터라 그림자가 브라우저와 픽셀 동일.
- 캡처 PNG들을 base64로 임시 HTML(`@page{size:1280px 720px;margin:0}`, 슬라이드당 page-break)에 박아 `page.pdf()` 출력. 이미 래스터라 그림자 재발산 없음.
- screen의 `fit()` 스크립트가 .slide에 건 `transform:scale()`은 PDF 직전 `transform:none`으로 무력화(안 하면 페이지 어긋남).
- **트레이드오프**: 텍스트가 비선택 래스터, 파일 큼(16p≈5.9MB). 발표 풀스크린 용도엔 무방.

### 대안 — 벡터 유지(선택 가능 텍스트가 꼭 필요할 때만, 리스크 큼)
- `page.pdf()` 벡터 유지 + 주입 CSS로 `.stat.hi/.barhead/.callout/.cmp-card.hi{box-shadow:none}`. 단 다른 벡터 발산 가능성이 남으므로 **전 슬라이드 전수확인 필수**.

### 검증 규율 (충실도 검증 도구 선택)
- **`sips` 신뢰 금지**: sips(macOS ImageIO)는 blur box-shadow를 회색/연색 사각형으로 **오판**한다(이번에 15p 오진). 그림자 충실도는 **Chrome PDF 뷰어로 직접** 열어 확인. 단 최종이 래스터 조립 PDF면 sips 1페이지 검수는 신뢰 가능.
- 구조검증은 `mdls`(페이지수·960×540pt 등). **문제로 지목된 슬라이드를 반드시 포함**해 전후 비교.

### 환경 메모 (맥미니 Playwright)
- `chromium.launch({channel:'chrome',headless:true})` 사용(ms-playwright 캐시 브라우저 경로불일치라 executablePath 지정 실패). 프로젝트 ESM이라 변환 스크립트는 `.cjs`. 웹폰트는 `document.fonts.ready` 대기. 로고가 상대경로(`assets/logo.png`)면 폴더 없을 때 깨지므로 사전 배치.

### 판별 질문 (어느 길을 갈 것인가)
- **Q1. 컬러/대형 box-shadow나 큰 그라데이션이 있는가?** 없음 → 일반 벡터 `page.pdf()`로 충분. 있음 → Q2로.
- **Q2. '화면과 100% 일치'와 '선택 가능 텍스트' 중 무엇이 우선인가?** 화면 일치 우선(발표용) → **처음부터 스크린샷 조립**. 선택 텍스트 필수 → 대안(box-shadow:none)+전수검증. **애매하면 기본값: 발표 PDF는 스크린샷 조립**(충실도 우선, 재작업 회피).

## 스크린샷 기반 검수: HTML 우선, PDF는 1회 변환으로 종결 (토큰 폭증 방지, 2026-07-08)

> 출처: malgnai 구축 가이드(13페이지 PDF) 제작 세션 실측 + 같은 날 COO 후속 지침(우선순위 명확화). presenter 단일 호출이 **159턴/34.6M 토큰/$16.80**(같은 세션 writer 120턴/$7, reviewer 91턴/$4.7 대비 압도적) 소요. 해당 세션 트랜스크립트를 턴 단위로 복원하면, `make-pdf.mjs`→`pdftoppm`(전 페이지 PNG 렌더)→Read(스크린샷 확인)→Edit 사이클을 **6라운드** 반복했고, 라운드별 확인 페이지 수는 **13 → 4 → 4 → 7 → 13 → 2**(총 44장)였다. 원인은 **PDF 변환 이후에도 스크린샷을 반복 재검토**하며 이미 확인 끝난 이미지까지 대화 히스토리에 누적 재전송한 것. (사내 교훈 아카이브에 상세 4부 기록 존재)

- **핵심 원칙(최우선): 노력 배분은 HTML > PDF다.** 스타일가이드 준수·로고·레이아웃·텍스트 등 실제 품질은 전부 HTML 단계에서 결정된다. HTML을 스타일가이드 기준으로 꼼꼼히 만들고, 검수는 **대표 페이지 1장 스크린샷**으로 가볍게 반복하며 정확도를 여기서 확보한다. **PDF 변환은 HTML이 확정된 뒤 1회 수행하고 끝내는 부차적 단계**다 — 변환 후 스크린샷을 다시 열어 재수정 루프를 돌리지 않는다.
- **PDF 단계는 1회 변환 + 1회 무결성 확인으로 종결.** `pdftoppm`으로 전체 페이지를 뽑아 보는 것은 "재검수 루프"가 아니라 페이지 수·빈 페이지·잘림을 보는 **단일 최종 게이트**(위 "넘기기 전 렌더 자기검증")다. 문제가 있으면 HTML에서 고치고 PDF를 다시 1회 뽑아 1회만 재확인한다 — 여러 라운드를 계획하지 않는다.
- **변환 도구 실패 시 폴백**: 헤드리스 브라우저/변환 스크립트(Chrome headless `--print-to-pdf`, playwright `page.pdf()` 등)가 에러를 내거나 결과가 깨지면, 그 도구를 고치려 반복 디버깅하지 않는다. **일반 브라우저의 "파일 → 인쇄 → PDF로 저장"**으로 즉시 대체한다 — 항상 되는 폴백이 있으므로 변환 실패를 붙잡고 씨름하는 것 자체가 턴 낭비다. (화면 100% 일치가 필수라 스크린샷 조립 파이프라인을 쓰는 경우는 예외 — 위 "확정 해법 — 스크린샷 조립" 경로를 그대로 따른다.)
- **(예외: 여러 페이지 확인이 불가피할 때)** 전역 CSS 토큰·렌더 스크립트 자체 교체처럼 모든 페이지에 영향 주는 변경 뒤에는 표본검수로 나머지를 신뢰하지 않고 전체를 본다. 실측 사례의 라운드1(13장, 최초)·라운드5(13장, `make-pdf.mjs`→`make-pdf-plain.mjs` 스크립트 교체)가 이 예외였고, 라운드2·3(각 4장)은 이미 영향 페이지만 선별한 좋은 사례였다. 이 예외 상황에서도 **이미 확인 끝난 페이지는 이미지 재첨부 대신 텍스트로 기록**("pg-01~03 확인완료, 문제없음")하고, 수정은 배치로 모아 라운드 수 자체를 줄인다(저해상도 `pdftoppm -r 72`로 중간 확인, 최종만 `-r 100` 이상).
