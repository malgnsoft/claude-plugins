# 기획의도 부합성 vs 동작정확성 — 축 분리

> 출처: `docs/analysis/djkim-knowhow-analysis-2026-08-13.md` §3.3 — 타 AI 조직의 서비스 고도화 루프 설계를 우리 언어로 재정리. 원문은 인용하지 않고 개념만 재서술함.

서비스나 화면의 완료 검증에는 성격이 다른 두 가지 질문이 섞여 들어오기 쉽다.

- **기획 부합성**: 이 결과물이 요구자가 원래 의도한 것과 실제로 맞는가. 버튼이 눌리고 데이터가 정확히 저장돼도, 애초에 그 화면이 만들려던 사용자 경험·비즈니스 목적과 어긋나 있으면 이 축에서는 실패다.
- **동작 정확성**: 이 결과물이 기술적으로 버그 없이 동작하는가. 입력값 검증이 되는가, 예외 상황에서 죽지 않는가, 화면이 명세대로 렌더되는가 — 요구자의 의도와는 무관하게 "짠 대로 돌아가는가"만 본다.

두 축은 서로 다른 실패 모드를 잡아낸다. 동작은 완벽한데 기획과 어긋난 결과물(정확하지만 엉뚱한 것), 반대로 기획 의도는 정확히 반영했는데 버그가 있는 결과물(맞는 것을 만들었지만 부정확하게 동작)은 완전히 다른 조치를 요구한다 — 전자는 요구사항 재확인·설계 재검토, 후자는 디버깅·테스트 보강이다. 이 둘을 하나의 검수 통과/실패로 뭉뚱그리면, 통과했을 때 "무엇이 확인된 것인지"가 불분명해지고 실패했을 때도 "그래서 어디를 고쳐야 하는지"가 흐려진다.

## 왜 처음부터 분리해야 하는가

검수를 시작할 때부터 이 두 질문을 같은 체크리스트 항목에 섞어두면, 검수자는 대개 더 확인하기 쉬운 동작 정확성 쪽으로 쏠린다 — 버튼 클릭·값 검증·에러 핸들링은 관찰하고 재현하기 쉽지만, "이게 요구자가 원한 것과 맞는가"는 원 발화·요구사항 문서를 다시 대조해야 하는 별도의 노력이 든다. 두 축을 하나의 체크리스트에 섞어두면 후자가 은근슬쩍 생략되기 쉽다. 처음부터 두 축을 별개 절차로 분리해두면 각각에 필요한 만큼의 노력이 따로 배정된다.

## 실무 적용 방식

우리 `qa-engineer`는 구현 코드를 테스트하고 결과를 보고하는 역할이라 동작 정확성 쪽에 자연스럽게 무게가 실린다. 기획 부합성 판정은 원 요구사항(requirements.md/prd.md 또는 사용자의 원 발화)과 결과물을 나란히 놓고 "이게 그 의도와 맞는가"를 별도로 확인하는 절차이며, 동작 정확성 검증(버그·예외처리·명세 준수)과 같은 체크리스트 항목으로 섞지 않는 편이 낫다. `reviewer`가 다관점 패널로 산출물을 검토할 때도, 페르소나별 관점이 사실은 이 두 축 중 어느 쪽을 보고 있는지 구분해두면 통합 보고서에서 "기획과 어긋난 문제"와 "기술적으로 깨진 문제"를 서로 다른 심각도·조치 경로로 분류하기 쉬워진다.

이 문서는 개념 정리에 그친다. `qa-engineer`나 `reviewer`의 실제 체크리스트 구조를 바꾸는 것은 행동 규칙 변경이므로, 이 노트를 근거로 각 에이전트 MD를 직접 고치지 않고 검수 체크리스트를 짤 때 참고 개념으로만 활용한다.
