# 자율형 반복 운영 및 업데이트 원칙

> 핵심: 무한 자율 반복이 아니라 "경계가 명확한 자율" — 비용 대비 효과가 떨어지는 순간 멈추고 대표 판단을 받는다.

## 원칙 한 줄 요약

자율 반복은 **수확 체감**이 빠르다. 3~5회 상한을 두되, 실제 종료는 "개선 폭이 소소해지는 순간"에 하고, 그 이후는 자동 반복 대신 **대표 피드백**을 받아 방향을 재설정한다.

## 왜 무한 반복이 아닌가 (비용 대비 효과)

| 회차 | 개선 효과 | 회당 비용(토큰) | 판단 |
|------|----------|---------------|------|
| 1~2회 | 큰 결함·핵심 개선 (大) | 회차마다 거의 일정 | 반드시 수행 |
| 3~4회 | 중간 다듬기 (中) | 회차마다 거의 일정 | 가치 있으면 수행 |
| 5회~ | 미세 조정만 (小) | 회차마다 거의 일정 | **멈춤 — 토큰 낭비** |

- 핵심은 **비대칭**이다: 회당 비용은 거의 일정한데 회당 효과는 빠르게 줄어든다. 그래서 늦게 멈출수록 손해가 누적된다.
- 효과 곡선이 비용 곡선 아래로 내려가는 지점(보통 3~5회)에서 자동 반복은 손해다.
- 에이전트는 "더 다듬을 곳"은 무한히 찾지만 "이게 진짜 중요한가"는 판단하지 못한다.
- **대표 피드백 1회 = 자율 반복 10회보다 방향성 가치가 크다.** 잘못된 방향으로 더 반복하는 비용을 원천 차단한다.

## 운영 규칙

```
1. 최대 3~5회 반복 (작업 규모에 따라 상한 설정)
2. 조기 종료(우선): "직전 회차 대비 중대한 개선 없음" → 즉시 정지
   - 회차 상한은 안전장치일 뿐. 3회에서 소소해지면 거기서 멈춘다.
   - "5회 채우기"가 아니라 "소소해지면 멈추기"가 핵심.
3. 정지 후 보고: 무엇을/왜 멈췄는지 + 남은 후보 개선안을 대표에게 보고
4. 대표 피드백 → 방향 재설정 → 다시 진행
```

## 작업 규모별 상한 기준

| 작업 규모 | 권장 상한 |
|----------|----------|
| 소규모 (단일 산출물 다듬기) | 3회 |
| 중규모 (여러 산출물·다관점 리뷰) | 4회 |
| 대규모 (전체 흐름·여러 팀 연계) | 5회 |

> 상한은 천장일 뿐 목표가 아니다. 어느 규모든 "소소해지면 멈추기"가 먼저다.

## 종료 조건 (셋 중 하나라도 충족 시 정지)

- **수확 체감**: 직전 회차 대비 중대한 개선이 없음 (최우선 트리거)
- **회차 상한**: 3~5회 도달
- **예산 상한**: 사전 정의한 토큰/비용 한도 소진

## 정지 시 대표 보고 양식

```markdown
## 반복 작업 정지 보고

- 작업: [무엇을 반복했는가]
- 수행 회차: N회 (상한 M회)
- 정지 사유: [수확 체감 / 회차 상한 / 예산 상한]
- 달성한 개선: [회차별 핵심 변경]
- 남은 후보 개선안: [했지만 효과 작아 보류한 것들]
- 대표 판단 요청: [방향 유지 / 재설정 / 종료 중 선택]
```

## 일일 토큰 예산 게이트 (PM 필수)

토큰 비용은 가장 큰 운영 변수다. PM은 작업 시작 전·반복 진입 전에 **오늘 누적 토큰**을 확인하고, 한도 초과 시 업무를 중단한다.

### 조회 수단 (실제 경로)

- API: `GET /api/claude/tokens?since=YYYY-MM-DD&until=YYYY-MM-DD`
  → `{ daily: [{ date, total, by_model }], model_usage }`
- DAO: `ClaudeDao.findTokenStats({ since, until })` — 날짜별 총합 + 모델 분해
- 데이터 소스: `claude_token_stats` 테이블 (날짜·모델별 토큰)

> 오늘 날짜를 since/until 동일하게 넣으면 당일 누적 `total`을 바로 얻는다.

### 한도 기준: 실측 기반 (고정 수치 아님)

Claude Code 구독 플랜(Max $100 등)은 **공식 토큰 환산 한도가 없다.** 실제 단위는 "5시간 롤링 윈도우 + 주간 상한"이며, 모델(Opus가 훨씬 빨리 소진)·캐시 적중률·대화 길이에 따라 토큰으로는 들쭉날쭉하다. 따라서 한도는 추측하지 않고 **우리 시스템이 실측한 값**으로 정한다.

기준 설정 방법:
1. 며칠간 `daily[].total`을 모니터링해 **정상 운영일의 평균 일일 토큰**을 파악한다.
2. 그 평균의 **80%를 경고선**, **100%를 정지선**으로 잡는다 (대표가 조정 가능).
3. 새 데이터가 쌓이면 평균을 갱신해 임계치를 자가 조정한다.

> 즉 "$100 플랜이 몇 토큰이냐"를 알 필요 없이, **관찰된 평소 사용량 대비 비율**로 과소비를 감지한다. 평소보다 비정상적으로 많이 쓰는 날을 잡아내는 것이 목적이다.

### 한도 초과 시 행동: 즉시 중단 + 대표 보고

```
1. 작업/반복 시작 전 오늘 누적 토큰(total) 확인
2. 일일 한도 도달 시:
   - 진행 중 작업은 안전하게 마무리 (중간 산출물 손실 방지)
   - 신규 작업 / 추가 반복은 중단
   - 대표에게 보고 후 승인 대기 (자동 재개 금지)
3. 대표 판단(한도 상향 / 내일로 이월 / 종료) → 그에 따라 진행
```

### 한도 초과 보고 양식

```markdown
## 일일 토큰 한도 도달 보고

- 오늘 누적 토큰: N (한도: M)
- 모델별 분해: [by_model 요약 — 어디서 많이 썼는지]
- 중단한 작업: [신규/반복 중 멈춘 것]
- 마무리한 작업: [안전하게 끝낸 것]
- 대표 판단 요청: [한도 상향 / 내일 이월 / 종료]
```

> 반복 종료 조건의 "예산 상한"과 동일한 게이트다. 회차 상한보다 **토큰 한도가 먼저 걸리면 토큰 한도를 우선**한다.

## 검증 (유령 보고 금지)

각 반복은 실제 증거를 남긴다. "개선했다"는 자기 보고만으로는 회차로 인정하지 않는다.
- 산출물(스크린샷·판정·worklog·diff 등) 실물 첨부
- 검증을 루프 안에 둔다 — 검증 없는 반복은 비용만 늘린다
- 관련: UI/UX 리뷰 사이클의 산출물 필수 원칙과 동일

## 비용 측면 주의

- 토큰 소비는 선형이 아니라 곱셈으로 늘 수 있다 → 종료 조건 + 예산 상한 필수
- 사람 승인 게이트는 **되돌리기 어려운 행동**(배포·삭제·외부 발송)에만 둔다. 내부 반복(리뷰→수정→재리뷰)은 자율로 돌린다.
- 매 반복은 learning loop에 기록되어야 "반복"이 "개선"이 된다 (안 그러면 같은 실수 반복).
