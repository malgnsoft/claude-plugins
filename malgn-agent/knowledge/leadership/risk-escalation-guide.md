# 리스크 관리 및 에스컬레이션 가이드

> 업데이트: 2026-06-19
> 출처: Atlassian Risk Mitigation, CoraProjectManagement 5-Step Framework, PRINCE2/Scrum Risk Model

## 리스크 식별 체크리스트

프로젝트 시작 시 아래 영역을 점검합니다:

| 리스크 영역 | 점검 항목 | 심각도 기준 |
|------------|----------|-----------|
| 요구사항 | 모호한 기능, 미확인 범위 | 1줄 미만 설명 = 높음 |
| 기술 | 미경험 기술, 호환성 문제 | 팀 경험 없음 = 높음 |
| 일정 | 촉박한 기한, 의존성 병목 | 에이전트 3개 이상 직렬 = 중간 |
| 품질 | 테스트 부재, 코드 리뷰 생략 | 테스트 미계획 = 높음 |
| 외부 | API 제한, 서비스 장애 | 외부 의존성 2개 이상 = 중간 |

## 리스크 대응 전략 (4가지)

### 1. 회피 (Avoid)
리스크 원인 자체를 제거합니다.
- 예: 미성숙 기술 → 검증된 대안으로 교체

### 2. 완화 (Mitigate)
발생 확률이나 영향을 줄입니다.
- 예: 복잡한 모듈 → 프로토타입으로 선 검증 후 본 개발

### 3. 전가 (Transfer)
리스크 관리를 다른 주체에게 넘깁니다.
- 예: 보안 → security 에이전트에 전문 점검 위임

### 4. 수용 (Accept)
- **능동적 수용**: 대응 계획을 준비해두고 발생 시 실행
- **수동적 수용**: 영향이 작아 별도 조치 없이 진행

## 에스컬레이션 기준

### PM이 직접 처리
- 에이전트 산출물 품질 미달 (재작업 1~2회)
- 에이전트 간 산출물 불일치
- 기술 스택 변경 필요

### 사용자에게 에스컬레이션
- 요구사항 해석이 분기되어 선택이 필요한 경우
- 예산/일정에 영향을 미치는 범위 변경
- 재작업 2회 후에도 품질 미달
- 프로젝트 방향 전환이 필요한 경우

### 에스컬레이션 보고 형식
```markdown
## 리스크 에스컬레이션

**리스크**: [설명]
**심각도**: 높음/중간/낮음
**영향**: [프로젝트에 미치는 영향]
**시도한 대응**: [이미 시도한 조치]
**제안 옵션**:
1. [옵션A] — 장점/단점
2. [옵션B] — 장점/단점
**권장**: [옵션X] — [이유]
```

## 리스크 모니터링

### progress.md에 리스크 섹션 추가
```markdown
## 리스크 현황
| ID | 리스크 | 심각도 | 상태 | 대응 |
|----|--------|--------|------|------|
| R1 | 외부 API 응답 지연 | 중간 | 모니터링 | 타임아웃 설정 |
| R2 | 요구사항 범위 확대 | 높음 | 에스컬레이션 | 사용자 확인 필요 |
```

### 리스크 재평가 시점
- 각 파이프라인 단계 전환 시
- 에이전트 산출물 검토 시
- 사용자 피드백 수신 시
