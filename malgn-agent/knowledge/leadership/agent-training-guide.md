# 1장. 훈련 시스템 개요 및 철학

## 1.1 목적과 목표

맑은AI 에이전트 시스템(19명)은 역할별 전문성을 가진 AI 협업 팀이다. 이 훈련 가이드는 다음 세 가지를 달성하기 위해 존재한다.

- **역량을 측정 가능하게**: 스킬 점수·경험 점수로 객관화하여 "느낌"이 아닌 수치로 관리
- **학습을 지속 가능하게**: 매 프로젝트마다 교훈을 축적해 다음 프로젝트에서 반복 실수를 제거
- **산출물 품질을 높이게**: "MD가 잘 쓰여 있나"가 아니라 "실제로 잘 해내는가"를 기준으로

**정량 목표:**

| 지표 | 목표 |
|------|------|
| 에이전트별 최종 점수 | 70점 이상 (B급 이상) 유지 |
| 프로젝트 재작업률 | 20% 미만 |
| 신규 에이전트 온보딩 | 2시간 이내 |

## 1.2 핵심 원칙 5가지

> **원칙 1: 산출물 기반 진단**
> MD 키워드 점수는 보조 지표다. 에이전트가 실제로 만든 것이 기준이다.
> "리뷰 보고서가 프로젝트명만 바꾸면 다른 데 붙일 수 있는가?" — YES면 약한 산출물이다.
> 진단할 때 항상 실제 산출물 파일을 열어 읽는다.

> **원칙 2: 지속적 학습**
> 한 번 가르치고 끝이 아니다. 매 프로젝트 회고 후 교훈을 MD와 knowledge에 반영한다.
> 이미 반영한 교훈은 중복 반영하지 않도록 학습 보고서로 추적한다.

> **원칙 3: 최소 MD, 최대 Knowledge**
> MD는 역할 정체성과 원칙만 담는다. 상세 절차·예시·체크리스트는 knowledge 파일에 위임한다.
> MD가 짧을수록 세션 로드 비용이 낮다. Knowledge가 깊을수록 실제 품질이 높다.

> **원칙 4: 토큰 효율은 상시 기준**
> 새 지침을 MD에 추가할 때마다 "이 지침이 턴·토큰을 늘리지 않는가"를 확인한다.
> 모든 에이전트에 자기중단·압축 반환·(리더형) 서브 감독 3종이 박제되어 있어야 한다.

> **원칙 5: 교훈 일반화 게이트**
> 단일 사례에서 얻은 교훈을 영구 규칙으로 올리기 전, 4부 구조(전제조건/권장행동/반례/판별질문)를 채워야 한다.
> "항상/무조건/절대" 단정형 규칙은 반려. 반례 검토를 마친 경우에만 예외.

**핵심 요약**: "MD 키워드가 아닌 실제 산출물로, 매 프로젝트마다, 교훈을 게이트 통과 후 지식으로 쌓는다."

# 2장. 에이전트 MD 표준 포맷

## 2.1 포맷 철학

**최소 MD, 최대 Knowledge.** MD는 역할 정체성·원칙·토큰 규율·knowledge 경로만 담는다. 스킬 상세·절차·예시·체크리스트는 knowledge 파일에 위임하고 MD에서 경로로 참조한다. MD가 짧을수록 세션 로드 비용이 낮고, knowledge가 풍부할수록 실제 품질이 높다.

## 2.2 7섹션 구조

모든 에이전트 MD는 아래 7개 섹션으로 구성된다. 섹션 순서는 고정이다.

| 섹션 | 내용 | 주의사항 |
|------|------|---------|
| 헤더 | 역할 1줄, 팀, 모델, 점수 태그 | 역할은 "무엇을 만들어 누구에게 전달"로 동사 명시 |
| 핵심 원칙 | 행동 원칙 5개 이내 | 추상 형용사 금지, 관찰 가능한 행동만 |
| 스킬 정의 | 스킬 테이블 (배점 합산 100점) | 배점은 핵심 가치 비례로 차등 부여 |
| 경험 이력 | 프로젝트 경험 + 소소한 학습 이력 | 기여와 성과는 측정 가능하게 |
| 지식 참조 | knowledge 파일 경로 목록 | 파일 없으면 경로 추가 전 파일 먼저 생성 |
| 금지/승인 | 금지·승인 필요 목록 | skill-definitions.js EMPLOYEE_CARDS와 동기화(미번들 — 없으면 각 에이전트 MD를 직접 대조) |
| 토큰 효율 | 자기중단·압축반환·(리더형) 서브감독 | 리더형은 서브 감독 항목 반드시 포함 |

## 2.3 샘플 에이전트 포맷 예시 — architect

```markdown
# architect (시스템 아키텍트)

**역할**: PRD를 받아 시스템 구조·API 명세·데이터 모델을 설계하고 개발팀에 전달
**팀**: 개발팀 | **모델**: opus
<!-- skill_score: 76/100 exp_score: 45/100 total: 70/100 -->
<!-- last_trained: 2026-07-09 -->

---

## 핵심 원칙

1. 설계 결정에는 반드시 트레이드오프 근거를 명시한다 (왜 이 기술을 선택했나).
2. API 경로는 버전(/v1/)을 포함한다. 버전 없는 경로는 설계 결함이다.
3. 데이터 모델은 ERD + 인덱스 전략까지 포함해야 완성으로 본다.
4. 확장성 설계는 개념이 아니라 구체적 패턴(어떤 캐시, 어떤 큐)으로 명시한다.
5. 보안 아키텍처는 인증/인가 흐름도가 없으면 미완성이다.
```

# 3장. 스킬 정의 및 점수 체계

## 3.1 스킬 점수 계산

**자동 측정 명령**: `node bin/sync-agents.js`(이 스크립트는 이 플러그인에 번들되지 않음 — 운영 프로젝트에 구축되어 있다면 그 경로를 사용, 없으면 수동 산정)

MD 키워드를 스캔해 스킬별 level(1~5)을 자동 계산한다.

| Level | 기준 |
|-------|------|
| 5 | 전용 섹션 + 높은 빈도 + 깊은 디테일 모두 충족 |
| 4 | 대부분 충족, 한 축 부족 |
| 3 | 다뤄지긴 하나 깊이/전용성 부족 |
| 2 | 언급 수준 |
| 1 | 사실상 미커버 |

**환산 공식**:
```
스킬 원점수 = Σ(각 스킬의 level × 배점/5)

예시: 스킬A(배점 25점, level=4) → 20점
     스킬B(배점 20점, level=5) → 20점
     스킬C(배점 20점, level=3) → 12점
```

**중요**: 키워드 점수는 보조 지표다. reviewer가 4.6점을 받았어도 실제 산출물 진단에서 페르소나 편중 약점이 발견된 것이 이 시스템의 실제 사례다.

## 3.2 경험 점수 적립 체계

| 이벤트 | 점수 |
|--------|------|
| 프로젝트 완료 참여 | +5점 |
| 재작업 없이 1회 통과 | +3점 |
| 리뷰어 Critical 0건 | +2점 |
| 소소한 학습 이력 추가 | +1점/건 |
| 재작업 발생 | -2점 |

**적립 절차**:
1. 프로젝트 완료 후 PM이 trainer에게 "경험 점수 갱신" 지시
2. Trainer가 해당 에이전트 MD의 경험 이력 섹션에 행 추가
3. `malgnai-mcp agent_learning_log_add`로 이력 기록

## 3.3 최종 점수 공식

```
최종점수 = 스킬점수 × 0.8 + 경험점수 × 0.2
```

**등급 정의**:

| 등급 | 점수 범위 | 의미 |
|------|----------|------|
| S | 90~100점 | 벤치마크 — 다른 에이전트의 학습 표준으로 활용 |
| A | 85~89점 | 우수 |
| B | 70~84점 | 양호 — 목표 기준선 |
| C | 55~69점 | 개선 필요 — 집중 학습 스케줄 수립 |
| D | 55점 미만 | 집중 학습 대상 — 즉시 모드 1·7 실행 |

**핵심 요약**: "스킬 80% + 경험 20%, 70점 미만이면 즉시 행동."

# 4장. 지식 문서(knowledge) 관리 체계

## 4.1 knowledge 폴더 구조

```
knowledge/  (이 플러그인 기준 상대 경로)
├── common/          ← 전체 공통 (token-efficient, beyond-mediocre 등)
├── leadership/      ← pm, trainer
├── planning/        ← planner, researcher
├── proposal/        ← capture-strategist, rfp-analyst
├── finance/         ← finance
├── marketing/       ← marketer
├── design/          ← ux-designer, visual-designer
├── architecture/    ← architect
├── backend/         ← backend-dev
├── frontend/        ← frontend-dev
├── quality/         ← qa-engineer
├── security/        ← security
├── devops/          ← devops
├── writing/         ← writer
├── presentation/    ← presenter
├── review/          ← reviewer (재사용 페르소나 자산)
└── lessons/         ← 프로젝트 회고 교훈
```

## 4.2 스킬별 지식 문서 작성 기준

**좋은 knowledge 파일의 4요소:**

| 요소 | 설명 | 금지 패턴 |
|------|------|-----------|
| 문제 상황 | 어떤 상황에서 이 문서를 읽어야 하는가 | "항상 중요하다" |
| 핵심 원칙 | 이 스킬의 본질적 판단 기준 | 출처 없는 권고 |
| 구체적 패턴 | 실제로 적용할 수 있는 절차·예시·체크리스트 | 개념만 나열 |
| 반례/주의 | 이 문서가 틀리는 경우 | 케바케로 끝나는 문서 |

## 4.3 교훈 일반화 게이트 (4부 구조)

단일 사례에서 얻은 교훈을 영구 규칙으로 올리기 전 이 4부 구조를 반드시 채워야 한다.

```
전제조건   : 이 교훈이 적용되는 상황 (X한 경우에 한해)
권장 행동  : 그래서 Y하라
반례/예외  : 이 교훈이 틀리는 경우 최소 1개
판별 질문  : 적용자가 갈림길에서 던질 질문 1~2개 → 각 답에 명확한 행동
```

**실제 교정 사례:**
- 나쁨: "화면 분류는 무조건 데이터 group-by" — 전칭, 반례 없음 → 반려
- 좋음: "분류가 자주 변동하고 권위 출처가 데이터면 group-by, 닫혀 있고 정책/스키마가 권위면 명시 등록 — 판별: 6개월 뒤 분류가 늘 수 있나?"

## 4.4 업데이트 주기 및 방법

| 트리거 | 액션 |
|--------|------|
| 프로젝트 완료 후 회고 | `lessons/[프로젝트명].md` 작성 |
| 에이전트 산출물 약점 발견 | 해당 에이전트 knowledge 보강 |
| 외부 베스트 프랙티스 수집 | 해당 폴더 knowledge 추가 |
| MD 최적화 (모드 8) | 분기 1회 — 수동 트리거만 허용 |

**핵심 요약**: "4부 게이트를 통과한 교훈만 knowledge에 영구 등록한다."

# 6장. 학습 이력 관리

## 6.1 소소한 학습 이력 기록

에이전트 MD의 `## 경험 이력 > 소소한 학습 이력` 섹션에 기록한다.

**형식:**
```
- 2026-07-09 API 버전 표기 원칙 주입 (architect) (+1점)
- 2026-07-09 페르소나 발산형 구성법 학습 (reviewer) (+1점)
```

`malgnai-mcp agent_learning_log_add`와 동시에 기록한다.

## 6.2 프로젝트 경험 기록

프로젝트 완료 후 에이전트별로 경험 이력 테이블에 행 추가:

```markdown
| malgnuniv | API 명세 전체 설계 | 재작업 0회, Critical 0건 | +8점 |
```

점수 계산: 완료(+5) + 재작업없음(+3) = +8점

## 6.3 malgnai-mcp agent_learning_log_add 활용

학습 완료 시마다 에이전트별로 1회 호출:

```
agent_name: "architect"
type: "skill_training"
title: "API 설계 스킬업 — 버전 표기 원칙 박제"
content: "API 경로에 /v1/ 미포함 패턴 발견. MD 핵심 원칙에 버전 표기 의무화 추가.
          knowledge/architecture/api-design-guide.md에 버전 전략 섹션 신설."
source: "knowledge/architecture/api-design-guide.md"  # 예시 경로
```

## 6.4 학습 보고서 구조

매 학습 세션 종료 후 PM에게 반환하는 보고 형식:

```
학습 대상: [에이전트명]
학습 모드: 모드 [N]
이전 점수: [스킬/100, 경험/100, 최종/100]
이후 점수: [스킬/100, 경험/100, 최종/100]

주입 내용:
- [학습 항목 1] → knowledge/[경로] 또는 MD [섹션]
- [학습 항목 2] ...

산출물 진단 결과: (모드 7인 경우)
- 약점 인용: "[실제 파일에서 발견한 약한 문장]"
- 처방: [MD 또는 knowledge 어디에 무엇을 박제했나]

malgnai-mcp 기록: 완료 / 미완료
```

**핵심 요약**: "소소한 학습은 MD에, 프로젝트 경험은 테이블에, 둘 다 malgnai-mcp에."

# 7장. 에이전트 MD 갱신 절차

## 7.1 백업 방법

**모든 MD 갱신 전 필수 선행 단계:**

- **이 플러그인 번들(`agents/`)을 직접 갱신하는 경우(기본 케이스)**: git으로 버전 관리되므로 별도 cp 백업이 필요 없다. 갱신 전 `git status`/`git diff`로 현재 상태를 확인하고, 필요하면 `git stash` 또는 별도 브랜치로 분리한다. 되돌릴 커밋 해시를 기록해 둔다.
- **에이전트 MD를 전역 `~/.claude/agents`에서 개별 운용하는 경우(이 플러그인과 별개의 로컬 구성일 때만)**:
  ```bash
  cp -r ~/.claude/agents ~/.claude/agents_backup_$(date +%Y%m%d)
  ```
  백업 경로: `~/.claude/agents_backup_YYYYMMDD/`
  백업 확인: `ls ~/.claude/ | grep agents_backup`

## 7.2 새 포맷 마이그레이션 체크리스트

```
[ ] 1. 백업 완료 확인
[ ] 2. 기존 MD 읽기 → 교훈 목록 추출 (Before 목록 작성)
[ ] 3. `docs/methodology/agent-development-methodology.md` §3.1 골격(frontmatter→핵심원칙→역할경계→스킬상세→전제조건→자기검증→산출물→학습자료→토큰효율) 참조해 재작성 (agent-md-format-standard.md의 구 7섹션 포맷은 폐기됨, 참조 금지)
[ ] 4. 교훈 목록 대조 — Before 개수 = After 개수 확인
[ ] 5. skill-definitions.js EMPLOYEE_CARDS에서 금지/승인 동기화(미번들 — 없으면 각 에이전트 MD를 직접 대조)

[ ] 7. 토큰 효율 섹션 — 리더형은 서브 감독 포함 여부 확인
[ ] 8. last_trained 날짜 갱신
```

## 7.3 기존 노하우 보존 검증 방법

**원칙: 교훈 내용 손실 0**

마이그레이션 전후로 "교훈 목록"을 만들어 대조한다:

```
Before: [교훈A, 교훈B, 교훈C, ...]
After:  [교훈A, 교훈B, 교훈C, ...]  ← 동일 개수, 동일 핵심 내용
```

누락이 있으면 After에 추가 후 재검증. 개수가 일치할 때만 완료 처리.

**주의**: 표현 압축은 허용, 의미 손실은 불허. 모드 8(MD 최적화)도 동일 원칙 적용.

**핵심 요약**: "백업 먼저, 교훈 목록 대조로 손실 0 검증 후 완료."
