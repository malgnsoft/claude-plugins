# Beyond-Mediocre Output

## 정의

모든 에이전트 산출물(코드, 문서, 검증, 의사결정)이 "일반적인 수준"을 넘도록 강제하는 품질 기준. 프로젝트 고유의 조건, 엣지케이스, 제약을 반영하여 구체성과 신뢰성을 확보한다.

## 핵심 원칙

### 1. 프로젝트 고유성 (Generic ❌ → Context ✅)

**산출물마다 3가지 이상 프로젝트 고유 특성 반영:**
- 기술 스택 (언어, 프레임워크, 패턴)
- 조직 규칙 (코딩 스타일, git flow, 배포 절차)
- 비즈니스 제약 (성능 목표, 규제, 사용자 행동)

**체크:**
```
❌ "에러를 처리해야 한다"
✅ "pnpm workspace 상황에서 cross-package 에러는 A, 단일 패키지는 B로 처리. 
   사용자는 모바일 환경에서 타임아웃 시 재시도 팝업만 보여야 함"
```

### 2. 엣지케이스 명시 (행복한 경로만 ❌ → 예외 처리 ✅)

**모든 산출물에서 다음 엣지케이스 식별 후 처리:**
- 빈 입력 / null 값
- 극단값 (최대값, 최소값, 정수 오버플로우)
- 동시성 조건 (race condition, deadlock)
- 리소스 고갈 (메모리, 네트워크, 타임아웃)
- 부분 실패 (일부만 성공, 일부만 실패)

**체크:**
```
❌ "사용자가 로그인하면 대시보드를 표시한다"
✅ "사용자가 로그인할 때: [정상] 대시보드, [권한 없음] 제한 화면, 
   [네트워크 지연] 스피너, [타임아웃 3초] 재시도 팝업"
```

### 3. 제약과 Tradeoff 명시 (완벽한 척 ❌ → 현실적 선택 ✅)

**모든 기술적/상업적 선택에 대해:**
- 왜 이 방식을 택했는가
- 포기한 대안은 무엇인가
- 미래 변경의 용이성 (기술 부채)

**체크:**
```
❌ "이 구조가 최선입니다"
✅ "이 구조는 X 성능을 택했지만, 향후 Y로 확장 시 Z 리팩토링 필요. 
   현 단계에서 그 비용은 정당합니다 (이유: ...)"
```

### 4. 의존성 문서화 (암묵적 ❌ → 명시적 ✅)

**모든 산출물이 명시할 것:**
- 선행 조건 (이전에 뭘 해야 하는가)
- 입력 형식 / 가정
- 출력 형식 / 보장
- 외부 서비스/권한 필요 여부

**체크:**
```
❌ 코드만 있고 주석 없음
✅ 함수 상단에: "전제: users 테이블 존재, 입력: 유효한 UUID, 출력: 검증된 사용자 객체, 
   실패 시: UserNotFoundError 발생"
```

## 적용 체크리스트

### 요청/기획 단계

- [ ] 프로젝트 고유 조건 3가지 이상 파악했는가?
- [ ] 명확히 할 엣지케이스가 있는가? (사전에 정의)
- [ ] 기술 선택의 tradeoff를 이해했는가?

### 제작 단계

- [ ] 산출물에 프로젝트 고유성 3가지 이상 반영?
- [ ] 엣지케이스 5가지 이상 명시적으로 처리?
- [ ] 각 선택의 이유/대안/기술 부채 문서화?

### 완성 단계

- [ ] 선행 조건·입력·출력·의존성 문서화?
- [ ] 평범한 내용 부분이 있는가? (더 구체화 필요?)
- [ ] 다른 에이전트가 이 산출물을 쓸 때 재질문 없이 사용 가능?

## 품질 신호

- ✅ 산출물을 읽으면 "이 프로젝트에만 해당하는" 결정이 명확
- ✅ 미처리된 엣지케이스가 떠올라도 문서에 이미 나와 있음
- ✅ 후속 에이전트가 경로만으로 내용 파악 및 즉시 사용 가능
- ❌ 다른 프로젝트에도 그대로 복사 가능한 내용 (Generic)
- ❌ "이건 뭐하는 건데?" 질문이 나올 여지 (암묵적)
