# 작업 등급 → 검증 강도 (전 에이전트 공통)

> ⚠️ risk_level(server/lib/autonomy.js — 자율엔진 내부 개념, malgnai-hub 연동판에는 해당 없음)과 축이 다르다 — 이름도 다르게 씀(등급명에 "Risk"를 쓰지 않음):
> risk_level = "자율엔진이 이 실행단위를 사람 승인 없이 굴려도 되는가"(집행 게이트, 워커가 사이클마다 매김).
> 이 문서의 등급 = "PM가 위임 전에, 에이전트가 검증을 얼마나 깊게 할지"(자기검증 깊이, 위임 시 1회 판정).
> 기계적으로 맞대응시키지 말 것 (Micro 등급 배포 설정 변경도 risk_level=high일 수 있고, Refactor 등급 리팩터링의 실행단위 risk_level은 low일 수 있다).

## 5등급 판정표

| 등급 | 기준 | 위임/직접처리 | 승인 주체 | 리뷰 깊이(reviewer) | QA 최소기준 | 캡처 깊이(common-screen-verification-and-capture 매핑) | 재검토 시 |
|---|---|---|---|---|---|---|---|
| Micro | 문구·CSS·단일파일 수정, 조회·오타 | PM 직접 처리 | → pm.md 권한표 | 생략(원칙상 reviewer 미호출) | 눈검증 | trivial — 캡처 생략 가능 | - |
| Standard | 일반 기능·API·버그수정 | 위임 | → pm.md 권한표 | 조건부 — 아래 "Standard(Fast Path 아님)의 reviewer 호출" 절의 트리거에 걸릴 때만 약식(페르소나 1~2, 발산형 생략 가능), 아니면 생략 | 정상흐름 + 주요 예외 1개 | standard — 완성시점 1회 + 경량체크리스트 4항목 | - |
| Sensitive | DB·권한·인증·배포·결제·개인정보·대량데이터 (노출 범위에 따라 검증 깊이 조정 가능 — "노출 범위" 절 참조) | 위임 + Impact Check 선행 | → pm.md 권한표 | 풀패널(발산형 포함 2~4명) 필수 — 노출 범위 축소 3조건을 모두 충족한 위임만 약식(아래 "노출 범위" 절) | 정상+예외+권한/데이터/롤백 확인 | critical — 상태전이마다 캡처 + Full Checklist(화면 성격이 정하므로 노출 범위 축소 대상 아님) | 동일 target_id 재검토는 축소/증분 모드 가능(§ 아래 참조) |
| Exploration | 원인분석·구조파악, 무엇을 고칠지 모름 | 위임(시간·산출물 제한) | → pm.md 권한표 | 결론 검증만 | 없음 | trivial — 결론 검증만이라 캡처 불필요 | - |
| Refactor | 구조개선·중복제거(기능변화 없음) | 위임 + 변경 전후 기준 선행 | → pm.md 권한표 | 풀패널 필수 | 기존 동작 동일성 확인 | standard — 동일성 확인 목적(UI 변경 수반 시 critical로 상향) | 동일 target_id 재검토는 축소/증분 모드 가능(§ 아래 참조) |

**승인 주체는 이 표에 값으로 두지 않는다** — 등급을 판정한 뒤 승인·위임을 실행하기 직전에, 정본인 `${CLAUDE_PLUGIN_ROOT}/agents/pm.md`의 "PM 권한 참조표"에서 그 등급 행을 열어 확인한다. 같은 값을 두 곳에 두면 한쪽만 고쳐져 조용히 갈린다. 등급과 무관하게 항상 사람 승인이 필요한 행위(비가역·대외 영향·정책 신설)와 전역 자산 승격 실행의 담당도 그 표를 따른다. **아래 "노출 범위" 절의 축소가 적용된 위임도 이 규칙에서 예외가 아니다** — 축소는 리뷰 깊이만 내리고 승인 주체는 건드리지 않으므로, 축소된 Sensitive 건도 pm.md 권한표의 Sensitive 행(사람 승인 필수)을 그대로 연다.

캡처 깊이의 상세 기준(체크리스트 항목·상태전이 캡처 방법 등)은 `common-screen-verification-and-capture` 스킬을 따른다.

## 빠른 판단

**등급은 고친 파일이 몇 개인가로 가르지 않는다 — 위험과 가역성으로 가른다.** 파일 개수는 위험의 대리지표로 쓸 수 없다(한 파일만 고치는 인증 로직 변경이 다섯 파일에 걸친 문구 교체보다 훨씬 위험하다). 위에서부터 순서대로 본다.

```
① 고위험 도메인의 **동작**을 건드린다 → Sensitive
   (같은 파일 안이라도 문구·CSS·오타처럼 동작을 바꾸지 않는 수정은 ④ Micro다)
   도메인 목록은 위 판정표의 Sensitive 행이 정본이다 — 여기 다시 나열하지 않는다
   (같은 목록을 두 벌 두면 한쪽이 좁아진 채 갈리고, 판정에서는 좁은 쪽이 조용히 이긴다).
   그 행의 단어에 딱 들어맞지 않아도 **되돌릴 수 없거나(비가역 데이터 변경·마이그레이션·삭제)
   조직 밖으로 나가는(외부 공개 API contract의 중대한 변경, 외부 사용자에게 큰 영향) 성격이면
   그 행에 해당하는 것으로 본다** — 넓은 쪽으로 읽는다.
② 무엇을 고칠지 아직 모름 → Exploration
③ 기능 변화 없이 구조만 바꿈 → Refactor
④ 위 판정표 Micro 행에 해당(문구·CSS·단일파일 수정, 조회·오타) → Micro
⑤ 그 밖 → Standard. 이 안에서 Fast Path 5조건을 대조한다(아래 절).
사용자 규모·배포 범위는 등급을 정하는 축이 아니다 → 아래 "노출 범위" 절로 검증 깊이만 조정한다.
```

**"애매하면 무거운 쪽으로 기운다"는 위험이 애매할 때만이다.** 두 종류의 불확실을 섞지 않는다.
- **위험의 불확실 → 상향 근거다.** 이 변경이 인증·권한·데이터 비가역성·대외 영향에 닿는지 판단이 서지 않으면 안전측으로 올린다.
- **방법의 불확실 → 상향 근거가 아니다.** 어느 파일을 고칠지, 어떤 API를 쓸지, 구현이 몇 줄일지 아직 모르는 것은 담당 에이전트가 착수해서 푸는 문제다. 이걸 위험으로 착각해 등급을 올리면 간단한 작업마다 상류 단계와 리뷰가 붙어 비용만 늘고 결과물은 그대로다.

### 구조냐 강도냐 — 보안이 걸린 변경

**판별 기준은 하나다: 이 변경이 "누가 무엇에 접근할 수 있는가"의 경계를 옮기는가.** 옮기면 구조이고 ①에 해당해 Sensitive다. 경계는 그대로 두고 그 안의 촘촘함만 조절하면 강도이고, 강도 항목은 **그것만으로는 등급을 올리지 않고, security 에이전트 호출을 강제하지도 않는다** — 저위험 작업이면 Standard(Fast Path 5조건을 채우면 Fast Path) 그대로 두고 기능 구현과 함께 점진적으로 강화한다.

**강도처럼 보이지만 경계가 움직이는 변경이 있다 — 오분류의 대가가 큰 쪽은 이 방향이다.** 이름이 "세분화"·"필드 추가"·"값 조정"이어도 아래에 해당하면 강도가 아니라 구조이고 Sensitive다.
- 권한을 **넓혀** 새 주체가 접근하게 되는 변경. 좁히려던 변경이라도 조건을 잘못 결합해 실제 범위가 넓어지면 마찬가지다 — **분류는 의도가 아니라 결과로 한다.**
- 게이트·소유권/테넌시 필터를 처음 도입하거나 제거·우회하는 변경.
- 기존에 응답으로 나가지 않던 개인정보·자격증명·타 주체 소유 정보를 새로 싣는 변경.
- fail-closed·파라미터화 쿼리 같은 최소 요건을 **깨는** 방향의 변경(무설정 시 통과로 전환, 검증 우회 플래그 추가 등).

**어느 항목이 구조이고 어느 항목이 강도인지의 항목 목록은 Skill `domain-backend-api-security` "언제 정하는가" 절에만 두고 여기 복제하지 않는다** — ①이 도메인 목록을 복제하지 않는 것과 같은 이유다. 위 네 가지는 그 목록이 아니라, 목록을 열기 전에 먼저 걸러내야 하는 **방향**이다. 여기서 걸리지 않았고 어느 쪽인지 판단도 서지 않으면 정본을 열어 항목과 대조한다 — 열어보지 않은 채 "강도겠지"로 내리지 않는다.

그래서 "여기에 레이트 제한도 걸면 좋겠다"류의 발견은 **위험의 불확실이 아니라 개선 여지**다. 상향 근거로 쓰지 말고 프로젝트의 `docs/security-plan.md`에 항목으로 적어 둔다(개발 단계 보안 발견의 적재처와 같은 문서다) — 강도 항목이 눈에 띈다는 이유로 등급을 올리면 저위험 작업마다 상류 단계와 보안 점검이 붙어 비용만 늘어난다. 적재처 없이 "나중에"로 넘기면 미룬 강화가 그대로 사라진다.

## Standard의 Fast Path — 오버헤드를 걷어내는 경로

Fast Path는 **새 등급이 아니라 Standard 안의 진행 방식**이다. 등급은 Standard 그대로 두고(검증 강도의 기준도 판정표 Standard 행 그대로), 그 등급이 관행적으로 끌고 오는 주변 절차만 걷어낸다. Micro와 다르다 — Micro는 위임 자체가 없는 PM 직접 처리이고, Fast Path는 담당 에이전트에게 **위임은 하되** 그 주변 오버헤드를 생략한다.

**5조건 — 모두 충족해야 하고, 하나라도 어긋나면 일반 Standard로 간다**
1. 요구사항이 명확하다(무엇을 만들면 되는지 되물을 것이 없다).
2. 새 아키텍처·제품 결정이 필요 없다(기존 패턴·구조를 그대로 따른다).
3. 영향 범위가 국소적이다(고친 자리 밖으로 동작이 번지지 않는다).
4. 쉽게 되돌릴 수 있다(revert 한 번으로 원상복구되고 남는 부작용이 없다).
5. 위 "빠른 판단" ①에 해당하지 않는다(판정표 Sensitive 행의 요소도, 비가역·대외 성격도 없다).

**생략하는 것**: WBS · planner/architect 등 상류 단계 · 별도 reviewer 호출.
**하는 것**: 담당 에이전트 1명에게 위임(그 변경에 딸린 인접 파일 수정은 같은 담당자가 함께 처리) · 그 변경에 필요한 테스트만 수행(판정표 Standard 행의 QA 최소기준을 변경 범위에 한정해 적용) · PM이 diff와 테스트 결과를 확인하고 종료.

**착수 후 이탈 — 담당 에이전트가 그 자리에서 멈추고 알린다.** 5조건은 착수 전 판정이라 실제로 파보면 틀릴 수 있다. Fast Path는 정의상 reviewer가 붙지 않아 이걸 잡아줄 제3자가 없으므로, **조건이 깨진 것을 발견한 담당 에이전트 본인이 유일한 안전장치다.** 작업 중 아래 중 하나라도 확인되면 계속 밀어붙이지 말고 즉시 PM에게 알린다 — 영향 범위가 고친 자리 밖으로 번진다 / 새 아키텍처·제품 결정이 필요하다 / 요구사항을 되물어야 한다 / 되돌리기가 revert 한 번으로 끝나지 않는다 / 판정표 Sensitive 행에 닿는다. PM은 보고를 받으면 그 건을 일반 Standard(고위험 요소가 드러났으면 Sensitive)로 전환하고, 생략했던 절차(reviewer 호출·상류 단계·WBS) 중 전환된 등급이 요구하는 것을 다시 붙인다. **이미 진행한 분량은 되돌리지 않고 전환된 등급의 검증을 그 위에 얹는다** — "여기까지 왔으니 그냥 끝내자"가 이탈을 덮는 가장 흔한 경로다.

## Standard(Fast Path 아님)의 reviewer 호출 — 조건부

일반 Standard도 reviewer를 자동으로 부르지 않는다. 아래 트리거 중 **하나 이상**에 해당할 때 약식 리뷰(페르소나 1~2, 발산형 생략 가능)를 호출한다.

- 변경 범위가 넓다
- 여러 모듈이 서로 얽힌다
- 요구사항에 해석의 여지가 크다
- 회귀 위험이 크다
- PM이 결과에 확신이 서지 않는다
- 사용자가 리뷰를 명시적으로 요구했다
- 중요한 사용자 흐름에 영향을 준다

트리거에 하나도 걸리지 않으면 담당 에이전트의 self-test·lint·단위 테스트 + PM의 diff·결과 확인으로 종료한다. **이 조건부는 Standard 한정이다** — Sensitive/Refactor의 풀패널 필수, Exploration의 결론 검증은 그대로다.

## 노출 범위에 따른 검증 깊이 조정 (Sensitive 한정)

등급은 **무엇을 건드리는가**(요소)로 매기고, 노출 범위는 **틀렸을 때 누가 얼마나 다치는가**로 따로 본다. DB를 쓰는 1인용 로컬 도구와 DB를 쓰는 대외 서비스는 같은 "DB 사용"이지만 사고의 크기가 다르다. 그렇다고 규모를 등급에 섞어 Sensitive를 Standard로 내리지는 않는다 — 등급을 내리면 사용자가 늘었을 때 재판정할 신호가 사라지고, "사내용이라서"가 인증·권한 검증을 건너뛰는 만능 면제 사유가 된다.

**노출 범위 2축** (요구사항 수집·위임 판정이 같이 쓰는 어휘)
- 사용자 규모: 개인 1인 / 단일 팀·부서 내부 / 사내 전사 / 조직 밖 외부 사용자
- 배포 대상: 로컬 실행 / 사내 서버(외부 미노출) / 외부 공개 서비스

**한 단계 축소 가능 — 아래를 모두 충족할 때만**
- 사용자가 개인 또는 단일 팀 내부이고, 배포가 로컬 실행 또는 사내 서버(외부 미노출)다.
- 취급 데이터가 그 팀이 스스로 만든 것이다 — 제3자 개인정보·고객 데이터·결제정보가 없다.
- 사고가 나도 복구를 그 팀 안에서 끝낼 수 있다(대외 고지·환불·법적 통지가 필요 없다).

**축소되는 것은 리뷰 깊이 하나뿐이다 — 풀패널 → 약식(페르소나 1~2, 발산형 생략 가능).** 나머지는 그대로 간다:
- **승인 주체는 축소 대상이 아니다.** Sensitive는 축소돼도 **사람 승인 필수** 그대로이며, PM 단독 승인으로 갈음할 수 없다(pm.md "PM 권한 참조표"의 Sensitive/Refactor 행).
- **캡처 깊이도 축소 대상이 아니다.** 캡처는 등급이 아니라 화면 성격(결제·인증·삭제 등)이 정하므로 `common-screen-verification-and-capture` §3의 위험도 판정을 그대로 따른다 — 노출 범위가 좁다는 이유로 critical 화면을 standard로 내리지 않는다.
- **QA 최소기준의 권한·데이터·롤백 확인도 축소하지 않는다** — 그것이 애초에 이 작업을 Sensitive로 만든 요소다.

**축소 금지 — 하나라도 걸리면 규모와 무관하게 Sensitive 그대로**: 제3자 개인정보·결제·인증 자격증명 취급 / 외부에서 접근 가능한 엔드포인트 / 되돌릴 수 없는 삭제·마이그레이션 / 배포 파이프라인·시크릿 자체 변경.

축소를 적용하면 PM은 위임 메시지에 **축소 근거 3값**(사용자 규모·배포 대상·데이터 성격)을 한 줄로 싣는다. 근거가 없으면 규모가 커졌을 때 무엇을 되돌려야 하는지 알 수 없다. **3값 중 하나라도 빠진 위임은 reviewer가 풀패널(축소 없음)로 처리한다**(안전측 기본값). reviewer는 3값이 실려 있어도 PM의 축소 주장을 그대로 받지 않고 위 3조건·축소 금지 목록을 직접 대조하며, 불충족을 발견하면 풀패널로 격상하고 그 사유를 보고서에 적는다.

## 동일 대상 재검토 — 축소/증분 모드

Sensitive/Refactor 등급 산출물이 짧은 기간 내 여러 번 재수정돼 reviewer에 반복 위임되는 경우, 매번 풀패널을 새로 돌리지 않는다. PM은 위임 시 `target_id`(안정 슬러그)를 발급/재사용하고, reviewer는 다음 기준으로 모드를 판정한다. PM은 위임 메시지에 **재검토 3요소**(`target_id`·직전 리뷰 경로·리스크 범주)를 모두 싣는다 — 하나라도 누락되면 reviewer는 최초 리뷰(풀패널)로 처리한다.

**동일 대상 인정 조건 (모두 충족 필요)**: 동일 target_id + 직전 리뷰로부터 7일 이내 + 리스크 범주 불변(인증→배포처럼 도메인이 바뀌면 절대 동일 target_id 불가) + 리뷰 대상 파일 실질 중첩.

**풀패널 강제 승격 조건 (하나라도 해당하면 축소 불가)**: 직전 Critical/Major 미해결 존재 / 직전에 없던 새 실행경로·리스크 표면 다수 등장 / 다른 Sensitive 하위도메인 진입 / 재검토 4차 이상 누적 / PM·사용자의 명시적 풀패널 요청.

상세 절차(모드 3단계, 페르소나 재사용 방식, 보고서 템플릿)는 Skill `reviewer-persona-panel-standard`와 `${CLAUDE_PLUGIN_ROOT}/agents/reviewer.md`를 따른다.
