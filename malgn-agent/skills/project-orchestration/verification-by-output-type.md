# §5 부록. 산출물 유형별 추가 검증 항목

> Skill `project-orchestration` §5의 부록이다. 색인은 `skills/project-orchestration/SKILL.md`에 있다(이 파일을 열라고 지시한 그 파일이며 이미 로드돼 있다).
> 이 파일에서는 `CLAUDE_PLUGIN_ROOT` 변수가 치환되지 않는다 — 플러그인 자원을 실제로 열거나 실행하는 지시는 색인 쪽에 둔다.

§5의 공통 검증(경로 실재·재지시 2회·실물 검증·정직 보고·이슈 종결)에 더해, 검증 대상이 아래 유형에 해당할 때만 추가로 거친다. 각 항목은 그 유형에서 **검사 도구나 보고서만으로는 드러나지 않는** 실패를 막는다.

- [ ] **설계 산출물** — 설계가 "새로 도입한다"고 주장하는 핵심 함수·로직마다 직접 `grep -rn`으로 기존 사용처와 대조했는가? 형제 리소스에 이미 동일 로직이 있는데 신규 도입으로 설계되는 일이 있고, 설계 문서만 읽어서는 드러나지 않는다.
- [ ] **frontend-dev의 `Write` 전체 재작성** — `git diff`의 맨 앞·맨 끝 몇 줄을 직접 대조해 스트레이 `</content>` 같은 툴 출력 포맷 잔재가 파일 경계 바깥에 섞이지 않았는지 확인했는가? 문법검사는 이걸 통과시킨다.
- [ ] **이전 세션의 "검증 완료(grep 0건)" 주장 인수** — 그 주장을 이어받아 후속 작업을 시작하기 전에 ①`git status`/`git diff`로 실제 커밋 여부와 ②같은 grep 패턴 재실행으로 정말 0건인지를 실물 재확인했는가? 미커밋 상태가 완료로 오인되거나, 패턴 자체가 오탐이라 0건이 나온 경우가 있다.
- [ ] **용어·i18n 치환(도메인 전환)** — 카테고리어 키워드 grep만으로 끝내지 않고, 도메인 특유 고유명사(과목명·건물명 등 구체 사례)까지 나열해 함께 grep했는가? 카테고리어만으로는 고유명사 잔존을 놓친다.
- [ ] **화면 캡처 보고** — 탭 전환처럼 같은 URL에서 클라이언트 상태만 바뀌는 화면을 "각각 검증했다"고 보고받으면, 최소 1~2개 스크린샷 파일을 직접 열어 실제로 다른 내용인지 확인했는가? 파일명만 다르고 같은 화면이 반복 캡처되는 일이 있다.
