# Token Usage Diagnosis Skill

## Definition

Claude Code는 각 PC에 `~/.claude/projects/**/*.jsonl`로 세션 원본을 남긴다. 이 스킬은 그 로그를 분석하는 플러그인 번들 스크립트 `bin/analyze-usage.mjs`를 실행해, "왜 이렇게 토큰을 많이 썼는지" 묻는 직원에게 근거 있는 진단과 규칙기반 효율화 가이드를 제시한다.

- **대상:** 특정 소수 전문 에이전트 전용이 아니다. 사용자가 자기 세션에서 직접 트리거하는 범용 자가진단 도구 — PM이 위임하거나(Micro 등급, `common-task-grading-and-verification-depth` 참고), 세션 중인 어느 에이전트든 사용자가 물으면 바로 실행한다.
- **구조적 한계:** 각 PC의 로그는 그 PC 사용자 자신의 것만 존재한다. 다른 사람 데이터에 접근할 방법이 없으므로 이 진단은 언제나 "실행한 사람 자신"만 다룬다 — 팀/조직 전체 집계나 타인과의 비교는 이 도구로 할 수 없다.
- **핵심 목표:** 스크립트가 이미 계산한 수치와 규칙기반 가이드를 있는 그대로 전달하고, 그 위에 우선순위·맥락 설명만 자연어로 덧붙인다. 새 숫자·비용·원인을 절대 지어내지 않는다(이 스킬에서 가장 중요한 제약).

## 실행 도구: `bin/analyze-usage.mjs`

**사전 조건 없음** — 순수 Node.js 내장 모듈만 사용하므로 설치 없이 바로 실행된다.

```bash
node <malgn-agent 플러그인 경로>/bin/analyze-usage.mjs [--days N] [--project <cwd 부분일치>] [--top N] [--out <md파일경로>]
```

- `--days N` 기본 1(오늘, 로컬 타임존 기준). 최근 N일(오늘 포함) 집계.
- `--project S` cwd에 S가 부분 포함된 세션만 집계(필터 없으면 전체 프로젝트).
- `--top N` 세션/API호출 순위 상위 개수. 기본 5(API 호출 Top은 자동으로 그 2배, 기본 10).
- `--out PATH` 같은 리포트를 마크다운 파일로도 저장(지정하지 않으면 콘솔 출력만).

출력(콘솔=마크다운 동일 내용): 총량 요약, 캐시 히트율, 일자별 추이(2일 이상 데이터 있을 때만), 세션별 토큰 순위, 가장 비싼 개별 API 호출 Top N, 반복 호출 패턴, 세션 파편화 분석, 그리고 마지막에 **"효율화 가이드"** 섹션(캐시히트율<50%/반복호출 존재/턴당 API 호출≥15/단일세션 토큰 편중≥40%/세션 파편화(하루 세션≥5개+세션당 평균 턴≤2)/사이드체인 비중≥30% — 해당 조건이 실제로 참일 때만 각 항목이 나타난다).

**의도적으로 없는 것**: 비용($/원) 추정. 단가는 시점에 따라 바뀌어 최신성을 보장할 수 없으므로 스크립트도, 이 스킬도 비용을 계산하거나 추정하지 않는다.

## 자연어 → 옵션 매핑

사용자 표현을 옵션으로 그대로 대응시킨다. 애매하면 기본값(오늘, 전체 프로젝트, Top 5)으로 실행한 뒤 필요시 좁힌다.

| 사용자 표현 예시 | 옵션 |
|---|---|
| (특정 기간 언급 없음), "오늘" | 옵션 없음(기본 `--days 1`) |
| "이번 주", "최근 일주일" | `--days 7` |
| "이번 달", "최근 한 달" | `--days 30` |
| "이 프로젝트만", 특정 프로젝트명 언급 | `--project <이름 부분일치>` |
| "더 자세히", "Top 10개 보여줘" | `--top 10` |
| "기록으로 남겨줘", "파일로 줘" | `--out <경로>` 추가(저장 규칙 참고) |

예:
```bash
node <malgn-agent 플러그인 경로>/bin/analyze-usage.mjs --days 7 --project claude-plugins --top 10
```

## 결과 해석 원칙 (가장 중요한 제약)

- **스크립트 출력을 있는 그대로 인용한다.** 특히 "효율화 가이드" 섹션은 이미 관측된 수치가 조건을 만족할 때만 규칙기반으로 나오는 결과다 — 그 문장을 그대로 신뢰하고, 그 위에 우선순위 부여·상황 설명 정도만 자연어로 덧붙인다.
- **스크립트가 계산하지 않은 것을 스킬이 만들어내지 않는다.** 비용/원화 추정, 근본 원인 단정, 스크립트에 없는 새 수치 가공 전부 금지. 예: 캐시 미스가 왜 발생했는지 스크립트가 알려주지 않으면 "정확한 원인은 알 수 없습니다 — 다만 관측된 패턴은 X입니다"까지만 말한다.
- 이 원칙은 Skill `common-verifiable-output-and-honesty`의 claimed/verified 구분과 같은 정신이다: **스크립트 출력 = verified(실행 결과)**, **그 위에 얹는 해석 = claimed(추론)**이며 이 둘을 문장에서도 섞지 않는다(예: "관측 결과 캐시 히트율 42%입니다(verified). 짐작건대 관련 없는 작업을 한 세션에서 이어간 것으로 보입니다(claimed, 확정 아님)").

## 효율화 가이드가 비어있을 때

"관측된 데이터 범위에서는 뚜렷한 비효율 패턴이 발견되지 않았습니다"가 나오면 그대로 **"특이사항 없음"**으로 보고한다. 억지로 개선점을 만들어내 문제를 지어내지 않는다.

## 데이터 없음 / 에러 상황

스크립트가 이미 다음을 자체 처리한다 — 스킬이 별도 방어 로직을 추가로 만들 필요 없다:
- `~/.claude/projects` 디렉터리 자체가 없음 → 스크립트가 안내 메시지를 내고 종료(exit 1)
- 기간/프로젝트 필터에 맞는 세션이 없음 → "조건에 맞는 데이터가 없습니다" 안내

두 경우 모두 스크립트의 안내 문구를 그대로 사용자에게 전달한다.

## 우선순위 부여 (해석 층위 — 스크립트 계산이 아님을 명시)

효율화 가이드에 여러 항목이 동시에 뜨면, 다음 순서로 먼저 짚어주는 것을 권장한다(스크립트는 항목 간 순서를 매기지 않으므로 이 순서는 스킬의 해석 판단이다 — "스크립트가 우선순위를 정했다"고 오도하지 않는다):

1. **캐시 히트율 저하** — 매 요청마다 비용에 즉시 영향
2. **단일 세션 토큰 편중 / 세션 파편화** — 작업 습관 교정으로 가장 쉽게 개선 가능
3. **반복 호출** — 국소적이라 영향이 상대적으로 작음
4. **턴당 API 호출 과다 / 사이드체인 비중 과다** — 작업 특성(복잡한 멀티스텝 작업 등)일 수도 있어 성급히 문제로 단정하지 말고 상황을 먼저 물어본다

## 셀프서비스 한계 (정직 고지)

- 이 진단은 실행한 사람 PC의 로컬 로그만 본다. 팀/조직 전체 집계, 타인과의 비교는 구조적으로 불가능하다 — 그런 요청이 오면 "내 데이터만 볼 수 있습니다"라고 명시한다.
- 비용($/원) 추정은 하지 않는다(위 "의도적으로 없는 것" 참고). 사용자가 원화 환산을 요구해도 근거 없는 단가를 지어내 답하지 않는다 — 필요하면 사내 공식 단가 출처를 사용자에게 먼저 확인한다.

## 저장 규칙

기본은 콘솔 출력(대화 응답)만으로 충분하다 — 개인 세션 로그 기반의 1회성 진단 리포트를 프로젝트 `docs/`에 상시 저장할 필요는 없다(`common-output-storage-and-path-management`가 정의하는 장기 보존 문서 위계와는 다른 성격). 사용자가 "기록으로 남겨줘/파일로 줘"라고 명시할 때만 `--out`으로 마크다운 저장 후 절대경로를 보고한다 — 저장 위치는 진행 중인 프로젝트 맥락이면 그 프로젝트의 scratchpad/임시 경로, 그 외에는 사용자에게 위치를 확인한다.

## Example Usage

```
사용자: "요즘 토큰 왜 이렇게 많이 나가지? 이번 주 것 좀 봐줘"

→ node <malgn-agent 플러그인 경로>/bin/analyze-usage.mjs --days 7 실행

→ 보고 (스크립트 출력 그대로 인용 + 해석 얹기):
"이번 주 집계 결과(2026-08-04~08-10, 세션 12개, 총 1.2억 토큰 — verified):
- 캐시 히트율 38%로 낮습니다(verified). 관련 없는 작업을 한 세션에서 이어가며 컨텍스트를 자주 리셋했을 가능성이 있습니다(claimed, 스크립트가 원인까지 알려주진 않습니다).
- 단일 세션(a1b2c3d4)이 전체의 52%를 차지합니다(verified) — 우선순위 상 가장 먼저 볼 항목입니다.
- 반복 호출 3건 탐지(verified), 영향은 상대적으로 작습니다.
전체 리포트는 위 표를 참고하세요. 비용 추정은 제공하지 않습니다(단가 최신성 보장 불가)."
```

## Integration Notes

- **PM(게이트웨이) 처리:** VSCode COO 게이트웨이로 들어온 이런 요청은 PM이 Micro 등급으로 직접 처리한다 — 전문 에이전트 위임이 필요 없다(`common-task-grading-and-verification-depth` 참고).
- **개인정보 유의:** 산출물에 세션별 cwd(작업 디렉터리 절대경로) 등 개인 작업 정보가 포함된다. 다른 사람과 공유하거나 팀 채널에 붙여넣기 전에는 이 점을 알린다.
  - **"반복 호출 패턴" 표도 노출면이다:** 이 표는 도구 input을 `JSON.stringify` 후 120자까지 truncate해 원문 그대로 찍는다(`bin/analyze-usage.mjs` 323~336행 수집, 486~497행 렌더링). Read 도구(file_path만)는 안전하지만, 같은 세션에서 Bash 명령어 전문·Edit/Write의 content·new_string 일부·WebFetch 쿼리스트링(토큰이 포함될 수 있음)이 2회 이상 반복되면 그 원문 일부가 리포트에 그대로 노출된다. 공유 전 이 표를 확인하고, 민감한 원문이 보이면 가리거나 제외한다.
  - **malgnai-hub 등 중앙 저장소에 원문 그대로 기록 금지:** 이 리포트는 로컬 1회성 개인 진단 데이터다. `work_record`/`decision_record` 등 회사 전체가 검색 가능한 중앙 저장소에는 리포트 원문을 그대로 남기지 말고, 요약 수치·결론만 기록한다 — 로컬 데이터가 중앙 저장소로 그대로 전파되지 않게 한다.
- **로그 스키마 변경 시:** Claude Code 세션 로그(`.jsonl`)의 필드 구조가 바뀌면 `bin/analyze-usage.mjs`의 파싱 로직이 먼저 갱신되어야 한다 — 이 스킬 자체는 스크립트를 감쌀 뿐 로그를 직접 파싱하지 않는다.
