# Git Safety & Concurrency

## 정의

한 저장소를 여러 세션·프로세스·에이전트가 동시에 만지는 환경에서, **다른 쪽의 작업을 지우지 않고** 내 작업만 정확히 커밋하기 위한 규율. 그리고 실행하면 되돌리기 어려운 git 행동 앞에 복구 지점을 먼저 만드는 절차.

전제는 하나다 — **세션 시작 시점에 본 저장소 상태는 이미 낡았을 수 있다.** git log·STATUS.md·서브에이전트 보고는 그 시점의 스냅숏이지 지금의 사실이 아니다.

## 1. 착수 직전 확인 (스냅숏을 신뢰하지 않는다)

승인된 작업에 손대기 직전에 다시 본다.

- `git log --oneline -5` — 같은 작업이 다른 프로세스(대화형 세션 등)에서 이미 진행·완료되지 않았는가.
- `git status` — 내 것이 아닌 미커밋 변경이 워킹트리에 있는가.
- 진행 상태 문서(STATUS.md·WBS·이슈 목록)의 "미커밋·미반영·미승격·planned" 라벨은 착수 근거가 되지 않는다 — 갈래별 대조 방법은 아래 §1-1.
- 서브에이전트가 "검증 완료"라고 보고한 파일도 직접 다시 Read한다(claimed ≠ verified).

### 1-1. 진행 상태 라벨 4갈래 대조 (라벨을 보고 착수를 판단하기 직전)

갱신 누락으로 이미 처리된 항목이 stale하게 남아 있으므로, 갈래마다 라벨이 아니라 실물을 본다.

1. **git 상태 서술** — 진행중 항목이 "미커밋"·"미승격"·"미반영" 같은 파일시스템/git 상태 서술이면 착수 전 `git status`/`git log`로 실물부터 대조한다.
2. **WBS 항목·이슈 트래커 상태** — "planned"·"우선순위 높음" 라벨을 신뢰해 바로 착수하지 않는다. 여러 세션·에이전트가 번갈아 작업하는 프로젝트에서는 완료 처리 시 진행 상태 문서만 갱신하고 WBS/이슈 트래커 동기화를 빠뜨리므로, 착수 전 최소 grep 기반 코드 실측(언어별 키 개수 비교, 대상 로직 존재 여부 등)으로 이미 해소됐는지 먼저 확인한다.
3. **반복 지시** — "최우선으로 반영해" 같은 지시가 다시 전달되면, 그 건이 실제로 아직 미완료인지 진행 상태 문서의 종결 표기 + `git log` + WBS 대조로 먼저 확인한다. 이미 종결된 건이 다시 전달돼 중복작업을 유발한다.
4. **감사·리뷰 문서의 "미반영" 라벨** — 문서 자체의 라벨을 정본으로 신뢰하지 않고, 착수 전 대상 코드를 직접 grep해 실제로 미반영 상태인지 재확인한다.

**이미 해소된 것으로 확인되면 그 자리에서 `issue_resolve`로 닫는다.** 확인만 하고 넘어가면 다음 세션이 같은 항목을 또 대조하고, 그 목록을 미해소로 믿고 중복 착수한다(부분 해소면 `result`에 해소분·잔여분을 적어 닫고 잔여만 새로 연다).

## 2. 커밋 직전 재확인 (같은 확인을 한 번 더)

착수 시점의 확인은 커밋 시점의 안전을 보장하지 않는다. 그 사이에 다른 프로세스가 커밋했을 수 있다.

- 커밋 직전 `git log -1`과 진행 상태 문서를 **다시** 읽는다. 착수 때와 다르면 강제로 진행하지 말고 `ps aux`로 동시 실행 프로세스가 있는지 먼저 확인한다.
- 다르다는 사실을 확인했으면 덮어쓰지 않는다 — 내 변경을 다른 커밋 위로 옮기거나(rebase), 사람 판단 지점으로 되돌린다.

## 3. `git add -A`는 스테이징 범위를 대조하고 쓴다

동시 프로세스가 있는 상태에서 전면 스테이징하면 다른 세션의 미커밋 변경까지 같은 커밋에 흡수된다. 결과적으로 유실 없이 보존되더라도, 그 사실을 밝히지 않으면 이력 추적이 흐트러진다.

- `git add -A` 직전 `git status`로 **스테이징될 파일이 내 작업 범위와 정확히 일치하는지** 확인한다.
- 범위 밖 변경이 섞여 있으면 ①가능하면 경로를 지정해 부분 스테이징하고, ②불가피하게 흡수했으면 커밋 메시지에 "X도 함께 흡수(다른 세션 작업)"라고 명시한다.

## 4. 되돌리기 어려운 행동 전에 되돌릴 지점을 먼저 확보한다

**대상**: merge, 대량 삭제, force push, 다수 커밋 일괄 처리, 브랜치 삭제, 이력 재작성(rebase/filter).

사람 승인을 받은 뒤에도 곧바로 실행하지 않는다. **승인 여부와 복구 가능성은 별개**다.

1. 영향 대상을 열거한다 — 어떤 브랜치·파일·레코드가 바뀌는가.
2. 그 프로젝트가 쓰는 수단으로 되돌릴 지점을 만든다 — 작업 브랜치 분리, 백업 파일, 태그, 스냅샷.
3. 그 다음에 실행한다.

리뷰·평가(reviewer/evaluator 검증)는 **변경 이후**에 오므로 이 단계를 대신하지 못한다. 확보할 수단이 없으면 실행하지 않고 사람 승인 지점으로 되돌린다.
