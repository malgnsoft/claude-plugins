# System Design Principles Skill

시스템 아키텍처 설계에서 평범함을 넘고 완결성을 보장하는 핵심 4대 의무와 우수 설계 7대 재사용 기법입니다.

## 4대 설계 의무 (Self-Verification Checklist)

### ① 트레이드오프 의무
**원칙**: "X를 쓴다"고 단정하지 말고, "왜 X인가 + 무엇을 포기했나"를 명시한다.

모든 중요한 기술·구조 선택에 **검토한 대안 ≥1개와 트레이드오프**를 명시합니다.

**형식**:
```
선택: X
대안: Y, Z
선택 이유: ~
포기한 것 (X의 제약): ~
제약 감당 방안: ~
```

**체크리스트**:
- [ ] 주요 기술 선택(프레임워크, DB, 아키텍처 스타일)마다 대안 명시
- [ ] 순환논리 제거 ("Cloudflare Workers 특성에 최적화" ❌ → 실제 트레이드오프 ✅)
- [ ] 제약이 핵심 기능에 미치는 영향까지 설계 (예: Workers 30초 CPU 제한 → LLM 스트리밍 불가 대응)

---

### ② 프로젝트 고유성 의무
**원칙**: 이 프로젝트에서만 나올 설계가 산출물의 중심에 있어야 한다.

표준 CRUD·표준 3계층은 빠르게 처리하고, **핵심 도메인에 설계 분량과 깊이를 집중**합니다.

**체크리스트**:
- [ ] planner의 `prd.md` 경쟁사 비교표 중 **어느 셀을 인용해 기술적으로 무엇을 다르게 설계했는가**를 명시했는가? (예: "경쟁사 A·B가 못하는 X 기능 → 실시간 동기화가 필요해 WebSocket 채널을 별도 설계")
- [ ] 차별점(핵심 도메인)이 별도 섹션으로 깊게 다뤄졌는가?
- [ ] 표준 요소(인증, 기본 API 구조)는 한두 페이지에 끝냈는가?
- [ ] PRD가 범용적이라 인용할 차별점 셀이 없다면, 설계로 억지 보완하지 않고 planner/PM에 prd.md "차별점" 섹션 보강을 반려 에스컬레이션했는가? (설계 전면 재작성 아님)

---

### ③ 비정상 케이스 의무
**원칙**: Happy path만 그리지 않는다.

다음을 **반드시** 설계에 포함합니다 (해당 시):

**체크리스트**:
- [ ] 외부 호출 타임아웃·실패 시 동작 설계
- [ ] **트랜잭션 경계와 부분 실패** (예: "세션 완료→AI요약 생성"에서 요약 실패 시 상태 일관성)
- [ ] **멱등성** (재시도 안전 — 상태변경/결제 API는 idempotency key로 중복 방지)
- [ ] 배치/대량 처리의 부분 성공 정책
- [ ] Rate limit 도달 시 응답 전략
- [ ] LLM 연동이면: 토큰 추적, 스트리밍 중단, 컨텍스트 윈도우 전략

**자주 빠지는 것들**:
- 동시성/TOCTOU ("존재 확인 후 생성"은 DB UNIQUE 제약으로 방지)
- 관측가능성 (외부 호출 성공률·지연·에러율을 어디서 보나)
- 장애복구 (상태 보유 시스템의 백업주기·RPO/RTO·스키마 마이그레이션)
- 재시도/멱등키 ("실패 기록"에서 멈추지 말고 재시도까지)

---

### ④ 완결성 체크리스트 의무
**원칙**: 각 산출물 유형의 필수 항목을 빠뜨리지 않는다.

**API 엔드포인트마다**:
- [ ] 요청/응답 JSON 예시
- [ ] 주요 에러 응답 + 상태 코드
- [ ] 권한 규칙 (누가 이 API를 쓸 수 있는가)
- [ ] 검증 규칙 (필드 형식·길이·필수 여부)

**DB 테이블마다**:
- [ ] 인덱스 + 그 인덱스를 **왜** 그 순서로 뒀는지 (쿼리 패턴 근거)
- [ ] 제약 (FK·UNIQUE·CHECK)
- [ ] 정규화/비정규화 판단 근거
- [ ] 시계열·대용량 테이블은 집계 테이블/파티셔닝 전략

**일관성**:
- [ ] 페이지네이션·에러 응답·네이밍이 문서 전체에서 동일한가?

## 우수 설계 7대 재사용 기법

차용 대상: 실서비스 우수 설계 문서에서 역추출한 기법들입니다.

### A. 추적성 사슬
**개념**: PRD 모듈 → BC → 엔티티 → DB 테이블 → API를 ID로 1:1 매핑

**실행**:
- 모든 컬럼·엔드포인트·규칙에 **FR/NFR/RV-ID를 괄호로 역참조**
- 답 못 다는 항목은 과설계거나 추적 누락

```
예시:
- Column: session_status ENUM (FR-001: 세션 생애주기 추적)
- Endpoint: GET /sessions/{id} (FR-001 조회, NFR-002: <1초 응답)
- DB Index: (coach_id, date, start_time) UNIQUE (FR-001 중복 방지)
```

---

### B. 도메인 경계 우선
**개념**: 각 BC마다 책임 범위를 명시적으로 정의

**실행**:
- BC마다 `포함모듈/핵심엔티티/책임/데이터소유권` 기록
- Read-only BC(대시보드·리포트)와 횡단관심사(알림·감사)는 별도로 떼어 "소유권 없음" 명시

```
예시:
BC: Coaching Session
- 포함: 세션 예약, 진행, 피드백
- 핵심 엔티티: Session, Feedback
- 책임: 세션 생애주기 관리
- 데이터 소유권: Session 테이블 쓰기 권한 보유

BC: Analytics (읽기 전용)
- 포함: 코칭 효과 분석, 대시보드
- 책임: 정보 제공
- 데이터 소유권: 없음 (다른 BC의 데이터 Read만)
```

---

### C. 상태 머신 명시
**개념**: 생애주기 엔티티는 상태 ENUM + 허용 전이만 화살표로 기록

**실행**:
- 상태 ENUM 정의 (예: DRAFT → PENDING → APPROVED → REJECTED)
- 허용 전이만 화살표로 표시 (불가능한 전이는 명시하지 않음)
- 전이를 일으키는 API 매핑
- 전이 부수효과 (타임스탐프·알림·외부호출) 기록

```
예시:
Session: SCHEDULED → ACTIVE → COMPLETED → ARCHIVED
  SCHEDULED → ACTIVE: API PUT /sessions/{id}/start (부수효과: send_reminder 취소)
  ACTIVE → COMPLETED: API PUT /sessions/{id}/complete (부수효과: generate_summary, send_feedback_email)
  COMPLETED → ARCHIVED: 시간 기반 자동 전이 (30일 후)
```

---

### D. 권한 매트릭스
**개념**: 리소스×역할 격자 + row-level 격리 규칙

**실행**:
- 리소스×역할 매트릭스 작성 (예: Admin/Coach/User 권한)
- Row-level 격리 규칙 명시 (본인/배정/소유 기반 WHERE)

```
예시:
| 리소스 | Admin | Coach | User |
|--------|-------|-------|------|
| Session (자신) | R/W | R/W | R |
| Session (타인) | R/W | - | - |
| Feedback | R/W | R/W | R |
| Analytics | R/W | R | - |

WHERE 규칙:
- Coach는 WHERE coach_id = $1 (배정받은 세션만)
- User는 WHERE user_id = $1 (자신의 세션만)
```

---

### E. 트레이드오프 표
**개념**: 제약(예: Workers 30초)을 적으면, 그게 핵심기능에 주는 영향+대응까지

**실행**:
- 3열 표: 현재 제약 | 트레이드오프 | 향후 확장
- 확장성 결정은 "지금 박을 소급불가 결정 / 나중에 더할 것" 2열로 분리

```
예시:
| 제약 | 영향 | 대응 |
|------|------|------|
| Cloudflare Workers 30초 CPU | LLM 스트리밍 불가 | 짧은 프롬프트만 처리, 장시간 작업은 Queue→Job 구조 |
| SQLite 단일 파일 | 동시성 제한 | 프로토타입 단계 제한, 실서비스는 Postgres로 마이그레이션 계획 |
```

---

### F. 비정상 케이스를 워크플로우에 인라인
**개념**: 외부호출마다 타임아웃·실패동작·대안경로를 흐름에 끼워넣기

**실행**:
- 실패 상태를 DB ENUM에 넣기 (예: `email_status='failed'`)
- 설계-DB-API가 한 사실을 가리키게 구성

```
예시:
세션 완료 워크플로우:
  1. mark session COMPLETED
  2. generate AI summary
    - 성공 → store in summary_content
    - 타임아웃(>30s) → summary_status='timeout', scheduled_retry
    - 실패 → summary_status='error', queue for manual review
  3. send feedback email
    - 성공 → email_status='sent'
    - 실패(rate limit) → email_status='deferred', queue with backoff
```

---

### G. 문서 분할 전략
**개념**: 길어지면 인덱스문서 + 분할 본문으로 구성

**실행**:
- 인덱스 문서: 요약 + 공통원칙 + 분할안내표
- 횡단규칙(네이밍·에러규약·페이지네이션)은 **인덱스 한 곳에만 정의**

```
예시:
문서 구조:
- architecture.md (인덱스: 개요 + 공통 원칙)
  - architecture/01-context-containers.md (C4 Context/Container)
  - architecture/02-components-apis.md (Component 다이어그램 + API 리스트)
  - architecture/03-data-model.md (데이터 모델)

공통원칙 (인덱스에만):
- 네이밍: 엔티티는 단수형, 엔드포인트는 복수형
- 에러: { error: "ERROR_CODE", message: "..." }
- 페이지네이션: { data: [...], cursor: "...", has_next: boolean }
```

## 자기 검증 (보고 전 — 생략 불가)

산출물을 완성한 후 반드시 다음을 확인하세요:

- [ ] **① 트레이드오프 충족**: 중요한 선택마다 대안과 트레이드오프가 명시되었는가?
- [ ] **② 고유성 충족**: 핵심 도메인이 표준 기능보다 깊게 다뤄졌는가? 경쟁사 비교표의 어느 셀을 인용해 무엇을 다르게 설계했는지 명시했는가 — 인용할 차별점이 없으면 억지 설계 대신 planner/PM에 반려 에스컬레이션했는가?
- [ ] **③ 비정상 케이스 충족**: 타임아웃·부분실패·트랜잭션·멱등성을 설계했는가?
- [ ] **④ 완결성 충족**: 모든 엔드포인트·테이블이 완결성 체크리스트를 통과하는가?
