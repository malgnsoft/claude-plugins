# Token-Efficient Collaboration

## 정의

팀 에이전트 간 협업 시 불필요한 토큰 낭비를 제거하고, 핸드오프 명확성을 높이는 협업 표준. 파일 기반 저장소를 중심으로 경로 참조만 교환하여 컨텍스트 윈도우 효율을 극대화한다.

## 대원칙 — 효율 우선, 단 문제 해결이 최우선

토큰은 절대량이 제한된 자원이지만 우선순위는 분명하다: **문제 해결 실패 > 토큰 낭비.** 아끼려다 일을 못 끝내는 것이 최악이며, 필요한 조사·검증·재작업은 생략하지 않는다. 판단 기준은 "이 토큰을 쓰지 않으면 결과 품질이 실제로 나빠지는가?" — 아니라면 쓰지 않는다.

## 핵심 원칙

### 1. 파일 저장 → 경로 반환 (중복 전송 금지)

- **생성물은 파일에 저장 후 절대 경로만 반환** — 같은 내용을 파일과 메시지에 중복 전송하지 말 것
- 수신 에이전트는 필요 시 Read로 파일 내용 참조 (메시지 재전송 요구 금지)
- 예시:
  ```
  ❌ 나쁜 예: "검토 결과는 다음과 같습니다: [100줄 리뷰 전문]"
  ✅ 좋은 예: "검토 완료. 결과: /absolute/path/to/review-2025-07-10.md"
  ```

### 2. 필요한 만큼만 읽는다 (Read What You Need)

- 파일 전체를 습관적으로 Read하지 말고, Grep/Glob으로 위치를 먼저 찾고 **필요한 구간만** Read
- 넓은 탐색은 Explore/general-purpose 에이전트에 위임해 **결론만** 회수 (파일 덤프 회수 금지)
- 방금 수정한 파일은 재확인용으로 다시 Read하지 않는다
- **같은 기준문서/대상문서를 여러 번 원본으로 Read하게 되는 구조에서는, 매번 다시 Read하지 않는다** — 둘 중 하나에 해당하면 이 원칙을 적용한다: (1) N개 항목(에이전트/스킬 등)을 공통 기준문서에 **순회(sequential) 대조**하는 작업, (2) **병렬 다중 에이전트가 동일 대상(문서/산출물)을 각자 검토·토론·대조**하는 작업(예: reviewer 페르소나 패널이 같은 리뷰 대상을 여러 명이 각자 Read하는 경우). 전자는 호출자 자신이 반복 Read하고, 후자는 서로 다른 서브에이전트들이 같은 문서를 중복 Read한다는 점만 다를 뿐 낭비 구조는 동일하다.
  - (a) 기준문서/대상문서를 1회만 Read해 핵심을 압축본으로 스크래치패드에 저장해두고, 이후 항목별 대조(순회 케이스) 또는 각 관점의 검토(병렬 케이스)는 압축본만 참조한다.
  - (b) 서브에이전트로 위임하는 구조라면, 위임 프롬프트에 문서 발췌를 인라인으로 넣어 각 서브가 원본을 스스로 Read하지 않게 한다 — 병렬 다중 에이전트 케이스(예: 여러 페르소나가 같은 리뷰 대상을 검토)에서는 위임자가 대상 문서를 1회 Read한 뒤 각 서브 위임 프롬프트에 인라인으로 넘기는 방식이 기본이다.

### 3. 팀 구성은 일에 맞게 (Right-Size the Team)

- 단순 작업·1회성 질의·조사에 풀 파이프라인을 가동하지 않는다
- 불필요한 단계는 생략하되, **품질에 꼭 필요한 검증·리뷰 단계는 토큰을 이유로 생략하지 않는다**

### 4. 재작업 최소화 (정확한 요청 → 1회 제작)

- **첫 요청에 모든 조건/기준 포함** — 후속 요청으로 수정/재작업 반복 금지
- 모호한 요청은 즉시 정정(AskUserQuestion 또는 명확화 질문) — 잘못된 방향으로 길게 가는 것보다 시작 전 확인이 싸다
- 완성도 기준 사전 명시: "프로젝트 고유성 3가지 포함", "엣지케이스 A/B 검증" 등

### 5. 턴 예산을 통제한다 (Turn Budget) — 가장 놓치기 쉬운 낭비

토큰은 산출물 크기뿐 아니라 **대화 턴 수 × 누적 컨텍스트**로도 늘어난다. 서브에이전트가 목표 없이 탐색·자문자답을 반복하면 매 턴 전체 컨텍스트가 재과금돼 조용히 폭증한다.

- 위임 전 "몇 턴이면 끝나는가"를 어림한다 — 단순 조회·수정은 1~3턴, 설계·구현도 대체로 한 자리 턴 안에서 끝나야 정상
- 목표를 완수하면 즉시 멈추고 반환한다 ("혹시 더"식 추가 탐색·재확인·과잉 검증 반복 금지)
- 탐색은 Grep/Glob/Explore로 **병렬 1턴에 폭으로** 훑는다 — 파일을 하나씩 순차로 열며 턴을 소모하지 않는다
- 2~3턴 시도해도 막히면 같은 접근을 반복하지 말고, 막힌 지점을 요약해 되묻는다 (배회는 재작업보다 은밀한 낭비)

### 6. 서브에이전트를 감독한다 (Supervise Delegates)

호출자는 위임으로 끝이 아니라 서브에이전트의 소비를 감독할 책임이 있다.

- 위임 프롬프트에 **범위·산출물·턴 예산**을 명시해 서브가 스스로 멈출 기준을 준다 ("X를 만들면 끝. 못 찾으면 3턴 내 보고")
- 서브가 예산을 초과하거나 배회하는 조짐이면 계속 두지 말고 중단·재지시한다
- 서브의 반환은 압축을 강제한다 — 서브가 전문을 게워내면 그 자체가 턴·토큰 낭비다

### 7. 경로 명시·추적성 확보

- **모든 산출물은 절대 경로로 기록** — 상대 경로/구두 설명 금지
- malgnai-hub에 파일 경로 포함: `work_record`, `decision_record` 등
- 수신 에이전트는 경로로 파일 위치 즉시 확인 (재설명 요청 금지)

### 8. 인수 확인은 work_record 한 줄로 (품질 게이트 아님)

- 다른 에이전트의 산출물을 인수해 **실제로 사용/반영**했다면, malgnai-hub `work_record`(status: `progress` 또는 `completed`)에 "무엇을 반영했는지" 1줄만 남긴다
- 이는 품질 검증도 반려 절차도 아니다 — 발신자가 "받았는지 몰라서" 매번 방어적으로 재설명을 덧붙이는 낭비를 줄이려는 가벼운 확인 신호일 뿐
- 산출물 자체에 문제가 있으면 반려 여부는 기존처럼 수신 에이전트가 개별 판단한다 — 이 확인 절차가 반려를 대신하거나 반려를 강제하지 않는다
- 단순 참고용 Read·아직 반영 안 한 검토 중 상태는 대상이 아니다 — 실제로 사용/반영한 시점에만 남긴다

## 핸드오프 체크리스트 (1회성 협업 종료)

- [ ] 파일이 지정된 위치에 저장됨
- [ ] 경로가 절대 경로로 기록됨
- [ ] 메시지에는 경로와 핵심 3줄만 포함
- [ ] 재작업 필요 여부 사전 결정 (애매함 제거)
- [ ] 수신 에이전트가 Read 없이 경로만으로 파일 위치 파악 가능
- [ ] 산출물을 실제로 사용/반영했다면 work_record에 "무엇을 반영했는지" 1줄 확인 로그를 남김 (품질검증·반려 아님)

## 적용 체크리스트

### 협업 시작 (요청 전)

- [ ] 요청에 모든 조건/기준/산출물 형식 포함?
- [ ] 재작업 가능성 줄이기 위해 사전 정정 필요한 모호한 부분 있는가?
- [ ] 이 단계/에이전트가 결과 품질에 실제로 필요한가? (불필요하면 생략, 필요하면 유지)
- [ ] 몇 턴이면 끝나는지 어림했는가? (위임 시 서브에 턴 예산도 함께 전달)

### 산출물 생성 중

- [ ] 파일에만 저장, 메시지에는 경로만?
- [ ] 절대 경로 사용하고 상대 경로/구두 설명 없음?
- [ ] 파일 전체 대신 필요한 구간만 읽는가?
- [ ] 목표 완수 후 즉시 멈추는가? (배회·과잉 검증 없이)

### 핸드오프 시

- [ ] malgnai-hub에 파일 경로 포함해서 기록?
- [ ] 메시지 본문은 경로 + 핵심 3줄 이하?
- [ ] 수신 에이전트가 Read로 파일 참조 가능한가?
- [ ] (수신 측) 산출물을 실제로 반영했다면 work_record에 1줄 확인 로그를 남겼는가? (문제 있으면 반려는 별개 판단, 이 로그가 반려를 막지 않음)

### 후속 (재작업 최소화 · 감독)

- [ ] 첫 요청 기준으로 1회 제작이 완성도 기준 충족?
- [ ] 사소한 수정은 직접 Edit로 처리 (재작업 요청 금지)?
- [ ] (호출자) 서브에이전트가 턴 예산을 초과·배회하지 않는지 감독했는가?
