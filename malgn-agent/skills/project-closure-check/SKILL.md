# 라운드 종결 점검

## 정의

작업·검증 라운드를 **닫기 직전** 한 번 도는 절차다. "이번 라운드가 실제로 해소한 것"과 "hub에 열린 채 남아 있는 것"을 대조해, 어긋난 만큼을 닫는다.

**이 절차가 따로 있는 이유는 종결을 깜빡해서가 아니라, 조회를 잘못하면 결과가 틀리기 때문이다.** 같은 프로젝트의 WBS를 두 방식으로 물으면 한쪽은 완료 항목 전량이, 다른 쪽은 완료 0건이 돌아온다 — 단계 1이 그 갈림이다. "열린 것을 닫아라"는 지시만 알고 도구를 임의로 고르면 "닫을 것이 없다"는 그릇된 결론에 도달하고, 그 결론은 조용히 지나간다.

이슈 종결의 **원칙**(누가 닫는가 · 무엇을 근거로 닫는가 · 부분 해소를 어떻게 다루는가)은 Skill `common-learning-loop-knowledge-management` "이슈 종결(Close)"이 정본이다. 이 스킬은 그 원칙을 라운드 종결 시점에 **어떤 호출로 실행하는가**를 다룬다.

## 단계 0 — 대상 프로젝트 확정

- `projectId`는 `<cwd>/STATUS.md` 상단에서 읽는다.
- **없으면 `project_bootstrap`을 부르지 않는다** — 없는 프로젝트를 새로 만들어버린다. 사람에게 묻고, 이번 종결 점검은 "미수행 + 사유"로 보고한다.
- hub 기록·조회 도구를 쓸 수 없으면 기록 공통 폴백(Skill `common-learning-loop-knowledge-management` "기록 도구를 쓸 수 없을 때")을 따른다.

## 단계 1 — WBS 실상태 조회 (여기가 갈림길이다)

- `wbs_list(projectId, includeDone:true)`를 부른다.
- 판정은 응답의 **`summary` 블록**(`total`/`planned`/`inProgress`/`done`/`delayed`)으로 한다. items 배열을 눈으로 세지 않는다.
- **`project_get_context(sections=['wbs'])`를 이 용도로 쓰지 않는다** — 이 뷰는 `summary`가 없고 `status:"done"` 항목을 반환하지 않아, 세면 반드시 "완료 0건"이 나온다.
- `wbs_list`도 **기본값은 done 버킷을 제외한다.** `includeDone:true`를 빼면 같은 오독이 난다.
- `summary.total === 0`이면 이 프로젝트는 WBS를 쓰지 않는다 → 단계 3으로 건너뛴다(WBS 미사용 프로젝트를 미종결로 오인하지 않는다).

## 단계 2 — 이번 라운드와 겹치는 WBS 항목 선별

- 이번 라운드가 손댄 파일·주제와 겹치는 **리프** 항목을 고른다. 겹침 판정은 라운드 맥락을 가진 내가 한다 — 제목 문자열 일치로 기계적으로 고르지 않는다.
- **그룹(자식 있는) 노드는 후보에서 제외한다** — `status`를 done으로 직접 바꿀 수 없고(`STATUS_DONE_LEAF_ONLY`), 자식 롤업인 `bucket`·`computedProgress`가 진짜 신호다. `status:'planned'`인데 `bucket:'done'`·`computedProgress:100`이면 정상이지 미종결이 아니다.

## 단계 3 — 열린 이슈 조회·선별

- `project_get_context(projectId, sections=['issues'], limit=<적정값>)` — 이 도구는 **열린 이슈만** 돌려주므로 이 용도에는 맞다(단계 1과 용도가 다르다). 여기서 `issueId`도 회수된다.
- 응답에 이슈 `description` 전문이 실려 **본문이 긴 이슈가 섞이면 응답이 수 KB로 뛴다.** 열린 이슈가 많으면 `limit`을 낮춰 제목·심각도만 먼저 훑고, 후보로 좁힌 것만 본문을 본다. 이 비용은 절차 본문보다 크다.
- 주제로 넓게 훑어야 하면 `project_search_history(projectId, query, types=['issue'])`를 보조로 쓴다.
- **검증 전용 역할(reviewer 등)이 보고서에 "종결 후보"로 지목한 것을 여기서 수거한다** — 그들은 지목까지만 하므로, 수거하지 않으면 그 지목은 어디에도 도달하지 않는다.

## 단계 4 — 실물 대조 후 종결

겹치는 항목이라도 **실물로 해소를 확인한 뒤에만** 닫는다(claimed ≠ verified). 확인 수단이 없으면 닫지 말고 "확인 불가"로 보고한다.

- **WBS**: `wbs_update(projectId, id, status:'done', progress:100, completedDate:'<YYYY-MM-DD>')` — `completedDate`를 반드시 함께 적는다. 이 인자는 실제로 자주 빠지고, 빠지면 계획 대비 실제 소요를 나중에 되짚을 수 없다.
- **이슈**: `issue_resolve(projectId, issueId, result)` — `result`는 필수다. 확인 근거(파일:라인, 확인 방법)를 여기에 적는다.
- **부분 해소**: 열린 이슈를 나중에 갱신하는 도구는 없다(`issue_update` 미제공). ①`result`에 해소분·잔여분을 항목 단위로 적어 닫고 ②잔여만 `issue_record`로 다시 연다. 이때 `idempotencyKey`는 원 이슈와 구분되게 잡는다 — 같은 키를 재사용하면 새 이슈가 생기지 않는다.

## 단계 5 — 결과 보고 (침묵 금지)

닫은 것 · 남긴 것과 사유 · 확인 불가한 것을 라운드 보고에 싣는다. **닫을 것이 없으면 "없음"을 명시한다** — 점검이 실제로 돌았다는 것을 남기는 유일한 흔적이다.

## 비정상 케이스

| 케이스 | 처리 |
|---|---|
| hub 도구가 없거나 호출이 실패한다 | 단계 0의 공통 폴백. 못 남긴 사실과 내용을 반환문에 적는다 |
| `projectId`를 모른다 | `project_bootstrap` 금지. 사람에게 묻고 "미수행 + 사유" |
| WBS를 쓰지 않는 프로젝트다 | `summary.total === 0` → 단계 1·2 생략, 이슈만 점검 |
| 열린 이슈가 대량이다 | 겹치는 것만 선별. 전량 훑기는 토큰만 쓰고 오종결 위험을 키운다 |
| 그룹 노드에 `status='done'`을 시도했다 | `STATUS_DONE_LEAF_ONLY`. 재시도하지 말고 해당 리프를 닫는다 |
| 이미 닫힌 이슈에 `issue_resolve`를 불렀다 | `NOT_FOUND` 계열. 에러를 삼키지 말고 보고에 적는다 |
| 이 절차가 한 라운드에 두 번 돌았다 | 자연 멱등 — 이미 닫힌 항목은 조회 결과에 나오지 않는다 |
| 라운드가 여러 세션에 걸친다 | 이 절차는 상태를 갖지 못한다. 각 세션이 자기 라운드를 닫을 때 각각 돈다 |

## 자기 검증

- [ ] WBS 판정을 `wbs_list(includeDone:true)`의 `summary`로 했는가 — `project_get_context(sections=['wbs'])`로 대신하지 않았는가?
- [ ] 닫은 항목 전부를 실물로 확인했는가 — 라벨·주장이 아니라?
- [ ] `wbs_update`에 `completedDate`를, `issue_resolve`에 `result`를 넣었는가?
- [ ] 부분 해소를 원본 이슈에 "일부 해소"로 남기지 않고, 닫고 잔여를 새로 열었는가?
- [ ] 닫을 것이 없었다면 "없음"을 보고에 명시했는가?
