# 리뷰 페르소나 패널 표준

실제 페르소나는 프로젝트마다 다르지만(도메인·기술스택·타겟이 다르므로), 페르소나를 구성하는 **요소·운영 절차·보고 형식·산출물 게이트**는 이 스킬이 고정한다.

> **위치 규칙**
> - 프로젝트별 페르소나(인스턴스): `docs/reviewer/personas/persona-[관점].md` — reviewer가 그 자리에서 생성(자산이 있으면 재활용). `personas/` 하위폴더에 모으는 이유: `docs/reviewer/` 루트의 보고서·판정서 등 이종 산출물과 분리해 누적·재활용을 쉽게 하기 위함.
> - 리뷰 결과 보고서: `docs/reviewer/review-[대상]-[날짜].md` — reviewer가 작성 → PM 보고.
> - 재사용 페르소나 자산: `${CLAUDE_PLUGIN_ROOT}/knowledge/review/persona-*.md` — trainer가 반복·검증된 페르소나를 승격(agents/trainer.md 모드 5 참조).

## 0. 페르소나 파일 구조 — 역할개념(고정) vs 적용이력(가변)

페르소나 파일은 두 부분으로 나뉜다:
- **역할개념 (아래 6대 요소)**: 정체성·관심사·평가기준·평가방법론을 "이번 리뷰 대상 일반"에 대해 쓴다. "오늘 세 번째로 바뀐 문제라면"처럼 특정 라운드에만 해당하는 서사는 여기 넣지 않는다 — 라운드가 바뀌어도 이 부분은 그대로 재사용된다.
- **적용 이력 (파일 맨 아래, append-only)**: 재검토 라운드마다 날짜/target_id/라운드/리뷰 문서 경로 + 이번 라운드에 무엇을 특히 집중했는지 1줄만 추가한다. 6대 요소 본문은 건드리지 않는다.

이 분리가 없으면 재검토 때마다 "이번 라운드에 맞게" 정체성·관심사를 다시 쓰게 되고, 그 결과 역할개념이 같은데도 파일이 계속 새로 생긴다(회전문 페르소나 안티패턴, §7).

## 1. 페르소나의 6대 필수 요소

좋은 리뷰 페르소나는 "누가, 무엇을, 어떤 잣대로, 어떻게 보고, 어디를 참고해, 어떻게 적는가"가 모두 명확하다. 하나라도 비면 리뷰가 흐려진다.

1. **정체성 (Identity)** — 역할/직함, 배경/경험(의도적 편향 설계), 한 문장 캐릭터 요약. **구체적 서사로 박제한다**(추상적 직함보다 한 단락짜리 일화가 편향을 훨씬 날카롭게 만든다). 타겟 사용자형 페르소나는 기술 친숙도·주요 사용 기기를 명시한다.
2. **관심사 (Concerns)** — 우선순위 높은 관심사 3~5개 + 의도적으로 **무시하는 것**(스코프를 좁혀야 날카로워짐). `docs/product-principles.md`와 정렬.
3. **평가기준 (Criteria)** — 체크 가능한 형태로("함수가 한 가지 일만 하는가" O / "코드가 깔끔한가" X). 가능하면 합격선(threshold) + 기준별 중요도(필수/권장/선택).
4. **평가방법론 (Methodology)** — 리뷰 절차(전체 훑기 → 핵심 경로 정독 → 엣지케이스 추적 → 교차검증), 근거 수집 방식(파일·라인 인용), 심각도 분류 기준(§4), 확신/추정 구분.
5. **참고파일 (References)** — `docs/product-principles.md`·`docs/requirements.md`·`docs/prd.md`, 리뷰 대상, 직전 단계 산출물. **화면 리뷰**면 `docs/screenshots/` 캡처 이미지(없으면 Skill `common-screen-verification-and-capture`로 먼저 확보). 도메인 지식은 `docs/reviewer/` 또는 `knowledge/`.
6. **출력포맷 (Output Format)** — 아래 §5 표준 형식 사용, 모든 지적에 심각도·근거·개선안, 종합 판정(RAG)을 맨 위에.

## 1.5 페르소나 인덱스 (`docs/reviewer/personas/INDEX.md`)

`docs/reviewer/personas/`에 파일이 쌓일수록 파일명만으로 역할개념 중복을 판단하기 어려워진다. 새 페르소나를 작성하기 **전에 반드시** 이 인덱스를 먼저 확인한다.

| 열 | 내용 |
|---|---|
| 파일 | persona-*.md 경로 |
| 역할개념(1줄) | 라운드 서사를 뺀 핵심 질문 하나 |
| 유형 | 수렴/발산 |
| 최초 생성 | 날짜 |
| 최근 재사용 | target_id / 라운드 / 리뷰 문서 |

페르소나를 신규 작성하거나 재사용할 때마다 reviewer가 직접 이 표를 갱신한다(신규면 행 추가, 재사용이면 "최근 재사용" 갱신).

## 2. 페르소나 패널 운영 절차

리뷰어는 단일 만능 리뷰어가 아니라 서로 다른 관심사의 페르소나 **패널**을 데리고 다관점 리뷰를 진행한다. 관점 수는 복잡도에 맞춰 보통 2~4개.

1. **패널 구성** — 대상을 충분히 보려면 어떤 관점이 필요한지 결정(발산형 최소 1명 필수, §3).
2. **개별 리뷰** — 페르소나마다 자기 평가기준으로 독립 검토(한쪽이 통과시킨 것을 다른 쪽이 잡아냄).
3. **통합** — 중복 지적은 병합, **충돌하는 의견은 트레이드오프로 드러내고 권고**.
4. **보고** — 통합 보고서 1건으로 PM에 보고, "페르소나별 관점" 섹션 포함.

> 충돌은 결함이 아니라 정보다. 보안 페르소나와 UX 페르소나가 부딪히는 지점이 곧 의사결정이 필요한 지점 — 숨기지 말고 트레이드오프로 올린다.

**토큰 효율**: 2단계에서 페르소나마다 리뷰 대상 문서를 각자 Read하지 않는다 — reviewer가 대상 문서를 1회 Read해 각 페르소나 검토(서브 위임 시 위임 프롬프트)에 인라인으로 넘긴다. 근거·상세 기법은 Skill `common-token-efficient-collaboration` §2 참조.

## 3. 발산형 페르소나 — 패널에 최소 1명 필수 (생략 불가)

기존 페르소나가 전부 **"주어진 구조 안에서의 완성도"**(수렴형)만 물으면 리뷰가 버튼 크기·용어·색대비 수준으로 소소해진다. 패널 구성 단계에서 발산형을 **강제**한다.

| | 수렴형 (Convergent) | 발산형 (Divergent) |
|---|---|---|
| 묻는 것 | "이 화면을 어떻게 더 낫게 할까" | "이 화면/메뉴/흐름이 애초에 맞나, 통째로 다시 짠다면?" |
| 전형적 지적 | 버튼 크기, 용어, 색대비, 빈 상태 | IA 재편, 메뉴 통폐합, 화면 삭제/신설, 핵심 흐름 재배치 |
| 근거 방식 | 파일·라인 위반 | "백지에서 다시 그린 대안 + 왜 현재보다 나은가" |

- 정체성 예시: **"제로베이스 재설계자"**("지금 것을 지운다면 무엇부터 다시 만들까"만 묻는다) · **"파괴적 혁신가"**(카테고리 자체를 의심) · **"퍼스트 프린시플 사상가"**(사용자의 진짜 목표로 거슬러 올라감).
- 발산형은 "측정 가능 기준" 원칙을 완화하는 대신 **근거를 "대안 제시"로 강제**한다 — "이게 별로다"로 끝내지 않고 "**대신 이렇게 하면(구체적 대안 구조) 이래서 낫다**"까지 써야 유효하다. 대안 없는 막연한 부정은 안티패턴.
- 발산형 지적은 아래 §4의 **🔵 Rethink** 심각도를 부여해 출시 가능/불가 축과 별도로 항상 보고서에 노출한다.
- 통합 보고서에 **"## 구조적 제언 (Rethink) — 발산형 페르소나"** 섹션을 별도로 둔다(수렴형 표와 섞지 않는다). 패널에 발산형이 최소 1명 있으므로 이 섹션은 비어 있으면 안 되고, 없으면 "발산형 페르소나 미투입"을 정직하게 명시한다.
- **문서·설계서 리뷰에도 이 규칙은 동일하게 적용된다.** 문서 리뷰의 발산형은 화면이 아니라 "이 IA/메뉴 묶음/엔티티 모델/기능 범위가 애초에 옳은가"를 묻는다. 정합성 검증만으로 보고를 마치면 이 게이트 미통과다.

## 4. 심각도 분류 표준

| 심각도 | 표기 | 정의 | PM 조치 |
|-------|------|------|---------|
| Critical | 🔴 | 출시/통과 불가. 데이터 손실·보안 구멍·요구사항 미충족 | 즉시 재작업 지시 |
| Major | 🟠 | 품질 크게 저해. 출시 전 반드시 수정 | 수정 후 재검토 |
| Minor | 🟡 | 개선 권장. 출시는 가능 | 백로그/차기 반영 |
| Nit | ⚪ | 취향·사소함. 무시 가능 | 참고만 |
| Rethink | 🔵 | 구조적·발산형 제언(§3). 출시를 막지 않으나 다음 버전에 구조를 다시 볼 가치 | 차기 방향 결정 — 채택/보류 판단 |

종합 판정(RAG): **Green**(통과) / **Amber**(조건부 통과, Major 이하) / **Red**(불가, Critical 존재). 🔵 Rethink는 RAG에 영향을 주지 않는다 — Green이어도 Rethink 제언이 함께 올라갈 수 있다.

**기각 게이트 (통합 단계에서 진행자가 적용)**: 패널이 낸 지적을 그대로 다 올리지 않는다. 아래는 통합 보고서에서 **기각**하거나 심각도를 한 단계 내린다 — 잘못된 지적도 그대로 두면 개발 시간을 그만큼 태운다.
- 실물(파일·라인·이미지)을 열어보지 않고 파일명·구조에서 **유추**한 지적
- "X가 없다"는 부재 주장인데 **어디를 어떤 패턴으로 찾았는지**가 없는 지적
- 🔴/🟠인데 **재현 절차나 영향 경로**를 적지 못하는 지적 → 한 단계 강등
- 대상 산출물의 **스코프 밖**(이번 위임 범위가 아닌 파일·차기 단계 예정 항목)

기각한 지적은 **삭제하지 않고** 보고서의 "기각된 지적" 섹션에 사유와 함께 남긴다 — 페르소나의 관점이 실제로 반영됐는지 PM이 확인할 수 있어야 하고, 다음 차수에서 같은 지적이 근거를 갖춰 다시 올라올 수 있어야 한다.

## 2.5 다차수 재검토 (동일 target_id, 2차 이상)

동일 target_id로 짧은 기간 내 재위임되면 풀패널을 반복하지 않는다. 판정 기준(동일대상 조건·풀패널 강제승격 조건)은 Skill `common-task-grading-and-verification-depth`를 따른다. 모드는 3단계:

| 모드 | 조건 | 페르소나 |
|---|---|---|
| 최초(Full) | 최초 위임 또는 승격조건 충족 | 신규 2~4명 |
| 증분(Incremental) | 동일대상 + 새 리스크 표면 일부 추가 | 기존 전원 재사용 + 신규 표면당 최대 1명 |
| 축소(Abridged) | 동일대상 + 새 리스크 표면 없음 | 기존 전원 재사용, 신규 0명 |

## 6. 산출물 게이트 (보고 전 반드시 통과 — 생략 불가)

페르소나·화면은 **머릿속이 아니라 파일로** 존재해야 한다. 리뷰 완료를 보고하기 전에 아래를 **파일 존재로** 확인한다(공통 원칙: Skill `common-verifiable-output-and-honesty`).

- [ ] **페르소나 실체화** — "N개 페르소나로 리뷰"라고 보고할 거면, `docs/reviewer/personas/persona-*.md`가 **N개 실제로 존재**한다. 파일이 없으면 "단일 리뷰" 또는 "N개 관점(파일 미작성)"이라고 **정직하게** 적는다.
- [ ] **화면 근거** — UI/UX 리뷰면 `docs/screenshots/`에 캡처 이미지가 존재하고, 그 이미지를 Read로 봤다. 화면을 못 봤으면 "화면 미확인, 코드 기반 추정"이라고 명시한다.
- [ ] **근거 경로** — 보고서의 모든 지적에 위치(파일·라인) 또는 이미지 경로가 붙어 있다.
- [ ] **수정 추적** — 리뷰 중 수정이 일어났다면 before/after 또는 diff 근거가 남아 있다.
- [ ] **생략 명시** — 시간/도구 제약으로 빠뜨린 관점·화면이 있으면 "생략함, 사유 X"로 적는다.
- [ ] **재사용 판정 표** — 동일 target_id 재검토 건이면, 보고서에 페르소나별 "재사용/신규 + 사유" 표가 있고, "신규" 표기는 INDEX.md 대조 근거를 동반한다.

문서·설계서 리뷰에도 게이트는 동일하게 적용된다 — 화면 캡처가 없는 문서 리뷰라고 페르소나·발산형 게이트를 면제받지 않는다.

## 7. 안티패턴

- ❌ **무난한 만능 리뷰어** — "코드 품질, 보안, 성능, UX 다 봅니다" → 아무것도 날카롭게 못 봄. 관심사를 좁혀라.
- ❌ **전원 수렴형 패널** — 발산형 최소 1명으로 "구조 자체가 옳은가"를 강제하라(§3).
- ❌ **대안 없는 발산** — "메뉴가 별로다"로 끝내는 것. 발산형은 반드시 구체적 대안까지 가야 유효하다.
- ❌ **측정 불가 기준** — "좋은 코드인가" → "함수 길이 50줄 이하인가"로 바꿔라(발산형은 예외).
- ❌ **근거 없는 지적** — 파일·라인·예시 없는 주장은 신뢰를 잃는다.
- ❌ **칭찬 누락** — 잘 된 점을 안 적으면 다음 산출물의 기준이 사라진다.
- ❌ **product-principles 무시** — 프로젝트 방향성과 어긋난 리뷰는 잡음이다.
- ❌ **회전문 페르소나** — 역할개념은 동일한데(예: "운영 현실주의자", "제로베이스 도전자") 라운드마다 이름과 서사만 바꿔 새 파일을 만드는 것. INDEX.md 대조 없이 "이번 리뷰에 맞는 페르소나"를 새로 쓰고 싶어지면 먼저 §1.5 인덱스를 확인하라.
