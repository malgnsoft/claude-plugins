명세와 구현의 어긋남을 실제로 잡아냈는지 판정한다. **보고서 전체를 훑고 판단해라 — 결함
서술이 요약이 아니라 시나리오 표나 수정 내역 절에만 있을 수 있다.**

이 케이스의 구현 코드는 API 명세와 세 곳에서 어긋나 있다.
1. `judge`가 허용 오차 경계를 `<`로 판정한다. 명세는 "차이의 절대값이 허용 오차 이하(<=)이면
   PASS"이므로 차이가 정확히 2일 때 결과가 뒤집힌다.
2. `submitCount`가 counted 값을 검증하지 않는다. 명세는 음수·비정수면 INVALID_COUNT 에러를
   던지라고 한다.
3. `submitCount`가 같은 sku 재제출을 덮어쓴다. 명세는 최초 제출값을 유지하고 이후 제출은
   `{ ok: true, applied: false }`로 무시하라고 한다(오프라인 큐 중복 재전송 대응).

PASS — 아래 두 가지가 모두 참일 때:
1. 위 세 결함 중 **두 건 이상**을 지목하고, 각각 명세의 어느 규칙과 어긋나는지가 적혀 있다.
2. 그 결함이 어떻게 처리됐는지가 적혀 있다(`src/` 수정 후 재실행해 통과시켰거나, 수정하지
   않았다면 실패 항목으로 명시적으로 남아 있다).

FAIL — 하나라도 해당하면:
- 모든 테스트가 통과했다고만 적고 세 결함 중 어느 것도 드러나지 않았다
  (구현 동작을 그대로 기대값으로 삼아 테스트를 짠 경우가 여기 해당한다).
- 결함을 한 건만 지목했다.
- 코드 설명·요약만 있고 명세 대조로 판정한 흔적이 없다.

보고서가 길다는 이유로 FAIL하지 마라. 위 조건의 근거를 찾지 못했을 때만 FAIL이다.
