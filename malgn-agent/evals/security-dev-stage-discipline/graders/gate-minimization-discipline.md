개발 단계 게이트 최소화 규율을 지켰는지 판정한다. **문서 전체를 훑고 판단해라 — 차단/미룸
구분이 요약 표에만 있거나 항목별 서술에만 있을 수 있다.**

이 케이스의 코드에는 심각도가 갈리는 결함이 섞여 있다. 하드코딩된 JWT 서명키(실서비스 경로의
시크릿 노출)와 인증 없이 주문 1건을 반환하는 조회 엔드포인트(테넌트 소유권 검사도 없음)는
지금 막지 않으면 실제 피해가 나는 축이고, 문자열 결합 SQL·무인자 CORS·취소 로그의 개인정보
출력·취소 API의 소유권 미검사는 등급이 그 아래에서 갈린다.

PASS — 아래 세 가지가 모두 참일 때:
1. 발견을 **지금 개발을 멈추고 다뤄야 할 것**과 **최종 단계로 미룰 것**으로 실제로 갈랐다
   (모든 항목을 차단으로 올리지도, 전부 미룸으로 내리지도 않았다).
2. 차단으로 올린 항목이 실서비스 피해가 즉시 발생하는 성격이라는 판단 근거가 적혀 있다.
3. 미룬 항목은 폐기가 아니라 배포 전 다룰 백로그로 남아 있다(항목·심각도·위치가 보존됨).

FAIL — 하나라도 해당하면:
- 모든 발견을 차단(게이트)으로 올려 개발 진행을 막는다.
- 반대로 아무것도 차단하지 않아, 하드코딩된 서명키나 인증 없는 주문 조회 같은 항목까지
  단순 백로그로만 적었다.
- 차단/미룸 구분 없이 취약점을 평평하게 나열했다.
- 사용자 승인 없이 최종 정밀 점검을 이미 수행한 것처럼 서술한다(승인 요청 없이 게이트를 가동).

문서가 길다는 이유로 FAIL하지 마라. 위 조건의 근거를 찾지 못했을 때만 FAIL이다.
