## 토론 1: "판단 품질 일관성" 축을 추가할 가치가 있는가

### 사실관계 확인 (토론 전 증거 수집)
사용자가 지목한 3개 skill의 실제 대상 범위를 grep으로 확인했다:

| Skill | description 원문 | 메인루프(PM)가 named audience에 포함되는가 |
|---|---|---|
| `verifiable-output-and-honesty` | "...frontend-dev/qa-engineer/reviewer/ux-designer/visual-designer가 작업 결과를 보고할 때 사용." | **아니오** — 5개 서브에이전트만 명시, PM/메인세션 제외 |
| `common-beyond-mediocre-output` | "...모든 에이전트가 산출물을 작성·검토할 때 상시 참조." | **예** — "모든 에이전트"로 이미 포괄 |
| (3번, "물을지 스스로 진행할지" 판단 경계) | 별도 skill 없음. `project-orchestration` SKILL.md:141 "에스컬레이션(사용자 승인 필수): 전칭 규칙 신설, 공용 구조 변경, 기존 원칙 충돌, 에이전트 역할 변경, 되돌리기 어려운 결정"으로 이미 실질 커버 | 해당 없음 — 이미 블록 3문단의 `project-orchestration` 포인터가 간접 커버 |

또한 `agents/pm.md:141`은 `verifiable-output-and-honesty`를 **skill이 아니라 knowledge 파일**로만 인용한다 — pm.md 자신도 이걸 능동 skill-invoke 대상으로 명시하지 않는다.

**핵심 발견**: 이 저장소를 포함한 모든 세션은 SessionStart에 사용 가능한 skill 목록(이름+description)이 시스템 리마인더로 항상 주입된다(이 토론 세션 자신이 실증 사례 — 이번 태스크 시작 시 skill 목록에 `verifiable-output-and-honesty`가 description과 함께 이미 보였다). 즉 **발견성(discoverability) 문제가 아니라 적용범위 필터링(applicability filtering) 문제**다 — description이 named agent를 나열하는 방식이라, "나는 PM/메인세션이니 이건 내 것이 아니다"로 모델이 스스로 걸러낼 개연성이 있다. 이건 추정이 아니라 skill description 원문 자체가 그렇게 쓰여 있다는 grep 사실에 근거한다.

### 페르소나별 입장

**회의적 검증 설계자 — 조건부 찬성**
"약한 신호"가 아니라 **측정 가능한 증거**로 확인된 갭이다: `verifiable-output-and-honesty` description이 5개 named agent만 나열하고 PM을 뺀 것은 grep 한 줄로 재현 가능한 사실이다. 다만 `common-beyond-mediocre-output`은 스스로 "모든 에이전트"라고 이미 선언했으므로, 여기에 이 블록이 별도 포인터를 추가하는 것은 **이미 커버된 것을 중복 명시**하는 것 — 근거가 약하다. 3번(질문/진행 경계)도 project-orchastration의 기존 에스컬레이션 조항으로 실질 커버됨을 확인했으므로 신규 텍스트가 불필요하다. → **1번만 추가, 2·3번은 추가하지 않는다.**

**운영/유지보수 현실주의자 — 조건부 찬성, 드리프트 경고 추가**
`pm-orchestration-nudge.mjs`를 재확인한 결과, 마커 감지 로직(`claudeMd.includes(INSTALLED_MARKER)`)은 **이미 v1 마커가 설치된 프로젝트에서는 재설치를 트리거하지 않는다** — 즉 이 파일 내용을 지금 바꿔도, 이미 설치를 마친 다른 프로젝트들의 CLAUDE.md는 자동으로 갱신되지 않는다(수동 재설치 또는 향후 버전 마커 정책 변경이 있어야 함). 이건 이번 개정 범위 밖의 별도 이슈이지만, "내용을 고쳐도 기 설치본엔 반영 안 됨"이라는 한계는 COO에게 명시적으로 알려야 한다. 추가 자체(1번)는 찬성 — 이미 존재하는 skill을 가리키는 것뿐이라 유지보수 부담이 project-orchastration 포인터와 동종(신규 리스크 카테고리 아님).

**제로베이스 재설계자 — 발산형, 아래 Rethink 참조**
1번을 블록에 추가하는 것 자체엔 반대하지 않지만, "이 문제의 근본 원인이 정말 블록에 텍스트를 더 넣는 것으로 풀리는가"를 재검토했다. 아래 별도 섹션 참조.

### 결론
**추가한다 — 단, 3개 중 `verifiable-output-and-honesty` 1개만.** 근거:
- `common-beyond-mediocre-output`은 이미 "모든 에이전트" 자기선언으로 커버 → 추가 시 중복
- 3번(질문/진행 경계)은 이미 `project-orchestration`의 에스컬레이션 조항으로 커버 → 추가 시 중복
- `verifiable-output-and-honesty`만 실제 명시적 갭(named audience에서 PM 제외)이 grep으로 확인됨 → 추가할 가치 있음

토큰비용 대비 편차감소 효과 판단: 대상을 3개→1개로 좁혀 추가 비용을 최소화했고, 그 1개도 이미 블록에 있던 `claimed≠verified` 개념의 자연스러운 연장(전혀 새로운 개념이 아니라 "완료 인정" 규율을 "보고 방식" 규율로 한 뼘 넓히는 것)이라 개념적 부담도 낮다.

## 잘 된 점
- 사용자가 제기한 3개 후보 중 실제로 grep 근거가 있는 갭(1번)과, 이미 다른 경로로 커버된 항목(2·3번)을 구분해낸 것 — "다 넣으면 안전하다"는 손쉬운 결론을 피하고 예산 규율을 지켰다.
- 압축을 통해 신규 추가에도 불구하고 총 글자수가 직전 확정본보다 31자 줄었다(634→603) — "기능을 얹으면 예산이 늘어난다"는 자명한 트레이드오프를 정면으로 다뤄 실제로 상쇄했다.
- 재론 금지 제약 2건을 착수 전/후 두 번 코드 대조로 재확인해 암묵적 재론을 방지했다.
