01 · Process Overview

왜 다시 만들었나 — 5단계로 검증까지 마쳤다

초안 하나 던지고 끝내지 않았다 — 방법론부터 최종 검증까지, 낸 사람과 다른 사람이 다시 보는 구조를 5번 반복했다.

02 / 08
1
방법론 수립

5인 전문가 패널(아키텍처·프롬프트엔지니어링·품질검증·위임오케스트레이션·최종사용자) 초안 → 교차비평 → 통합 → 3인 적대적 검증을 거쳐 판정 기준(방법론 rubric v1.0) 확정

2
전수 감사

확정된 rubric으로 기존 산출물 119개 파일(agents 21 · skills 35 · knowledge 59 · hooks 4)을 전수 판정

3
결정 확정

감사에서 나온 결정 필요 사항 15건(D1~D15)을 전문가 토론으로 확정 — 고영향 4건은 제안 → 반박 → 최종결정 절차를 거침

4
전면 재구축

확정된 결정 기준으로 실제 파일 재작성 — 오케스트레이션 트랙 재설계, 에이전트 21개 전체 정비, 보안 스킬 재편, knowledge 정리

5
독립 재검증

재구축에 참여하지 않은 별도 팀이 112개 파일을 3라운드(전수스캔 → 적대적 재검증 → 메타검증)로 처음부터 재확인 → PASS

05 · Why Trust This

신뢰성은 선언이 아니라 반복된 재확인에서 나온다

방법론도 5인 패널 + 3인 검증, 감사도 15개 결정 배치 후 통합, 결정도 제안 → 반박 → 확정, 재구축도 편집 → 검증 → 수정 — 그리고 마지막엔 재구축에 참여하지 않은 별도 팀이 112개 파일을 처음부터 다시 스캔했다.

독립 재검증에서 실제로 찾아낸 것
  • · 결함 25건을 새로 발견해 수정 (frontend-dev.md·qa-engineer.md·reviewer.md 등에 남아있던 옛 도구 참조 포함)
  • · "수정 완료"라는 자체 보고까지 다시 의심하고 재확인하는 3라운드 절차를 거침
  • · 그 결과 미수정 2건을 추가로 확인 — 후속 감독 세션이 직접 처리 예정
  • · 최종 결론: PASS (방법론 100% 정합 확인)
