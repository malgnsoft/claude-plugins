# 맑은소프트 에이전트 개발방법론 (최종본 v1.0)

**버전**: v1.0 · **작성일**: 2026-08-07
**안내**: 이 문서는 `malgn-agent` 플러그인의 **2단계 전수분석**과 **3단계 재작성**을 착수할 때 그대로 쓰는 판정 기준(rubric)이다. 감사·재작성 세션은 새 판정 기준을 그 자리에서 발명하지 않고 이 문서의 조건→행동 규칙을 그대로 적용하며, 이견이 있으면 §10.2 절차로 개정한다.

> **지위**: A(architecture)·B(prompt-engineering)·C(quality-verification)·D(delegation-orchestration)·E(end-user-adoption) 5개 초안과 그 교차비평을 병합한 최종본. 5개 초안은 `docs/architecture/`, `docs/guides/`, `docs/agent-development-methodology-draft.md`(E), 스크래치패드(C·D)에 원형 그대로 보존하고 이 문서로 대체하지 않는다 — 개별 초안이 더 상세히 다룬 논거를 찾을 때의 1차 사료로 남긴다.
> **용도**: `malgn-agent` 플러그인(agents 21·skills 38·knowledge 54·hooks 2)의 **기존 전수 감사**와 **전체/부분 재작성** 여부를 판정하는 rubric으로 그대로 쓴다. 추상 선언이 아니라 "이 조건이면 이렇게 판단한다"는 실행 가능한 규칙만 담는다.
> **모순 해소 원칙**: 5개 초안이 서로 다른 결론을 낸 지점(등급 체계, product-principles.md 처리, learning-loop 중복, reviewer 트리거, 재작성 임계값)은 아래 각 절에 **"[병합판정]"** 표시로 최종 결정과 근거를 명시했다. 결정에 이견이 있으면 이 문서를 고치지 말고 `decision_record`(importance 4~5)로 대안을 먼저 기록한 뒤 §10 절차로 개정한다.

## 0. 목적과 적용 범위

**목적**: 이 문서는 malgn-agent의 산출물(Agent/Skill/Knowledge/Hook)을 **누가 만들든 동일한 기준으로 판정**할 수 있게 하는 rubric이다. 새로 만들 때도, 전수 감사할 때도, 재작성 여부를 정할 때도 같은 문서를 쓴다.

**적용 범위**: `malgn-agent/{agents,skills,knowledge,hooks}` 아래 산출물의 **작성 시점(authoring-time)** 표준. 다음 3개 문서와 층위가 다르며 대체하지 않는다.

| 축 | 질문 | 담당 문서 |
|---|---|---|
| 검증 깊이 축 | 일반 코드/문서 변경을 얼마나 깊게 검증할까 | `common-task-grading-and-verification-depth` |
| 산출물 품질 축 | 이 산출물이 평범함을 넘었는가 | `common-beyond-mediocre-output` |
| 오케스트레이션 축 | 누가 만들고, 누구에게 넘기고, 누가 검증하고, malgnai-hub에 언제 남기는가 | 본 문서 §8~9 |
| **작성 표준 축 (본 문서 §1~7)** | **agent/skill/knowledge/hook을 어떤 구조·문장으로 써야 LLM이 일관되게 실행하는가** | 본 문서 |

새 규칙을 어디에 쓸지 애매하면: "검증을 얼마나 깊게 할지"는 task-grading에, "산출물을 어떤 구조로 만들지"는 본 문서에 쓰고, 다른 쪽에는 "상세는 X 참조" 1줄만 남긴다(중복 서술 금지 — §10에서 이 문서 자신에게도 적용).

**중요한 구분 (혼동 시 사고로 이어짐)**: 이 방법론이 다루는 것은 malgn-agent가 **설치되는 고객 조직에서의 운영 방식**(malgnai-hub 연동, `pm.md` 오케스트레이션)이다. `claude-plugins` 저장소 **자신**의 운영 방식(malgnai-hub 연동, 이 세션 자체가 PM)과는 별개다 — §9에서 이 두 파이프라인을 표로 명확히 분리한다.

## 1. 4계층 모델 — 정의와 경계 판정 기준

### 1.1 계층 정의

| 계층 | 담는 것 | 로드 시점 | 변경 빈도 | 강제성 |
|---|---|---|---|---|
| **Agent** (`agents/*.md`) | 역할 정체성·핵심 원칙·역할 경계·산출물 계약·knowledge/skill 참조 목록 | 해당 역할 호출 시 항상 전량 로드 | 낮음(역할 자체가 바뀔 때만) | 명시 호출 |
| **Skill** (`skills/*/SKILL.md`) | "무엇을 하라/하지 마라"는 실행형 체크리스트·절차 | `description` 매칭 시 동적 로드 | 중간 | 자동 트리거 |
| **Knowledge** (`knowledge/**/*.md`) | 왜 그 규칙이 필요한가 — 배경·사고사례·트레이드오프 | 에이전트가 Read로 명시 호출할 때만 | 낮음(추가만, 거의 불변) | 참조(pull) |
| **Hook** (`hooks/*`) | 세션 생애주기 이벤트 자동 개입(컨텍스트 주입/리마인드) | SessionStart/Stop 등 **매번 무조건** | 매우 낮음 | 자동·강제 |

핵심 차이는 **로드 비용**과 **강제성**이다. Agent는 항상 전량 로드되므로 짧아야 하고, Skill은 필요할 때만 로드되므로 절차를 상세히 담아도 되며, Knowledge는 호출 전엔 전혀 로드되지 않으므로 가장 길어도 된다. Hook은 매 세션 무조건 실행되므로 토큰·시간 비용이 0에 수렴해야 한다(§6).

### 1.2 최종사용자 인지 부담 층위 (U0/U1/U2)

> 명명 주의: CLAUDE.md의 세션 부트스트랩 L0/L1/L2(문서 로드 우선순위)와는 **다른 축**이다. 혼동을 피하기 위해 이 문서에서는 **U(User-facing)0/1/2**로 표기한다.

malgn-agent는 개발자만이 아니라 기획·디자인·마케팅·재무를 포함한 **전 직원**에게 배포된다. 신규 지식을 어디에 둘지는 "비개발자가 무엇을 몰라도 되는가" 기준으로 정한다.

| 층 | 담당 | 사용자가 배워야 하는 것 | 실측 사례 |
|---|---|---|---|
| U0 자동 | `hooks/` | 없음 — 세션을 열면 이미 컨텍스트가 있다 | `sessionstart-context.mjs`(SessionStart), `stop-mcp-reminder.cjs`(Stop) |
| U1 명시 호출 | `agents/` 21종 + PM | 자기 팀 에이전트 이름 1~2개, 또는 "PM에게 말하면 알아서 위임한다"는 사실 | marketer.md: "마케팅 직원은 `marketer` 이름 하나만 알면 됨" |
| U2 심화 | `skills/`·`knowledge/` | 원칙적으로 없음 — 에이전트가 내부적으로 참조 | knowledge/README.md: "에이전트 MD가 Read로 참조" |

**배치 결정 트리 (Hook↔Skill↔Agent, A안의 훅 4조건을 Q2 노드에 내장해 통합)**:

```
Q1. 실패/오작동 시 비가역이거나 금전·대외 영향이 있는가?
    YES → 명시 호출(Agent) + 사람 승인 게이트 필수. 자동화 금지.
    NO  → Q2

Q2. 거의 모든 세션에서 100% 필요한가?
    YES → Hook 후보. 아래 4조건을 모두 통과해야 신설한다(하나라도 실패하면 Skill/Agent 원칙으로 대체):
          ① 이벤트 트리거 필연성 — SessionStart/Stop 등 특정 생애주기 시점이 아니면 의미가 없는가
          ② 무해 시 0비용 — 개입할 것이 없으면 토큰·프롬프트 오염이 정확히 0인가(코드로 확인 가능해야 함)
          ③ 강제가 아니라 주입/리마인드 — exit code로 작업을 막거나 자동으로 고치지 않는가
          ④ 모든 세션·프로젝트에 보편 타당한가(특정 프로젝트 전용이면 그 프로젝트의 매니페스트로)
    NO  → Q3

Q3. 특정 파일 패턴·작업 유형·키워드가 있을 때만 필요한가?
    YES → Skill의 description 트리거로 자동 발견되게 설계
    NO  → Q4

Q4. 사람의 취향·전문 판단·도메인 지식이 개입해야 하는가?
    YES → Agent 명시 호출(또는 PM이 대신 판단해 위임)
```

**예시 1 (Q2 4조건 적용)**: "PR 생성 전 lint를 강제로 돌리는 훅"은 조건③(강제·차단형) 위반 — 훅이 아니라 qa-engineer 스킬의 자기검증 체크리스트나 CI로 옮긴다. "매 세션 시작 시 malgnai-hub 최근 decision 3개 요약 주입"은 ①필연·③주입뿐·④보편 통과, ②(decision 없을 때 0비용인가)만 구현으로 검증 후 채택 — **조건부 정당화**.

**흔한 오판 두 가지(E안)**: (1) 비가역 동작(Q1=YES)을 Skill 자동 트리거로만 걸어두면 사람 승인 없이 절차가 진행될 위험이 있다 — 반드시 Agent 경계+게이트 문장으로 명문화한다. (2) 매 세션 100% 필요한 것(Q2=YES)을 Agent 호출로만 남겨두면 매번 사람이 이름을 불러야 한다 — Hook 승격을 재검토한다.

### 1.3 Skill/Knowledge 경계

`knowledge/common/skill-vs-knowledge-boundary.md`를 **그대로 채택**한다(신규 문서 발명 금지). 실무 판정법만 재수록:

- **문체 판정**: 이 문단에서 "왜"를 빼도 뜻이 통하면 **Skill**(체크리스트로 압축), 안 통하면 **Knowledge**.
- **링크 방향(절대)**: Skill→Knowledge 참조는 허용, **Knowledge→Skill 참조는 금지**(순환 참조 방지). 배경 설명 문서가 "따라서 X 스킬을 따르라"로 끝나면 그 지시문은 Skill로 옮기고 Knowledge엔 배경만 남긴다.
- **이관 절차(정본, 이미 8건 실행된 선례)**: ① Knowledge의 실행형 문단(체크리스트·절차)을 골라낸다 → ② Skill로 옮겨 SKILL.md 형식(frontmatter `name`+`description`)으로 재구성한다 → ③ 원 Knowledge엔 "(YYYY-MM-DD 본문은 skills/X로 이관) 배경만 남음" 스텁을 남긴다(삭제 금지, 연혁 추적성) → ④ 참조하던 모든 Agent MD 경로를 `grep -rl`로 전수 확인해 갱신한다.
- **모범 사례(감사 시 대조 기준점)**: `knowledge/common/beyond-mediocre-output.md`(신설 사유+사고사례만)와 `skills/common-beyond-mediocre-output/SKILL.md`(체크리스트만)는 중복 서술 없이 경계가 정확히 지켜진 정답 예시다. `token-efficient-collaboration` 짝도 동일하게 건강하다.

## 2. 신설 vs 확장 판단 플로우

### 2.1 새 Agent vs 기존 Agent+Skill (순서대로 적용)

1. **호출자가 다른가?** — PM 팀 구성표에서 "이 산출물의 최종 책임자"로 지목할 기존 에이전트가 없으면 신규 에이전트 후보, 있으면 Skill 후보.
2. **산출물의 성격이 다른가, 절차만 다른가?** — 다른 종류의 문서/파일을 만들면(architect의 `docs/architecture.md` vs 신규 요청의 `docs/financial-model.md`) 신규 에이전트. 같은 산출물인데 특정 상황에서 절차만 추가되면(backend-dev의 API인데 서버리스 스택이라 체크리스트 추가) 기존 에이전트+Skill.
3. **역할 경계가 이미 있는 에이전트와 겹치는가?** — 겹치면 신규 에이전트를 만들지 않고 기존 두 에이전트의 순차 위임 팀 구성으로 해결한다. **에이전트 경계는 산출물 종류로 나뉘어야지 업무 크기로 나뉘면 안 된다.**
4. **역량이 여러 에이전트에 공통으로 필요한가?** — 2개 이상 에이전트가 같은 절차를 필요로 하면 신규 에이전트가 아니라 **Skill**이다(에이전트를 늘리면 같은 절차가 N군데 중복 인라인된다).

**반례 검증**: `localizer`는 산출물(용어집 감사·번역)이 writer/marketer와 다르고 전문성 폭이 좁고 깊어 신규 에이전트가 **정당**하다. 반대로 "AI 검색 기능 전문 에이전트" 신설은 **부당**하다 — 산출물은 여전히 backend-dev의 `docs/api-spec.md`/`src/`이고 필요한 건 knowledge 참조 경로 1개뿐이다. 실제로 이 저장소는 새 에이전트 없이 backend-dev·architect MD의 "학습 자료" 절에 조건부 참조만 추가하는 방식으로 처리했다 — 이것이 올바른 선례다.

### 2.2 Skill 신설 여부 판정 트리

```
이 내용이 "무엇을 하라"인가?
├─ YES → 명령형·3~5분 분량인가?
│         ├─ YES → Skill (2개 이상 에이전트가 재사용 가능하면 우선순위 상향)
│         └─ NO  → 왜/사고사례/트레이드오프가 있는가?
│                   ├─ YES → Knowledge
│                   └─ NO  → 미완성. 다시 쓴다.
└─ NO(설명형) → Knowledge
```
프로젝트 1회성 특수 사례("A 프로젝트에서만 해당")는 Knowledge에도 넣지 않는다 — 그 프로젝트의 STATUS.md/malgnai-hub로 보낸다. 이 플러그인은 회사 전체 배포용이라 프로젝트 특수 교훈이 섞이면 이식성이 깨진다.

### 2.3 중복 판정 절차 (통합 — A/C/E 세 초안이 독립적으로 같은 절차에 수렴)

1. **기계적 1차 스캔(A)**: `grep -r <핵심 키워드>`로 기존 자산이 요구의 80% 이상을 이미 커버하는지 확인한다. 80% 이상 겹치면 신규 작성 대신 기존 자산을 확장한다.
2. **description 교집합 대조(C)**: 신규/수정 대상의 `description`을 기존 skills 38종과 나란히 놓고, "동일 트리거 문구에 반응하는 스킬이 2개 이상 되는가"를 확인한다.
3. **긍정형 배타 트리거 요구**: 교집합이 의심되면 각 description이 **"언제 이걸 여는가"를 긍정형으로, 서로 배타적으로** 진술하는지 확인한다. "이 스킬은 X와 중복되지 않는다"류 상호 해명문은 통과 근거가 아니다 — 해명이 필요하다는 것 자체가 선택 지점이 모호하다는 신호다.

   실제 선례(2026-08-24 보안 스킬 정리): `domain-backend-api-security`↔`domain-backend-security-audit`는 양쪽에 상호 해명문이 있었지만, 서로를 "먼저 참조하십시오"라고 가리켜 **항상 함께 읽히는 관계**였다 → 해명문을 다듬는 대신 한쪽을 흡수해 통합했다. 반대로 `domain-security-audit-checklist`↔`domain-serverless-edge-api-security`는 해명문끼리 서로를 지목했지만 실측 교집합이 거의 없었다 → 통합이 아니라 트리거 문구 재작성이 답이었다.

   판정 절차: ① 체크리스트 항목을 나열해 교집합을 실측한다 → ② 항상 함께 읽히면 통합, ③ 안 겹치는데 헷갈리면 이름·트리거 재작성, ④ 진짜 인접 경계면 한쪽에 권위자를 지정하고 나머지는 위임 방향만 한 줄로 적는다.
4. **확신 없으면 단정 보류(E)**: 후보 스킬의 전문을 아직 읽지 않았다면 "결함 없음"으로 단정하지 않고 "중복률 실측 필요" 상태로 감사 대기열에 남긴다. 실측 없이 유지/폐기를 확정하지 않는다.
5. **[D13 해소, 2026-08-07] 분산 병합(Distributed Merge) 절차**: 하나의 Knowledge/Skill 소스가 단일 대상이 아니라 여러 스킬에 섹션 단위로 흩어져 흡수되어야 하는 경우:
   a. 섹션 단위로 위 1~4번 절차(기계적 스캔·description 교집합·상호배제 문구·확신 없으면 단정보류)를 각 (섹션, 대상 스킬) 쌍마다 개별 적용한다 — 소스 전체를 한 번에 단일 판정하지 않는다.
   b. 대상 후보가 여러 곳(예: 스킬 A 또는 B)으로 갈릴 때는, 이미 어떤 agent MD가 특정 주제를 특정 스킬의 authoritative pointer로 명시 지정해 놓았는지(`grep -rn <주제키워드> agents/`)를 먼저 확인한다 — 기존 pointer가 있는데 그 스킬에 실제 내용이 없다면(agent-MD-drift), 새 포인터를 만들기보다 그 기존 pointer를 채우는 배치를 우선한다.
   c. 어느 대상 스킬에도 60% 미만으로만 겹치는 잔여 섹션이 남으면, 그 섹션만 따로 떼어 §2.2 신설 판정 트리를 적용한다(억지로 기존 스킬에 끼워넣지 않는다).

**1산출물-1권위자 원칙**: 같은 산출물 유형을 두 에이전트가 모두 "만들 수 있다"고 서술하면 실패로 판정한다.

### 2.4 승격/강등 기준

- **개인 스킬 → malgn-agent 편입**: 최근 **6개월** 내 **3회 이상**의 실제 참조/재사용 요청이 있었을 때만 승격 후보로 본다("앞으로 여러 프로젝트에서 쓰일 것 같다"는 주관적 예상만으로는 부족하다 — 셀 수 있는 지표가 없으면 승격하지 않고 추가로 6개월을 관찰한다). 재사용 문맥이 특정 프로젝트의 스키마·브랜드명 등에 의존하지 않아야 한다. 편입 경로: trainer 초안 이식 → evaluator/reviewer 검증 → PM 병합.
- **malgn-agent 내부 스킬 세분화(강등/재명명)**: 실제로 참조하는 에이전트 MD를 `grep -rl`로 센다 — **1개**면 그 에이전트 전용으로 재명명(무접두어), **2~4개**면 `domain-*`, **5개 이상**이면 `common-*` 유지. 이 5개는 21개 에이전트의 "과반"(11개)이 아니라 **절대 수 기준의 고정 거버넌스 임계값**이다 — "과반"이라는 표현은 쓰지 않는다. §4.2·§7.1·부록A는 이 세 구간(1개/2~4개/5개 이상)을 그대로 재사용하며, 별도의 숫자를 새로 정의하지 않는다.
- **[D9 해소, 2026-08-07] 이 절은 "유지 시 명명" 규칙이지 "유지 여부" 규칙이 아니다**: 위 참조 수 기준 재명명 규칙은 콘텐츠 자체가 §2.2(1회성 특수사례 배제)·중복판정(§1.3/§2.3)을 이미 통과한 스킬에만 적용된다 — 참조 에이전트가 1개라는 사실만으로 §2.2 위반 콘텐츠나 그 유일 참조 에이전트에 이미 완전히 인라인 중복된 콘텐츠까지 자동으로 재명명·유지 대상이 되는 것은 아니다. 그런 경우 "유지 여부"는 §2.2/중복판정이 우선 결정하고, 이 절은 유지가 확정된 이후의 명명에만 적용한다(사례: `skills/malgnai-discussion-culture` — §2.2 위반 + pm.md와 완전 중복이라는 이유로 참조 1개임에도 재명명이 아니라 retire로 판정됨).
- 이 세 구간은 서로 겹치지 않는다 — 참조 에이전트가 정확히 2개인 스킬은 항상 `domain-*`이고, 정확히 1개인 스킬은 항상 무접두어다.
- 접두어는 Claude Code 런타임 동작에 영향을 주지 않는다 — **사람이 감사할 때 쓰는 거버넌스 신호**일 뿐이다. "이름이 범용처럼 보이는데 실제로는 좁다"는 불일치 자체가 audit finding이다.

## 3. 에이전트 MD 작성 표준

### 3.1 골격 (사실상 표준, 21개 전원 준수 — 신규 구조 발명 금지)

`frontmatter(name/description[/tools])` → 핵심 원칙 → 역할 경계 → 스킬 상세(있으면) → 전제 조건 → 자기 검증 → 산출물 → 학습 자료(필수/참고 2단) → 토큰 효율.

이 골격 일관성 자체가 "직원이 어느 에이전트 MD를 열어봐도 같은 위치에서 같은 정보를 찾을 수 있다"는 발견가능성 계약이다. 신규 에이전트를 추가하거나 기존 에이전트를 수정할 때 이 골격을 깨는 것은 러닝커브 훼손으로 간주한다.

### 3.2 페르소나 필수 5요소

| 요소 | 결여 시 실패 시나리오 | 판정 질문 |
|---|---|---|
| ① 정체성 1문장 | 역할이 뒤섞여 다음 행동을 예측 불가 | 본문 첫 문장만으로 "무엇을 하는지" 한 번에 말할 수 있는가? |
| ② 호출 조건 | PM이 팀 구성 시 언제 넣을지 판단 불가 | "호출자" 줄에 트리거(누가/언제)가 구체 동사로 적혀 있는가? |
| ③ 역할 경계(한다/안한다) | 인접 에이전트와 책임이 겹쳐 위임이 왕복 | "경계" 항목이 **인접 에이전트 이름을 지목**해 그쪽 소관이라 명시했는가?(예: "구현은 backend-dev 영역, 손대지 않는다") |
| ④ 산출물 계약 | 검증 불가능한 "설명만 하고 끝" 위험 | "산출물" 섹션에 파일 경로 패턴(`docs/xxx.md`)과 필수 필드가 명시돼 있는가? |
| ⑤ 완료 정의(자기검증) | "완료" 기준이 매 세션 다르게 해석됨 | 체크리스트를 그대로 실행하면 제3자도 완료/미완료를 판정할 수 있는가(자문형 "잘 했는가?"가 아니라 검증 가능한 사실인가)? |

**판정 규칙**: 5요소 중 하나라도 없으면 "구조 미완성"으로 기록한다. 5요소가 다 있어도 ②·③이 다른 파일과 모순되면(두 에이전트가 서로 "이건 내 영역 아니다") **더 구체적으로 지목한 쪽을 정본**으로 삼는다.

### 3.2-bis [D14 해소, 2026-08-07] 판정 규칙 — Agent MD ↔ Knowledge 내용 중복

**기본값**: 절차·표·예시가 두 파일에 실질적으로 동일하게 반복되면 **Knowledge를 정본**으로 삼고 Agent MD는 압축한다(§1.1 로드비용 비대칭 근거 — Agent는 매 세션 전량 로드, Knowledge는 Read 명시 호출 시만 로드).

**예외**: 중복 섹션이 §3.1 골격의 필수 섹션(핵심원칙·역할경계·전제조건·자기검증·산출물·학습자료, 그리고 실측상 21/21 전원이 채택한 스킬 상세)에 위치하면 섹션을 완전 삭제하지 않는다(발견가능성 계약 훼손 방지) — 3~5줄 요약(또는 핵심 항목 bullet)으로 압축하고 학습 자료 섹션의 Knowledge 경로로 위임한다.

**판정 예시(pass)**: `writer.md`의 "스킬 상세"에 있는 "평범함 탈출 4대 기법"(4줄, 기법명만 나열) vs `knowledge/writing/document-writing-guide.md`의 "평범한 문서를 넘는 4가지 기법"(26줄, 배경·예시·출처 포함) — Agent=압축 요약, Knowledge=정본 상세 패턴의 모범 사례.

### 3.3 도구 권한(Tools) 부여 원칙

21개 에이전트 실측 결과 `tools:` 명시는 6개뿐(capture-strategist/finance/localizer/marketer/rfp-analyst/writer), 나머지 15개는 기본값(전체 도구)이다. 이 관측에서 도출한 원칙:

1. **기본값(미지정)은 코드/구성 변경이 본질인 역할에만 허용**한다 — architect/backend-dev/frontend-dev/devops/qa-engineer/pm/trainer/evaluator/security처럼 Edit·Write·Bash로 실제 파일을 고치는 것이 산출물 자체인 에이전트.
2. **분석·조사·집필 전용 역할은 명시적으로 좁힌다** — `Read, Grep, Glob, Write, WebFetch, WebSearch`로 제한해 프로젝트 소스를 실수로 건드리는 사고를 원천 차단한다. Edit 없이 Write만 주는 이유: 산출물이 신규 문서 생성이지 기존 코드 수정이 아니다.
3. **Bash·Edit을 예외 추가할 때는 사유가 드러나야 한다** — `localizer`(다국어 대량 치환), `rfp-analyst`(제출 서류 포맷 검사). 드러나지 않으면 감사에서 과다 권한으로 표시한다.
4. **신규 에이전트 tools 결정 절차**: (a) 산출물이 코드/구성 변경인가 → 미지정. (b) 산출물이 문서/보고서뿐인가 → 기본 세트(`Read, Grep, Glob, Write, WebFetch, WebSearch`)에서 시작. (c) 기본 세트에 없는 도구가 필요한가 → 최소한만 추가하고 핵심 원칙에 이유 1줄 기록.
5. **실행력 있는 도메인 차등 게이트**: marketer/finance는 실제로 돈을 움직이는 결정을 만든다 — 이미 "집행 승인 필요 항목 표"(marketer), "실제 투자 집행 권한 없음"(finance)을 갖고 있다. **동일한 실행력을 가진 devops(배포)·security(취약점 공개·패치)도 같은 수준의 명시적 게이트 문구가 있어야 하며, 없으면 즉시 fail**로 판정한다(감사 §7 D항목).

**예시**: writer(문서 작성)가 Bash를 가지면 "참고 자료를 찾겠다"며 빌드/배포 스크립트를 실행해 devops 영역을 침범할 수 있다 — 도구 하나가 역할 경계를 무력화한 실패 시나리오.

## 4. 스킬 작성 표준

### 4.1 description — "검색 인덱스"로 취급한다

Skill의 `description`은 사람이 읽는 소개문이 아니라 자동 매칭 엔진에 들어가는 검색 키다. **"[무엇을 하는가] — [언제 쓰는가]" 2단 구조를 표준으로 고정**한다.

**기계적 판정 기준**:
1. "~할 때 사용" 류 **트리거 절이 최소 1개** 있는가? 정의만 있고 트리거가 없으면 자동 매칭 실패 위험.
2. 트리거 절은 **사용자가 실제로 입력할 법한 표현**을 포함해야 한다("보안 검토 관련 작업 시"보다 "보안 감사해줘"에 가까운 명사/동사).
3. **중복 트리거 감사**: 같은 도메인어("보안" 등)를 공유하는 스킬이 3개 이상이면(현재 `domain-backend-api-security`/`domain-serverless-edge-api-security`/`domain-security-audit-checklist`), 각 description의 "언제 여는가"가 **하나의 축 위에서 배타적으로** 갈리는지 확인한다(이 3종은 "무엇을 보고 있는가" 축 — 라우트 한 건 / 이 스택의 코드베이스 / 프로젝트 전체 태세). 축이 없거나 두 스킬이 같은 칸에 들어가면 "트리거 충돌 후보"로 표시.
4. description 길이는 **1~3문장, 300자 내외**를 상한으로 삼는다.

### 4.2 명명 규칙 — 3단 접두어 (관측 기반)

실제 35개 스킬 접두어 분포(`common-*` 6개, `domain-*` 16개, 무접두어 13개)를 의도적 표준으로 명문화한다.

**[2026-08-07 재검증 정정]** 위 분포는 §2.4 참조 수 구간 재적용 결과다 — 재검증 감사에서 `grep -rl`로 실측한 결과 `architecture-patterns-reference`(2)·`external-research-and-citation`(2)·`compliance-matrix-template`(2)·`pre-deployment-verification-gate`(2)·`reference-benchmarking-standard`(3)·`shipley-proposal-methodology`(4)·`software-test-design-techniques`(2)·`system-design-principles`(2)·`training-scorecard-eval`(2)·`visual-design-token-system`(3)·`backend-api-implementation-patterns`(2) 11개가 참조 2~4개인데도 무접두어였다 — `domain-*`로 일괄 재명명해 위 분포에 반영했다(디렉터리·frontmatter·agents/*.md 인용 전량 갱신 완료).

| 접두어 | 적용 기준(§2.4와 동일 구간을 그대로 재사용 — 별도 기준 아님) | 배치 |
|---|---|---|
| `common-*` | **5개 이상** 에이전트 참조(21개 중 과반이라서가 아니라 §2.4의 고정 임계값 5개를 통과해서) | `skills/common-<name>/SKILL.md` |
| `domain-*` | **2~4개** 에이전트 참조 — 특정 기술 스택/보안 도메인에 묶인 경우와, 기술 스택과 무관하게 2~4개 에이전트의 협업 클러스터에 공유되는 절차를 모두 포함 | `skills/domain-<name>/SKILL.md` |
| 무접두어 | **정확히 1개** 에이전트만 참조 — 방법론/절차 1건을 캡슐화한 그 에이전트 전용 스킬 | `skills/<name>/SKILL.md` |

1개/2~4개/5개 이상 세 구간은 겹치지 않는다 — 참조 에이전트가 정확히 2개인 스킬을 "협업 클러스터라 무접두어"로 판정하지 않는다(§2.4와 동일 경계). 신설 스킬은 배치 전 이 표에 스스로를 대조해 접두어를 정한다. 실제 사용 범위보다 넓은 접두어(1개 에이전트만 쓰는데 `common-`)는 감사에서 즉시 재명명 대상이다.

**카운트 방법과 예외(전 에이전트 인프라 규칙 버킷)**: 기본 카운트는 `grep -rl <스킬명> agents/*.md` 직접 인용 수다. 단, 다수 에이전트 MD는 스킬을 경로로 명시 인용하지 않고 Skill 도구의 description 자동매칭으로 호출되므로(예: `architect.md`는 어떤 스킬도 경로로 인용하지 않는다), grep 인용수를 "전 에이전트 인프라 규칙"류(도메인 지식이 아니라 산출물 형식·의사결정 절차·학습 루프 등 에이전트 운영 방식 자체를 규정하는 스킬)에 그대로 적용하면 실제 설계 범위보다 좁게 나온다. 이런 스킬은 다음 **두 조건을 모두** 만족할 때만 예외로 인정해 grep 카운트 대신 `agents/trainer.md`의 "1순위 공통 스킬(모든 모드 필수)" 표 등재 여부로 접두어를 판정한다:

1. description이 도메인 지식이 아니라 에이전트 운영 방식(산출물 저장·의사결정 절차·품질 기준·학습 루프 등) 자체를 규정한다.
2. `agents/trainer.md`의 "1순위 공통 스킬" 표에 이미 등재되어 있다 — 스킬 자신의 description이 "전 에이전트용"이라고 주장하는 것만으로는 예외를 주장할 수 없다(자기선언 방지). 이 표에 신규 등재하는 것 자체가 §4.2 검토 대상이며, 등재만으로 접두어가 자동 승격되지 않는다 — 이후 실제 grep 인용이 쌓이면 일반 규칙으로 재평가한다.

현재 이 예외로 `common-*`를 유지하는 스킬은 4개뿐이다: `common-beyond-mediocre-output`(grep 3), `common-learning-loop-knowledge-management`(grep 1), `common-output-storage-and-path-management`(grep 1), `common-product-principles-reference`(grep 1). 나머지 2개(`common-task-grading-and-verification-depth` grep 7, `common-token-efficient-collaboration` grep 18)는 예외 없이 일반 규칙만으로 5개 이상을 충족한다. `domain-*` 접두어에는 이 예외를 적용하지 않는다(도메인 보안 스킬군의 grep 1 사례는 별도 재편 결정 사항).

### 4.3 지시문의 모호성 제거

모호성 판정은 "사람이 이해했는가"가 아니라 "이 문장만으로 서로 다른 두 세션이 동일한 행동을 하는가"로 검사한다 — LLM은 사람과 달리 재질문으로 보정하지 않고 그럴듯한 답을 확신 있게 낸다.

| 유형 | 안티패턴 예시 | 교정 원칙 |
|---|---|---|
| 정도부사 | "적절히 검증하라" | 등급·수치·체크리스트로 치환(`common-task-grading-and-verification-depth`의 5등급표가 모범) |
| 암묵 조건 | "필요하면 reviewer를 부른다" | if-then 명시. "Sensitive 등급은 reviewer 풀패널 필수, Standard는 약식" 처럼 등급→행동 매핑까지 내려간다 |
| 열린 수량어 | "여러 개", "몇 가지 이상" | 하한/상한 숫자 명시(`beyond-mediocre-output`의 "엣지케이스 5가지 이상"이 모범) |

**모범 패턴**: architect.md "설계 4대 의무"는 트레이드오프를 "선택/대안/선택 이유/포기한 것/감당 방안" 5개 슬롯으로 강제한다 — "트레이드오프를 명시하라"는 열린 지시가 아니라 채워야 할 필드 목록으로 좁힌 것이 핵심. 새 규칙은 이 패턴(열린 지시 → 슬롯 형식)을 기본값으로 삼는다.

### 4.4 Few-shot(예시) 사용 기준

**필요한 경우(3가지 중 하나)**: (a) 출력 포맷이 프로젝트 고유이거나 표준 학습 데이터에 없는 형태, (b) 동일 실수가 2회 이상 관찰된 재발 실패 패턴(1회성 사건을 바로 예시로 승격하지 않는다), (c) 판정 경계가 이분법적이고 헷갈리기 쉽다.

**개수·형식**: 최소 단위는 ❌/✅ 1쌍(`common-beyond-mediocre-output` 패턴이 표준). **1쌍이면 충분하고 3쌍 이상은 과잉**으로 판정한다 — 예시가 늘수록 한계효용이 급감하고 다음 지시문을 컨텍스트에서 밀어낸다. 예시는 그 스킬이 실제로 다루는 도메인의 구체 명사를 써야 한다.

## 6. 훅(Hook) 정당화 기준

§1.2의 배치 결정 트리 Q2 노드에 4조건이 이미 통합되어 있다. 여기서는 감사 시 점검 방법만 명시한다.

- **① 이벤트 필연성**: 그 개입이 SessionStart/Stop 같은 특정 생애주기 이벤트에서만 유효한가. 에이전트가 스스로 "지금 확인해야지"라고 판단할 수 있으면 훅이 아니다.
- **② 무해 시 0비용**: `sessionstart-context.mjs`는 STATUS.md도 드리프트도 없으면 빈 문자열을 반환하고, `stop-mcp-reminder.cjs`는 기록할 실질 작업이 없으면(Read/Grep만 썼으면) 리마인더를 건너뛴다 — "혹시 몰라서 매번 경고"는 기준 미달이며, 감사 시 코드로 직접 실행해 확인한다.
- **③ 강제가 아니라 주입/리마인드**: 훅이 작업을 막거나(exit code 차단) 자동으로 무언가를 고치면 안 된다 — 되돌리기 어려운 부작용의 책임 소재가 불분명해진다. 차단이 필요한 정책은 CI/서버 측 검증으로 옮긴다.
- **④ 보편 타당성**: 특정 프로젝트/에이전트에만 의미 있는 로직은 훅이 아니라 그 프로젝트의 `.claude/doc-drift.json` 매니페스트나 해당 에이전트 원칙으로 넣는다.

경로는 `hooks/<event>-<purpose>.mjs|cjs`, `hooks/hooks.json`에 `${CLAUDE_PLUGIN_ROOT}` 상대경로로만 등록한다(개인 절대경로 금지).

## 7. 품질 게이트 — 등급별 검증 강도와 reviewer 필수조건

### 7.1 [병합판정] 등급 체계는 기존 5단계 하나만 쓴다 — 5단계 전원에 판정 절차를 정의한다

C안은 문서형 산출물에 5단계(Micro/Standard/Sensitive/Exploration/Refactor)가 안 맞는다며 별도 3단계(trivial/standard/sensitive)를 신설했고, D안은 같은 대상에 기존 5단계를 그대로 재사용했다. **두 라벨을 동시에 쓰면 "Standard인데 sensitive"처럼 표기가 꼬인다.**

**최종 결정**: `common-task-grading-and-verification-depth`의 5단계(Micro/Standard/Sensitive/Exploration/Refactor)를 **유일한 표기**로 유지한다. 이 스킬의 5등급 판정표(빠른 판단 포함)가 **정본**이며, 이 절은 그 정본을 malgn-agent 산출물 개발·감사 맥락에 적용하는 방법만 정의한다(정본 표를 재복사하지 않는다 — §10.1 중복 서술 금지 원칙).

**5단계는 하나의 표에서 동시에 산출되지 않는다** — "지금 하는 일이 무엇인가"에 따라 먼저 갈래를 타고, Micro/Standard/Sensitive 3개만 아래 Reach×Reversibility 보조 절차로 판정한다. Exploration과 Refactor는 이 보조 절차를 쓰지 않고 별도 조건으로 직접 판정한다.

```
Q1. 아직 파일을 고치지 않고 조사·판정만 하는가(전수 감사 채점 §9.6, 중복 스캔 §2.3, §9.7 판정 자체)?
    YES → Exploration. 정본 표 그대로: 위임(시간·산출물 제한) + 결론 검증만, reviewer 풀패널 불필요.
    NO  → Q2
Q2. §9.7 판정 결과 "해당 파일만 재작성" 또는 "트랙 전체 재작성"으로 이미 확정됐는가
     (= 기능·역할 변화 없이 구조·서술만 다시 쓰는 작업인가)?
    YES → Refactor. 정본 표 그대로: 풀패널 필수 + 변경 전후 기준(재작성 전 결함 목록) 선행.
    NO  → Q3(아래 표)로 Micro/Standard/Sensitive 중 하나를 정한다.
```

**Q3 — Reach×Reversibility 판정표(Micro/Standard/Sensitive 전용, malgn-agent 산출물 개발 한정 보조 절차)**:

| Reach(확산범위, `grep -rl`로 셈) × Reversibility(되돌리기비용) | 등급 |
|---|---|
| Local(0개 참조 — 이 파일 외 아무도 참조하지 않음) × Cheap(git revert로 완전 원복) | **Micro** |
| Local × Costly, 또는 Shared(1~4개 참조) × Cheap | **Standard** |
| Shared × Costly, 또는 Universal(5개 이상 참조, 또는 hooks/plugin.json/marketplace.json/CLAUDE.md 부트스트랩처럼 전 세션 무조건 로드) × (Cheap/Costly) | **Sensitive** |

Reach의 세 구간(Local=0개/Shared=1~4개/Universal=5개 이상)은 **§2.4 강등/재명명 기준의 참조 수 구간을 그대로 재사용**한다 — 이 절에서 별도 숫자를 새로 정의하지 않는다. 이렇게 하면 "이 스킬은 domain-* 감이다(참조 2~4개)"라는 §2.4 판정과 "이 스킬 변경은 Standard다(Shared×...)"라는 이 절의 판정이 항상 같은 `grep -rl` 결과 하나에서 함께 나온다.

**판정 규칙(Q3 이후)**:
- `grep -rl`했을 때 다른 agents/skills/knowledge 파일이 걸리면 최소 Shared → 최소 Standard.
- **[등급 무관 고정 규칙]** `hooks/`, `plugin.json`, `marketplace.json`, `CLAUDE.md` 부트스트랩 절, 에이전트의 **"역할 경계"·"위임 모델" 절 변경**은 위 표의 결과와 무관하게 **즉시 Sensitive로 고정**한다. 이렇게 하면 C안의 "역할경계 변경은 파일 유형 기준으로 항상 풀패널"과 D안의 "등급 기준" 트리거가 자동으로 일치한다 — Standard로 잘못 낮게 판정될 여지 자체를 없앤다.
  - **[D1 정정] 이 고정 규칙과 §9.7 "국소 패치" 행의 상충 해소**: `COO`/개인 페르소나 잔존은 실제로 "## 역할 경계" 섹션의 "호출"·"경계"·"에스컬레이션" 필드 안에 존재하는 경우가 대부분이다(21개 에이전트 실측 확인). 이 경우 §9.7 행1("A위반은 grep 1회로 국소패치·Standard")과 이 고정 규칙("역할경계 절 변경은 무조건 Sensitive")이 동일 대상에 상충 판정을 내린다. **이 고정 규칙이 §9.7의 "국소 패치(Standard)" 판정보다 항상 우선한다**: 편집이 grep 1회로 전량 특정·치환 가능한 국소패치 규모라도, 그 편집이 "역할 경계"·"위임 모델" 절 내부를 건드리면 §9.7 표의 국소패치 행이 아니라 이 고정 규칙이 적용되어 등급은 Sensitive다. 판정 기준은 **파일 경로(위치)**이지 문구의 무게가 아니다 — "단순 호칭 치환인지 정책 문장 변경인지"로 다시 나누지 않는다(D1 결정).
  - **[D2 정정, 2026-08-07] 위 D1 규칙을 §9.7 30% 카테고리 임계값에 대입한 결과**: 위치 기준(D1)을 적용하면, agents 21개 중 "## 역할 경계" 섹션(호출/경계/에스컬레이션 필드)에 `COO` 잔존이 있는 파일은 실측 20개(pm.md 제외 전원, 감사보고서 §6 D2 및 이 세션 grep 실측 일치) — 이는 이미 **30%(7/21) 임계값을 20/21≈95%로 크게 초과**한다. 따라서 §9.7 "카테고리 내 30% 이상" 조건은 agents 카테고리에서 **실제로 발동**한다(잠정권고 "미발동"을 기각). agents 카테고리는 §9.7 트랙 전체 재작성(Refactor·카테고리 단위) 대상으로 즉시 승격하며, architect 대안설계 선행 + reviewer 풀패널 2회(착수/완료) 절차를 따른다. 단, 순수 명칭 치환만으로 위임 로직이 그대로 보존되는 절대다수 사례이므로, 재작성은 "COO를 지우고 새로 설계"가 아니라 **"호출자를 pm.md로 정정 + 승인권한·소관 서술이 실제 pm.md 위임모델과 여전히 합치하는지 파일별 1회 대조"** 범위로 한정한다(architect 대안설계는 이 대조 기준표 수립에 한정, 전면 재설계 아님) — 그렇지 않으면 재작성 비용이 실제 결함 규모(대부분 표기)를 과도하게 초과한다.
- 애매하면 무거운 쪽(Sensitive)으로 기운다.
- 등급은 **PM(위임자)이 위임 전 1회 판정**하고 위임 프롬프트에 명시한다(수신 에이전트의 임의 추정 금지).
- 표기 없을 때 기본값은 **Standard**(안전측 기본값, 정본 표와 동일).
- "오타·문구 수정"이라도 그 문구가 행동 규칙 문장("~하지 않는다", "반드시 ~한다")이면 Micro가 아니라 최소 Standard다.
- Exploration 조사 중 "이 파일을 고쳐야 한다"는 결론이 나오면, 그 순간부터는 Q2/Q3로 다시 넘어가 별도 등급을 매긴다 — 조사에 쓴 등급이 그대로 수정 작업의 등급이 되지 않는다.

### 7.3 reviewer 풀패널 — 필수 트리거, 적용 단위, 전용 페르소나

**필수 트리거(하나라도 해당하면 생략 불가)**: ① 등급이 Sensitive 또는 Refactor(§7.1에 의해 Refactor는 항상 풀패널 대상). ② `common-*` 6종 중 하나를 수정한다(전 에이전트가 상시 참조하므로 결함이 즉시 전사 확산). ③ 신규 에이전트 21종 초과 추가, 또는 기존 에이전트 "역할 경계"·"위임 모델" 절 변경(§7.1에 의해 자동으로 Sensitive와 일치). ④ hooks 로직 변경(매 세션 자동 실행). ⑤ "전수 감사" 또는 "전체 재작성" 결론 자체.

**적용 단위(파일당 vs 배치/트랙당) — 실행 비용을 최소 10배 좌우하는 결정이므로 명시한다**: 위 트리거에 해당하더라도, 실제로 몇 번 풀패널을 도는지는 §9.7의 판정 결과(국소 패치/파일 단위 재작성/트랙 전체 재작성)에 따라 다음과 같이 고정한다 — 담당자가 임의로 단위를 넓히거나 좁히지 않는다.

| §9.7 판정 | 적용 단위 |
|---|---|
| 국소 패치(Standard) | **배치 전체 1회** — grep 1회로 특정되는 동일 유형 결함을 여러 파일에 일괄 치환하는 경우, 파일마다 반복하지 않는다. 예: 38개 스킬 전체의 malgnai-mcp→malgnai-hub 도구명 일괄 치환은 치환 배치 전체에 약식 검증 1회. |
| **역할 경계·위임 모델 절 내부 치환**(§7.1 고정 규칙, grep 1회로 특정 가능한 국소패치 규모라도 등급=Sensitive) | **파일당 1회, 풀패널이되 체크리스트형으로 경량화** — §7.1 고정 규칙이 §9.7의 국소패치 행보다 우선하므로 배치 1회로 낮추지 않는다(예: 21개 에이전트의 "호출자: COO"→"호출자: pm.md" 치환은 각 파일의 역할경계 절에 그 이상의 위임범위·승인주체·에스컬레이션 대상 서술이 딸려 있는지를 파일마다 개별 확인해야 하므로 파일당 1회). 단, 매 파일 동일한 심사 기준(아래 체크리스트)을 재사용해 세션당 소요를 최소화한다: ①치환 후에도 승인/실행/에스컬레이션 권한 서술이 실제 오케스트레이터(pm.md)의 실제 권한 범위와 일치하는가(예: security.md의 "COO 위임 정책(medium 이하 직접결정)"처럼 이전 COO 전용 권한 문구가 남아있지 않은가) ②호출 시점·조건 서술이 pm.md 기준으로도 여전히 유효한가. |
| 해당 파일만 재작성(Refactor, 파일 단위) | **파일당 1회** — 각 파일의 구조 자체가 독립적으로 다시 설계되므로 배치로 묶지 않는다. |
| 트랙 전체 재작성(Refactor, 트랙 단위) | **트랙당 총 2회** — 착수 시 대안 설계(architect 참여)에 1회, 트랙 완료 시 최종 통합 검수에 1회. 트랙 내부 개별 파일 재작성마다 반복하지 않는다. |
| 방법론 자체 개정(§10.2) | **개정 건당 1회** |

국소 패치인지 파일 단위 재작성인지 판단이 갈리면, evaluator가 §9.7 절차로 먼저 등급을 정하고 나서 이 표를 적용한다 — 검증을 생략하기 위해 임의로 배치 단위를 넓히지 않는다. **역할 경계·위임 모델 절 치환은 이 판단 자체를 거치지 않는다** — 위치(그 절 내부인지)만으로 즉시 "역할 경계·위임 모델 절 내부 치환" 행으로 확정한다(§7.1).

**[D1 결정, 근거]** `agents/*.md`를 실사하면 "역할 경계" 절의 COO 표기는 대부분 순수 호칭이 아니라 승인·실행·에스컬레이션 권한 서술과 얽혀 있다 — 예: `security.md`("COO 위임 정책(medium 이하 직접결정)의 예외"), `reviewer.md`("실제 실행은 COO(또는 COO가 위임한 실행 주체)만"), `evaluator.md`("승격 대상 선정은 COO 소관" / "COO가 별도 채널로 승인 여부 판단"), `trainer.md`("승격 실행·최종 기록은 각각 evaluator·COO" / "COO 판정에 올린다"), `researcher.md`("최종 전략 결정은 COO/사용자"), `marketer.md`("사람 승인 후 COO/담당자가 집행"), `frontend-dev.md`("COO 승인 없이는 편집하지 않습니다"). devops.md·security.md만 예외적으로 정책이 얽혀 있다는 감사자의 잠정 권고(2트랙 분리)는 실제 파일 분포와 맞지 않아 채택하지 않는다 — "단순 호칭 치환"과 "정책 포함"을 줄 단위로 구분하는 것 자체가 코더가 매번 판단해야 하는 모호한 기준(§4.3 위반)이 되므로, 파일 경로(역할 경계/위임 모델 절 내부 여부) 하나로 판정하는 밝은 선(bright-line) 규칙을 유지한다.

**이 저장소 전용 페르소나 4종(발산형 1명 필수 규칙과 결합)**:
- **이식성 심사관(수렴형)** — 개인 경로·개인 페르소나·특정 프로젝트 전용 가정이 남아 있는가만 본다.
- **신입 직원(수렴형)** — 배경지식 0에서 이 MD/스킬만 읽고 실제로 작업을 수행할 수 있는가(암묵 지식·미정의 약어 검출).
- **경쟁 스킬 조사관(수렴형)** — 기존 38개 스킬/54개 지식과 내용이 겹치거나 모순되는가(§2.3과 연결).
- **제로베이스 재설계자(발산형, 필수)** — 이 에이전트/스킬이 애초에 이 형태로 존재해야 하는가, 다른 자산에 흡수·삭제되는 게 낫지 않은가를 구체적 대안 구조와 함께 제시.

### 7.4 회귀 점검 — 충돌·중복 탐지 절차 (Standard 이상)

1. **역참조 스캔**: `grep -rl "<변경 대상>" malgn-agent/agents malgn-agent/skills malgn-agent/knowledge` — 변경 전 이 파일을 가리키던 모든 문서를 목록화하고 변경 후에도 인용이 유효한지 하나씩 대조한다. "표본 몇 개만 고치고 완료로 보고"를 구조적으로 차단한다.
2. **중복 판정**: §2.3 절차를 그대로 적용.
3. **모순 판정**: 새 문구가 기존 `common-*`/`pm.md` 원칙과 반대 방향을 가리키지 않는가. 모순이면 어느 쪽이 최신/상위 규칙인지 decision으로 명시하고 하위 문서를 갱신한다.
4. **경로 실재 대조**: 문서 내 모든 파일 경로 참조를 `ls`/`test -f`로 실재 확인한다. 존재하지 않는 도구/문서를 인용할 경우 "번들 안 됨" 각주를 반드시 붙인다 — 각주 없이 기정사실처럼 인용하면 **Sensitive 결함**으로 취급한다.
5. **doc-drift 대조**: 구조 서술(개수·폴더)을 바꿨다면 `.claude/doc-drift.json`과 `CLAUDE.md`를 함께 갱신하고 `pnpm run check-docs`를 실행한다.

### 7.5 실사용 시나리오 테스트

"읽었을 때 그럴듯하다"는 검증이 아니다. **Standard**: 대표 요청 문장 1개로 실제 트리거 여부·산출물 형식을 1회 실행 검증(시뮬레이션 서술 금지, 실제 도구 실호출). **Sensitive**: (1) 정상 경로 재현 — 실제 서브에이전트 호출로 의도한 형식·내용이 나오는지 실물 대조, (2) 오용/경계 경로 재현 — 판정이 애매한 경계 사례를 던져 문서가 모호함 없이 행동을 결정짓는지 확인(실패하면 sensitive 통과 기준 미충족). **전역 승격급 산출물**: 실사용 인터뷰 1회 추가 — 최소 1개 실제 참조 에이전트를 호출해 "이 변경 이후 실사용에 문제가 없는가"를 직접 확인한다.

### 7.6 도구 공백을 전제로 게이트를 설계한다

`evaluator.md`/`trainer.md`는 `promote-agent.mjs`/`promote-skill.mjs`/`promote-knowledge.mjs`/`bin/record-eval.mjs`를 필수 절차처럼 인용하지만 이 도구들은 malgn-agent에 번들되어 있지 **않다**(STATUS.md 열린 이슈 `929edddc`). 즉 이 두 핵심 에이전트 MD 자체가 이미 §7.4의 "경로 실재 대조" 게이트를 통과하지 못하는 상태다.

이 방법론은 이 공백을 "도구를 만들면 해결"로 미루지 않는다 — §7.2의 게이트 표는 스크립트 실행이 아니라 grep/ls/diff와 사람(evaluator/reviewer)의 판정만으로 완결되도록 설계했다. **판정 규칙**: 에이전트/스킬 MD가 실재하지 않는 스크립트·문서 경로를 당연히 있는 것처럼 서술하면, 파일 개수·최신성과 무관하게 Sensitive 결함(실행 불가능한 지시)으로 채점한다. `evaluator.md`/`trainer.md`는 이 rubric으로 재감사할 최우선 후보로 지정한다.

**[§9.7과 즉시 연동]** evaluator.md·trainer.md **둘 다** 이 절 기준으로 §7.4 "경로 실재 대조" 게이트를 통과하지 못한다고 이미 자인했다 — 이는 §9.7 "핵심 3종(pm/evaluator/trainer) 중 2개 이상 실행 불가 지시" 조건을 이 문서 채택 시점에 **이미 충족**시킨다. §9.8에서 "재확인 필요"로 격하하지 않고 즉시 착수 대상 1순위로 등록한다(상세 근거·범위는 §9.7·§9.8).

## 8. 위임/오케스트레이션 원칙

### 8.1 PM 직접처리 vs 위임

Micro만 PM 직접 처리, 나머지는 반드시 위임한다(속도가 빠르다는 이유로 등급을 무시하지 않는다 — 이 방법론 병합 작업 자체도 이 규칙의 적용 대상이었다). 에이전트/스킬/knowledge 신설·수정은 Standard~Sensitive → 반드시 trainer→evaluator→reviewer 체인, PM이 직접 재작성하지 않는다.

**위임 실패 시 종료 경로(3택, "PM이 결국 직접 고쳤다" 금지)**: 위임이 **완전 반려 후 재위임 기준으로 2회** 실패하면(사소한 보정 질문·부분 수정 요청은 재시도 횟수에 포함하지 않는다 — 전체 산출물을 반려하고 다시 맡긴 경우만 카운트) PM은 3번째 시도를 직접 수행하지 않고 (a) 담당 교체, (b) 더 작은 슬라이스로 재분해, (c) 사람 에스컬레이션 중 하나를 택한다.

### 8.2 에이전트 역할 중복 방지

21/21 에이전트 전원이 `## 역할 경계` 섹션을 보유하고 "이 에이전트는 X를 하지 않는다"는 네거티브 스코프 + 인접 에이전트명을 명시하는 관습이 이미 있다(예: rfp-analyst.md "제안서 집필(writer), 전략(capture-strategist), 리뷰(reviewer)는 담당하지 않습니다"). **이 관습을 신규/개정 전 항목에 강제한다** — 판정 절차는 §2.3과 동일(교집합 탐지 → 네거티브 스코프 확인 → 미비 시 재작성).

**pm.md 자체 비대화 판정**: `pm.md`가 개별 사고 1건에서 나온 lesson을 원칙처럼 인라인 나열하는 부분은, 문장 단위로 "일반 원칙"과 "1회성 사고 교훈"을 분류한다 — 일반 원칙은 사고 서술을 뺀 규칙 문장으로 압축하고, 사례성 서술은 knowledge/leadership로 이관하며 pm.md엔 규칙 1줄+참조만 남긴다(§10의 정량 기준과 동일).

### 8.3 위임 컨텍스트 전달 표준 — "위임 패킷" 8항목

Standard 이상 위임 시 다음 8항목이 모두 있어야 "완전한 위임"이다. 하나라도 빠지면 "불완전한 위임"으로 간주한다.

① 작업 등급 ② 범위(포함/제외)+금지 목록 ③ 입력 산출물 절대경로 ④ 산출물 형식+저장 경로(파일명 규칙) ⑤ 완료 기준(Definition of Done) ⑥ 턴/토큰 예산 ⑦ 선례 참조(decision/issue id) ⑧ 검증 방식 지정(reviewer 필요 여부·등급)

각 항목은 실제 실패 사례와 대응한다: 등급 누락→검증 깊이 임의추정, 금지목록 누락→거버넌스 파일 임의확장, 완료기준 애매→오판정. **공식 흡수**: 신규 스킬을 만들지 않고 `common-token-efficient-collaboration`의 "핸드오프 체크리스트" 절에 흡수한다(Standard 등급 편집, trainer 위임+reviewer 약식 검증).

### 8.4 서브에이전트 결과 통합·검증 책임

검증 책임은 항상 PM. "완료" 보고는 claimed일 뿐 verified가 아니다.

**실물 대조 필수 조건(하나라도 해당하면 텍스트 보고만으로 완료 처리 금지)**: 다수 대상 일괄 위임(각각 개별 확인), Write 전체 재작성(git diff 처음/끝 대조), 재배치 작업(역참조까지 `grep -rl` 확인), 공식·대외 배포 산출물(직접 렌더링 확인).

**재작업 상한**: 검증→문제→재지시+재검증 최대 2회 → 초과 시 §8.1의 종료 경로 적용, PM이 대신 완성하지 않는다. 미검증 항목은 "미검증+사유"로 정직 보고한다(`verifiable-output-and-honesty` 원칙).

**등급별 reviewer 투입**: Standard=약식, Sensitive·Refactor=풀패널 필수(일정 압박으로 낮추지 않음), 전역 자산 승격 실행은 PM이 아니라 evaluator.

### 8.5 실패 유형 4종 → 기록 매핑

| 실패 유형 | 예시 | 기록 대상 | 학습 자산화 |
|---|---|---|---|
| (a) 산출물 품질 미달 | 근거 없는 수치, happy-path만 서술 | `activity_log`/`work_record` | `common-beyond-mediocre-output` 보강 후보 |
| (b) 팀 구성/위임 오류 | 불필요한 풀파이프라인 가동, 등급 오판 | `decision_add`/`decision_record`(importance 재판정) | `common-task-grading-and-verification-depth` 보강 후보 |
| (c) 도구/경로 오류 | 존재하지 않는 파일 참조, 개인 절대경로 잔존 | `issue_add`/`issue_record` → 해결 후 resolve | 감사 rubric §9.6 A/G 항목으로 흡수 |

## 9. 회사 배포 특수요건 — 이식성·malgnai-hub 연동

### 9.1 malgnai-mcp(이 저장소 자신) vs malgnai-hub(배포 제품) — 절대 혼동 금지

| | malgnai-mcp | malgnai-hub |
|---|---|---|
| 누가 쓰나 | `claude-plugins` 저장소 세션 자신(로컬) | malgn-agent가 설치된 고객 조직의 모든 세션(원격) |
| 도구명 | `decision_add`/`issue_add`/`activity_log`/`lesson_add`/`memory_add` | `decision_record`/`issue_record`/`work_record`/`wbs_*`/`project_bootstrap` |
| lesson 파이프라인 | 있음(`lesson_add`/`lesson_list`/`lesson_classify`) | **없음** — pm.md는 이미 이 공백을 "해당 없음"으로 명시 처리(52·206·253행) |
| 승인 큐 | `command_add` | 없음 — `AskUserQuestion`으로 대체 |

**[9.1의 판정 기준, D §6 판정기준8]** malgnai-hub 도구를 인용할 때 실제로 존재하는 도구인지 확인한다. 로컬 malgnai-mcp 전용 도구(`decision_add`/`issue_add`/`activity_log`/`lesson_*`/`memory_add`)를 제품 문서(malgn-agent)에 잘못 베끼지 않는다. `lesson_*`/`memory_add`/`command_add` 등 malgnai-hub에 없는 기능은 우회 도구를 발명하지 않고 pm.md가 이미 취한 방식(교훈은 decision/work record에 녹여 기록, 승인은 AskUserQuestion)을 표준으로 삼는다.

### 9.2 malgnai-hub 연동이 언제 필수인가

| 도구 | 필수 조건 |
|---|---|
| `wbs_add`/`wbs_bulk_add` | Standard 이상 다단계 작업 착수 즉시 |
| `wbs_update` | 단계 완료·상태 변경 시마다 |
| `decision_record` | 대안이 존재하는 갈림길, 특히 아키텍처·정책·역할 변경급 |
| `issue_record`/`issue_resolve` | 장애물·실패 발견 즉시/해결 즉시 |
| `work_record` | Standard 이상 위임의 진행/완료 |

`importance`는 습관적으로 3을 쓰지 않는다: 4~5=아키텍처/정책/역할 변경, 2~3=일반 구현 결정, 1=사소. 조회 정렬이 importance DESC이므로 값이 한쪽에 쏠리면 과거 중요 결정이 밀려난다 — 분포가 한 값에 90%+ 쏠리면 판정 습관 재교육 대상.

### 9.3 [최우선 감사 항목, E §6-F를 정본 채택] malgnai-hub 어댑테이션 정합

**fail 조건**: malgnai-mcp 전용 도구명(`decision_add`, `issue_add`, `activity_log`, `lesson_add`, `memory_add` 등 malgnai-mcp 버전 시그니처 — malgnai-hub 쪽 이름인 `decision_record`/`issue_record`/`work_record`(§9.1 표)와 혼동하지 말 것)이 malgnai-hub 연동판 문서(agents/skills/knowledge)에 "해당 없음" 처리 없이 그대로 호출 예시로 남아있음. `pm.md`는 이미 명시적으로 처리했으나(52·63·206·253행) **skills 38개+knowledge 54개 전체는 미검증** — 감사 대기열 최우선순위로 지정한다. 특히 `common-token-efficient-collaboration`과 `common-output-storage-and-path-management`는 malgnai-mcp 시절 도구명·개인 경로 관례를 그대로 쓰고 있을 가능성이 지목되었으므로(§9.5 표 참조) 우선 확인 대상이다.

### 9.4 이식성(Portability) 판정

**fail 조건**: `grep -rn "/Users/" <파일>` 또는 개인 브랜딩(특정 개인 페르소나 이름) 잔존. **확인 방법**: `grep -rl` 전수 스캔(표본 아닌 전체). 이 판정은 §7.3의 "이식성 심사관" 페르소나와 §9.5 감사 체크리스트 A항목에서 재사용한다.

### 9.5 [1-2 해소] `common-product-principles-reference` 처리 순서

C안은 `docs/product-principles.md`가 없다는 사실을 "전제 조건 미충족"으로 보고 파일 신설을 권고했고, D·E안은 스킬 본문에 "제품 프로젝트가 아니면 적용 대상 아님"이라는 조건부 생략 문구 추가를 권고했다. 두 방향은 양립 가능하지만 순서가 다르다.

**최종 결정**: **D·E의 조건부 생략 문구 추가를 필수 최소 조치로 먼저 실행**한다(Standard 편집) — 코드 프로젝트가 아닌 요청(마케팅 단독 리포트 등)에서 존재하지 않는 파일을 찾다가 멈추는 마찰을 즉시 제거하기 때문이다. `docs/product-principles.md` 신설(C안)은 그 다음의 **선택적 확장**으로 격하한다 — 이 저장소 자체의 원칙 문서가 필요하다고 판단되면 그때 별도 위임한다.

### 9.6 전수 감사 rubric (A~G, 파일 단위 pass/fail)

| 항목 | fail 조건 | 확인 방법 |
|---|---|---|
| A. 이식성 | 개인 경로/개인 브랜딩 잔존 | `grep -rl "/Users/\|~/.claude" <전체>` |
| B. 골격 일관성 | §3.1 순서 이탈, 또는 description이 호출 시점을 명시 안 함 | 육안 대조 |

### 9.7 [1-5 해소] "전체 재작성" 임계값

C안은 "전체 파일 모집단의 30%"를, E안은 "카테고리 내 30%"(분모가 다름)를 제시했다 — 같은 감사 데이터로 다른 결론이 날 수 있다.

**최종 결정**: 둘을 **OR**로 합친다.

| 판정 | 등급(§7.1) | 조건 | 처리 |

## 10. 개정 프로세스

### 10.1 이 문서 자체의 비대화 방지 (자기지시 규칙)

이 문서도 아래 정량 기준의 적용 대상이다. 새로운 반례·판정 규칙이 확정되면 **표의 행으로만 추가**한다(산문 단락을 덧붙이지 않는다).

- "핵심 원칙"류 섹션이 비협상 규칙 7개를 넘으면 초과분은 하위 절이나 별도 knowledge로 뺀다.
- 규칙 1개는 1~2문장을 넘지 않는다. "왜"(배경)가 들어 있으면 knowledge로 분리하고 규칙 문장에는 결론만 남긴다.
- lesson/사건 인용은 규칙당 최대 1개, 그것도 괄호 안 1줄 각주로만(§8.6 표처럼 사건 서사는 표로만 압축).
- 예외의 예외가 2단 이상 중첩되면 산문 대신 조건→행동 표로 재작성한다.
- 같은 규칙 문장이 3개 이상의 agents/*.md에 원문 복붙돼 있으면 공용 skill로 승격하고 각 md에는 "Skill X 참조" 1줄만 남긴다(이미 `common-token-efficient-collaboration`이 이 형태를 확립).
- description·핵심 원칙처럼 매 세션 로드되는 영역은 압축 우선순위가 가장 높고, "학습 자료"·"참고" 섹션은 구체성 우선순위가 더 높다.

### 10.2 개정 트리거와 절차

1. 전수 감사·실사용 중 이 문서의 판정 기준과 실제 사례가 어긋나는 지점을 발견하면, 그 자리에서 문서를 고치지 않고 대안을 `decision_record`(importance는 §7.1 등급 판정에 따름 — 판정 기준 자체 변경은 최소 4)로 먼저 기록한다.
2. §7.3의 reviewer 풀패널 필수 트리거 ⑤("전수 감사/전체 재작성 결론 자체")를 이 문서의 실질적 개정에도 적용한다 — 판정 기준을 바꾸는 것은 그 자체로 Sensitive 산출물이다.
3. 승인된 개정은 이 문서에 표의 행으로 반영하고, 5개 원본 초안(§ 서두 지위 표기)은 그대로 사료로 남긴다 — 원본 초안을 소급 수정하지 않는다.
4. 이 문서가 8개 대주제(§1~10 실질 7개 절)를 넘겨 비대해지면, 그 시점에 §10.1 원칙을 이 문서 자신의 분할 승격 판단에 적용한다.
