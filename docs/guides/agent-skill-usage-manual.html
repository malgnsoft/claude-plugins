01 · 왜 이렇게 쓰나

당신은 에이전트를 지휘하지 않습니다

01 · 왜 이렇게 쓰나

직접 처리 vs 위임, 기준은 등급입니다

PM은 모든 요청을 5등급 중 하나로 판정합니다. Micro만 PM이 즉시 직접 처리하고, 나머지는 전문 에이전트에게 위임합니다 — 직원이 이 등급을 직접 매길 필요는 없습니다.

03 / 19
등급기준처리 방식
Micro오탈자·조회·문구/CSS 한 줄 수정PM이 즉시 직접 처리 (승인 불요)
Standard일반 기능 개발·문서 작성·버그 수정전문 에이전트에게 위임 + PM 단독 승인
SensitiveDB·권한·인증·배포·결제·개인정보위임 + reviewer 풀패널 + 사람 승인 필수
Exploration원인 분석 중, 무엇을 고칠지 아직 모름위임(시간·범위 제한) + 결론만 검증
Refactor기능 변화 없는 구조 개선위임 + reviewer 풀패널
한 줄 요약 — 애매하면 PM은 항상 무거운 등급으로 기웁니다. 직원은 등급을 계산하지 않아도, "이거 중요한 건인데?" 싶으면 그냥 요청만 하면 PM이 알아서 신중하게 다룹니다.

01 · 왜 이렇게 쓰나

PM이 요청 하나를 처리하는 5단계

직원이 보는 것은 "요청 한 문장"과 "최종 보고" 둘뿐이지만, 그 사이에서 PM은 이 5단계를 거칩니다.

04 / 19
1
요청 분석

요청을 5등급(Micro~Refactor) 중 하나로 판정하고, 어떤 전문 영역이 필요한지 식별합니다.

2
팀 구성

업무 유형별 표준 패턴에 맞춰 에이전트 순서를 정합니다 (예: planner→architect→backend-dev→frontend-dev→qa-engineer).

3
위임

각 에이전트에게 입력 산출물·기대 결과·저장 경로를 명확히 전달하며 순차로 맡깁니다 (산출물 의존성 때문에 병렬이 아니라 순차).

4
검증

산출물이 실제로 존재하고 요구사항과 일치하는지 PM이 직접 대조합니다. 미흡하면 최대 2회 재작업을 지시합니다.

5
통합 보고

여러 에이전트의 산출물을 하나로 묶어 2~3분 안에 읽을 수 있는 결과로 요약해 전달합니다.

핵심 통찰

스킬 이름은 몰라도 됩니다

common-*, domain-* 스킬 36개는 에이전트가 작업 중 스스로 꺼내 쓰는 내부 매뉴얼입니다. 직원이 할 일은 스킬명을 외우거나 지정하는 게 아니라, 무엇을 원하는지 한 문장으로 명확히 말하는 것뿐입니다.

"이 문서 슬라이드로 만들어줘"라고만 말하면, presenter가 스타일가이드 토큰을 어떻게 적용할지는 presenter의 몫입니다 — 직원은 결과물만 확인하면 됩니다.

02 · 자주 쓰는 에이전트

기획 · 설계 — planner · architect

새로운 기능·서비스를 시작할 때 PM이 가장 먼저 배치하는 두 에이전트입니다.

05 / 19
pm · 항상 시작점
요청을 분석해 팀을 구성·위임하고, 결과를 검증해 통합 보고하는 프로젝트 매니저
언제: 별도로 다른 에이전트를 지정하지 않은 모든 요청
호출 예시: "로그인 기능 만들어줘" (그냥 이렇게만)
planner
고객 요구사항을 분석해 requirements.md·prd.md를 작성하는 기획 전문가
언제: 신규 기능·서비스를 기획 단계부터 시작할 때
호출 예시: "이 아이디어 기획서로 정리해줘"
architect
PRD 기반으로 시스템 아키텍처·기술스택·API 명세·데이터 모델을 설계하는 전문가
언제: 새 아키텍처 결정이 필요한 개발 착수 시점
호출 예시: "이 기획을 기술 설계로 만들어줘"
셋 다 단독 호출도 가능합니다 — 기획서만 필요하면 "planner"를 직접 지정해도 되고, 그냥 PM에게 요청하면 필요할 때 PM이 알아서 넣어줍니다.

02 · 자주 쓰는 에이전트

구현 · 검증 — backend-dev · frontend-dev · qa-engineer

설계가 끝난 뒤, 실제로 동작하는 코드를 만들고 테스트하는 3단계입니다.

06 / 19
backend-dev
아키텍처 문서를 기반으로 실제 동작하는 백엔드 코드를 구현하는 전문가
언제: 설계 문서가 준비된 API·서버 로직 구현 단계
호출 예시: "이 설계대로 API 만들어줘"
frontend-dev
설계 문서를 기반으로 웹/앱 프론트엔드 UI를 구현하는 전문가
언제: 화면·UI 컴포넌트를 실제로 만들어야 할 때
호출 예시: "로그인 화면 만들어줘"
qa-engineer
구현된 코드를 테스트하고 결과를 보고하는 QA 전문가
언제: 백엔드·프론트 구현이 끝난 직후
호출 예시: "이 기능 테스트해줘"
세 에이전트는 산출물 의존성이 있어 순차로만 진행됩니다 — PM이 backend-dev 산출물을 frontend-dev에게 넘기고, 그 결과를 다시 qa-engineer에게 넘기는 식입니다.

02 · 자주 쓰는 에이전트

검토 · 문서 · 발표 — reviewer · writer · presenter

결과물을 다듬고, 정식 문서로 만들고, 사람 앞에 내놓을 형태로 바꾸는 3단계입니다.

07 / 19
reviewer
리뷰 페르소나 패널을 구성해 산출물을 다관점으로 검토하고 통합 보고하는 진행자
언제: 중요 산출물을 최종 확정하기 전
호출 예시: "이 제안서/코드 검토해줘"
writer
제안서·보고서·기술 문서 등 비즈니스 문서를 전문적으로 작성하는 전문가
언제: 정식 문서로 산출해야 할 때
호출 예시: "이 내용 보고서로 정리해줘"
presenter
문서 내용을 프레젠테이션 슬라이드로 구성해 PDF/HTML로 만드는 전문가
언제: 발표 자료·슬라이드 매뉴얼이 필요할 때
호출 예시: "이 보고서 슬라이드로 만들어줘" 이 문서 자체가 예시
지금 보고 있는 이 슬라이드 문서 자체가 presenter가 만든 산출물입니다 — writer/researcher가 만든 내용을 presenter가 재구성한 것이 아니라, 이번 경우는 실제 md/agent 파일을 직접 근거로 삼아 작성했습니다.

02 · 자주 쓰는 에이전트

에이전트 자체를 키우는 trainer · evaluator

지금까지의 8명과 결이 다릅니다 — 업무 결과물이 아니라 malgn-agent 플러그인 자체를 개선하는 특수 목적 에이전트입니다.

08 / 19
trainer · 에이전트 교관
다른 에이전트들의 스킬을 분석하고 학습 자료를 정리해 knowledge·MD 초안을 작성
언제: 특정 에이전트를 더 잘 쓰게 만들고 싶을 때
호출 예시: "backend-dev 스킬업 시켜줘"
evaluator · 판정·승격 전담
에이전트/스킬/knowledge 산출물을 rubric으로 채점·판정하고 게이트 통과 시 PR로 승격까지 실행
언제: trainer 초안 완료 후, 또는 개선안을 실제 반영할 때
호출 예시: "이번 개선안 평가하고 승격해줘"
일반 업무 요청("~ 만들어줘")과 에이전트 개선 요청("~ 학습시켜줘")은 다른 트랙입니다. PM이 trainer 초안 → evaluator 판정·승격의 흐름으로 이어받으며, 사람 승인이 필요한 변경은 evaluator가 반드시 그 시점을 표시합니다.

★ 핵심 명령어

★ 핵심 명령어

남길 규칙과 내보낼 자리를 배치 기준표로 정리해 CLAUDE.md를 슬림화합니다.
이렇게 말하면
"프로젝트 회고해서 교훈 남겨줘"
끝난 프로젝트의 산출물·기록을 분석해 재사용 가능한 교훈을 뽑아 다음 프로젝트의 자산으로 남깁니다.
이렇게 말하면
"다관점 페르소나로 이거 검토해줘"
리뷰 페르소나 패널이 서로 다른 관점에서 교차 검토한 뒤 통합 보고서로 정리합니다.
이렇게 말하면
"architect 학습시켜줘"
해당 에이전트의 MD·Knowledge에 학습 자료를 추가해 역량을 키웁니다.
이렇게 말하면
"이 에이전트 평가해줘"
rubric으로 채점하고, 기준을 통과하면 승격까지 실행합니다.
이렇게 말하면
"내 토큰 사용량 봐줘"
로컬 세션 로그를 분석해 캐시 히트율·반복 호출 패턴을 진단합니다.
이렇게 말하면
"진행상황 관리해줘"
WBS로 진행·리스크를 추적하며 팀 위임 모델대로 진행합니다.
여기 없는 요청도 괜찮습니다 — 문장이 구체적일수록 PM이 등급과 담당을 더 정확히 판정합니다.

06 · 안티패턴

PM이 못 하는 것도 있습니다

이 한계들은 버그가 아니라 설계입니다 — 중요한 결정에는 항상 사람 또는 전문 검증이 개입하도록 만든 안전장치입니다.

16 / 19
Sensitive/Refactor 등급은 PM 단독 승인 불가
반드시 reviewer 풀패널을 거치고, 최종 승인은 사람(직원/대표)이 합니다
개별 산출물을 직접 작성하지 않음
코드·설계·문서·디자인은 항상 전문 에이전트가 작성 — PM은 trivial 편집만 예외
전역 에이전트/스킬/knowledge 승격은 PM 권한 밖
evaluator가 rubric으로 판정하고 git PR로 승격을 실행 — PM은 대상 선정만 담당
위임 실패가 2회 반복되면 PM이 직접 완수하지 않음
담당 교체, 작업 재분해, 사람 에스컬레이션 중 하나를 택합니다 — 무한 재시도하지 않습니다
궁금하면 언제든 "이거 지금 어느 등급이야?", "누가 승인해야 해?"라고 PM에게 그냥 물어보세요 — 판단 기준을 숨기지 않습니다.
