# 맑은소프트 에이전트 개발방법론 (초안 v0.1)

> **용도**: 이 문서는 `malgn-agent`의 agents/*.md·skills/*.md를 **작성·전수감사·재작성**할 때 쓰는 판정 기준(rubric)이다. 추상 선언이 아니라 "이럴 때는 이렇게 판단한다"는 실행 가능한 규칙만 담는다. 배경·이유가 필요하면 이 문서를 knowledge로 분리하지 않고 각 규칙 옆에 1줄 근거만 남긴다(이 문서 자체가 §5의 원칙을 스스로 지킨다).
>
> **관점**: 이 시스템은 사람이 아니라 **LLM이 system prompt로 소비**한다. 따라서 모든 판정 기준은 "사람이 읽고 이해하는가"가 아니라 "LLM이 매 턴 이 지시를 정확히·일관되게 실행하는가"를 기준으로 삼는다.
>
> **기존 자산과의 관계**: 이 문서는 6개 common-* 스킬(beyond-mediocre-output/task-grading/token-efficient-collaboration/output-storage/product-principles/learning-loop)을 대체하지 않는다. 그것들은 **산출물 품질·검증 기준**(무엇을 만들 것인가)이고, 이 문서는 **에이전트 정의 자체의 작성 기준**(그 지시를 어떻게 코딩할 것인가)이다. 층위가 다르므로 공존한다 — 단, §5·§6에서 이 6종 자체도 감사 대상에 포함한다.

## 1. 페르소나 정의의 필수 요소

현재 agents/*.md(architect·frontend-dev·reviewer·pm 등)는 이미 공통 골격을 쓰고 있다: `frontmatter(name/description)` → 정체성 한 문장 → 핵심 원칙 → 역할 경계 → 스킬 상세 → 전제 조건 → 자기 검증 → 산출물 → 학습 자료. **이 골격 자체는 유지한다.** 감사 시에는 새 구조를 발명하지 말고, 각 섹션이 실제로 아래 5요소를 채우고 있는지만 판정한다.

| 요소 | 결여 시 실패 시나리오 | 판정 질문 |
|---|---|---|
| ① 정체성 1문장 | 여러 역할이 뒤섞여 다음 행동을 예측 불가 | frontmatter `description`을 빼고 본문 첫 문장만 읽어도 "이 에이전트가 무엇을 하는지" 한 번에 말할 수 있는가? |
| ② 호출 조건 | PM이 팀 구성 시 이 에이전트를 언제 넣을지 판단 불가 | "호출자" 줄에 트리거(누가/언제)가 구체 동사로 적혀 있는가, 아니면 "COO/단독"처럼 공백인가? |
| ③ 역할 경계(한다/안한다) | 인접 에이전트와 책임이 겹쳐 위임이 왕복 | "경계" 항목에 **인접 에이전트 이름을 지목**해 그쪽 소관이라고 명시했는가? (예: frontend-dev.md의 "비주얼 디자인은 visual-designer 영역" — 이 패턴이 기준) |
| ④ 산출물 계약 | 검증 불가능한 "설명만 하고 끝" 위험 | "산출물" 섹션에 파일 경로 패턴(`docs/xxx.md`)과 필수 필드가 명시돼 있는가? |
| ⑤ 완료 정의(자기검증) | "완료"의 기준이 매 세션 다르게 해석됨 | 자기검증 체크리스트를 그대로 실행하면 제3자가 봐도 완료/미완료를 판정할 수 있는가(체크박스가 진짜 검증 가능한 사실인가, 아니면 "잘 했는가?" 같은 자문형인가)? |

**판정 규칙**: 5요소 중 하나라도 없으면 그 agents/*.md는 "구조 미완성"으로 감사 리포트에 기록한다. 5요소가 다 있어도 ②·③이 다른 파일과 모순되면(예: 두 에이전트가 서로 "이건 내 영역 아니다"라고 함) 우선순위는 **역할 경계가 더 구체적으로 지목한 쪽**을 정본으로 삼는다.

## 2. 트리거 조건 서술 — description은 "검색 인덱스"다

Skill의 `description` 필드는 사람이 읽는 소개문이 아니라 **자동 매칭 엔진에 들어가는 검색 키**다. 현재 목록(system-reminder의 스킬 리스트)을 보면 이미 대다수가 `[무엇을 하는가] — [언제 쓰는가]` 2단 구조를 따르고 있다(예: `common-task-grading-and-verification-depth`: "작업 등급에 따라 검증 강도를 맞춰 과소·과잉 검증을 방지. COO가 위임 전 검증 깊이를 판정하거나, 에이전트가 자기검증 수준을 정할 때 사용"). **이 2단 구조를 표준으로 고정한다.**

**판정 기준(기계적으로 적용 가능)**:
1. description에 "~할 때 사용", "~할 때", "요청 시" 류 **트리거 절이 최소 1개** 있는가? 없으면(정의만 있고 트리거가 없으면) 자동 매칭 실패 위험 — 예: "전 에이전트 산출물 품질 기준"처럼 트리거 없이 정의만 있는 문장은 그 뒤에 반드시 "~시 사용"이 와야 한다(실제로 6개 common-*는 모두 이 패턴을 지킴 — 유지).
2. 트리거절은 **사용자가 실제로 입력할 법한 표현**을 최소 1개 포함해야 한다. "코드 리뷰 관련 작업 시"보다 "코드 리뷰해줘", "PR 봐줘" 같은 발화에 가까운 명사/동사가 낫다. `code-review` 스킬의 트리거("Review the current diff... at the given effort level")처럼 실제 슬래시커맨드/발화 패턴을 그대로 반영한 것이 모범.
3. **중복 트리거 감사**: 두 스킬의 트리거절이 같은 상황(예: "보안 검토 시")을 가리키면 자동 매칭이 둘 다 후보로 올려 혼선을 준다. `domain-backend-api-security` / `domain-serverless-edge-api-security` / `domain-security-audit-checklist`처럼 같은 도메인어를 공유하는 스킬이 여럿이면, 각 description의 "언제 이걸 여는가"가 **하나의 축 위에서 배타적으로** 갈려야 한다(이 3종은 "무엇을 보고 있는가" — 라우트 한 건 / 이 스택의 코드베이스 / 프로젝트 전체 태세). "이 스킬은 X와 중복되지 않는다"류 해명문은 통과 근거가 아니다 — 해명이 필요하다는 것 자체가 선택 지점이 모호하다는 신호이며, 게다가 description은 상시 로드라 그 해명문 비용을 매 세션이 문다. 축이 없거나 두 스킬이 같은 칸에 들어가면 "트리거 충돌 후보"로 표시.
4. description 길이는 **1~3문장, 300자 내외**를 상한으로 삼는다. 그 이상 길어지면 트리거 판별에 필요한 핵심 키워드가 부사어에 묻힌다 — 본문에 넣을 내용을 description에 욱여넣지 않는다.

## 3. 지시문의 모호성 제거

LLM에게 모호한 지시는 "대체로 맞지만 가끔 다르게 해석되는" 실패를 만든다 — 사람과 달리 재질문으로 스스로 보정하지 않고 **그럴듯한 답을 확신 있게 낸다**는 점이 핵심 위험이다. 따라서 모호성 판정은 "사람이 이해했는가"가 아니라 "이 문장만으로 서로 다른 두 세션이 동일한 행동을 하는가"로 검사한다.

**모호성의 3유형과 교정 패턴**:

| 유형 | 안티패턴 예시 | 교정 원칙 |
|---|---|---|
| 정도부사 | "적절히 검증하라", "충분히 검토" | 등급·수치·체크리스트로 치환. `common-task-grading-and-verification-depth`의 5등급표가 모범(Micro/Standard/Sensitive/Exploration/Refactor + 등급별 QA 최소기준) |
| 암묵 조건 | "필요하면 reviewer를 부른다" | if-then 명시. "Sensitive/Refactor 등급 산출물은 reviewer 풀패널 필수, Standard는 약식으로 충분" (pm.md 기존 패턴) 처럼 등급→행동 매핑까지 내려간다 |
| 열린 수량어 | "여러 개", "몇 가지 이상" | 하한/상한 숫자 명시. `beyond-mediocre-output`의 "엣지케이스 5가지 이상", "프로젝트 고유성 3가지 이상"이 모범 |

**판정 규칙**: 지시문에서 정도부사·암묵조건·열린수량어를 grep(눈으로) 훑어 하나라도 발견되면, 그 문장이 이미 다른 곳(체크리스트·등급표)에서 구체화돼 재참조하고 있는지 확인한다. 재참조 없이 그 문장 자체가 유일한 근거면 교정 대상.

**반례로 남길 좋은 예**: architect.md의 "설계 4대 의무"는 트레이드오프를 "선택/대안/선택 이유/포기한 것/감당 방안" 5개 슬롯 형식으로 강제한다 — "트레이드오프를 명시하라"는 열린 지시가 아니라 **채워야 할 필드 목록**으로 좁힌 것이 핵심. 새 규칙을 쓸 때 이 패턴(열린 지시 → 슬롯 형식)을 기본값으로 삼는다.

## 4. Few-shot(예시) 사용 기준

**예시가 필요한 경우 (3가지 중 하나라도 해당하면 최소 1쌍 삽입)**:
- (a) 출력 포맷이 프로젝트 고유이거나 표준 학습 데이터에 없는 형태다 (예: `decision_record`에 넣을 reason/impact 텍스트 형식, WBS bucket 판독 규칙)
- (b) 규칙 문장만으로는 재발한 실패 패턴이다 (동일 실수가 2회 이상 관찰된 경우에 한해 — 1회성 사건을 바로 예시로 승격하지 않는다)
- (c) 판정 경계가 이분법적이고 헷갈리기 쉽다 (예: `skill-vs-knowledge-boundary.md`의 "Skill이 할 말 vs Knowledge가 할 말" 대비 문장)

**예시가 불필요한 경우**: 이미 모델이 일반 지식으로 정확히 아는 절차(예: "git commit 메시지에 Co-Authored-By 포함"), 또는 규칙 자체가 이미 슬롯 형식으로 완전히 구체화된 경우(§3의 교정 결과물에는 추가 예시가 대개 불필요).

**개수·형식 기준**:
- **최소 단위는 ❌/✅ 1쌍이다.** `common-beyond-mediocre-output`의 "❌ 에러를 처리해야 한다 / ✅ pnpm workspace 상황에서 cross-package 에러는 A, 단일 패키지는 B로…" 패턴이 표준. Bad 예시 없이 Good 예시만 주면 "왜 이게 필요한지"가 전달 안 돼 다른 맥락에 과잉 일반화될 위험이 있다 — 반드시 대비쌍으로.
- **1쌍이면 충분하다. 3쌍 이상은 과잉으로 판정한다** — 예시가 늘수록 한계효용이 급감하고, 예시 자체가 다음 지시문을 덮어 컨텍스트를 잠식한다(§5와 연결).
- 예시는 **그 스킬/에이전트가 실제로 다루는 도메인의 구체 명사**를 써야 한다("데이터를 처리한다" 같은 범용 예시는 전이 효과가 약하다). architect.md의 "표준 CRUD는 빠르게, 핵심 도메인(WebSocket 채널 등)에 깊이"처럼 실제 산출물 어휘를 그대로 쓴 예시가 기준.

## 5. 과잉 지시로 인한 성능 저하 방지 — 최우선 감사 포인트

**증상 메커니즘**: 규칙이 늘어날수록 (a) 서로 다른 우선순위의 규칙이 평면적으로 나열돼 실제 충돌 시 어느 쪽을 따를지 모델이 즉흥 판단하게 되고 (b) 매 턴 전체 규칙을 다시 "읽는" 비용이 늘며 (c) 뒤로 갈수록 지시가 앞부분 지시에 묻혀 실효성이 떨어진다(recency/position bias). 이는 사람의 "규정집이 두꺼우면 대충 훑는다"는 실패와 같은 종류이며, LLM도 예외가 아니다.

**이번 조사에서 관찰된 구체적 안티패턴** (감사 시 동일 패턴을 다른 파일에서도 찾을 것):
- `pm.md`의 "핵심 원칙" 절이 **약 40개 항목·250줄**을 나열하며, 각 항목이 `(lesson 'xxx')` 형식으로 특정 과거 사건을 인용한다. 이는 **"일반화된 행동 규칙"과 "사건 로그"가 한 문서에 뒤섞인 것**이다 — 새 세션이 이 파일을 읽을 때 "지금 이 사건이 다시 일어날 확률이 있는 규칙인가, 아니면 1회성 사고 기록인가"를 구분할 방법이 없다.
- `common-output-storage-and-path-management`(SKILL.md)는 `~/.claude/skills`, `~/.claude/agents/coo.md` 등 **malgn-agent 플러그인 이식 이전의 개인 전역 경로**를 여전히 예시 트리 구조에 담고 있다 — 플러그인 사용자에게는 존재하지 않는 경로다. 규칙이 실제 배포 환경과 어긋나면 "지시가 많아서" 위험한 게 아니라 "지시가 틀려서" 위험해진다 — 이는 §5가 아니라 별도 이식성 결함이지만, 규칙이 방대해 이런 드리프트가 숨어도 걸러지지 않는다는 점에서 같은 뿌리다.

**정량적 판정 기준(감사 체크리스트에 그대로 사용)**:
1. "핵심 원칙"류 섹션이 **비협상 규칙 7개**를 넘으면 초과분은 하위 항목("스킬 상세")으로 강등하거나 별도 knowledge로 뺀다. (7은 임의 상한이 아니라 — 이 문서 자체 §1~6이 6개 절인 것과 같은 근거: 한 번에 참조 가능한 규칙 묶음의 경험적 상한)
2. 규칙 1개는 **1~2문장**을 넘지 않는다. 그 안에 "왜"(배경 설명)가 들어 있으면 knowledge로 분리하고 규칙 문장에는 결론(행동)만 남긴다 — `skill-vs-knowledge-boundary.md`가 이미 정의한 원칙을 여기서 재확인한다.
3. `lesson`/사건 인용은 규칙당 **최대 1개**, 그것도 괄호 안 1줄 각주로만 — 사건의 전후 맥락(누가 언제 무엇을 했다는 서사)을 규칙 본문에 그대로 남기지 않는다. 서사가 필요하면 knowledge/history로 옮기고 규칙에는 링크만.
4. 같은 md 파일 안에서 **뒤 문단이 앞 문단의 예외를 다루는 구조**(A 규칙 → 나중에 "단, X면 예외" → 또 나중에 "그 예외의 예외")가 2단 이상 중첩되면 규칙 자체를 표(조건→행동)로 재작성한다. 산문으로 중첩 예외를 쌓지 않는다.
5. 하나의 md 파일을 처음 읽는 사람이(또는 모델이) **"지금 당장 지켜야 할 규칙"과 "참고용 사례"를 제목만 보고 구분**할 수 있는가 — 못 하면 재구조화 대상.

## 6. 토큰 효율과 명확성의 트레이드오프

**원칙 우선순위**: 명확성이 이긴다. 단, "명확함"과 "장황함"은 다르다 — 압축은 **반복 제거**로 하고 **구체성 삭제**로 하지 않는다.

**판정 규칙**:
- 같은 규칙 문장이 **3개 이상의 agents/*.md에 원문 그대로 복붙**돼 있으면 공용 skill로 승격하고, 각 md에는 "Skill `X` 참조" 1줄만 남긴다. (이미 `common-token-efficient-collaboration`처럼 각 agent md 말미에 "상세: Skill 참조"로 위임하는 패턴이 확립돼 있다 — 신규 규칙도 처음부터 이 형태를 취한다.)
- 반대로, **그 에이전트에만 해당하는 구체 규칙**(예: frontend-dev의 vue-zero Blob URL 패턴)을 억지로 짧게 줄이지 않는다 — 이 경우 장황해 보여도 삭제하면 실제 실패(잘못된 import 경로 사용 등)로 이어지므로 명확성이 우선한다.
- description·핵심 원칙처럼 **매 세션 반드시 로드되는 영역**은 압축 우선순위가 가장 높고, "학습 자료"·"참고" 섹션처럼 **필요할 때만 펼쳐 보는 영역**은 구체성 우선순위가 더 높다 — 즉, 압축은 "항상 읽히는 상단"에 먼저 적용하고 "필요시 참조하는 하단"은 상대적으로 관대하게 둔다.
- 압축 여부를 판단할 때 "이 문장을 지워도 다음 세션이 같은 행동을 하는가?"를 기준으로 삼는다. 지워도 행동이 같으면 중복(제거 대상), 다르면 정보(유지 대상).

## 8. 이 문서의 갱신 규칙

이 문서 자체도 §5·§6의 대상이다. 전수감사·재작성 과정에서 새로운 반례·판정 규칙이 확정되면 이 문서에 **표의 행으로만** 추가한다(산문 단락을 덧붙이지 않는다). 섹션이 8개를 넘길 정도로 커지면 그 시점에 이 문서 자체를 분할 승격 대상으로 판정한다(§6의 "명확성 vs 압축" 원칙을 스스로에게 적용).
