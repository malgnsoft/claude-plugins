## 0. 이 설계가 딛고 선 확정 사실 (재조사하지 않는다)

| # | 사실 | 출처 |
|---|---|---|
| 1 | **훅이 hub를 조회하는 것은 불가능하다.** hub MCP의 OAuth 토큰은 `~/.claude/.credentials.json`에 실체가 없고(길이 0·만료 0) macOS 키체인에 별도 보관된다. 이 경로는 (a) macOS 전용이라 Windows 직원 환경에 없고 (b) Claude Code 앱의 금고를 훅이 몰래 읽는 셈이라 공식 지원 경로가 아니다 | 세션 직접 실증(PM) |
| 2 | **고정 토큰 전환(`userConfig.device_token` 승격)은 스코프 밖이다.** 회사 전체 인증 방식을 바꾸는 별개 보안 결정으로 분리됐다 | 사용자 판단 |
| 3 | **스킬은 훅과 근본적으로 다르다.** 별도 프로세스가 아니라 이미 인증된 살아있는 세션 안에서 모델이 직접 호출한다 → hub 인증 문제가 없고, `wbs_list`·`project_get_context`를 그 자리에서 불러 **진짜 상태**를 확인할 수 있다. 훅 설계의 원리적 한계("가시화일 뿐 진짜 검증이 아니다", 트랜스크립트 관측 의존)가 여기서 해소된다 | 방향 전환의 핵심 근거 |

이 세 가지가 설계 공간을 정의한다. 아래는 전부 이 위에서 성립한다.

> **확정 사실 1의 범위를 정확히 읽는다 — 이 문서가 한 번 넓게 읽었다.** 배제되는 것은 **"훅 프로세스가 hub에 인증해 진짜 상태를 조회하는 것"**이다. 배제되지 **않는** 것이 둘 있다:
> - **`hooks/pm-orchestration-block.md`(주입되는 텍스트 자산)에 한 줄을 더하는 것** — hub 인증이 필요 없다. 이것이 §6의 옵션 2다.
> - **이미 배포돼 도는 `hooks/stop-mcp-reminder.cjs`** — 로컬 전사만 읽고 hub를 부르지 않는다(§5-2).
>
> 확정 사실 1을 "훅이라는 글자가 들어가면 전부 제외"로 읽으면, **인증과 무관한 후보 둘이 검토도 없이 사라진다.**

## 0-5. 기준선 수치 — **먼저, 이 절 자신이 한 번 틀렸다**

### 0-5-1. 정정의 정정 — 반증은 성립하지 않았다

이 절의 이전 판은 *"브리핑의 기준선 수치(WBS 39개 중 done 0건 / 이슈 12건 전부 open)가 실물과 다르다"*고 적고 브리핑을 반증했다. **그 반증은 성립하지 않는다 — 두 수치가 서로 다른 프로젝트의 것이기 때문이다.**

| | 가리키는 프로젝트 | 이 설계 세션이 조회할 수 있었나 |
|---|---|---|
| 브리핑의 "39개 중 done 0건 / 12건 전부 open" | **malgn-vscode** | **불가능** |
| 이전 판이 "실물"이라며 들이댄 `wbs_list`·`project_get_context` 응답 | **claude-plugins**(이 저장소) | 가능 |

hub MCP 도구는 **세션이 속한 프로젝트만** 조회한다. 이 설계 작업은 claude-plugins에서 돌았으므로 malgn-vscode의 hub 상태는 **애초에 볼 수 없었다.** 그런데 이전 판의 재현 절차는 `projectId=<malgn-vscode의 project_id>`라고 적었다 — 실제로 물은 것은 claude-plugins인데 라벨은 malgn-vscode였다. **수치가 틀린 것이 아니라 수치에 붙은 프로젝트 라벨이 틀렸고, 그 라벨 위에 "브리핑이 틀렸다"는 결론이 세워졌다.**

> **이 문서가 이제부터 지키는 규율:** 모든 수치에 **어느 프로젝트 · 어느 도구 · 어느 옵션**을 함께 적는다. 셋 중 하나라도 빠진 수치는 근거로 쓰지 않는다.

### 0-5-2. claude-plugins 확정값 (PM 직접 조회 — 재측정하지 않는다)

| 항목 | 값 | 도구 |
|---|---|---|
| WBS | **total 210 · planned 40 · inProgress 24 · done 146** | `wbs_list(includeDone:true)`의 `summary` |
| 열린 이슈 | **14건** | `project_get_context(sections=['issues'])` |

이 절의 이전 판이 적었던 "total 84 / done 51 / 열린 이슈 10"은 **같은 프로젝트(claude-plugins)의 더 이른 시점 값**이다. 프로젝트가 살아 있으므로 다시 재면 또 달라진다 — 그래서 위 값에도 "PM이 이 보강 라운드에 직접 조회한 값"이라는 시점 라벨이 붙는다.

### 0-5-3. 조회 함정은 사실로 확정됐다 (PM 재현)

프로젝트 라벨은 틀렸지만 **그 과정에서 드러난 도구 동작 차이는 PM이 claude-plugins에서 직접 재현해 확인했다. 이것이 이 라운드의 최대 성과다.**

| 호출 (프로젝트: claude-plugins) | 돌아온 것 | done을 셀 수 있나 |
|---|---|---|
| `wbs_list(projectId, includeDone:true)` | `summary` 블록(`done:146`) + 전량 | **가능** |
| `project_get_context(projectId, sections=['wbs'])` | **`summary` 블록이 아예 없고**, 반환된 items에 `status:"done"`이 **단 하나도 없다**(전부 planned/in_progress) | **불가능.** 세면 반드시 "done 0건" |

**`project_get_context(sections=['wbs'])`는 구조적으로 종결을 볼 수 없는 뷰다.** 그런데 이 도구는 `skills/project-orchestration/SKILL.md`:109 §5의 5항이 종결 점검용으로 지정한 바로 그 도구다(그 줄은 `sections=['issues']`를 쓰지만, "현황을 조회한다"는 동작을 이 도구로 배운 사람이 WBS에도 같은 도구를 쓰는 것은 자연스럽다).

> **§5가 종결 점검용으로 지정한 도구를 지시대로 쓰면 done을 볼 수 없다.** 종결 점검을 하라는 문장을 네 번째로 추가해도 이 함정은 그대로다.

## 0-6. 이 함정이 여는 새 가설 — 문제 정의 자체가 바뀔 수 있다

조회 함정이 사실로 확정되자, 브리핑의 "39개 중 done 0건"(malgn-vscode)을 설명하는 방식이 둘로 갈린다. **두 진단은 처방이 완전히 다르다.**

| | **가설 1 — 진짜 미갱신** | **가설 2 — 조회 함정의 산물** |
|---|---|---|
| 주장 | malgn-vscode에서 종결이 실제로 안 걸렸다 | 종결은 걸렸는데 조회가 그걸 숨겨 "안 걸린 것처럼" 보였다 |
| 함의하는 처방 | **리마인드 강화** — 종결하라는 지시가 종결 주체에게 닿게 만든다 | **조회 방법 교정** — 무엇을 어떻게 물어야 진짜 상태가 보이는지를 심는다 |
| 이게 참이면 유리한 옵션 | 옵션 2·3·4(트리거를 상시 텍스트에 심는 쪽) | 옵션 1(절차 지식을 스킬 본문에 담는 쪽) |

### 0-6-1. 현재 증거로 어디까지 판별되는가

**내가 실제로 열 수 있었던 malgn-vscode 증거는 로컬 전사뿐이다**(hub는 조회 불가 — §0-5-1). 아래는 이 보강 라운드에 직접 측정한 값이다.

> **측정 범위:** 프로젝트 **malgn-vscode** / 대상 `~/.claude/projects/-Users-hopegiver-workspace-malgn-vscode` 아래 **`.jsonl` 247개 전량**(메인 세션 44 + 서브에이전트 전사 203) / 방법 JSONL을 파싱해 `message.content[]`의 `type=="tool_use"` 블록만 집계(문자열 grep은 산문까지 세어 과다계상된다) / 시점 이 보강 라운드.

| 관측 | 값 | 어느 가설을 지지하는가 |
|---|---|---|
| `wbs_update` 호출 | **72회**, 그중 `status='done'` 인자 **56회** | **가설 2.** 종결 도구는 대량으로 불렸다 |
| `issue_resolve` 호출 | **14회** | **가설 2.** 이슈 종결도 실제로 걸렸다 |
| `issue_record` 호출 | 22회 | (열림 22 vs 닫힘 14 — 한 방향으로 기우는 경향 자체는 남는다) |
| `wbs_list` 호출 | **3회, 전부 `includeDone:true`** | **가설 2에 불리.** 이 세션들은 올바른 파라미터를 썼다 |
| `project_get_context` 호출 | 4회, **그중 `sections`에 `'wbs'`가 포함된 것은 0회** | **가설 2에 불리.** 함정 도구를 WBS 조회에 쓴 흔적이 malgn-vscode 전사에 없다 |
| `status='done'`에 `completedDate` 동반 | 56회 중 **29회**(52%) | 어느 가설과도 무관 — 별개의 실증된 누락 |

**판별된 것:** "malgn-vscode에서 종결 도구가 거의 안 불렸다"는 **강한 형태의 가설 1은 전사로 반증된다.** `status='done'` 56회 · `issue_resolve` 14회가 실재한다.

**판별되지 않은 것 (정직하게 적는다):**
1. **그 호출들이 성공했는지 모른다.** 전사에서 센 것은 *호출*이지 *결과*가 아니다. 그룹 노드에 `status='done'`을 시도하면 `STATUS_DONE_LEAF_ONLY`로 실패하는데(§3-3), 실패분이 몇인지 세지 않았다.
2. **malgn-vscode의 hub 현재 상태를 볼 수 없다.** 도구가 자기 프로젝트만 조회하므로 "그래서 지금 done이 몇 건인가"는 이 세션에서 원리적으로 확인 불가다. 확인하려면 **malgn-vscode 세션에서 `wbs_list(includeDone:true)`를 직접 불러 `summary`를 보는 수밖에 없다.**
3. **"39개 중 done 0건"이라는 수치의 출처를 모른다.** 위 표대로 malgn-vscode 전사에는 함정 도구(`project_get_context(sections=['wbs'])`) 사용 흔적이 0회다. 그러므로 **"malgn-vscode 세션이 함정에 걸려 그 수치를 얻었다"는 형태로는 가설 2가 지지되지 않는다.**

### 0-6-2. 그래서 남는 세 번째 가능성

위 3번 때문에 가설 2를 그대로 채택할 수 없다. 같은 무게로 놓아야 할 것이 하나 더 있다:

> **가설 3 — 수치의 출처 자체가 불명이다.** "39개"가 어느 도구·어느 옵션·어느 시점의 값인지 어디에도 적혀 있지 않다. 이 문서 §0-5-1이 방금 겪은 것과 **정확히 같은 종류의 사고**다(측정은 했는데 라벨이 틀렸다). 라벨 없는 수치는 그 자체로는 미갱신의 증거도, 함정의 증거도 되지 못한다.

**판별 방법은 하나뿐이고, 이 세션에서는 할 수 없다:** malgn-vscode 세션에서 `wbs_list(projectId, includeDone:true)`를 불러 `summary.done`을 보면 즉시 갈린다. done이 유의미하게 크면 가설 2·3, 0에 가까우면 가설 1이다. **이건 1회 도구 호출이고 이 설계의 어느 옵션보다 싸다 — §8의 갈림길로 올린다.**

### 0-6-3. 가설과 무관하게 참인 것 — 설계의 공통 항목

**조회 함정 교정은 어느 가설이 참이든, 어느 옵션을 고르든 필요하다.** 근거는 malgn-vscode가 아니라 claude-plugins에서 PM이 직접 재현한 §0-5-3이다 — 같은 hub에 같은 프로젝트를 두 방식으로 물었는데 한쪽은 done 146, 한쪽은 done 0이 나온다. 이건 가설이 아니라 도구 동작이다.

따라서 이 설계의 구성은 이렇게 갈린다:

| | 가설 판별 전에도 확정 | 가설 판별 후에 정해도 되는 것 |
|---|---|---|
| **무엇** | 올바른 조회 절차(함정 회피 + 그룹 노드 + `completedDate` + `issue_resolve` 제약)를 **어딘가에 글로 남긴다** | 그 절차를 **어디에 두고 무엇으로 발동시키는가**(옵션 1~4 중 선택·조합) |
| **왜** | 도구 동작에서 직접 나오는 사실이라 가설과 독립이다 | 가설 1이면 트리거 강화가, 가설 2면 절차 교정이 더 큰 몫을 한다 |

### 0-6-4. 브리핑의 진단은 어떻게 되는가

| 브리핑의 진단 | 이 보강 후 |
|---|---|
| "종결 기록이 write-only다 — 등록만 걸리고 종결이 안 걸린다" | **강한 형태는 반증됨**(전사 기준). 다만 열림 22 vs 닫힘 14로 **한 방향으로 기우는 경향**은 남는다 |
| "§5 문장이 지켜지지 않는다" | **부분 유지.** 지켜진 흔적은 있으나 **올바르게 지켜졌는지 확인할 방법이 조직에 없었다** |
| "장치가 필요하다" | **유지, 다만 목적이 갈린다** — 가설 1이면 더 강한 트리거, 가설 2면 올바른 조회 절차. §0-6-3의 공통 항목은 어느 쪽이든 필요하다 |

**claude-plugins 쪽 잔여 부채도 실재한다**(열린 이슈 14건). 다만 이 문서가 대상으로 삼는 실패는 "전면 붕괴"가 아니라 "부분 누락"이고, 설계 강도는 거기에 맞춰야 한다.

## 1. 호출 격차의 원인 규명 — 왜 어떤 스킬은 12~14번 열리고 어떤 스킬은 1번 열리는가

### 1-1. 측정값 재확인 (범위 명시)

malgn-vscode 서브에이전트 트랜스크립트 202개에서 `Skill` 도구의 `skill` 인자만 집계했다(자연어 매칭 없음).

> **범위·시점 주의(§0-5-1의 규율 적용):** 아래 값은 **프로젝트 malgn-vscode / 로컬 전사 / 이전 판 작성 시점**의 것이다. malgn-vscode는 활성 프로젝트라 전사가 계속 늘어난다 — 이 보강 라운드에 다시 세니 **서브에이전트 전사는 203개**(메인 44 포함 총 247)로 늘어 있었다. 아래 표의 **상대 비교(어떤 스킬이 열리고 어떤 스킬이 안 열리는가)는 그대로 유효하지만, 절대 호출수를 다른 문서에 인용할 때는 이 시점 라벨을 함께 옮긴다.**

| 스킬 | 호출 | 크기 |
|---|---|---|
| `common-task-grading-and-verification-depth` | **12** | 16,758B |
| `reviewer-persona-panel-standard` | **9** | 17,909B |
| `common-screen-verification-and-capture` | 3 | — |
| `domain-git-safety-and-concurrency` / `domain-backend-api-security` | 각 2 | — |
| `project-orchestration` · `project-standards` · `domain-system-design-principles` · `domain-pre-deployment-verification-gate` | 각 1 | 18,524B(첫째) |

메인 세션 44개에서는 스킬 호출이 계 8회뿐이고(`run` 5 · `project-standards` 2 · `token-usage-diagnosis` 1) `project-orchestration`은 0회다.

### 1-2. 먼저 기각한 가설 두 개 (둘 다 실측으로 반증됐다)

**가설 A — "위임 프롬프트가 스킬 이름을 직접 적어줘서 열린다."** → **기각.**
스킬 호출이 발생한 서브에이전트 전사에서, 그 스킬 이름이 최초 위임 프롬프트에 문자열로 들어 있었는지 대조했다.

| 스킬 | 호출 | 프롬프트에 이름 명시됨 | 명시 없이 스스로 열었음 |
|---|---|---|---|
| `common-task-grading…` | 12 | **0** | 12 |
| `reviewer-persona-panel-standard` | 9 | 1 | 8 |

압도적으로 **프롬프트가 지목하지 않았는데 에이전트가 스스로 열었다.** 호출을 만드는 것은 위임자가 아니라 에이전트 MD의 참조 구조다.

**가설 B — "위임 프롬프트에 실린 값(작업 등급)이 트리거다."** → **약함.**
서브에이전트 202건 중 프롬프트에 "등급"이 언급된 것이 140건인데 `common-task-grading` 호출은 12건이고, 그 12건 중 프롬프트에 등급이 있던 것은 5건뿐이다. 입력 값이 트리거라면 140건 대부분이 열렸어야 한다.

**그리고 가장 깨끗한 자연실험이 하나 있다.** 같은 프로젝트에서 `malgn-agent:pm`이 서브에이전트로 실행된 전사 6건을 골라냈다(첫 프롬프트에 오케스트레이션·팀 구성·PM 역할이 명시된 것). 이 6건은 **동일한 `agents/pm.md`를 로드한 자리**다.

> **6건 중 `common-task-grading`을 연 것이 3건, `project-orchestration`을 연 것이 0건이다.**

즉 "PM이 pm.md를 안 읽어서"가 아니다. **pm.md가 확실히 로드된 그 자리에서도** 한 스킬은 열리고 다른 스킬은 열리지 않는다. 차이는 로드 여부가 아니라 **참조 구문의 생김새**에 있다.

### 1-4. 규명 결과 — 두 조건이 동시에 깨져 있다

호출되는 스킬 둘은 아래 두 조건을 **모두** 만족하고, `project-orchestration` §5는 **둘 다** 어긴다.

> **조건 ①(자족 불가):** 참조처가 그 내용을 갖고 있지 않아서, 열지 않으면 다음 행동을 **할 수 없다**. 등급표·Fast Path 5조건·축소 금지 목록·페르소나 6대 요소·보고서 형식은 전부 스킬에만 있다 — 심지어 참조처가 *"여기 옮겨 적지 않는다"*고 명시적으로 못을 박는다.
>
> **조건 ②(시점 정합):** 호출 지시가 걸린 시점이 곧 그 내용이 필요한 시점이다.

§5가 열리지 않는 이유는 이렇게 정리된다:

1. **자족한다.** PM은 "라운드 끝에 기록/종결해야 한다"는 것도, 그 도구가 `issue_resolve`라는 것도 훅 블록과 pm.md에서 이미 안다. 열어야 할 이유가 없다.
2. **트리거가 다른 시점에 걸려 있다.** "위임 전"에 호출하라는 지시를 따라 스킬을 열더라도, 라운드가 닫힐 즈음 §5는 컨텍스트 저 뒤에 있다. 아예 안 열렸으면 존재하지 않는다.
3. 그리고 pm.md:134의 체크리스트 항목은 §5를 가리키지만 **조건부**다(*"①설계 산출물 ②Write 전체 재작성 … 중 하나에 해당하면"*) — 대부분의 라운드는 여기서 걸러진다. 무조건 통과하는 게이트가 아니다.

**선행 문서 A-1의 "시점 불일치" 가설은 확인됐다. 다만 그것만으로는 부족하다** — `common-task-grading`도 "착수/위임 전"이라는 같은 계열의 시점 트리거를 쓰는데 12번 열린다. 시점 정합은 필요조건이지 충분조건이 아니고, **지배적 변수는 조건 ①(자족 불가)**이다. 이 구분이 다음 장의 설계를 결정한다.

## 2. "왜 이번엔 호출되는가" — 이 설계의 기제

문장을 네 번째로 추가하는 것이 아니라, **조건 ①과 ②를 구조적으로 성립시킨다.**

### 2-1. 조건 ①(자족 불가)을 만드는 재료는 이미 손에 있다 — §0-5-3의 조회 함정

지금까지 종결 점검에 대해 조직이 갖고 있던 지식은 *"라운드 끝에 열린 이슈를 보고 닫아라"*였고, 그건 MD 한 줄로 복제 가능했다. 그래서 세 곳에 복제됐고, 그래서 아무도 스킬을 열 이유가 없었다.

**그런데 그 지시를 따라도 결과가 틀린다는 것이 §0-5-3에서 실측으로 드러났다.** 올바른 종결 점검에는 MD 한 줄로 옮겨지지 않는 지식이 필요하다:

- `project_get_context(sections=['wbs'])`는 **종결을 볼 수 없는 뷰**다(done 제외 + summary 없음). 이걸 쓰면 반드시 "done 0건"이 나온다.
- `wbs_list`는 기본값이 done 버킷을 제외한다. **`summary`를 읽거나 `includeDone:true`를 줘야** 실제 진척이 보인다.
- 그룹(부모) 노드는 `status='done'`으로 **바꿀 수 없다**(도구 설명 원문: *"그룹(자식 있는) 노드는 progress/status=done을 직접 지정할 수 없다"*). 실물에도 `status:'planned'`인데 `bucket:'done'`·`computedProgress:100`인 노드가 7건 있다 — 이걸 모르면 "안 닫힌 항목"으로 오인해 헛수고하거나 `STATUS_DONE_LEAF_ONLY` 에러를 맞는다.
- `issue_resolve`에는 `result`가 필수이고, **열린 이슈를 갱신하는 도구가 없다**(도구 설명 원문: *"열린 이슈를 나중에 갱신하는 기능은 없다(issue_update 미제공)"*) — 부분 해소는 "닫고 잔여를 새로 연다"로만 처리된다.
- `issue_record`는 `idempotencyKey`가 필수다 — 잔여를 다시 열 때 키를 어떻게 잡는지 모르면 중복이 생긴다.

> **이 다섯 가지를 모르면 종결 점검의 결과가 틀린다. 그리고 이 다섯 가지는 지금 어느 MD에도 없다.** 조건 ①이 여기서 성립한다 — 새 스킬은 "무엇을 하라"가 아니라 **"어떻게 해야 결과가 맞는가"**를 담고, 그건 요약으로 갈음되지 않는다.

**증거는 §0-5-3의 재현이다.** 같은 hub에 같은 프로젝트(claude-plugins)를 두 방식으로 물었더니 한쪽은 `done:146`, 한쪽은 `status:"done"` 0건이 돌아왔다. 도구 동작 자체가 그렇다 — 이것이 "안 열면 틀린 값을 보게 된다"의 실증이다.

> **여기서 한 가지를 과장하지 않는다.** 이전 판은 이 대목에서 *"종결이 61% 진행된 프로젝트가 done 0건으로 관측됐고 그 위에 설계 위임이 세워졌다"*고 적었다. **그 인과는 확인되지 않았다**(§0-6-1) — 브리핑 수치는 다른 프로젝트의 것이고, 그 수치가 이 함정에서 나왔다는 증거는 없다. 함정의 실재는 확정이고, **함정이 실제 오독을 일으킨 사례는 미확인**이다. 조건 ①의 근거로는 전자만 쓴다.

### 2-2. 조건 ②(시점 정합)를 만드는 방법 — 다시점 스킬에서 종결 절을 떼어낸다

`project-orchestration`이 다시점 스킬인 한, 어느 한 절의 시점에 트리거를 맞추면 나머지 절이 어긋난다. 배치를 아무리 바꿔도 마찬가지다(선행 문서 A-1이 이미 배치 변경을 기각했다).

**그러므로 종결 시점 절을 독립 스킬로 분리해 자기 트리거를 준다.** 그 스킬의 description은 라운드 종결만 가리킨다 — "위임할 때"가 아니라 "**닫을 때**".

### 2-3. 조건 ③(호출 주체가 그 자리에 있는가) — 여기가 완전히 해소되지 않는다

조건 ①·②를 갖춰도, 스킬은 결국 **누군가 호출해야** 실행된다. 그 누군가는 라운드를 닫는 주체(PM)다. 실측이 말하는 것:

- 스킬 description은 매 세션 전 에이전트에게 주입된다. 기준선 42세션 내내 `project-orchestration`의 description이 모델 눈앞에 있었지만 메인 세션에서 0회 발동했다.
- **description 단독 트리거가 "라운드 종결" 시점에 발동한 사례는 이 표본에 한 건도 없다.**
- 반대로 에이전트 MD의 **자기검증 체크리스트 항목**으로 박힌 스킬은 12회 열렸다.

→ 따라서 **description만으로 충분하다고 주장할 근거가 없다.** 이것이 §6에서 **상시 자산 한 곳에 트리거를 심어야 하는 이유**이고(어느 자산인지는 §6-1의 도달 범위 실측이 정한다), 동시에 이 설계가 요구사항 3을 완전히 충족하지 못하는 이유다(§5).

## 3. 설계 — 무엇을 만드는가

### 3-1. 구성

```
[신설]  skills/project-closure-check/SKILL.md        ← 이름은 제안. project-* 계열에 맞춤
          └ 목표 크기 3~5KB (조건부 비용: 호출 시에만 로드)
          └ description: "라운드를 닫기 직전"만 트리거로 지목
          └ 내용: 조회 절차(파라미터 함정 포함) + 겹침 판정 + 종결 실행 + 비정상 케이스

[이관]  skills/project-orchestration/SKILL.md §5의 5항
          └ 본문을 새 스킬로 옮기고, 그 자리에는 포인터 한 줄만 남긴다 (본문 바이트 감소)

[한 줄]  hooks/pm-orchestration-block.md 15행 다음에 포인터 1줄(278B)  ← §6-4·6-7이 권고
```

**트리거를 어느 상시 자산에 심을지는 §6이 4개 후보를 비교해 따로 판단한다.** 위 구성은 §6-7의 권고안(② 훅 블록 + ① 스킬)을 반영한 것이고, `agents/pm.md`는 **지금은 무변경**을 권고한다(§6-6 — 메인 세션 도달률 0%가 실측됐다). 이전 판은 반대로 `pm.md` 한 줄 + 훅 블록 무변경을 권고했는데, **§6-1의 도달 범위 실측이 그 권고를 뒤집었다.**

### 3-2. 새 스킬이 호출된 뒤 실제로 하는 일 (훅과 달리 **진짜 검증**이 가능한 부분)

아래는 스킬 본문의 **요구사항**이다. 최종 문안은 trainer가 제안하고 PM이 검증한다(위임 지시서에 설계를 쓰지 않는다는 이 저장소 규율).

**단계 0 — 대상 확정**
- `projectId`는 `<cwd>/STATUS.md` 상단에서 읽는다. 없으면 **`project_bootstrap`을 부르지 않는다**(없는 프로젝트를 새로 만들어버린다) — 사람에게 묻고 종결 점검은 "미수행 + 사유"로 보고한다.

**단계 1 — WBS 실상태 조회 (여기가 함정 구간)**
- `wbs_list(projectId, includeDone:true)`를 부른다.
- 판정은 **`summary` 블록**(`total/planned/inProgress/done/delayed`)으로 한다. items 배열을 세지 않는다.
- **`project_get_context(sections=['wbs'])`를 이 용도로 쓰지 않는다** — done이 빠지고 summary가 없어 반드시 "종결 0건"이 나온다.
- `summary.total === 0`이면 이 프로젝트는 WBS를 쓰지 않는다 → 단계 2로 건너뛴다(WBS 미사용 프로젝트에 대한 오탐 방지).

**단계 2 — 이번 라운드와 겹치는 항목 선별 (훅이 못 하던 일)**
- 이번 라운드가 손댄 파일·주제를 기준으로 겹치는 **리프** 항목을 고른다.
- **그룹 노드는 후보에서 제외한다** — `status`를 done으로 바꿀 수 없고(`STATUS_DONE_LEAF_ONLY`), 자식 롤업인 `bucket`·`computedProgress`가 진짜 신호다. `status:'planned'` + `bucket:'done'`은 정상이지 미종결이 아니다.
- 겹침 판정은 **모델이 한다.** 훅 설계에서는 이걸 "판정하지 않는다"고 명시해야 했지만(문자열 매칭은 위조 가능), 스킬은 라운드의 맥락을 갖고 있으므로 판정할 수 있다. **이것이 스킬 방식의 실질 이득이다.**

**단계 3 — 이슈 조회·선별**
- `project_get_context(projectId, sections=['issues'], limit=50)` — 이 도구는 **열린 이슈만** 돌려주므로 이 용도에는 맞다(단계 1과 달리 여기서는 올바른 도구다. 두 도구의 용도가 다르다는 것 자체를 스킬이 명시해야 한다).
- 열린 이슈가 많으면(claude-plugins 확정값 **14건** — §0-5-2) 전량을 훑지 않는다. 이번 라운드가 손댄 파일·주제와 겹치는 것만 고른다.
- **reviewer 등 검증 전용 역할이 보고서에 "종결 후보"로 지목한 것을 여기서 수거한다** — 그들은 지목까지만 하므로 수거하지 않으면 그 지목은 어디에도 도달하지 않는다(현행 §5의 이 문장은 그대로 유효하므로 이관한다).

**단계 4 — 실물 대조 후 종결**
- 겹치는 항목이라도 **실물로 해소를 확인한 뒤에만** 닫는다(claimed ≠ verified). 확인 수단이 없으면 닫지 않고 "확인 불가"로 보고한다.
- WBS: `wbs_update(projectId, id, status:'done', progress:100, completedDate:<YYYY-MM-DD>)` — `completedDate`를 함께 적는다. **malgn-vscode 전사 247개 전량**(§0-6-1 측정 범위)에서 `status='done'` **56회 중 `completedDate`가 동반된 것은 29회(52%)**뿐이다 → **누락이 실제로 잦은 지점**이라 스킬이 못을 박아야 한다. 이 수치는 §0-6의 가설 판별과 무관하게 성립한다(호출은 실재하고, 그 인자에 무엇이 들어갔는지는 전사만으로 확정된다).
- 이슈: `issue_resolve(projectId, issueId, result)` — `result`는 필수다.
- **부분 해소**: `result`에 해소분·잔여분을 적어 닫고, 잔여만 `issue_record`로 다시 연다. 열린 이슈를 갱신하는 도구는 없다. 재등록 시 `idempotencyKey`는 원 이슈와 구분되게 잡는다(같은 키를 재사용하면 새 이슈가 생기지 않는다).

**단계 5 — 결과 보고 (침묵 금지)**
- 닫은 것, 남긴 것과 사유, 확인 불가한 것을 라운드 보고에 싣는다.
- **닫을 것이 없으면 "없음"을 명시한다.** 조용히 넘어가지 않는 것이 이 스킬이 남기는 유일한 흔적이다(§5의 한계와 직결).

## 4. 프로젝트 고유성 (설계 4대 의무 ②)

이 설계에서 표준적인 부분(스킬을 만들고 MD에서 참조한다)은 짧게 지나가고, 깊이를 준 곳은 둘이다:

> **① `wbs_list` / `project_get_context`의 기본 파라미터가 종결을 숨긴다**는 이 조직 고유의 실측 사실(§0-5-3).
>
> **② 제품 자산별 도달 범위**(§6-1) — `hooks/pm-orchestration-block.md`는 메인 세션 44/44에 닿고 `agents/pm.md`는 0/44에 닿는다. 이건 malgn-agent의 로드 구조에서만 성립하는 값이고, **"가장 정확한 시점"과 "실제로 닿는 자리"가 다르다**는 것을 보여준다.

①은 malgnai-hub의 특정 도구 스키마에서만, ②는 이 플러그인의 훅·에이전트 구성에서만 성립한다 — 다른 프로젝트에 복붙되지 않는다. 그리고 이 설계의 **호출 동기 전체**가 여기서 나온다 — 조건 ①(자족 불가)을 성립시키는 재료가 이것이고, 이것 없이는 "문장 네 번째 추가"와 구조적으로 같아진다.

부수적으로: 이 발견은 **선행 조사에서 나오지 않았다.** 훅 기반 설계는 로컬 트랜스크립트만 관측했기 때문에 hub를 실제로 물어볼 수 없었고, 그래서 이 함정에 닿지 못했다. 확정 사실 3("스킬은 진짜 상태를 확인할 수 있다")이 설계 단계에서부터 배당을 냈다는 것 자체가 방향 전환의 사후 근거다.

## 5. 요구사항 3(사람에게 지속 리마인드)의 충족 수준 — **미충족으로 남는다**

숨기지 않고 적는다.

| 요구 | 훅 설계(폐기)가 주던 것 | 이 설계가 주는 것 |
|---|---|---|
| 라운드 종결 시점에 점검이 **발동**한다 | 기계적 보장(Stop 이벤트) | **보장 없음.** 모델이 호출해야 한다 |
| 점검이 **진짜 상태**를 본다 | 불가(트랜스크립트 관측뿐, 지연 오탐 있음) | **가능.** hub 직접 조회 — 이 설계가 더 강한 유일한 축 |
| 이번 라운드와 **겹치는지** 판정한다 | 불가(의도적으로 배제) | **가능.** 라운드 맥락을 모델이 갖고 있다 |
| 안 했을 때 **사람이 안다** | Stop `systemMessage` 한 줄 | **없음.** 스킬을 안 열면 흔적이 0이다 |
| **세션을 넘어 반복** 노출된다 | SessionStart + 원장 `pendingRounds` | **없음.** 스킬은 상태를 가질 수 없다 |
| 사람이 **끌 수 있다** | 환경변수 | 해당 없음(끌 것이 없다) |

**정직한 총평**: 이 설계는 "점검이 돌면 결과가 맞다"를 크게 개선하지만, **"점검이 돌게 만든다"와 "안 돌았을 때 알린다"는 훅보다 약하고, 후자는 사실상 0이다.** 훅이 제외된 이상 로컬에서 상태를 들고 있다가 다음 세션에 사람에게 말해줄 주체가 아무도 없다.

### 5-1. 옵션 2(훅 블록 보강)는 이 격차를 닫는가 — **닫지 못한다. 혼동하기 쉬운 지점이라 못을 박는다**

`hooks/pm-orchestration-block.md`를 보강하면 "매 세션 강제 주입"이므로 사람에게도 보일 것 같지만, **아니다.** 실물로 확인했다.

| 필드 | 누가 받는가 | PM 블록이 쓰는가 |
|---|---|---|
| `hookSpecificOutput.additionalContext` | **모델만**(대화 컨텍스트) | **이것을 쓴다** — `hooks/sessionstart-context.mjs`의 `emit()`이 본문 전체를 여기 싣는다 |
| `systemMessage` | **사람만**(터미널) | **본문에는 쓰지 않는다.** 이 훅에서 `systemMessage`가 채워지는 경우는 STATUS.md가 잘렸을 때의 경고 한 줄뿐이다 |

> **판정: 옵션 2가 만드는 것은 "모델에게 매 세션 닿는 경로"이지 "사람에게 보이는 경로"가 아니다.** 요구사항 3의 *발동* 축은 옵션 2가 크게 개선하지만(§6-4), *"안 했을 때 사람이 안다"* 축은 **여전히 0**이다.

### 5-2. 이미 배포된 Stop 훅 — 이 문서가 그동안 계산에 넣지 않았던 자산

`malgn-agent/hooks/stop-mcp-reminder.cjs`가 이미 Stop 이벤트에 붙어 있고, 실물을 열어보니 **종결 지시가 이 파일에도 이미 들어 있다**:

- `reason` 문자열이 네 도구를 열거하며 그중 하나가 *"`issue_resolve` — 그 이슈가 해소된 것을 확인했을 때 닫는 도구"*다.
- 출력은 `additionalContext`(모델) + `systemMessage` 한 줄(사람) **둘 다**다.

**그럼에도 이 훅은 종결 채널이 되지 못한다.** 발동 조건이 `hasWriteSignal && !alreadyRecorded`인데, `alreadyRecorded`는 **네 기록 도구 중 무엇이든 하나만 쓰이면 참**이 된다(`MCP_RECORD_TOOL_RE`). 즉 **`work_record`만 남기고 `issue_resolve`를 한 번도 안 부른 라운드에서는 훅이 침묵한다** — 종결 누락은 이 훅의 감지 대상이 아니다.

이 발견은 두 방향으로 작용한다:

| | 함의 |
|---|---|
| **이 설계에 유리** | "사람이 안다" 축이 완전한 0은 아니다. 기록을 **아무것도** 안 한 라운드는 이미 잡힌다 |
| **이 설계에 불리(더 중요)** | **"종결하라"는 지시가 있는 자리는 세 곳이 아니라 네 곳이었다**(선행 문서 §0-3이 센 세 곳 + 이 훅). 그리고 그 네 번째는 **매 턴 발동하는 훅**인데도 종결을 만들어내지 못했다. **"상시 텍스트에 문장을 한 줄 더 얹는다"는 접근(옵션 2·3·4가 전부 여기 속한다)의 기대효과를 낮춰 잡아야 한다는 실증**이다 |

### 5-3. 부분 보완 후보

어느 것도 이 격차를 닫지 못한다:

| 후보 | 평가 |
|---|---|
| hub `state`(`health`·`progress`)를 다음 세션 부트스트랩 L1에서 읽게 한다 | 새 자산 0. 그러나 **신뢰할 수 없다** — 관측된 `state`는 `phase:"completed"`인데 `progress:63`·`health:"warning"`으로 자체 모순이다(수동 갱신값이라 stale). 이걸 리마인드 채널로 삼으면 틀린 신호를 매 세션 주입한다 |
| `STATUS.md`에 "열린 이슈 N건" 한 줄 | 매 세션 자동 주입되는 채널. 그러나 ①3,000B 상한과 경합 ②갱신 주체가 또 PM이라 **같은 누락에 그대로 걸린다**(안 닫은 사람이 그 줄을 갱신할 리 없다) |
| Stop 훅의 발동 조건을 "종결 도구 미사용"까지 넓힌다 | **요구사항 3을 실제로 닫을 수 있는 유일한 후보**다(사람 가시 `systemMessage`를 이미 갖고 있다). **다만 이번 스코프 밖**(확정 사실 1) — 그리고 확정 사실 1이 훅을 배제한 근거는 *hub 인증*이었는데 **이 훅은 hub를 부르지 않는다**(로컬 전사만 읽는다). 즉 **배제 근거가 이 후보에는 적용되지 않는다.** §8의 갈림길로 올린다 |

> **이 격차를 받아들일지는 사람이 판단한다.** 설계가 요구를 다 못 채운다는 사실을 설계자가 숨기면 판단의 근거가 사라진다.

## 6. 어디에 심을 것인가 — 4개 후보 비교

### 6-0. 이 장이 답하는 질문

스킬 신설(§3)은 조건 ①(자족 불가)과 ②(시점 정합)를 만든다. **조건 ③(호출 주체가 그 자리에서 실제로 부른다)은 만들지 못한다.** 남는 트리거는 description 하나인데, 이 표본에서 **description 단독 트리거가 라운드 종결 시점에 발동한 사례가 0건**이다.

그래서 "어느 상시 자산에 트리거를 심을 것인가"를 별도로 정해야 한다. 후보는 넷이다.

### 6-1. 먼저 실측 — 각 자산이 **누구에게** 닿는가 (이 장의 결론을 뒤집은 측정)

### 6-3. 옵션 1 — 스킬 신설 (설계 본문은 §3)

조건 ①·②를 만드는 유일한 후보이고, **§0-6-3의 "공통 항목"(올바른 조회 절차)을 담을 그릇**이다. 다른 옵션들은 전부 "포인터"일 뿐 절차 자체를 담지 못한다(담으면 상시비용이 KB 단위로 는다).

**약점은 §5-2가 새로 실증했다** — "지시 문장을 상시 자산에 한 줄 더" 접근은 이미 네 곳에서 시도됐고(§0-3의 세 곳 + Stop 훅) 종결을 만들어내지 못했다. 그러므로 **옵션 1은 단독으로도 불충분하지만, 다른 옵션들도 옵션 1 없이는 "무엇을 어떻게"를 전달하지 못한다.**

### 6-4. 옵션 2 — `hooks/pm-orchestration-block.md` 보강 (**가장 유력**)

#### 이 파일의 존재 목적에 정합하는가

**정합한다.** 이 파일은 PM 행동규율의 정본이고, **15행이 이미 종결과 같은 층의 문장을 싣고 있다**:

> *"**마친 작업은 그 자리에서 기록한다** — 결정·이슈·작업 결과를 malgnai-hub(`decision_record`/`issue_record`/`work_record`)에 남기고…"*

이 문장이 다루는 것은 **새로 여는 것(기록)**이다. 열거된 세 도구에 **`issue_resolve`가 없다** — **이미 열린 것을 재점검해 닫는 것**은 이 블록 어디에도 없다. 공백이 정확히 이 항목 모양으로 비어 있다.

17행(*"상세 절차는 Skill `project-orchestration`을 호출해 따른다"*)이 유일한 스킬 포인터인데, 그것이 바로 실측상 메인 세션에서 **0회** 열린 그 트리거다. 같은 자리에 포인터를 하나 더 얹는 것이므로 **구조는 이미 있고 대상만 바뀐다.**

#### 상시비용 — "`pm.md`만 피하면 공짜"가 아니다

이 저장소 [에이전트 업그레이드 원칙]의 상시비용 규율을 **이 파일에도 동일하게** 적용한다.

| | 값 |
|---|---|
| 현재 크기 | **3,447B** |
| 최소판 추가 | **278B** (+8.1%) |
| 전체판 추가 | **410B** (+11.9%) |
| 곱셈 단위(실측) | **48** (메인 44 + 서브 4) — 옵션 4의 **약 7배** |
| 총 추가 바이트(같은 표본 기준) | 최소판 278×48 ≈ **13.3KB** vs 옵션 4 442×7 ≈ **3.1KB** |

**순이득 정당화 시도(정직하게):**
- **찬성 근거**: 이 278B가 닿는 자리가 **종결을 실제로 수행하는 유일한 자리**다(§6-1 — 메인 세션 100%). 옵션 4의 442B는 3.1KB로 싸지만 **종결 주체의 0%**에 닿는다. **싼 쪽이 도달하지 않으면 그건 절약이 아니라 낭비다.**
- **반대 근거(약하지 않다)**: §5-2가 보여준 대로 **상시 텍스트에 문장을 얹는 방식은 이미 네 번 실패했다.** 278B × 48이 실제 행동 개선으로 바뀐다는 **직접 증거는 없고**, 이 문서가 댈 수 있는 것은 "닿기는 한다"까지다. 도달은 필요조건이지 충분조건이 아니다(§1-4가 `common-task-grading`으로 이미 보인 논리와 같다).

> **판정: 도달 범위에서 옵션 2가 압도적이고, 효과 증명에서는 어느 옵션도 증거가 없다.** 이 상태에서 고른다면 "닿는 쪽"을 고르는 것이 합리적이지만, **"늘어난 바이트만큼 행동이 개선된다"는 증명은 이 문서가 제출하지 못한다.** 그 미검증을 감수할지는 사람이 정한다(§8).

#### 후보 문안 (trainer가 최종 문안을 제안하고 PM이 검증한다)

**최소판 (278B) — 15행 다음에 한 줄:**

> `**열어둔 것은 닫고 나서 보고한다** — 라운드를 닫기 직전 Skill \`project-closure-check\`를 호출해 WBS·이슈 현황을 실제 조회로 대조한다. 조회 파라미터를 잘못 고르면 종결된 항목이 목록에서 통째로 빠져 오독된다.`

**전체판 (410B)** 은 스킬 포인터 없이도 무엇을 해야 하는지 알 수 있게 도구까지 적는다 — 그러나 **그렇게 하면 조건 ①(자족 불가)이 깨져 스킬이 다시 안 열린다.** §1-3이 규명한 실패 패턴을 그대로 재현하는 꼴이다. **그러므로 최소판을 권고한다** — 포인터만 두고 절차는 스킬에만 둔다.

#### 요구사항 3에 대한 판정

**바꾸지 못한다.** §5-1에서 실물로 확인했다 — 이 훅은 본문을 `additionalContext`로만 보내고 `systemMessage`는 STATUS.md 절단 경고에만 쓴다. **모델 컨텍스트에 들어가지 사람 터미널에 뜨지 않는다.** "매 세션 강제 주입 = 사람도 본다"는 혼동을 이 문서는 명시적으로 기각한다.

### 6-5. 옵션 3 — 스캐폴딩 CLAUDE.md 템플릿 (**기각 권고**)

#### 먼저 사실 정정 — 그 문구는 생성되는 CLAUDE.md 안에 없다

브리핑은 *"생성되는 CLAUDE.md 안에 'PM 행동규율은 CLAUDE.md 본문에 들어가지 않는다'는 문구가 박혀 있다"*고 적었다. **실물과 다르다.**

| 위치 | 실제 내용 |
|---|---|
| `bin/new-project.mjs`:114~137 — **생성되는 CLAUDE.md 템플릿 본문** | 부트스트랩 3층 · STATUS.md 재작성 6트리거 · Project Overview · Tech Stack · Architecture. **PM 규율 관련 문구 없음** |
| `bin/new-project.mjs`:207 — **`console.log` 5번(스캐폴드 직후 터미널 출력)** | *"PM 행동규율은 CLAUDE.md 본문에 들어가지 않는다 — … SessionStart 훅이 매 세션 시작 시 그 정본(hooks/pm-orchestration-block.md)을 그대로 주입한다…"* |

**그래서 충돌의 성격이 달라진다.** 생성물 안의 문장과 모순되는 것이 아니라, **스캐폴더가 사람에게 선언한 설계 의도와 모순된다.** 문서상 모순은 아니지만 **원칙 위반이라는 점은 동일하다** — 오히려 "생성물엔 안 적혀 있으니 슬쩍 넣어도 티가 안 난다"는 점에서 더 나쁘다.

#### 이 항목 하나만 예외로 둘 근거가 있는가 — **없다고 본다**

그 원칙이 존재하는 이유는 **정본을 고쳐도 옛 사본이 낡은 채 남는 것을 막기 위해서**다. 종결 점검 절차는 **바로 그 "앞으로 고쳐질" 종류의 내용**이다 — 조회 함정은 hub 도구 스키마에 달려 있고, hub가 `project_get_context(sections=['wbs'])`에 summary를 실어주면(§8-7) 그 문장은 **즉시 거짓이 된다.** 그때 각 프로젝트 CLAUDE.md에 흩어진 사본은 아무도 갱신하지 않는다. **원칙이 막으려던 실패 양상에 이 항목이 정확히 해당한다.**

#### 반대 방향 증거도 있다 — 그러나 다른 것을 설명한다

claude-plugins 자신의 두꺼운 CLAUDE.md(PM 규율이 증폭된)가 malgn-vscode의 얇은 표준 CLAUDE.md보다 준수율이 좋았다는 관찰이 있다. **다만 이건 "CLAUDE.md에 넣어야 한다"를 지지하지 않는다** — 두 프로젝트는 성격·작업 종류·사람의 개입 빈도가 전부 다르고, 이 관찰에는 통제군이 없다. 지지되는 것은 **"프로젝트 고유 규율은 그 프로젝트 CLAUDE.md에 적으면 잘 지켜진다"**이지 **"제품 공통 규율을 프로젝트마다 복사하면 잘 지켜진다"**가 아니다. 종결 점검은 후자다.

#### 근본 한계 — 단독 해법이 될 수 없다

**템플릿을 고쳐도 이미 만들어진 프로젝트에는 소급되지 않는다.** malgn-vscode를 포함해 지금 문제가 관측된 프로젝트 전부가 대상에서 빠진다. **보완재로만 의미가 있고, 보완재치고는 원칙 비용이 너무 크다.**

#### 그래도 채택한다면 (조건부 명세)

- **위치**: 생성 CLAUDE.md의 `## 새 세션 부트스트랩` 절 아래 `**필수 규율:**` 줄(127행) 뒤에 한 줄. Project Overview 위.
- **분량**: 1줄 ~300B. 절차는 절대 넣지 않고 포인터만 — 넣는 순간 사본 드리프트가 시작된다.

### 6-7. 조합 권고 — 하나만 쓸 것인가

**단독으로 조건 ①②③을 다 만드는 옵션은 없다.** 매핑하면 이렇다:

| 조합 | 조건 ①<br>(자족 불가) | 조건 ②<br>(시점 정합) | 조건 ③<br>(실제로 부르는가) | 상시비용 순증 | 평가 |
|---|---|---|---|---|---|
| **①만** | ✅ 스킬 본문이 절차를 독점 | ✅ description이 종결만 지목 | ❌ 메인 세션 0회 전례 | ~300B(desc) | 조회 절차는 남지만 안 열릴 공산이 크다 |
| **②만** | ❌ 절차가 없어 "닫아라"만 반복 | ✅ | ⚠️ 닿지만 무엇을 할지 모름 | 278B×48 | 다섯 번째 잔소리가 된다(§5-2) |
| **③만** | ❌ | ⚠️ | ❌ 기존 프로젝트 제외 | ~300B | **단독 불가** |
| **④만** | ⚠️ | ✅ | ❌ 메인 세션 도달 0% | 442B×7 | 서브에이전트 PM 라운드에만 듣는다 |
| **② + ①** ⭐ | ✅ 절차는 스킬에만 | ✅ 블록 문면이 "닫기 직전"을 못 박음 | **✅ 상시 자산 중 유일하게 메인 세션 100% 도달** | 278B×48 + ~300B(desc) | **권고안** |
| ② + ① + ④ | ✅ | ✅ | ✅ + 서브에이전트 PM까지 | 위 + 442B×7 | 도달률 최대. 다만 같은 지시가 두 자리에 생겨 [변경이력 관리 원칙]의 사본 문제가 시작된다 — **한쪽만 갱신되면 갈린다** |

**권고: ② + ① (블록에 포인터 한 줄 + 절차는 스킬에).** 근거:
1. **역할 분담이 자연스럽다.** 블록은 "언제 무엇을 해야 하는가"의 정본이고(15행이 이미 그 층위), 스킬은 "어떻게 해야 결과가 맞는가"를 담는다. 절차를 블록에 넣으면 상시비용이 KB로 뛰고 조건 ①이 깨진다.
2. **도달과 내용이 각각 최적의 자리에 간다.** ②가 도달을, ①이 내용을 맡는다.
3. **④를 빼는 이유**: 같은 지시를 두 자리에 두면 사본이 생긴다. **먼저 ②+①로 가고, 서브에이전트 PM 라운드에서도 누락이 관측되면 그때 ④를 추가**하는 것이 이 저장소 원칙에 맞다.

**반대 결론도 성립한다 — 단정하지 않는다:**
- 새 스킬의 description은 **지금까지 존재한 적 없는 트리거**("라운드를 닫을 때")를 갖는다. "42세션 내내 눈앞에 있었는데 0회"라는 반례는 **다른 문구의 description**(위임·추적 시점)에 대한 것이라 그대로 적용되지 않는다. → **①만 먼저 배포하고 호출률을 전사로 측정한 뒤** ②를 추가하면, 그 278B×48의 효과를 **실제로 검증**할 수 있다. 지금은 추정뿐이다.
- 이 순서가 이 저장소의 **변경 동결 원칙**과 더 정합한다.

**나는 ②+①을 권고하되, "①먼저 → 측정 → ②"가 더 안전하다는 점을 인정한다.** §8-1로 올린다.

## 7. 이 설계가 하지 않는 것 (범위 명시)

- `userConfig.device_token`을 기본 인증으로 승격하는 것 — 확정 사실 2.
- hub 서버에 종결 점검용 REST/도구를 신설하는 것 — 이 저장소 범위 밖. 단 **`project_get_context(sections=['wbs'])`에 summary 블록이 없는 것**은 hub 쪽 개선 후보로 기록해 둘 가치가 있다(§8).
- 이슈 **등록** 품질 문제(§3-3 마지막 행의 XML 조각 혼입) — 별건.
- **malgn-vscode의 hub 상태를 판정하는 것** — 이 세션에서 원리적으로 불가능하다(§0-5-1). 가설 판별은 malgn-vscode 세션이 도구 1회를 호출해야 끝난다(§0-6-2).
- `agents/pm.md`·`skills/`·`hooks/`·`bin/` 파일 편집 — MD는 trainer, 코드는 backend-dev 전담.

## 8. 사람이 결정해야 하는 갈림길

> **0번을 먼저 본다 — 가장 싸고, 다른 모든 판단의 전제를 바꾼다.**

0. **가설을 먼저 판별할 것인가** (§0-6). **malgn-vscode 세션에서 `wbs_list(projectId, includeDone:true)`를 1회 불러 `summary.done`을 보면** "진짜 미갱신(가설 1)"과 "조회 함정의 산물(가설 2·3)"이 그 자리에서 갈린다. **이 설계의 어느 옵션보다 싸다(도구 호출 1회).** 결과에 따라 처방의 무게중심이 옮겨간다 — done이 크면 **조회 절차 교정(옵션 1)** 쪽으로, 0에 가까우면 **트리거 강화(옵션 2)** 쪽으로. 판별 없이 진행해도 §0-6-3의 공통 항목은 어차피 필요하므로 **진행을 막지는 않지만, 우선순위 배분이 달라진다.**
1. **어느 조합으로 가는가** (§6-7). 권고는 **②+①**(훅 블록 포인터 278B + 스킬)이다. 대안은 **①먼저 → 호출률 측정 → ② 추가**로, 한 라운드를 더 쓰는 대신 278B×48의 효과를 **추정이 아니라 측정**으로 판단하게 된다. **이전 판의 권고(`pm.md` 한 줄)는 §6-1 도달률 실측으로 철회했다.**
2. **옵션 2의 상시비용 순증(278B × 48)을 감수하는가** (§6-4). 도달 범위는 실측으로 압도적이지만, **"늘어난 바이트만큼 행동이 개선된다"는 직접 증거는 이 문서가 제출하지 못한다.** §5-2는 오히려 상시 텍스트 한 줄 추가가 네 번 실패한 전례를 보인다.
3. **스킬 신설이 변경 동결 원칙을 통과하는가.** 이 저장소 규칙상 "신규 스킬 신설"은 **보류 대상(구조 변경)**이다. 다만 §0-5-3의 조회 함정은 **PM이 직접 재현한 실증 결함**(같은 프로젝트를 두 방식으로 물어 done 146 vs done 0)이라 "결함 수정" 쪽으로 볼 여지가 있다. **이 분류는 사용자만 정할 수 있다.**
4. **최소안으로 축소할 것인가.** 스킬을 신설하지 않고 **조회 함정 다섯 줄만 기존 `project-orchestration` §5에 보태는** 안이 있다. 결함 수정에 가장 가깝고 변경이 가장 작다. 그러나 조건 ②(시점 정합)를 못 고치므로 "열리지 않는 파일 안의 정확한 정보"가 된다 — **효과는 낮지만 리스크도 낮다.**
5. **옵션 3(스캐폴딩 템플릿)을 기각하는가** (§6-5). 이 문서는 **기각을 권고**한다 — 소급이 안 되고, 스캐폴더가 의도적으로 세운 "PM 규율은 제품 정본 하나로 모은다"를 깬다. **다만 "신규 프로젝트만이라도 챙기자"는 반대 판단도 성립하므로 사람이 정한다.**
6. **요구사항 3의 미충족을 받아들이는가** (§5). **옵션 2는 이 축을 바꾸지 못한다**(§5-1 — 훅 주입은 모델 컨텍스트이지 사람 터미널이 아니다). 받아들이지 않는다면 남은 길은 **Stop 훅의 발동 조건 확장** 하나이고(§5-3), 그건 hub 인증이 필요 없어 **확정 사실 1의 배제 근거가 적용되지 않는다** — 재검토할지 정해야 한다.
7. **hub 쪽 개선을 별도 트랙으로 여는가** — `project_get_context(sections=['wbs'])`에 summary를 실어주면 이 함정 자체가 사라진다. 이 저장소 범위 밖이지만 **근본 해결에 가장 가깝고, 그게 되면 옵션 1 본문의 상당 부분이 불필요해진다.**
8. **스킬 이름** — `project-closure-check`는 제안이다. `project-*` 계열(orchestration/standards/retrospective)과 정합하고, 참조 에이전트가 1종이라 무접두어 규칙에도 맞는다.

## 9. 자기 검증 (설계 4대 의무 대조)

- **① 트레이드오프**: 스킬 신설 vs 대안 2종(§3-4), **상시 자산 4후보 비교표와 조합 매핑(§6-2·§6-7)**, 최소안(§8-4)까지 각각 선택/대안/이유/포기한 것/감당 방안을 적었다. 상시비용 순증을 "괜찮다"로 넘기지 않고 **바이트를 실제로 재서** 적었고, **효과 증거가 없다는 사실도 같이 적었다.**
- **② 고유성**: 표준 부분(스킬 신설·MD 참조)은 짧게 지나가고, 이 조직 고유의 도구 스키마 함정(§0-5-3·§2-1)과 **제품 자산별 도달 범위 실측(§6-1)**에 분량을 집중했다.
- **③ 비정상 케이스**: hub 실패 폴백·projectId 부재·WBS 미사용·그룹 노드 제약·멱등성·대량 이슈·위조·응답 토큰 폭증을 §3-3·§3-5에 넣었다.
- **④ 완결성**: 도구 호출을 인자 단위로 적었고(`includeDone`·`completedDate`·`result`·`idempotencyKey`), 각 도구의 제약을 스키마 원문에서 확인해 인용했다.
- **상태 라벨 규율 — 이 문서가 한 번 어겼고 §0-5-1에서 정정했다.** 이전 판은 claude-plugins를 조회하고 malgn-vscode 라벨을 붙여 "브리핑이 틀렸다"고 결론지었다. 이 판부터 **모든 수치에 프로젝트·도구·옵션·시점을 병기**한다.
- **미검증으로 남는 것 (셋)**:
  1. 이 설계가 실제로 호출률을 올리는지 — 배포 후 전사 재측정으로만 확인된다.
  2. **malgn-vscode의 hub 실제 상태** — 이 세션에서 조회 불가. §0-6의 가설이 갈리지 않은 채 남아 있다(판별 방법은 §8-0).
  3. **전사에서 센 종결 도구 호출이 성공했는지** — 호출을 셌지 성공/실패 응답은 세지 않았다.
