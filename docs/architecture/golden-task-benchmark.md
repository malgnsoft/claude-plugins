# 골든 태스크 벤치마크 — 설계

`malgn-agent`의 개별 에이전트를 **같은 과제로 반복 채점**해 시간에 따른 변화를 보는 체계.

지금까지 이 저장소에는 영속 저장된 골든 테스트케이스가 0건이었다. `domain-training-scorecard-eval`의
"Eval Set" 항목(가중치 25%)은 채점자가 매 회차 시나리오를 즉석에서 고르고 Pass/Partial/Fail만 남긴 뒤
시나리오 자체는 휘발된다. 그래서 "지난달보다 나아졌나"에 답할 수 없었다. 이 문서는 그 빈자리를 메운다.

기존 Scorecard의 "Eval Set" 이름·가중치·환산식은 **바꾸지 않는다.** 그 항목에 인용할 고정 자산을 공급할 뿐이다.

**구성물**
| 무엇 | 어디 | 배포됨? |
|---|---|---|
| 케이스 파일 | `malgn-agent/evals/<case>/` | 예(45개 파일 47,026 B — 디스크만, 컨텍스트 비용 0. §1) |
| 실행 래퍼 | `scripts/run-golden-eval.mjs` (`pnpm run eval:golden`) | 아니오 |
| 실행 이력 | `docs/evaluation/golden-task/history.jsonl` | 예(1회 = 1줄) |
| 실행 원본 | `docs/evaluation/golden-task/runs/` | 아니오(`.gitignore`) |

## 0. 하네스 사실관계 — 전부 이 PC에서 실행으로 확인했다

기억이나 요약이 아니라 실행 결과다. **`--help` 출력은 근거로 쓰지 않았다** — 이 라운드에서
`--help`와 실제 실행이 갈렸기 때문이다(아래 첫 줄).

| 사실 | 확인 방법 |
|---|---|
| `claude plugin eval`은 **얼리액세스 게이트로 막혀 있다** — 실행 시 `` `plugin eval` is currently in early access `` + exit 1 | 빈 디렉터리에서 직접 실행 |
| 그런데 `--help`는 게이트와 무관하게 정상 출력된다 | 위와 대조. **`--help`가 나온다 ≠ 실행 가능** |
| 게이트는 **조직 단위로 승인**돼야 열린다. 이 조직은 아직 승인 전이다 | 위와 동일 |
| 서브에이전트 멘션 표기는 `@agent-<plugin>:<agent>` | `docs/anthropic/agents/sub-agents.md`. `@<plugin>:<agent>`는 **틀린 표기** |
| eval 디렉터리는 **플러그인 루트 아래**여야 한다(절대경로·`..`·컴포넌트 디렉터리 불가) | 하네스 검증 메시지 원문 |
| HTML 리포트는 계정이 지원하면 **기본으로 claude.ai에 발행된다** | `--publish-report`가 "이미 기본값"이라고 명시 |
| `--allow-tools` 없이 케이스가 요구한 `Write`는 **거부**된다(하네스가 사전 경고까지 출력) | 승인 유/무 2회 대조 실행 |
| **케이스가 `allowed_tools`에 아예 적지 않은 도구(`Bash`)는 승인 없이도 실행된다** | `allowed_tools: [Read]`만 준 케이스에서 Bash 호출 성공 |
| 자식 세션 도구 목록에 **운영자 계정의 claude.ai 커넥터(Gmail·Drive·Calendar)가 등록돼 있다** | 실행 trace의 `init` 메시지 |
| 서브에이전트(`Agent` 도구)는 **비동기로 뜬다** — 즉시 반환되고 부모는 완료 알림을 기다려야 한다 | trace의 `Async agent launched successfully` + `task_progress` 이벤트 |

> **결론 하나: `plugin eval`은 OS 샌드박스가 아니다.** 하네스 문서도 "케이스를 돌리는 것은 그
> 플러그인을 설치하는 것과 같은 신뢰 결정"이라고 적는다. 우리가 쓴 케이스만 이 래퍼로 돌린다.

> **§5의 실측 비용·점수는 게이트가 열려 있던 1회성 실행에서 얻은 값이다.** 지금 이 저장소
> 상태에서 `pnpm run eval:golden`을 돌리면 승인 전이라 위 첫 줄의 메시지와 함께 실패한다.
> 재현하려면 조직 단위 정식 승인이 먼저다(§9 R1).

## 1. 케이스 파일 위치 → `malgn-agent/evals/`

**결정:** `malgn-agent/evals/<case-name>/`. 기본 위치를 그대로 쓰고 `--eval-dir`을 쓰지 않는다.

| 안 | 내용 | 판정 |
|---|---|---|
| **A. `malgn-agent/evals/` (채택)** | 하네스 기본 위치 | 배포 트리에 케이스가 실린다(47,026 B) |
| B. 저장소 루트 `evals/` | 배포 트리 밖 | **불가능** — 하네스가 플러그인 루트 아래 상대경로만 받는다(`..` 거부). `--eval-dir`로도 못 뺀다 |
| C. `malgn-agent/quality/evals/` + `experimental.evals` | 이름만 다름 | 배포 부담은 A와 같은데 매니페스트에 얼리액세스 키가 하나 더 실린다 |

**포기한 것:** 케이스 47,026 B(45개 파일)가 전 직원 클론에 포함된다.
**감당 방안:** 이 비용은 **디스크에만** 물리고 **컨텍스트에는 물리지 않는다.** 플러그인이 컴포넌트로
로드하는 디렉터리는 `agents/` `skills/` `commands/` `hooks/` `outputStyles/` `themes/` `workflows/`
`monitors/`뿐이고 `evals/`는 그중 없다. `plugin.json`도 커스텀 컴포넌트 경로를 선언하지 않는다.
→ **세션 시작 시 자동 로드되지 않고 매 세션 토큰 비용이 0이다.**
확인: 케이스 추가 후 `pnpm run check-assets` ERROR 0 유지, `pnpm run check-docs` 자산 개수 21/40/41 불변,
`claude plugin validate ./malgn-agent --strict` 통과.

## 2. `plugin.json`의 `experimental.evals` → 넣지 않는다

기본 이름 `evals`를 쓰면 매니페스트 키가 불필요하다(우선순위: `--eval-dir` > 매니페스트 > `evals/`).
넣으면 전 직원 배포 매니페스트에 얼리액세스 단계의 실험 키가 하나 늘고, 정식화되며 키 이름이 바뀌면
배포본을 다시 고쳐야 한다. **얻는 것이 없으므로 넣지 않는다.**

## 3. 실행 방식 → 래퍼 `scripts/run-golden-eval.mjs` (`pnpm run eval:golden`)

맨손 `claude plugin eval`이 기본값으로 잘못하는 것 세 가지 — 전부 사람이 매번 기억해야 하는 것들이다.

1. **결과가 배포 트리 안에 쌓인다.** 기본 출력은 `<플러그인>/evals/results/<타임스탬프>/`.
   → 래퍼가 `--output-dir`로 `docs/evaluation/golden-task/runs/`로 뺀다.
2. **HTML 리포트가 claude.ai에 자동 발행된다.** 리포트에는 케이스 프롬프트·채점 루브릭·산출물 발췌가 들어간다.
   이 플러그인은 `LicenseRef-Malgnsoft-Proprietary`이고 발행할 업무상 이유가 없다.
   → 래퍼가 **`--no-publish`를 기본값으로 강제**한다. 발행이 필요하면 사람이 `-- --publish-report`로 명시해야 한다.
3. **실행 조건이 매번 달라져 시계열이 깨진다.** `--runs`·`--model`·`--judge-model`·`--threshold`가 고정되지
   않으면 점수 변화가 플러그인 변화인지 실행 조건 변화인지 구분되지 않는다. → 래퍼가 고정한다(§5).

추가로 래퍼가 하는 일:
- **`pnpm` 인자 정리** — `pnpm run eval:golden -- --runs 3`의 `--`는 pnpm이 벗겨주지 않고 그대로 넘어온다.
  그대로 `claude`에 전달되면 "옵션 파싱 종료" 기호로 해석돼 **그 뒤의 `--allow-tools Write`까지 통째로 무시된다.**
  래퍼가 `--`를 걷어낸다.
- **하드 게이트 판정**(§4-2) — 하네스 점수가 임계값을 넘어도 필수 그레이더가 깨졌으면 exit 1로 끝낸다.
- **오발동 가드** — `GOLDEN_EVAL_I_ACCEPT_COST=1` 옵트인이 없으면 예상 비용을 출력하고 실행을 거부한다.
  이 저장소는 마켓플레이스 클론 대상이라 `scripts/`·`package.json`이 전 직원 PC에 내려간다 —
  무심코 친 직원의 **자기 계정에** 비용이 청구되기 때문이다. `--dry-run`은 비용이 0이라 면제.
- **도구 승인** — `--allow-tools Write`. 단 이것은 **보안 경계가 아니다**(§0 — 선언하지 않은 Bash는 그냥 돈다).
- **회귀 이력 1줄 적재**(§6). `partial`·`skippedPaidGraders`면 "추세에서 제외하라"고 경고한다.
- **`--dry-run`** — 에이전트를 한 번도 돌리지 않고 케이스 파싱만 검증한다(비용 0). 케이스를 고친 직후 이걸 먼저 돌린다.

**자동 실행 없음.** 훅에 걸지 않고 `check-*` 계열에도 넣지 않는다. 사람이 명령을 칠 때만 돈다.

## 4. 파일럿 에이전트 → `architect` 1종

**선정 근거**
1. **플러그인 고유 행동의 밀도가 가장 높다.** architect MD는 4대 의무(①트레이드오프 ②고유성
   ③비정상 케이스 ④완결성)와 산출물 4종 계약을 문자로 못박는다 → 플러그인 유무 대조의 신호가 크다.
2. **기계 채점이 된다.** 산출물이 말이 아니라 **파일**이고, 필수 요소(대안·포기한 것·감당 방안 /
   에러·권한·검증 / 인덱스·제약 / 타임아웃·멱등)가 MD에 문자로 있다 → 대부분 정규식으로 채점된다.
3. **픽스처가 필요 없다.** 요구사항·PRD를 프롬프트에 실으면 되고 외부 코드베이스가 필요 없다
   → `context.scaffold_script`(작성자 bash를 실행자 권한으로 돌리는 기능)를 쓰지 않아도 된다.
4. **위임 사슬의 중간이다.** PM → architect → backend/frontend의 STAGE 2라 여기 품질이 하류의 상한이 된다.

**탈락 후보**
| 후보 | 이유 |
|---|---|
| `pm` | 스스로 여러 서브에이전트를 띄운다 → 1회 비용이 파일럿으로 감당 불가, 분산도 크다 |
| `reviewer` · `evaluator` | 리뷰 대상 픽스처가 필요하고, 픽스처가 낡으면 점수가 픽스처 탓으로 흔들린다 |
| `backend-dev` · `frontend-dev` | 실제 코드베이스 필요 → `scaffold_script` 의존 |
| `trainer` | 대상이 `agents/`·`skills/` 본문이라 케이스가 제품 본문 변경에 물려 자주 깨진다 |

### 4-1. 채점표 (가중치 합 14.0)

| 그레이더 | 종류 | 가중치 | 보는 것 |
|---|---|---:|---|
| `delegates-to-architect` | tool_used | 1 + **하드 게이트** | architect에 실제로 위임했는가(`arm: with-only`) |
| `writes-architecture-doc` / `-tech-stack-` / `-api-spec-` / `-data-model-` | file_exists | 0.5×4 | 산출물 4종 계약. 부분 점수를 남기려고 4개로 쪼갰다 |
| `artifacts-under-docs` | regex(files) | 1 | 4종이 흩어지지 않고 `docs/` 아래 있는가 |
| `tradeoff-obligation` | regex(file) | 2 | ①대안·포기한 것·감당 방안 |
| `api-completeness-obligation` | regex(file) | 2 | ④에러 응답·권한 규칙·검증 규칙 |
| `data-model-completeness-obligation` | regex(file) | 1 | ④인덱스·제약 |
| `abnormal-case-obligation` | regex(file) | 2 | ③타임아웃·멱등성 |
| `cites-comparison-table` | regex(file) | 1 | ②경쟁사 비교표 인용의 결정론적 하한선 |
| `uniqueness-obligation` | llm | 2 | ②인용을 근거로 실제로 다르게 설계했는가 |

판정 모델을 쓰는 그레이더는 **1개뿐**이다. 나머지는 전부 무료·결정론적이다.

### 4-2. 하드 게이트 — 가중합만으로는 막을 수 없는 것

**하네스의 채점은 가중합뿐이고 "이 그레이더는 필수" 같은 표시가 없다.** 그래서 이런 구멍이 생긴다:
`delegates-to-architect`(가중치 1)가 실패해도 **13/14 = 0.929로 임계값 0.9를 통과한다.**
즉 **위임이 죽고 프롬프트의 폴백("위임할 수 없으면 네가 직접 설계")이 발동해도 Green이 나온다.**
그러면 이 케이스는 architect가 아니라 **부모 세션을 채점한 것**이 되어 측정 자체가 무의미해진다.

가중치를 키워 막으려면 4 이상이 필요한데(`runs 2` 평균에서도 걸리려면), 그건 "위임 성공"이
4대 의무 두 개만큼 중요하다는 뜻이 되어 점수의 의미가 왜곡된다.

**채택: 점수 체계는 그대로 두고 채점 후처리로 분리한다.**
`scripts/run-golden-eval.mjs`의 `HARD_GATES`에 등록된 그레이더가 **한 번이라도** 실패하면,
가중 점수가 임계값을 넘더라도 래퍼가 **exit 1**로 끝내고 이유를 출력한다.
`arm: with-only`라 ablation 실행에서 `scored: false`가 되더라도 하드 게이트는 `passed`만 본다.
실패 사실은 `history.jsonl`의 `hardGateFailures[]`에도 남아 추세에서 걸러낼 수 있다.

```
HARD_GATES = { 'architect-design-obligations': ['delegates-to-architect'] }
```

새 케이스를 추가할 때 **"이게 실패하면 나머지 점수가 무의미해지는 그레이더"**가 있으면 여기 등록한다.

## 5. 비용 통제 기본값

**비용 공식(하네스 문서):** `케이스 × runs × arms` 에이전트 실행 + `llm/baseline` 그레이더당 판정 3회.

**실측(파일럿, `--runs 1 --ablation none`, 부모 sonnet / architect는 자기 MD의 opus)**

| 회차 | 결과 | 시간 | 비용 |
|---|---|---:|---:|
| 1회차 | 0.08 — 산출물 0종. **케이스 결함**(비동기 위임, §7-1) | 648초 | $0.52 |
| 2회차 | 0.46 — 산출물 2종. 같은 결함 + 판정 모델 오탐(§7-2) | 666초 | $1.97 |
| **3회차(케이스 수정 후)** | **1.00 — 그레이더 12개 전원 통과, exit 0** | **1,988초(33분)** | **$7.78** |

> **1·2회차가 싼 이유는 효율이 아니라 일을 덜 했기 때문이다.** 서브에이전트가 잘려서 문서를
> 0~2종만 쓴 상태의 비용이다. **정상 1회 비용은 $7.78 · 33분**이 기준선이다.
> 기본값 `--runs 2`면 **케이스 1종당 약 $16 · 1시간**이고, 등록된 4종을 전부 돌리면
> **약 $62 · 4시간**이다(architect 실측을 나머지 3종에 그대로 적용한 추정 — 3종은 아직 실측이 없다).
> 1종만 돌리려면 `-- --case <이름>`으로 좁힌다.
> → 이 벤치마크는 **PR마다 돌리는 도구가 아니라 릴리스 게이트 주기로 돌리는 도구다.**

| 항목 | 기본값 | 근거 |
|---|---|---|
| `--runs` | **2** | 하네스 기본은 3, "1회는 노이즈"라고 명시. 회당 $7.78이라 3회는 일상 반복이 불가능하다. 2회는 "한 번은 우연"을 거르는 최소값이자 아래 threshold의 노이즈 완충 장치다. 릴리스 게이트에서만 `-- --runs 3` |
| `--max-cost-usd` | **걸지 않음** | 하네스도 자체 기본값이 없다(`--help`가 "Optional hard cost ceiling"이라고만 적고 default를 표기하지 않는다) → 미지정이면 무제한. 상한을 걸면 걸린 런에서 **유료 그레이더(llm/baseline)만 건너뛰어지고 무료 그레이더는 그대로 채점된다**(`--help` 원문). 케이스마다 정확히 1개인 가중치 2짜리 llm 그레이더가 통째로 빠지면 전 케이스가 임계값 아래로 내려앉아 **예산 사고가 품질 회귀와 구분되지 않는다.** 릴리스 게이트 주기로 드물게 돌리는 도구라 상한으로 얻을 것보다 가짜 경보로 잃을 것이 크다. 상한이 필요하면 사람이 `-- --max-cost-usd N`으로 준다. 실행 전 비용 인지는 `GOLDEN_EVAL_I_ACCEPT_COST` 옵트인 가드가 담당한다 |
| `--threshold` | **0.9** | 하네스 기본 1.0은 llm 그레이더가 있으면 비현실적이고, 0.8은 너무 무디다. 가중치 14.0에서 **가중치 2짜리 의무 하나를 잃으면 0.857**이므로 0.9여야 그게 경보가 된다. 판정 모델이 한 번 헛발질해도 `runs 2` 평균이 (1.00+0.857)/2=0.93으로 받아내 오경보를 막는다. **단 임계값만으로는 위임 실패를 못 잡는다 → 하드 게이트(§4-2)가 따로 있다** |
| `--ablation` | **none** | 2배 비용을 매번 쓰지 않는다. Δ는 상시 지표가 아니라 **에이전트 MD를 크게 고친 라운드에서만** `-- --ablation with-without` |
| `--model` | **sonnet** | 부모 세션 모델 고정 — 안 하면 모델 롤아웃이 플러그인 회귀처럼 보인다. architect 서브에이전트는 자기 MD의 `model: opus`로 도므로 영향 없다 |
| `--judge-model` | **sonnet** | 하네스 기본 haiku는 **실측 오탐을 냈다** — 경쟁사 비교표를 인용한 전용 섹션이 명백히 있는 21,465자 문서에 FAIL·FAIL·FAIL. 하네스도 8,000자 초과 시 "판정 모델이 노이즈가 크다"고 경고한다 |
| 케이스 `max_turns` | 40 | 턴 소진은 run 에러로 점수를 깎는다. 비동기 서브에이전트를 기다리는 턴까지 감안 |
| 케이스 `timeout_seconds` | 2700 | **정상 1회가 33분이다.** 초기값 1800(30분)이었다면 정상 실행이 타임아웃으로 잘렸을 것이다 — 부분 산출은 곧 오측정이므로 넉넉해야 한다 |

**Δ(ablation) 실행 시 유의:** `arm: with-only` 그레이더(`delegates-to-architect`)는 ablation 실행에서
점수에서 빠지고 `--ablation none` 실행에서는 들어간다. **두 모드의 절대 점수를 직접 비교하지 않는다.**
이력에 `ablation` 필드를 남기는 이유가 이것이다.

## 6. 결과 저장과 회귀 추적

```
docs/evaluation/golden-task/
├── history.jsonl                 # 커밋 대상. 실행 1회 = 1줄
└── runs/<ISO타임스탬프>/          # .gitignore 대상
    ├── aggregate-result.json     # 하네스 v1 결과 문서(원본)
    └── report.html               # 자기완결 HTML 리포트
```

**커밋하는 것: `history.jsonl` 한 줄.** 필드는 `startedAt` · `pluginVersion` · `claudeVersion` ·
`model` · `judgeModel` · `ablation` · `threshold` · `runsPerCase`(실제로 돈 횟수) · `partial` ·
`costUsd` · `overallScore` · 케이스별 `{name, caseSha, score, passRate, scoreWithout, failedGraders[], hardGateFailures[]}` · `runDir`.
**어떤 그레이더가 떨어졌는지까지 남기므로, 점수만 보고 원인을 재현하러 되돌아갈 필요가 없다.**

**`caseSha`가 회귀 추적의 핵심이다.** 케이스 디렉터리(프롬프트 + 그레이더 전부)의 지문이라
채점표를 고치면 값이 바뀐다. **`caseSha`가 다른 회차끼리는 점수를 비교하지 않는다** — 같은
과제를 다르게 채점한 것이므로 추세선이 아니다. 이 규율이 없으면 "채점을 느슨하게 고쳐서 점수가
올랐다"가 개선으로 보인다.

**원장 규율: 행은 지우지 않는다.** 실행 1회 = 1줄이고, 나중에 "그때 케이스가 달랐다"는 이유로
과거 행을 삭제하지 않는다 — 그 구분은 `caseSha`가 하고, 지워버리면 실패했던 회차가 기록에서 사라진다.

**단, 이 불변량은 첫 두 회차부터 지켜지지 않았다(기록해 둔다).** §7의 1회차는 래퍼가 적재한 행을
내가 사후에 지웠고, 2회차는 래퍼를 거치지 않고 `claude`를 직접 불러 애초에 행이 없다. 당시 판단은
"케이스 정의가 바뀌었으니 비교 불가"였지만, `caseSha`는 **실행 시점의** 케이스를 해싱하므로 남겨뒀어도
정확했다 — 지운 것이 잘못이다. 그래서 위 규율을 명문화한다. 두 회차의 값은 §7에 서술로 남아 있다.
현재 `runs/` 디렉터리 수와 원장 행 수가 어긋나는 이유가 이것이다.

`partial: true`이거나 `skippedPaidGraders: true`인 회차는 **지우지 말고 표시된 채로 두고**, 추세를 볼 때만 제외한다.

**커밋하지 않는 것: `runs/` 원본.**
- 이 저장소는 `/plugin marketplace add`의 **클론 대상**이라 `docs/`도 통째로 내려간다.
  자기완결 `report.html`(수백 KB)이 회차마다 쌓이면 전 직원의 내려받기 용량이 된다.
- 원본은 다시 실행하면 되고, 실행 조건은 `history.jsonl`에 전부 있다.

**비교 규율:** `partial: true`인 줄과 `skippedPaidGraders`가 있던 회차는 추세에서 제외한다.
`pluginVersion`·`claudeVersion`·`model`이 다른 줄끼리 비교할 때는 그 차이를 먼저 의심한다.

## 7. 이 라운드에서 실제로 잡힌 것 — 케이스 저작 함정 2건

파일럿을 "돌아갈 것이다"가 아니라 실제로 돌렸기 때문에 나온 결함이다. **둘 다 케이스 저작 결함이지
에이전트 결함이 아니었다.** 다음에 다른 에이전트 케이스를 쓸 때도 그대로 밟게 될 함정이라 남긴다.

### 7-1. 서브에이전트는 비동기로 뜬다 — 부모가 기다리지 않으면 오측정된다

trace 원문: `Async agent launched successfully. ... The agent is working in the background.`
부모는 위임 직후 "백그라운드에서 진행 중이다 — 완료되면 알려주겠다"로 **턴을 끝냈고**, 세션이
종료되면서 서브에이전트가 작업 중에 잘렸다. 그 결과가 1회차 산출물 0종 / 2회차 2종이다.
점수 0.08 ↔ 0.46의 분산은 에이전트 품질이 아니라 **"잘리기 전까지 얼마나 썼나"라는 타이밍 노이즈**였다.

→ 프롬프트에 **"완료 알림 전에 최종 답변 금지 + 4종 존재를 직접 확인 + 빠지면 같은 서브에이전트에게
이어서 시킬 것(네가 대신 쓰지 말 것)"**을 명시해 고쳤다. 마지막 단서가 없으면 부모가 대신 문서를 채워
architect가 아니라 부모를 채점하게 된다.

### 7-2. 판정 모델은 긴 한글 문서에서 오탐을 낸다

haiku 판정이 33 KB(21,465자) 설계문서를 FAIL·FAIL·FAIL로 판정했다. 그런데 그 문서에는
`## 1. 설계 출발점 — PRD 경쟁사 비교표에서 도출한 기술 결정`이라는 전용 섹션이 있고 비교표 셀을
직접 인용해 충돌 해결 규칙·분할 업로드·아웃박스를 설계하고 있었다. **명백한 오탐이다.**

→ ②의무를 둘로 쪼갰다: **사실 판정(인용이 있는가)은 정규식**으로 내리고, **질 판정만 판정 모델**에 남겼다.
판정 모델도 haiku → sonnet으로 올렸다. 원칙: **사실 여부는 판정 모델에 맡기지 않는다.**

**인과 주장은 여기까지만 한다(중요).** "haiku가 원인이고 sonnet이 해결했다"고는 말할 수 없다.
두 관측은 판정 모델과 대상 문서가 **동시에** 달랐고(21,465자 FAIL ↔ 40,072자 PASS), 같은 라운드에
정규식 그레이더가 하나 추가돼 교란 변수가 더 늘었다. 게다가 **통과한 문서가 오히려 1.9배 길었고**
하네스는 그 통과 판정에도 long-input 노이즈 경고를 그대로 붙였다. 지금 말할 수 있는 것은
**"정규식 분리 + 판정 모델 상향을 함께 넣었고, 그 뒤 1회 통과했다"**뿐이다(단일 표본).
llm 그레이더의 안정성은 미검증이다 → §9 R10.

## 8. 20종 확장 로드맵

현재 케이스는 4종(`architect` · `planner` · `qa-engineer` · `security`)이다. 나머지는 **파일럿이 두세 라운드
돌아 점수가 안정된 뒤에** 붙인다 — 케이스 21종을 먼저 만들어 놓고 채점 기준이 흔들리면 21배로 손보게
된다. §7이 그 근거다: 첫 케이스 하나에서도 저작 함정이 2건 나왔다.

| 단계 | 대상 | 붙일 조건 | 픽스처 |
|---|---|---|---|
| 1 (완료) | `architect` | — | 없음(프롬프트 인라인) |
| 2 (완료 — 조건 미충족 상태에서 사용자 명시 승인으로 진입) | `planner` · `qa-engineer` · `security` | 파일럿 점수가 2회 연속 ±0.1 이내로 안정 | 없음 / 작은 인라인 |
| 3 | `backend-dev` · `frontend-dev` · `devops` | 2단계 통과 + `scaffold_script` 사용 규약 확정 | 필요(작은 저장소 스캐폴드) |
| 4 | `reviewer` · `evaluator` · `trainer` | 3단계 통과 + 픽스처 노후화 관리 방법 확정 | 필요(리뷰 대상 산출물) |
| 5 | 나머지(`pm` 포함) | 4단계 통과 + 회당 총비용 상한 재산정 | 대상별 상이 |

각 단계는 **직전 단계 케이스가 회귀를 실제로 한 번이라도 잡았을 때** 다음으로 넘어간다.
잡은 적이 없으면 케이스를 늘리는 게 아니라 기존 케이스의 판별력을 먼저 고친다.

> **2단계로 넘어가기 전에 결정할 것 — 이 대형 케이스 형태를 유지할지부터 정한다.**
> 지금 케이스는 회당 $7.78·33분인데 그레이더 12개 중 절반은 "특정 단어가 파일에 있는가"를 본다.
> R8이 이미 "비용이 문제면 케이스를 쪼개는 쪽을 먼저 검토"라고 적어놨는데, 위 로드맵은 반대로
> 이 대형 케이스 **위에** 20종을 더 쌓는 순서다. 4대 의무를 각각 독립 측정하는 소형 케이스로
> 쪼개면 비용이 내려가고 "어느 의무가 깨졌는지"도 바로 나온다(지금은 14점 중 2점 손실로 뭉개진다).
> **R9(판별력 실측) 결과를 본 뒤 이 갈림길을 먼저 정하고 2단계에 들어간다.**

**실제로는 이 갈림길을 정하지 못한 채 2단계에 들어갔다.** 진입 조건(파일럿 2회 연속 안정)도
충족되지 않았다 — R1(조직 얼리액세스 미승인)으로 파일럿 실행 횟수가 0회라 두 조건 모두 **충족
자체가 불가능한** 상태였고, 사용자가 그 충돌을 보고받은 뒤 3종 신설을 명시적으로 승인했다.
따라서 **갈림길은 여전히 열려 있다(R16).** 4종 모두 대형 케이스 형태이며, 소형 케이스로 쪼갤지는
조직 승인 후 첫 실행(R9·R11)의 결과를 보고 정한다. 3단계 이후는 원래 조건을 그대로 따른다.

## 8-1. 승인 전 수동 실행 대체 경로 — `scripts/run-golden-eval-manual.mjs`

`claude plugin eval`(§0)의 얼리액세스 승인 없이도, **같은 케이스 정의(prompt.md + graders/*.md)를
그대로 읽어 `claude -p`로 직접 실행하고 이 스크립트가 직접 채점하는** 대체 실행기다.
근거: `claude plugin eval`은 OS 샌드박스가 아니라 "격리된 `claude -p` 세션 + 선언형 그레이더
채점"의 조합일 뿐이라는 §0의 확인 — 그 조합을 그대로 구현했다.

**우회가 아니다.** 얼리액세스 게이트가 걸린 `claude plugin eval` 서브커맨드 자체는 여전히
호출하지 않는다 — 케이스 정의 포맷과 채점 기준만 재사용해 다른 경로(일반 `-p` 실행)로 돈다.

**실행:** `node scripts/run-golden-eval-manual.mjs --dry-run`(비용 0, 파싱만) ·
`GOLDEN_EVAL_MANUAL_I_ACCEPT_COST=1 node scripts/run-golden-eval-manual.mjs`(실제 실행, 유료).
결과는 `docs/evaluation/golden-task/manual-history.jsonl`에 쌓인다 —
**공식 `history.jsonl`과 수집 방식이 달라 같은 줄로 비교하지 않는다.**

**공식 하네스와 다른 점**
| 항목 | 공식 하네스 | 수동 실행기 |
|---|---|---|
| 세션 격리 | 매 run 새 CLAUDE_CONFIG_DIR/HOME | 매 run 새 임시 작업 디렉터리 + `--strict-mcp-config`만 |
| 운영자 계정 MCP 커넥터 노출(R2) | 있음(실측된 결함) | `--strict-mcp-config`로 차단 — 오히려 이쪽이 더 격리됨 |
| mocks / `case.yaml` scaffold_script | 지원 | 미지원(이 저장소 케이스는 둘 다 안 씀 — 무해) |
| ablation(`--arm with|without`) | 지원 | **지원** — 플러그인 로드 여부만 스위치, `arm: with-only` 그레이더는 without에서 채점·하드게이트 제외(공식과 동일 규칙) |
| 공식 JSON/HTML 리포트·claude.ai 발행 | 있음 | 없음(콘솔 출력 + jsonl 한 줄) |

**R9(판별력 검증)를 이 경로로 먼저 처리할 수 있다** — `-- --arm without`으로 대조군을 돌리면
얼리액세스 승인을 기다리지 않고도 "플러그인이 실제로 점수를 끌어올리는가" Δ를 확인할 수 있다.
