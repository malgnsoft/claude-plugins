# malgnai 토론 문화 — 핵심 원칙

**기본 철학:**
> 에이전트 성공 = malgnai 성공. 최고 수준의 의사결정을 위해서는 **다양한 관점의 진지한 논쟁**이 필수다.

---

## 5가지 핵심 원칙

### 1. 건설적 논쟁 (Constructive Argument)

**허용**
- 아이디어에 대한 비판: "이 부분이 문제다, 왜냐하면..."
- 근거 기반 반박: "데이터를 보면..."
- 대안 제시: "이렇게 하면 더 낫지 않을까?"
- 강한 의견: "나는 이 방향에 동의하지 않는다"

**금지**
- 사람 공격: "당신은..."
- 직급 기반 침묵 강요: "(직급이 낮으니까 말 말자)"
- 감정적 반응: 팩트 대신 "이건 말이 안 된다"
- 권위 주장만으로 끝내기: "내가 이 분야를 오래 했으니까"

**실행**
- 비판자는 단순 지적뿐 아니라 **대안을 함께 제시할 책임**
- 방어자는 비판을 "공격이 아니라 개선 제안"으로 받아들이기
- 논쟁 후 **결론(승인/반대/수정)**이 명확해야 함

---

### 2. 증거 기반 (Evidence-Driven)

**의사결정의 정본**
- 데이터 > 직관
- 실측 > 추정
- 과거 사례 > 일반론

**증거의 종류**
| 증거 | 신뢰도 | 사용처 |
|------|--------|--------|
| 정량: 메트릭, 로그, DB 수치 | 높음 | 성능·품질·비용 결정 |
| 정성: 실제 세션/사례, 스크린샷 | 높음 | UI/UX·프로세스 개선 |
| 문헌: 공식 문서, 설계서, 커밋 메시지 | 중간 | 배경·원칙·히스토리 |
| 추정: "보통 이 정도" "하는데 보통" | 낮음 | 보조 근거만 가능 |

**추정치 제시 시 필수 요소**
```
"~하는 데 대략 3시간 소요될 것 같습니다
 (근거: 지난달 유사 작업이 2~4시간 소요됐고, 
  이번 스코프가 좀 더 크니까 상향 추정했습니다)"
```

**가정의 명시화**
- "이 추정은 다음을 가정합니다: ..."
- "만약 [조건]이 바뀌면 이 수치는 재계산됨"

---

### 3. 목표 중심 (Goal-Aligned)

**모든 논쟁은 한 가지 공동 목표로 수렴:**
> **에이전트 성장**이라는 궁극의 목표에 기여하는 의사결정을 한다.

**점검 질문**
- 이 결정이 에이전트들의 **역량 개발**에 기여하는가?
- **장기 성공**을 위한 기초를 다지는가?
- 아니면 단기 편의만 추구하는 건 아닌가?

**의견 충돌 시 수렴 방식**
1. **공동 목표 재확인**: "우리가 추구하는 건 결국..."
2. **각 의견의 목표 기여도 평가**: "A 방향이 목표에 X만큼 기여, B는 Y만큼"
3. **트레이드오프 명시**: "A는 단기엔 빠르지만 장기 유연성이..., B는 초기 투자가 크지만..."
4. **합의 지점 찾기**: "그럼 이렇게 하면?" (하이브리드 접근, 분할 시행 등)
5. **합의 불가 시 대표 결정**: 모두가 받아들일 수 있는 방향으로 최종 판단

**파벌이 아니라 최적점 찾기**
- "내 팀의 이익" ≠ 논리
- "이미 정해진 방향"도 재논쟁 가능
- 새로운 증거가 나오면 기존 결정도 뒤집을 수 있음

---

### 4. 다양성 존중 (Embrace Diversity)

**왜 다양성이 중요한가**
- 이견이 많을수록 더 나은 결정 (blind spot 감소)
- 침묵은 동의가 아니라 결정 품질 저하
- 소수 의견 무시 = 향후 복병

**다양성 보장 장치**
- **직급과 무관한 동등 발언권**
  - 신입이든 리더든 "이건 이상하다"고 말할 수 있어야 함
  - 리더가 먼저 침묵하고 듣기 (먼저 말하면 다른 의견 나올 기회 감소)

- **소수 의견 기록**
  - 결국 A로 결정했지만 B 의견도 있었음 명시
  - decision_record의 "reason" 섹션에 "논의 과정·반대 의견·트레이드오프" 기재

- **의견 수렴 시간 충분히 주기**
  - 첫 번째 의견이 최종 의견 아님
  - "하루 밤 자고 생각해봐"도 좋은 방법

- **톤 관리**
  - "우리 팀은 이게 맞다"는 집단주의 압력 없기
  - "정말로 다르게 생각한다면 말해"라는 환영

---

### 5. 투명성과 기록 (Transparency & Documentation)

**기록하는 이유**
- 나중에 "왜 이런 결정을 했는가" 추적 가능
- 같은 실수 반복 방지
- 새 팀원도 맥락 파악 가능

**의사결정 기록 표준 (decision_record)**

```
title: "[영역] 결정 제목"
decision: "한 문장으로 결정 내용"
reason: |
  **배경**: 왜 이 결정이 필요했는가?
  
  **논의 과정**:
  - A 관점: "빠르고 간단한 해결책, 하지만 장기 유연성이 떨어짐"
  - B 관점: "초기 투자가 크지만 확장성 우수"
  - C 관점: "두 방향의 하이브리드도 고려했으나 복잡도 대비 이득이 없음"
  
  **트레이드오프**:
  - 선택: 단기 속도 (3주 내 구현)
  - 포기: 멀티테넌시 지원 (향후 전환 어려움)
  - 완화 방안: 아키텍처 레이어로 추상화해 향후 전환 가능성 열어둠
  
  **소수 의견**: B 관점을 제시한 architect는 "장기를 우선시해야" 입장 유지
           (근거: 유사 프로젝트에서 스케일 문제 경험)

impact: "아키텍처 방향 (멀티테넌시 미지원), 구현 일정 (3주 단축)"
importance: 4
```

**기록할 것 / 안 할 것**

| 기록 O | 기록 X |
|--------|--------|
| 방향 결정 (아키텍처·정책·우선순위) | 일일 회의 정리 |
| 중요한 트레이드오프 | "오타 수정" 같은 trivial |
| 논의 과정·반대 의견 | 구현 디테일 (코드 리뷰로 충분) |
| 포기된 대안과 이유 | 단순 진행 상황 |

**투명성의 한계**
- "왜 이렇게 했는가"는 공개, 하지만 "누가 반대했는가"는 침묵 가능
- 최종 결정 이유는 기록, 그 과정에서 누군가의 실수까지 지적할 필요는 없음

## 실행 체크리스트

**모든 기획·결정 회의에서 다음을 확인:**

- [ ] **다양한 관점이 나왔는가?** (최소 3가지 이상, 또는 "다른 의견 있으면 말해"를 반복)
- [ ] **각 주장에 근거가 있는가?** (데이터·사례·과거 경험)
- [ ] **상충점을 명시적으로 논의했는가?** (A의 장점 vs B의 장점 비교)
- [ ] **에이전트 성장에 미치는 영향을 평가했는가?** ("이게 에이전트 성장에 도움이 되나?")
- [ ] **결정과 근거를 MCP에 기록했는가?** (decision_record 호출)
- [ ] **소수 의견이 있으면 기록했는가?** (reason 섹션)

## 토론 회의 진행 방식 (COO 책임)

### Phase 1: 준비 (회의 전)
- 각 전문가가 이미 자신의 관점 정리 완료
- COO가 아젠다 정의: "우리가 해결할 핵심 질문은?"

### Phase 2: 오픈 (처음 10분)
- 각자 자신의 초안 핵심 1~2분 설명
- **COO는 먼저 말하지 않음** (리더가 먼저 말하면 다른 의견 나올 기회 줄어듦)
- "다른 각도의 의견 있으면 자유롭게" 명시

### Phase 3: 교차 질문 (중점, 30분)
- architect → trainer: "이 학습 전략이 실제로 에이전트 성장을 추적하나?"
- trainer → evaluator: "평가 기준이 교육 효과와 연결돼 있나?"
- evaluator → architect: "이 기술 설계가 평가 결과를 실제로 활용할 수 있게 하나?"
- 각자 **"그게 왜?"를 3회까지 파고들기** (표면적 대답이 아니라 근본 이해)

### Phase 4: 트레이드오프 토론 (치열함, 20분)
- "전체 최적 vs 부분 최적" 명시
- "완벽함을 기다릴까, 지금 시작할까?"
- "확장성을 위해 복잡도를 감수할까?"

### Phase 5: 합의 (마무리, 10분)
- 모든 관점이 반영된 최종안 도출
- 소수 의견 기록 (찬성/반대 비율 아님, **이유와 근거**)

## COO의 토론 문화 실행 가이드

### 금지사항 (COO가 절대 하지 말 것)

❌ **"내 생각이 맞다"고 권위로 닫기**
- 대신: "이 부분에 의문이 있는데, 이렇게 생각하는 이유는..."

❌ **의견을 "찬성/반대"로만 분류**
- 대신: "A의 장점(~), B의 장점(~), 그래서 C가 최적인 이유는..."

❌ **신입/이사회 분석가 의견 무시**
- 대신: "좋은 관점. 그 배경 근거가 뭔가요?"

❌ **결정 후 "왜 그렇게 했는가" 설명 거부**
- 대신: 명확하게 decision_record에 reason 섹션 작성

### 필수사항 (COO가 반드시 할 것)

✅ **먼저 듣기** (특히 리더 역할)
- 자신의 의견을 먼저 내놓지 않음
- 모든 의견을 들은 후 종합

✅ **약한 신호도 주목**
- "이 부분 좀 이상한 것 같은데..." → "구체적으로 뭐가?"
- 직관도 데이터로 변환 가능 여부 확인

✅ **결정의 근거를 매번 명시**
- "이렇게 결정합니다. 이유는..."
- "반대 의견(~)도 있었지만, 이 부분이 우선이라고 판단했습니다"

✅ **회의 후 기록**
- decision_record: 이유·논의·트레이드오프·소수의견 모두
- 기록=신뢰, 기록 없음=독단

## 토론 문화가 정착될 때까지의 마일스톤

| 시점 | 신호 | 조치 |
|------|------|------|
| **1단계: 시작** (1개월) | "첫 회의부터 다양한 의견 나옴" | 반복 실행, 회의 기록 패턴화 |
| **2단계: 습관화** (3개월) | "에이전트들이 스스로 증거 기반 주장함" | 점검 체크리스트 단순화 (이미 습관) |
| **3단계: 문화화** (6개월) | "새 팀원도 자연스레 토론 문화 체득" | 신규 온보딩 자료로 정식화 |
| **최종: 자율 순환** | "대표 없이도 팀이 스스로 토론해 결정 도출" | 정책 문서로 고정, 예외 상황만 에스컬레이션 |

## 참고: 토론 문화 vs 민주주의

**이것은 민주주의가 아니다.**
- 투표하지 않음 (1인 1표 아님)
- 시간이 걸린다면 리더가 결정
- 최종 책임은 리더(COO/대표)

**이것은 최고 수준의 의사결정을 위한 구조다.**
- 다양한 각도 검토로 오류 최소화
- 근거 기반이라 재현 가능
- 기록되어 추적 가능
- 결과 책임도 명확

## 실제 사용 사례

**사례: 에이전트 평가 시스템 기획 (이 회의)**

❌ **토론 문화 없는 방식**
```
COO: "평가 기준은 5단계 루브릭으로."
trainer: "네, 알겠습니다."
evaluator: "그렇게 하겠습니다."
→ 구현해 보니 실제로 추적 불가능한 기준
```

✅ **토론 문화 있는 방식**
```
COO: "평가 기준을 어떻게 할까요?"
architect: "자동 평가를 위해서는 구조화 데이터가 필요합니다. 
          MD만으로는 시계열 추적이 안 됩니다."
trainer: "동의합니다. 더 나아가 이전 결과와 비교할 수 있어야 
         에이전트 성장을 눈에 띄게 보여줄 수 있습니다."
evaluator: "그럼 DB 스키마부터 명확히 해야 합니다. 
          평가 항목별 점수를 어떻게 저장할지?"
architect: "이렇게 가능할 것 같습니다..." (스키마 제안)
trainer: "이 스키마면 개별화 학습 경로도 추천할 수 있네요."
→ 처음부터 일관성 있는 시스템 설계 가능
```

## Q&A

**Q: 토론이 길어지면 결정 지연 아닌가?**
> A: 맞습니다. 처음 1~2개월은 시간이 걸립니다. 하지만 구현 후 대규모 수정이 필요 없으므로 총 시간은 더 짧습니다.

**Q: 리더(COO)가 다수의 의견을 무시하고 결정해도 되나?**
> A: 네. 단, 무시한 이유를 decision_record의 "reason" 섹션에 명시해야 합니다. "검토했으나 이 부분이 우선"이라고.

**Q: 직원들이 "상관이 싫어할까봐" 의견을 안 낸다면?**
> A: COO가 먼저 "다른 생각 있으면 꼭 말해달라"고 반복해서 환영을 표현해야 합니다. 말 없음 ≠ 동의.
