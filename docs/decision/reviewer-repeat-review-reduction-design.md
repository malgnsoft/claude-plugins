`docs/reviewer/personas/`를 대조한 결과, 문제는 "재사용 원칙이 아예 없었다"가 아니라 **재사용을 실행 가능하게 만드는 절차가 없었다**는 것이다.

| 라운드 | 리뷰 문서 | 페르소나 | 재사용 여부 |
|---|---|---|---|
| 1차 (08-10 18:32) | `review-pm-orchestration-block-sync-2026-08-10.md` | `persona-skeptical-verification-architect.md`, `persona-ops-maintainability-realist.md`, `persona-zero-based-redesigner.md`(발산) | (최초 생성) |
| 2차 (08-10 19:38) | `review-pm-block-propagation-mechanism-2026-08-10.md` | 위 3개 **그대로 재사용** — 관심사만 이번 라운드에 맞춰 적용 | ✅ 재사용 성공 |
| 3차 (08-10 20:14) | `review-pm-import-implementation-2026-08-10.md` | `persona-hook-execution-safety-verifier.md`, `persona-ops-drift-realist.md`, `persona-mechanism-zero-based-challenger.md`(발산) — **전부 신규 파일** | ❌ 재사용 실패 |

3차에서 새로 만든 페르소나 3개를 읽어보면, 역할개념은 사실상 기존과 동일하다:
- `persona-ops-drift-realist.md` ≈ `persona-ops-maintainability-realist.md` (둘 다 "6개월 후에도 살아있는가"를 묻는 운영 현실주의자, 방법론도 거의 동일 — git diff 대조 + 반복성 검증)
- `persona-mechanism-zero-based-challenger.md` ≈ `persona-zero-based-redesigner.md` (둘 다 "구조 자체가 최선인가"를 묻는 발산형, "대안 없이는 무효" 원칙까지 동일 문구)
- `persona-hook-execution-safety-verifier.md`만 진짜 신규 관심사(3차부터 처음으로 실제 `hooks.json` 실행경로가 검증 대상에 들어옴 — 1·2차는 "훅 텍스트 변경 없음"이 전제였던 설계 리뷰였음)

**근본 원인 3가지:**

1. **탐색 비용이 재사용 판단을 막는다.** `docs/reviewer/personas/`에 파일이 14개 누적돼 있는데, 이름만 보고는 겹치는지 알 수 없다(`ops-maintainability-realist` vs `ops-drift-realist`가 같은 개념인지는 본문을 읽어야 안다). reviewer.md·스킬 어디에도 "먼저 무엇을 찾아봐야 하는가"에 대한 절차가 없어, 매번 본문을 다 읽는 대신 그냥 새로 쓰는 쪽이 저항이 적다.
2. **"구체적 서사로 박제한다" 지침이 재사용과 충돌 방향으로 작동한다.** `reviewer-persona-panel-standard` §1은 정체성·관심사·참고파일을 "이번 리뷰 대상에 맞춰 구체적으로" 쓰라고 요구한다. 이 자체는 옳은 지침이지만, "역할개념(고정)"과 "이번 라운드 적용 내용(가변)"을 분리하는 구조가 없어서, 라운드가 바뀌면 정체성·관심사 문구까지 통째로 새로 쓰는 게 자연스러워 보인다. 실제로 3차 페르소나들은 관심사 문단에 "오늘 세 번째로 설계가 바뀐 문제라면" 같은 이번 라운드 전용 서사를 정체성에 박아 넣었다 — 이게 새 파일을 만드는 합리적 이유처럼 보이게 만든다.
3. **재사용 여부를 검증하는 게이트가 없다.** reviewer.md 49행 "기존 `docs/reviewer/personas/`에 페르소나가 있으면 재활용합니다"는 산출물 게이트(파일 존재 확인)와 달리 **체크리스트 항목이 아니다** — 안 지켜도 자기검증에서 걸리지 않는다. reviewer.md 33행 "산출물 게이트"는 "페르소나 파일이 N개 존재하는가"만 확인하지, "그 N개가 기존 걸 재활용한 것인가 신규인가"는 묻지 않는다.
4. **재검토 라운드를 잇는 연결고리가 없다.** 리뷰 문서 파일명이 주제어("block-sync" → "block-propagation-mechanism" → "import-implementation")로 매번 달라진다. 같은 기능의 몇 차 재검토인지 표시하는 고정 식별자(target_id)가 없어서, 3차 리뷰를 맡은 reviewer가 1·2차 리뷰·페르소나를 반드시 열어봐야 할 이유가 형식상 없다(사람이 위임 메시지에 링크를 챙겨줬을 때만 우연히 재사용됨 — 실제로 2차까지는 이게 됐다가 3차에서 끊겼다).

이 진단이 아래 설계의 근거다: 해법은 "재사용해라"는 문구를 더 강하게 쓰는 게 아니라, **탐색 비용을 낮추는 인덱스**, **역할개념/라운드적용을 분리하는 파일 구조**, **재사용 여부를 강제로 선언시키는 게이트**, **라운드를 잇는 식별자** 네 가지를 구조적으로 넣는 것이다.

## 1. "동일 대상 재검토" 판정 기준

### 1.1 핵심 개념: `target_id` (안정 식별자)

리뷰 대상 파일명(주제어 기반)과 별도로, **기능/의사결결정 단위**로 안정적인 `target_id`를 둔다. 같은 기능이 하루에 여러 번 수정돼 여러 번 리뷰돼도 `target_id`는 동일하게 유지된다.

- **발급 시점·주체**: PM이 Sensitive/Refactor 등급 산출물을 reviewer에 **최초로** 위임할 때 `target_id`를 발급해 위임 메시지에 명시한다(예: `target_id: pm-orchestration-block-propagation`). 짧은 kebab-case 슬러그, 리뷰 대상 파일명과 무관해도 됨.
- **재사용 시점**: 같은 기능을 **같은 날 또는 직전 리뷰로부터 7일 이내**, PM이 다시 reviewer에 위임할 때는 **반드시 같은 `target_id`를 명시**해야 한다. PM이 target_id를 빠뜨리면 reviewer는 "최초 리뷰"로 간주해 풀패널로 처리한다(안전측 기본값 — 위 5번째 근본 원인의 재발 방지).
- reviewer는 위임 메시지에 `target_id`가 있으면, 리뷰 착수 전 `docs/reviewer/review-*-{target_id 관련 키워드}*.md` 또는 이전 리뷰 보고서 front-matter의 `target_id`를 grep해 직전 라운드 문서·페르소나를 먼저 찾는다.

### 1.2 "동일 대상"으로 인정하는 조건 (AND, 보수적)

아래 4개를 **모두** 만족해야 축소/증분 모드 후보가 된다. 하나라도 어긋나면 다른 대상으로 간주해 최초 리뷰(풀패널)로 처리한다.

1. **동일 `target_id`** — PM이 위임 시 명시.
2. **경과일 ≤ 7일** — 직전 같은 target_id 리뷰 완료일로부터 7일 초과하면 컨텍스트가 stale해졌다고 보고 신규 target_id(=최초 리뷰)로 강제 분리.
3. **리스크 범주 불변** — PM이 최초 위임 시 Sensitive/Refactor 판정 근거로 든 blast radius 범주(예: "전역 자동실행 자산", "인증", "배포", "결제", "개인정보")가 이번 위임에서도 동일해야 한다. **범주가 바뀌면(예: 인증 변경이었다가 배포 변경으로 확장) 절대 같은 target_id를 쓰지 않는다** — PM이 새 target_id를 발급한다. 이것이 "도메인이 바뀐 변경까지 축소검증으로 새는" 것을 막는 1차 방어선이다.
4. **파일 실질 중첩** — 이번 리뷰 대상 파일 집합과 직전 리뷰 대상 파일 집합 사이에 최소 1개 이상 실질 중첩(같은 파일 또는 같은 설계 문서의 개정판)이 있다.

### 1.3 판정 주체와 기록

판정은 **PM이 위임 시 1차 판단**하고(target_id 발급/재사용 여부), **reviewer가 착수 시 2차 검증**한다(위 4조건을 직접 대조 — PM의 판단을 맹신하지 않음). reviewer가 2차 검증에서 조건 불충족을 발견하면(예: PM이 재사용을 지시했지만 실제로는 파일 집합이 전혀 안 겹침) 최초 리뷰로 격상하고 그 사유를 보고서에 명시한다.

## 2. 축소/증분 검증 모드 (3단계)

풀패널 vs 축소를 이분법으로 나누지 않는다. 실측 사례(3차 리뷰가 "완전 동일"도 "완전 신규"도 아니라 "기존 2개 관심사 + 신규 1개 관심사"였던 것)에 맞춰 **3단계**로 설계한다.

| 모드 | 조건 | 페르소나 처리 | 검증 범위 |
|---|---|---|---|
| **A. 최초(Full)** | target_id 최초 발급, 또는 §1.2 4조건 중 하나라도 불충족, 또는 §3 에스컬레이션 조건 충족 | 신규 2~4명 작성(발산형 포함) | 전체 |
| **B. 증분(Incremental)** | §1.2 충족 + 이번 라운드에 **직전 패널이 다루지 않던 새 리스크 표면**이 추가됨(예: 설계 리뷰 다음에 실제 구현/실행경로 리뷰가 처음 붙는 경우) | 직전 패널 전원 **재사용**(파일 그대로, §4의 적용이력만 append) + 새 리스크 표면당 **최대 1명** 신규 추가. 총 패널 크기는 "직전 패널 수 + 신규 표면 수"를 넘지 않음 | 직전 리뷰 이후 diff 전체 + 새 리스크 표면 집중 검토 |
| **C. 축소(Abridged)** | §1.2 충족 + 새 리스크 표면 없음(순수 재수정) | 직전 패널 전원 **재사용**, 신규 인원 0명 | 직전 리뷰 이후 diff만 + 직전 Critical/Major 해결여부 확인 위주 |

실측 사례에 이 표를 적용하면: 1차=A(최초), 2차=C(축소, 실제로 이렇게 됐음 — 옳았음), 3차=B(증분 — `hook-execution-safety` 1명만 신규 추가하고 나머지 2명은 기존 파일 재사용했어야 함, 실제로는 A처럼 3명 전부 신규 처리된 것이 문제).

### 2.1 축소(C)/증분(B) 공통 절차

1. 직전 같은 target_id 리뷰 보고서를 Read → **불변 이슈 ID(RV-001…)별 Critical/Major 목록**을 추출한다(기존 reviewer.md 76행 "다차수 리뷰" 규칙 — 이미 있는 규칙을 재검토 모드 판정에 명시적으로 연결).
2. diff 확보:
   - 코드/설정 대상: `git diff <직전 리뷰 시점 커밋>..HEAD -- <대상 경로>`
   - 설계문서 대상: 직전 리뷰가 참조한 문서 버전과 현재 버전을 라인 단위 대조(문서에 버전 이력이 없으면 reviewer가 두 시점 스냅샷을 확보해야 함 — 없으면 "diff 확보 불가, 전체 재검토로 격상"하고 사유 명시)
3. 재사용 대상 페르소나 파일을 Read하고, **파일은 수정하지 않은 채** 이번 라운드 적용 결과만 새로 생성한다(§4 참조 — "적용 이력" append 방식).
4. 각 재사용 페르소나는 자신의 기존 평가기준으로 diff 범위 내 신규 지적 + 직전 Critical/Major의 해결 여부(원본 라인 인용 vs 신규 라인 인용, "수정됨" 자체보고 금지 — 기존 reviewer.md 안티패턴 규칙 그대로 적용)를 확인한다.
5. (증분 모드 B만) 새 리스크 표면 담당 신규 페르소나 1명을 §4 6대 요소로 작성 — 단, 작성 전 §4.1 INDEX.md 대조를 반드시 거친다.
6. 보고서는 축소 전용 템플릿(§5)으로 작성한다 — 전체 템플릿을 다시 채우지 않는다.

## 3. 풀패널 강제 승격(에스컬레이션) 조건

아래 중 **하나라도 해당하면** B/C 모드를 쓰지 않고 A(최초/풀패널)로 강제 승격한다. reviewer는 착수 전 이 체크리스트를 먼저 통과시켜야 B/C를 선택할 자격이 생긴다(순서: 에스컬레이션 체크 → 통과 시에만 §1.2 동일대상 판정 → B/C 선택).

- [ ] 직전 리뷰의 Critical/Major 항목 중 **미해결**로 확인된 것이 하나라도 있다 (해결 여부는 자체보고가 아니라 reviewer가 원본 라인 대조로 직접 확인)
- [ ] 이번 변경이 직전 리뷰 대상 파일 집합에 **없던 실행 경로**를 새로 포함한다 (예: 직전엔 "훅 텍스트 무변경"이 전제였는데 이번엔 실제 `hooks.json`/스크립트 코드가 바뀜 — 3차 리뷰가 이 조건에 해당했다. 이 경우도 곧바로 A는 아니고, 새 표면 1개면 B, 새 표면이 다수/구조 전반이면 A로 판단)
- [ ] 이번 변경이 §1.2③의 리스크 범주를 벗어나 **다른 Sensitive 하위도메인**에 진입한다(예: 훅/정책 텍스트 변경이었다가 이번엔 DB 스키마·권한 로직까지 건드림)
- [ ] 같은 target_id의 재검토가 **4차 이상 누적**됐다 — 축소 모드로 절감하되, 같은 기능이 반나절~하루 안에 4번 이상 Sensitive 재수정된다는 것 자체가 설계 불안정 신호이므로, PM에게 "설계 자체를 안정화하고 재착수하라"는 별도 에스컬레이션(신뢰도 문제)을 하고 리뷰는 안전측으로 풀패널 처리한다
- [ ] PM 또는 사용자가 명시적으로 풀패널을 요청했다
- [ ] reviewer가 §1.2 4조건 대조 결과 하나라도 불충족을 발견했다

이 중 어느 것도 해당하지 않을 때만 B/C를 쓴다 — **애매하면 무거운 쪽(A)으로 기운다** 원칙(pm.md 기존 원칙과 동일 기준 적용).

## 4. 페르소나 재사용 강제 절차 (파일 구조 + 게이트)

### 4.1 `docs/reviewer/personas/INDEX.md` 신설 (탐색 비용 해소)

현재 14개 페르소나 파일을 이름만으로는 구분할 수 없는 문제(근본 원인 1)를 해소하기 위해, reviewer가 새 페르소나를 만들기 **전에 반드시 먼저 읽는** 경량 인덱스를 둔다.

```markdown
# 리뷰 페르소나 인덱스

새 페르소나를 만들기 전, 이 표에서 역할개념이 이미 있는지 먼저 확인한다. 겹치면 신규 파일을 만들지 않고 기존 파일을 재사용한다(§4.2).

| 파일 | 역할개념(1줄) | 유형 | 최초 생성 | 최근 재사용(target_id/라운드) |
|---|---|---|---|---|
| persona-skeptical-verification-architect.md | 설계 문서 내부 근거가 독립적 증거인지 의심하는 회의적 검증가 | 수렴 | 2026-08-10 | pm-orchestration-block-propagation / 1~2차 |
| persona-ops-maintainability-realist.md | "6개월 후에도 살아있는가"를 묻는 운영 현실주의자 | 수렴 | 2026-08-10 | pm-orchestration-block-propagation / 1~2차 |
| persona-zero-based-redesigner.md | 구조 자체가 최선인지 의심하는 발산형 | 발산 | 2026-08-10 | pm-orchestration-block-propagation / 1~2차 |
| ... | ... | ... | ... | ... |
```

- 유지 책임: 페르소나 파일을 새로 만들거나 재사용할 때마다 reviewer가 이 표의 해당 행을 갱신(신규면 행 추가, 재사용이면 "최근 재사용" 열만 갱신)한다.
- "역할개념(1줄)" 열은 **문체·이번 라운드 세부사항을 뺀 핵심 질문**만 적는다(예: "6개월 후에도 살아있는가"). 이 열끼리 의미가 겹치면 그게 곧 "동일 역할개념"이라는 신호다 — reviewer가 파일 본문을 다 읽지 않고도 1차 스크리닝 가능하게 하는 것이 목적.

### 4.2 페르소나 파일 구조 분리: 역할개념(고정) vs 적용이력(가변)

근본 원인 2(구체적 서사 요구가 재사용과 충돌)를 해소하기 위해, 페르소나 파일 템플릿에 섹션을 하나 추가한다.

- 기존 6대 요소(정체성/관심사/평가기준/평가방법론/참고파일/출력포맷)는 **역할개념 수준으로만** 쓴다 — "이번 라운드에 특화된 서사"를 정체성/관심사 본문에 박아넣지 않는다. (예: "오늘 세 번째로 설계가 바뀐 문제라면" 같은 라운드 한정 문장은 정체성에 넣지 않는다.)
- 파일 맨 아래에 **"## 적용 이력 (Application Log)"** 섹션을 append-only로 추가한다. 재검토 라운드마다 여기에 1개 항목만 덧붙이고, 위 6대 요소 본문은 건드리지 않는다.

```markdown
## 적용 이력 (Application Log)
- 2026-08-10 / target_id: pm-orchestration-block-propagation / 1차 (review-pm-orchestration-block-sync-2026-08-10.md): 훅+스킬 분리안 최초 검증
- 2026-08-10 / target_id: pm-orchestration-block-propagation / 2차 (review-pm-block-propagation-mechanism-2026-08-10.md): "정체성 지속성" 근거의 독립성 재검증
- 2026-08-10 / target_id: pm-orchestration-block-propagation / 3차 (review-pm-import-implementation-2026-08-10.md): @import 실제 구현의 안전성 재검증
```

이렇게 하면 "이번 라운드에 맞는 구체적 서사"는 적용 이력에 쌓이고, 정체성/관심사는 라운드가 바뀌어도 그대로 유지되므로 "새로 쓰는 게 자연스러워 보이는" 압력이 사라진다.

### 4.3 재사용 여부 선언 게이트 (신규 — 산출물 게이트에 추가)

근본 원인 3(재사용 위반이 걸러지지 않음)을 해소하기 위해, 리뷰 보고서 상단에 **페르소나별 신규/재사용 선언 표**를 필수 항목으로 추가한다. 이 표가 없으면 산출물 게이트 위반으로 간주한다.

```markdown
## 페르소나 재사용 판정 (게이트 — 생략 불가)
| 페르소나 | 판정 | 사유 |
|---|---|---|
| persona-ops-maintainability-realist.md | 재사용 | INDEX.md 대조 결과 동일 역할개념, 적용이력만 append |
| persona-zero-based-redesigner.md | 재사용 | 상동 |
| persona-hook-execution-safety-verifier.md | 신규 | INDEX.md에 "실행경로 안전성" 역할개념 없음 — 3차부터 처음 hooks.json 실제 실행이 검증대상에 포함되어 신규 추가 |
```

"신규"로 표기했는데 INDEX.md에 이미 동일 역할개념 행이 있으면(사후 검증에서 드러나면) PM 보고 시 이 표를 근거로 재작업을 요구할 수 있다 — 즉 이 표 자체가 재사용 강제의 실행 메커니즘이다(선언만 시키는 게 아니라, 선언 내용을 INDEX.md와 대조 가능하게 만들어 거짓 "신규" 표기가 걸리게 함).

## 7. 이 설계의 4대 의무 자기검증

① **트레이드오프**: target_id를 PM 수동 발급으로 설계(자동 추론 대신) — 대안은 파일 경로 유사도로 자동 판정이었으나, 유사도 알고리즘은 "인증→배포" 같은 도메인 전환을 안정적으로 못 걸러낼 위험이 있어 기각. 사람(PM)의 명시적 판단을 게이트로 세우고 reviewer가 2차 검증하는 이중 구조를 택함 — 대신 PM이 target_id 발급을 잊으면 축소 모드 혜택을 못 받는 비용이 있으나, 안전측 기본값(최초 리뷰 처리)이므로 품질 저하는 없음.

② **프로젝트 고유성**: 이 설계는 malgn-agent 자체 운영(전사 배포 자동실행 자산의 반복 설계변경)에서 실측된 문제를 다룬다 — 범용 리뷰 프로세스 이론이 아니라, 오늘 실제로 쌓인 9개 페르소나 파일의 실질 중복을 근거로 역할개념/적용이력 분리 구조를 도출했다.

③ **비정상 케이스**: diff 확보 불가(문서 버전 이력 없음) 시 격상 규칙(§2.1-2) / target_id 누락 시 안전측 기본값(§1.1) / PM 판단과 reviewer 재검증이 어긋나는 경우의 처리(§1.3) / 4차 이상 누적 시 설계 불안정 신호 별도 에스컬레이션(§3)을 명시했다.

④ **완결성**: 판정 기준(§1)·모드별 절차(§2)·에스컬레이션(§3)·강제 절차(§4)·보고서 템플릿(§5)·파일별 구체 문구(§6)까지 trainer가 그대로 옮겨적을 수 있는 수준으로 작성했다.
