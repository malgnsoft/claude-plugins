# 시스템 설계 패턴

## 아키텍처 패턴 비교

| 패턴 | 적합한 경우 | 복잡도 |
|------|------------|--------|
| 모놀리식 | 소규모, 빠른 프로토타이핑 | 낮음 |
| 모듈러 모놀리스 | 중규모, 점진적 분리 예상 | 중간 |
| MSA | 대규모, 팀 독립 배포 필요 | 높음 |
| 서버리스 | 이벤트 기반, 트래픽 변동 큰 서비스 | 중간 |

## C4 모델 (아키텍처 문서화)

### Level 1: System Context
시스템이 외부와 어떻게 상호작용하는지

```
[사용자] → [우리 시스템] → [외부 API]
                ↓
          [데이터베이스]
```

### Level 2: Container
시스템 내부 구성 요소

```
[웹 브라우저] → [API 서버] → [DB]
                    ↓
              [Worker/배치]
```

### Level 3: Component
컨테이너 내부 모듈

```
[Router] → [Controller] → [Service] → [Repository] → [DB]
```

## API 설계 원칙

### RESTful API 규칙
- 명사 복수형: `/users`, `/posts`
- 계층 관계: `/users/:id/posts`
- 동작은 HTTP 메서드로: GET/POST/PUT/PATCH/DELETE
- 필터링: `/users?role=admin&status=active`
- 페이징: `/users?page=1&limit=20`
- 정렬: `/users?sort=created_at&order=desc`

### 응답 형식 표준
```json
// 성공
{ "data": {...}, "meta": { "page": 1, "total": 100 } }

// 에러
{ "error": { "code": "VALIDATION_ERROR", "message": "이메일 형식이 올바르지 않습니다", "details": [...] } }
```

### HTTP 상태 코드
| 코드 | 의미 | 사용 |
|------|------|------|
| 200 | OK | 조회/수정 성공 |
| 201 | Created | 생성 성공 |
| 204 | No Content | 삭제 성공 |
| 400 | Bad Request | 잘못된 요청 |
| 401 | Unauthorized | 인증 필요 |
| 403 | Forbidden | 권한 없음 |
| 404 | Not Found | 리소스 없음 |
| 409 | Conflict | 중복/충돌 |
| 500 | Internal Error | 서버 오류 |

### DB 설계 깊이 — "테이블·컬럼 나열"을 넘는 4가지 (산출물 진단 2026-06-20)

> 실제 architect DB 산출물 진단에서, DB 설계가 API 설계보다 현저히 얕았다(테이블·컬럼만 나열, 근거·제약·성능 전략 부재). DB는 API와 동급의 핵심 산출물이다. 테이블마다 아래를 채운다.

1. **인덱스에 "왜 이 순서"를 적는다.** 복합 인덱스 `(a, b)`는 "a로 필터 후 b 정렬/범위" 쿼리에만 맞다. **쿼리 패턴을 먼저 적고 그에 맞춰 인덱스를 설계**한다. 같은 데이터라도 "개인 대시보드(coachee_id별)"와 "운영자 대시보드(날짜별 전체)"는 다른 인덱스가 필요하다 — 둘 다 있으면 둘 다 설계한다. 자주 읽는 컬럼만 거는 커버링 인덱스도 고려.
2. **제약을 DB 수준에서 강제한다.** FK·UNIQUE·CHECK를 명시한다. "애플리케이션에서 검증"은 앱 버그 시 데이터가 깨진다. 점수 범위(`CHECK score BETWEEN 1 AND 5`), 상태 enum, `start < end`, type별 조건부 NOT NULL 등은 DB가 막는다.
3. **정규화/비정규화 판단에 근거를 단다.** JSON 컬럼 vs 별도 테이블, 집계 테이블 도입 여부를 트레이드오프로 적는다. **시계열·대용량 테이블**(감정 체크인, 로그, 메시지 등 매일/매건 쌓이는 것)은 ① 범위조회 인덱스 ② 일/주/월 **집계 테이블**(매번 풀스캔 방지) ③ 규모 커지면 파티셔닝을 명시. "1000명 × 365일 = 36만 행"같은 추정으로 규모를 가늠.
4. **정책을 테이블 전체에서 일관 적용한다.** soft delete vs 물리 삭제, audit 컬럼(created_at/by), 타임존, enum 표기(snake_case)를 **모든 테이블에 같은 기준으로**. "원칙은 적었는데 절반의 테이블에만 적용"이 흔한 결함 — 원칙을 정했으면 빠짐없이 적용하거나, 예외엔 사유를 단다. 개인정보(PIPA 등) 삭제 정책은 어느 테이블이 물리삭제 대상인지 명시하고 실제 그 컬럼/전략을 넣는다.

## 분산·동기화 패턴 (로컬→중앙 / 멀티 디바이스 / 준실시간 수집)

> 출처: malgnai `central-monitoring.md` 산출물 진단(2026-06-20). "로컬 PC들이 중앙 서버로 push하고 모바일에서 모니터링" 류 설계에서, 평범한 설계는 happy-path만 그리고 데이터 유실/중복/시계오차를 놓친다. 아래는 그 약점을 구조적으로 막는, 검증된 패턴 세트다. 이 종류 시스템(로컬 수집기·에이전트 텔레메트리·오프라인 동기화·멀티 PC 통합)을 설계하면 해당 패턴을 **반드시 검토**한다.

### 1. 멱등 인입 + 아웃박스 (무손실 전송의 쌍)
유실 없이 전송하려면 두 패턴을 **함께** 써야 한다. 하나만 쓰면 깨진다.
- **멱등 인입**: 클라이언트가 `id`(UUID)를 생성해 보내고, 서버는 `INSERT ... ON CONFLICT(id) DO UPDATE`. 같은 레코드를 몇 번 재전송해도 중복이 안 생긴다.
- **아웃박스(store-and-forward)**: 평소엔 즉시 원격 push, **실패 시에만** 로컬에 append 후 나중에 재전송. 멱등이 보장돼야 재전송이 안전하다(→ 그래서 쌍이다).
- **저장 매체 트레이드오프**: 아웃박스에 SQLite vs **JSONL 한 줄 append**. 평상시 비어 있고 장애 중에만 쌓이는 임시 버퍼라면 JSONL이 운영부담(로컬 DB·마이그레이션)을 없앤다. "무손실은 지키되 로컬 상태는 최소화"가 핵심. 로컬 DB가 정말 필요한지 먼저 따진다(아래 §3 토폴로지).

### 2. 폴링 커서는 서버 인입 시각(`ingested_at`) 기준 — 클라이언트 시각 금지
증분 폴링(`?since=<cursor>`)의 커서를 **클라이언트 `created_at`으로 잡으면 안 된다.** 여러 디바이스의 시계가 어긋나면, 늦게 도착한 레코드가 폴링 윈도우를 빠져나가 **조용히 누락**된다. 커서는 **서버(D1/DB)가 인입 순간 찍는 단조 증가 시각(`ingested_at`)** 기준으로 잡고, 응답에 다음 커서를 함께 반환한다. 데이터가 적은 초기에 박아두는 게 가장 싸다(나중에 소급 불가). 향후 SSE/Durable Objects 전환을 대비해 증분 API 형태를 미리 갖춘다. 탭 비활성(`visibilitychange`) 시 폴링 중단 → 모바일 배터리/요청 절약.

### 3. 배포 토폴로지 트레이드오프 — 얇은 프록시 vs 로컬 DB (멀티 PC 운영 비용)
로컬에 무엇을 두느냐가 멀티 PC 운영 비용을 좌우한다. **변경 유형을 둘로 쪼개서** 비교하는 게 분석의 핵심:

| 변경 유형 | 얇은 프록시(로직·DB·인증 전부 서버) | 로컬 DB 보유 |
|---|---|---|
| 도구/인터페이스 시그니처 변경 | PC 갱신 | PC 갱신 (동일) |
| 로직·저장·스키마 변경 | **서버 배포 한 번** | PC 갱신 + **PC별 마이그레이션** |

- 하방(시그니처 변경)은 동일하고 상방(로직/스키마)만 프록시가 압도 → **비대칭**. 어떤 시나리오에서도 로컬 DB가 이기지 않는다.
- 반직관 포인트: "초기엔 자주 바뀌니 로컬 DB가 낫다"는 틀렸다. **자주 바뀔수록 마이그레이션 벌점이 더 자주 누적**되므로 프록시가 더 유리하다.
- 진짜 부담("PC 갱신이 귀찮다")은 구조가 아니라 **배포 메커니즘**으로 푼다: ① 하위호환 API(모르는 필드 무시·새 도구 추가, 구버전 PC 안 깨짐) ② `git pull` 단일 동작(프록시+수집기+아웃박스를 한 폴더=단일 배포 단위) ③ 버전 가시화(`X-Client-Version` 헤더 → 구버전 PC만 콕 집어 갱신) ④ 반자동 업데이트(PC가 많아질 때만).

### 4. 점진 확장 설계 — "지금 잠글 것 vs 나중에 더할 것"
멀티 PC·멀티테넌시 같은 장기 확장은 **데이터 모델을 갈아엎지 않고 컬럼·화면 추가로** 가능하게 설계한다. 단, **소급 불가능한 소수의 결정만 지금 박는다.** 위 사례에선 (a) opaque 키 모델, (b) `ingested_at` 커서 둘뿐 — 나머지(디바이스 식별 `device_id`, 권한 격리, 키 스코프/만료)는 실제 필요 시점에 추가. 설계서에 "지금 결정 / 나중에 추가 + 도입 시점"을 표로 분리해 명시하면, 과설계(YAGNI 위반)와 소급 불가 누락을 동시에 막는다.

### 4b. 설계서 ↔ 운영/설치 문서 일관성 (산출물 묶음 전체의 정합성)
완결성·일관성 의무는 *한 문서 안*뿐 아니라 **산출물 묶음 전체**(설계 ↔ API ↔ DB ↔ 설치/운영 가이드)에 적용된다. 설계 결정을 바꾸면 그 결정에 의존하는 **파생 문서를 같은 작업에서 함께 갱신**한다. 즉시 못 하면 문서 상단에 `⚠ 목표 대비 미반영: X` 를 명시한다 — **침묵하는 불일치는 금지**(설치가이드가 "이 설계의 적용 절차"라 주장하면서 옛 모델을 안내하면, 운영자가 그대로 깔다 보안 격리·무손실이 깨진다).
- **자기점검(보고 전)**: "이 결정을 따라야 할 다른 문서가 있나? 일치하나?" 특히 **인증 모델 · 로컬 상태(DB 유무) · 키 정책**처럼 운영자가 손으로 세팅하는 항목은 설치/운영 가이드와 반드시 대조한다.
- 사례(malgnai 2026-06-20): `central-monitoring.md`(목표: 프로젝트별 opaque 키 + JSONL 아웃박스 + 키 미설정 시 거부)와 `setup-guide.md`(현행: 단일 공유 키 + 로컬 SQLite + 키 미설정 시 자동 비활성화)가 정면 모순. 설계 변경이 설치가이드에 반영되지 않은 전형적 결함.

### 5. 키 인증 — opaque 토큰 + DB 매핑 (키에 정보를 인코딩하지 않는다)
멀티 디바이스/멀티 프로젝트 인입 인증: 단일 공유 키 금지(유출 시 폭발 반경 = 전체). 대신 **프로젝트/디바이스별 무작위 opaque 토큰**을 발급하고, "이 키가 누구인지"는 **DB가 답한다**(`api_keys` 테이블). 원칙: 서버엔 **해시만** 저장(평문은 발급 1회만 노출), 키 문자열을 파싱해 주체를 추론 금지, `revoked_at`으로 즉시 폐기·무중단 회전, `last_used_at`/`key_prefix`로 운영 가시성. 폭발 반경을 주체 단위로 격리한다.

## 우수 설계의 재사용 기법 — coaching(Coach Connect) 산출물 역추출 (2026-06-20)

> 출처: coaching 프로젝트의 실제 architect 산출물 진단(20·21 아키텍처, 30~34 DB, 40~46 API, 70~73 최종스펙). 이 설계는 **우수 사례**다. 평범한 설계와 무엇이 달랐는지 기법을 역추출해 박제한다. 아래는 "잘된 이유"를 일반화한 것이므로, 다음 설계에서 **해당 항목이 있으면 그대로 차용**한다.

### A. 추적성 사슬 — PRD → BC → 엔티티 → 테이블 → API를 ID로 꿰뚫는다
coaching 설계의 가장 강한 무기는 **모든 산출물이 ID로 역추적**된다는 점이다. 이게 "복붙 템플릿"과 "이 프로젝트 전용 설계"를 가른다.
- 모듈(A~J) → Bounded Context(BC-1~7) → 도메인 엔티티(19개) → DB 테이블(20개, BC 컬럼 명시) → API 그룹이 **표로 1:1 매핑**된다. DB 테이블 요약표가 `Bounded Context`와 `분할 문서` 열을 가진 게 대표적(`| users | User | BC-1 | 31-...md |`).
- 모든 컬럼·엔드포인트·규칙에 **FR-ID/NFR-ID/RV-ID 역참조**를 단다(`coach_notes ... (FR-020)`, `비밀번호 정책 (NFR-002)`, `24시간 규칙 ... (RV-014)`). 리뷰에서 나온 결정엔 RV-ID로 추적(`PRD FR-019 "상대방 확인 필요"는 "알림 발송"으로 완화 (RV-005)`).
- **기법**: 설계 착수 시 PRD의 FR/NFR에 ID를 부여(없으면 매기게 요청)하고, 산출물의 모든 결정 옆에 그 ID를 괄호로 단다. "이 컬럼/엔드포인트는 어느 요구사항을 충족하나?"에 답 못 하는 항목은 과설계(YAGNI)거나 추적 누락이다.

### B. 도메인 경계(Bounded Context)를 먼저 긋고 데이터 소유권을 명시한다
- 7개 BC마다 `포함 모듈 / 핵심 엔티티 / 책임 / 데이터 소유권`을 적었다. 특히 **읽기 전용 BC를 따로 표시**한 게 우수: "BC-6 분석/리포트: 다른 BC의 데이터를 읽기 전용으로 집계한다(데이터 소유하지 않음)", "BC-7 알림: 이벤트 수신하여 알림 생성하는 횡단 관심사".
- **기법**: 모듈러 모노리스라도 BC를 명시하면 (a) 2단계 서비스 분리 시 잘라낼 경계가 보이고 (b) "누가 이 테이블을 쓰는가"의 소유권 분쟁을 미리 차단한다. 횡단 관심사(알림·감사·인증)와 read-model(대시보드·리포트)은 별도 BC로 떼어낸다.

### C. 상태 머신을 명시적 전이 규칙으로 적는다 (ENUM + 허용 전이)
- sessions: `scheduled→in_progress→completed`, `scheduled→cancelled`, `scheduled→no_show`를 **허용 전이만 화살표로 나열**. session_summaries: `draft→confirmed`. 각 상태를 DB ENUM으로 잠그고, 전이 규칙을 워크플로우(9.4/9.5)와 교차 일치시킴.
- **기법**: 생애주기 있는 엔티티(주문·세션·결제·승인 등)는 ① 상태 ENUM ② **허용 전이만** 명시(금지 전이는 자동으로 배제) ③ 전이를 일으키는 API와 1:1 매핑 ④ 각 전이의 부수효과(타임스탬프 기록, 알림, 외부호출)를 워크플로우에 적는다.

### D. 역할×리소스 권한 매트릭스 (데이터 격리 규칙까지)
- `API 그룹 × (operator/coach/coachee)` 표로 권한을 격자로 그렸다. "전체 / 본인만 / 담당자만(읽기) / X"처럼 **수직 권한(역할)과 수평 격리(소유권)를 한 칸에** 표현. 추가로 데이터 격리 규칙을 산문으로 못박음("코치는 Assignment 기반 필터링", "저널은 코치에게도 비공개").
- **기법**: RBAC는 역할 목록만 적으면 미완성. **리소스×역할 매트릭스 + 행 단위(row-level) 격리 규칙**(본인/배정/소유 기반 WHERE 조건)을 함께 적어야 backend가 그대로 구현한다.

### E. 트레이드오프를 "리스크 → 영향 → 완화" 표로 강제한다
- 아키텍처 §11이 복잡도/비용/확장성/유지보수 4축으로 트레이드오프를 표로 정리. 특히 **확장성 표가 `현재 설계 / 트레이드오프 / 향후 대응` 3열**이라 "지금 안 하는 것"을 의도적으로 기록(단일테넌트 company_id 선반영, 대시보드 집계는 2단계 집계테이블, 인앱알림 폴링→2단계 SSE). Workers 30초 CPU 제한을 인식하고 그게 AI 스트리밍에 미치는 영향(SSE로 시작 지연 최소화, OpenAI 20초 타임아웃)까지 설계.
- **기법**: 제약을 적었으면 **그 제약이 핵심 기능에 주는 영향과 대응**까지 한 줄 더 쓴다. 확장성은 "지금/나중" 2열로 갈라, 지금 박을 소급불가 결정(company_id 컬럼)과 나중에 더할 것(집계 테이블)을 분리한다.

### F. 비정상 케이스를 워크플로우에 인라인으로 심는다
- 평범한 워크플로우는 happy path만 그리는데, coaching은 실패 분기를 같은 흐름에 끼워넣었다: 세션 요약 **생성 실패 시 빈 요약으로 저장→코치 수동 작성**(부분 실패 graceful degradation), 이메일 발송은 `waitUntil`로 Worker 종료 지연 + **실패 시 Notification에 실패 상태 기록**(notifications.email_status ENUM에 `failed` 포함 — 설계와 DB가 일치), 화상 서비스 장애 시 **채팅 세션을 대안**으로.
- AI 코치 API: 에러표에 `429 RATE_LIMIT_EXCEEDED`(분당 10회 비용제어), `502 EXTERNAL_SERVICE_ERROR`(OpenAI 통신오류), 컨텍스트 **최근 20메시지로 제한**(컨텍스트 윈도우 폭발 방지), preview는 **DB 저장 안 함** 명시.
- **기법**: 외부 호출(LLM·결제·이메일·화상)마다 타임아웃·실패 시 동작·대안 경로를 워크플로우에 인라인. "실패 상태"를 DB ENUM에 넣어 설계-DB-API가 한 사실을 가리키게 한다.

### G. 문서 분할 전략 — 인덱스 문서 + 분할 본문
- 큰 산출물(아키텍처/DB/API/최종스펙)을 `X0`(인덱스: 요약·설계원칙·분할 안내표) + `X1~Xn`(본문)으로 쪼갰다. 인덱스 문서가 **분할 안내표**(`파일 | 내용 요약`)와 **공통 설계 원칙**(네이밍·감사컬럼·soft delete·ID형식·타임존을 한곳에)을 담아, 본문은 원칙 반복 없이 테이블만 정의.
- **기법**: 산출물이 길어지면(1500줄+) 인덱스+분할로 나누되, **횡단 규칙(네이밍·에러규약·페이지네이션)은 인덱스 문서 한 곳에** 정의하고 본문에서 참조. 이러면 일관성 점검이 한 파일에서 끝난다.

### 보완점 — 이 우수 설계에도 빠진 관점 (다음 설계에서 메울 것)
우수 사례에도 happy-path 잔재가 있다. 아래는 coaching 설계에서 **실제로 비어 있던 곳**이라, 같은 유형 설계에서 의식적으로 챙긴다.
1. **동시성/경쟁 조건(TOCTOU) 미설계.** 세션 예약(`POST /sessions`)이 "step3 가용시간 검증 → step4 충돌 확인 → step5 INSERT"의 **check-then-insert**인데, sessions 테이블에 `(coach_id, scheduled_date, scheduled_start_time)` **UNIQUE 제약이 없다**. 동시 요청 2건이 같은 슬롯을 둘 다 통과해 이중예약될 수 있다. → **기법**: "이미 존재 확인 후 생성" 류는 앱 체크만으론 부족. **DB UNIQUE 제약(또는 트랜잭션+잠금)으로 경쟁을 막고**, 409 Conflict 응답을 설계한다. 예약·중복가입·재고차감·멱등결제가 대표.
2. **관측가능성(Observability) 부재.** audit_logs(감사)는 있으나 **운영 로깅·메트릭·트레이싱·알람·헬스체크 깊이**가 없다(`/health` 엔드포인트 1줄뿐). → **기법**: 외부 의존(OpenAI/이메일/화상/DB)마다 성공률·지연·에러율을 어디서 보는지, 임계치 알람을 어떻게 거는지 한 단락. 최소한 구조화 로깅 필드와 핵심 SLI를 명시.
3. **장애 복구·데이터 백업·마이그레이션 운영.** 외부 MySQL 백업 주기, 복구 목표(RPO/RTO), 스키마 마이그레이션 절차(무중단 배포 시 컬럼 추가/삭제 순서)가 없다. → **기법**: 상태를 가진 시스템(외부 DB 보유)은 백업·복구·마이그레이션을 배포 뷰에 최소 한 표로.
4. **재시도/멱등키.** 이메일 실패 상태는 기록하나 **재시도 정책**(Cron으로 `email_status='failed'` 재발송? 횟수 제한? 백오프?)이 미정. 상태변경 API의 멱등키도 없다. → **기법**: "실패 기록"에서 멈추지 말고 "그 다음 어떻게 복구하나"(재시도 트리거·횟수·백오프)까지. 비멱등 부수효과(이메일·결제·외부룸생성)는 멱등키로 중복 방지.
